# PR packet: P1.6 Registry CRUD remediation

## 1. Summary

P1.6 adds warm-shell CRUD for public Wallet, Account, and Address records. This remediation closes the stacked-review findings by validating relationships across complete public compartments, adding an explicit schema-safe clear operation for optional fields, and exercising the full CRUD/persistence flow in Chromium and Firefox. A warm-only registry store validates relationships and generates record UUIDs with `crypto.getRandomValues`; mutations are sent as a complete public projection through the typed private-channel write/acknowledgement pair. The cold vault session re-encrypts the updated public compartment, preserves the authenticated Vault ID, and leaves secret-compartment plaintext inside the cold realm.

Roadmap: [P1.6 Registry CRUD](../ROADMAP.md#phase-1--core-wallet).

## 2. Scope

In scope:

- Collection-specific public schemas for Wallet, Account, and Address records.
- Warm-only registry state, whole-compartment relationship checks, clone isolation, soft-hide, explicit optional-field clearing, and responsive public UI.
- `publicData.replace` and `publicData.updated` message types.
- Cold-session public-compartment replacement and durable save/reopen coverage.
- User help, architecture documentation, ADR-0031, CHANGELOG, roadmap marker, unit tests, and browser acceptance coverage.

Deliberately out of scope:

- Address verification state and migration, which is P1.11.
- Notes/tags/concealment workflows, which are P1.7.
- Device records, QR generation, and hardware-wallet verification.
- Any secret-bearing registry field or cross-realm secret operation.

## 5. Security impact

Yes: this item touches the message schema and the vault session's public plaintext replacement. It does not change the CSP or add a network host. The cold realm still has `connect-src 'none'`; no secret-bearing field is added to either direction.

New messages:

- Warm to cold `publicData.replace` accepts only `{ publicCompartment }`, then applies the existing message-size limit and collection-specific public validators.
- Cold to warm `publicData.updated` returns only the same sanitized public projection after the cold session has replaced its padded public plaintext.

The cold session refuses a Vault ID change and fails closed on a closed/saving session, health failure, network-mode drift, malformed object, or serialization failure. A failed acknowledgement locks the cold session rather than leaving a warm/cold write ambiguity.

The whole-compartment validator rejects orphaned account and address references before a snapshot or replacement is accepted. The update path accepts only an explicit `clearFields` list of optional fields; IDs and required relationships cannot be cleared. The only new randomness is public record UUID generation in the warm realm. It hard-fails if `crypto.getRandomValues` is absent; there is no `Math.random` fallback. No runtime dependency or external URL was added.

## 8. Assumptions made

- The existing public data model's Wallet, Account, and Address field names are authoritative; P1.11 owns later verification fields.
- P1.6 represents delete as `hidden: true` so history and references are not silently destroyed. Hard deletion is not exposed.
- A complete public projection is acceptable for P1.6 writes because the existing vault format already encrypts and pads the public compartment; a transaction log would require a separate structural decision.
- Legacy public records in these three collections must already carry their model-required IDs and valid relationships. A malformed, incomplete, or orphaned public record is rejected and the vault is locked rather than silently migrated.
- Empty optional form values are omitted on create; on update, an intentionally empty optional control is represented by an explicit `clearFields` operation. The store does not infer secret-bearing text as safe.

## 9. What to scrutinise

- The acknowledgement and rollback path in `src/main.js`: the UI marks the vault unsaved before sending, restores the previous snapshot on a typed error, and treats an unsolicited acknowledgement as anomalous.
- `createVaultSession.replacePublicData` in `src/cold/vault.js`: it must never mutate the old padded bytes until the new serialized public compartment and immutable-ID check have succeeded.
- `cleanPublicRelationships` and `validateRelationships`: the whole-compartment check is intentionally separate from per-record schema validation so orphaned references cannot enter snapshots or durable state.
- `clearFieldsForUpdate` and the warm form helpers: only optional fields may be cleared, and required IDs/relationships must remain present.
- The remaining untested mobile matrix. Desktop Chromium and Firefox passed the prescribed file-based flow, but that result is not inferred as Safari or mobile browser coverage.

## 10. Self-assessment

The desktop browser harness now covers the remediation path, including the asynchronous save/acknowledgement sequence and lock concealment. Mobile browsers and real hardware remain untested. The address form intentionally preserves an existing `used` flag when editing but does not edit that field yet; later verification and balance work should own those controls. No real seed, key, or vault file was committed.
