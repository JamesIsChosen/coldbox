# PR packet: P1.6 Registry CRUD

## 1. Summary

P1.6 adds warm-shell CRUD for public Wallet, Account, and Address records. A warm-only registry store validates relationships and generates record UUIDs with `crypto.getRandomValues`; mutations are sent as a complete public projection through the typed private-channel write/acknowledgement pair. The cold vault session re-encrypts the updated public compartment, preserves the authenticated Vault ID, and leaves secret-compartment plaintext inside the cold realm.

Roadmap: [P1.6 Registry CRUD](../ROADMAP.md#phase-1--core-wallet).

## 2. Scope

In scope:

- Collection-specific public schemas for Wallet, Account, and Address records.
- Warm-only registry state, relationship checks, clone isolation, soft-hide, and responsive public UI.
- `publicData.replace` and `publicData.updated` message types.
- Cold-session public-compartment replacement and durable save/reopen coverage.
- User help, architecture documentation, ADR-0031, CHANGELOG, roadmap marker, and tests.

Deliberately out of scope:

- Address verification state and migration, which is P1.11.
- Notes/tags/concealment workflows, which are P1.7.
- Device records, QR generation, and hardware-wallet verification.
- Any secret-bearing registry field or cross-realm secret operation.

## 5. Security impact

Yes: this item touches the message schema and the vault session's public plaintext replacement. It does not change the CSP or add a network host. The cold realm still has `connect-src 'none'`; no secret-bearing field is added to either direction.

New messages:

- Warm to cold `publicData.replace` accepts only `{ publicCompartment }`, then applies the existing message-size limit and collection-specific public validators.
- Cold to warm `publicData.updated` returns only the same sanitized public projection after the cold session has replaced its padded public plaintext.

The cold session refuses a Vault ID change and fails closed on a closed/saving session, health failure, network-mode drift, malformed object, or serialization failure. A failed acknowledgement locks the cold session rather than leaving a warm/cold write ambiguity.

The only new randomness is public record UUID generation in the warm realm. It hard-fails if `crypto.getRandomValues` is absent; there is no `Math.random` fallback. No runtime dependency or external URL was added.

## 6. Test evidence

New tests cover:

- Typed message whitelist additions, collection-specific fields, bounded text, timestamps, unknown text, secret keys, and malformed public data.
- Wallet/account/address creation, relationship failures, UUID uniqueness, clone isolation, updates, soft-hide, and randomness absence.
- Public-compartment replacement, Vault ID immutability, secret-compartment preservation, save, and reopen.
- Warm-only registry source contains no DOM or secret-handling identifiers.

There are no cryptographic test vectors in this item. `crypto.getRandomValues` is used for identifiers only; its absence is tested as a hard failure. Online vendor verification was run against the upstream releases and passed.

The browser harness was not testable in this environment because the pinned Playwright browser binaries were missing, and the in-app browser rejects `file://` navigation. No desktop/mobile browser result is inferred from another surface.

## 8. Assumptions made

- The existing public data model's Wallet, Account, and Address field names are authoritative; P1.11 owns later verification fields.
- P1.6 represents delete as `hidden: true` so history and references are not silently destroyed. Hard deletion is not exposed.
- A complete public projection is acceptable for P1.6 writes because the existing vault format already encrypts and pads the public compartment; a transaction log would require a separate structural decision.
- Legacy public records in these three collections must already carry their model-required IDs. A malformed or incomplete public record is rejected and the vault is locked rather than silently migrated.
- Empty optional form values are omitted on create; the store does not infer secret-bearing text as safe.

## 9. What to scrutinise

- The acknowledgement and rollback path in `src/main.js`: the UI marks the vault unsaved before sending, restores the previous snapshot on a typed error, and treats an unsolicited acknowledgement as anomalous.
- `createVaultSession.replacePublicData` in `src/cold/vault.js`: it must never mutate the old padded bytes until the new serialized public compartment and immutable-ID check have succeeded.
- The registry protocol rules in `src/protocol.js`: future registry fields must be added deliberately, otherwise unknown text remains rejected.
- The untested browser/device matrix. The page is user-facing and this packet does not claim that missing browser binaries or unavailable hardware have been replaced by static review.

## 10. Self-assessment

The implementation could still have UI-only issues that the missing browser harness would expose, especially responsive form behavior and the asynchronous lock/acknowledgement sequence. The address form intentionally preserves an existing `used` flag when editing but does not edit that field yet; later verification and balance work should own those controls. No real seed, key, or vault file was committed.
