**Exhaustive header tampering — all 65 bytes × all 255 alternative values.** The author's own test flips only bit 0 of each byte; I replaced every byte with every other possible value:

**65-byte AAD accounting checked by hand and confirmed by construction.** 8 magic + 2 version + 1 KDF id + 4 memory + 4 iterations + 1 parallelism + 1 cipher + 32 salt + 4 wrapped length + 4 public length + 4 secret length = 65. `header.bytes = bytes.slice(0, 65)` is the exact on-disk header, not a re-serialized object (`vault.js:472`, `vault.js:626`), and is passed as AAD to DEK unwrap and to both compartment operations. ## 4. Findings

### F1 — `createVault` writes the header's KDF parameters from mutable global state, not from the profile it actually used

**Severity:** blocking
**Location:** `src/cold/vault.js:382-390`; supporting state at `src/cold/crypto.js:98-108` (`setActiveKdf`, `setFallback`) and `src/cold/crypto.js:244-246` (`getKdfDetails`)

```js
kek = await cryptoLayer.deriveKey(options.passphrase, salt, profileName);
var details = cryptoLayer.getKdfDetails();
var header = makeHeader(details, salt, 64, ...);
```

`profileName` — the profile actually passed to `deriveKey` — is discarded. The header is built from `getKdfDetails()`, which returns a snapshot of the crypto layer's module-global `activeKdf`. Any other KDF operation that resolves between the `await` on line 382 and the read on line 383 rewrites that global, and `createVault` then writes a header describing someone else's derivation.

**Observed.** Two `createVault` calls started without awaiting between them, against the real vendored Argon2id:

```text
$ node t1.js
race h1 (requested paranoid m=262144 t=4): kdfId=1 m=19456 t=2 p=1
race h2 (requested fast     m=19456  t=2): kdfId=1 m=19456 t=2 p=1
race v1 OPEN FAILED: Vault authentication failed.
race v2 opens: OK

$ node t2.js            # same test, order swapped
v1 requested fast     -> header m=262144 t=4
v2 requested paranoid -> header m=262144 t=4
v1 OPEN FAILED: Vault authentication failed.
v2 opens OK
```

Two distinct failure modes, both silent at write time:

1. **Permanent data loss.** `v1` is returned successfully by `create()` and can never be opened by anyone, including with the correct passphrase, because `open` re-derives the KEK from the header's parameters and gets a different key. For a tool whose stated stakes are "a bug here can cost someone everything they own", a `create()` that returns a valid-looking, permanently unopenable vault is the worst available outcome.
2. **Silent KDF downgrade.** In the second run the header of `v1` advertises Argon2id at 256 MiB / t=4 (Paranoid) while its KEK was derived at 19 MiB / t=2 (Fast). The AAD cannot detect this — AAD stops an *attacker* rewriting the header; it does nothing when the *writer* records parameters it did not use. `docs/01-spec/vault-format.md` lists "KDF can't be downgraded — Parameters in AAD" as a threat property, and P0.16's provenance panel will report the header value as fact.

**Reachability.** Nothing calls this API today, but P0.11 installs it on `window.__coldboxVault` and the very next roadmap item, P0.12, is "Fast/Standard/Paranoid profiles … with an on-device timing benchmark offered before vault creation" — a benchmark that exercises `deriveKey` at several profiles is precisely the interleaving that triggers this. The defect is in the format layer and must be fixed here, not inherited by P0.12.

**Expected:** the header must be derived from the profile that was actually used. Fail closed if the crypto layer disagrees.

**Required action:** build the header from the normalized `profileName` local, and assert `profileFromDetails(cryptoLayer.getKdfDetails()) === profileName` immediately after `deriveKey` resolves, throwing on mismatch. Add a regression test that interleaves two `create` calls with different profiles and asserts each vault's header matches its own request and that each opens.

### F2 — Vault operations proceed after the AES-GCM known-answer test fails (fails open)

**Severity:** blocking
**Location:** `src/cold/vault.js:342-347` (`aesGcm`), `:357-422` (`createVault`), `:453-506` (`openVault`), `:601-690` (`openVaultSession`); `src/cold/index.html:25-30` script ordering; `src/cold/crypto.js:157-165`

`vault.js` is an IIFE that installs `window.__coldboxVault` unconditionally at parse time, before `src/cold/main.js` runs any of the cold realm's health checks. `createVault` guards only on `typeof cryptoLayer.deriveKey === 'function'` and `typeof cryptoLayer.getKdfDetails === 'function'`. It never consults `cryptoLayer.selfTest()`, the CSP canary result, the runtime-neutering result, or the randomness capability. `cryptoLayer.aesGcm(..., 'noble')` is likewise ungated — only the WebCrypto path checks `webCryptoState !== 'passed'` (`crypto.js:136-138`), and the vault layer always uses the `'noble'` path.

**Observed.** `@noble`'s GCM sabotaged so its NIST SP 800-38D known-answer test fails:

```text
$ node t7.js
AES-GCM known-answer test passed? false
cold main.js would call setCryptoFailure() -> data-vault-operations="refused"
__coldboxVault.create() STILL SUCCEEDED after a failed AES-GCM KAT. bytes = 131257
__coldboxVault.open() STILL SUCCEEDED. secretData = {"mnemonic":"test only"}
```

A mnemonic was encrypted and decrypted by a cipher implementation that had just failed its own correctness gate. Meanwhile `src/cold/main.js:181` sets `data-vault-operations="refused"` with the copy *"The pure-JS @noble AES-GCM known-answer test failed. Coldbox refuses all vault operations."* — the app tells the user it refused, and the API did not. The same holds for a failed CSP canary (`main.js:161`), a failed runtime network guard (`main.js:175`), and missing `crypto.getRandomValues` (`main.js:178`): all three set `data-vault-operations="refused"`, none of them disables `__coldboxVault`.

P0.10 could reasonably leave this ungated because the cold realm had no vault operations. P0.11 is the item that creates them, so the gate belongs here.

This is the `AGENTS.md` §3 "Fail closed" constraint and the review protocol's automatic-FAIL entry "A failure mode fails open".

**Required action:** gate `create`, `open`, `openPublic` and `openSession` on the cold realm's health state — at minimum the AES-GCM self-test result — and refuse with the generic error otherwise. Add a test that a failed KAT makes every vault entry point reject.

### F3 — A session opened offline keeps the secret subkey and secret plaintext live after the device comes online; `save()` never re-checks network state

**Severity:** advisory (must be fixed)
**Location:** `src/cold/vault.js:512-565` (`createVaultSession`, `save`), mode latched at `:614` and stored at `:647`

`resolveMode` is evaluated once, at open. `save()` then branches on the latched `state.mode`, with no further network check. A session opened while offline therefore continues to hold the derived `cbx/secret/v1` subkey and the decrypted secret compartment plaintext indefinitely, and re-encrypts the secret compartment on every save regardless of the device's current state.

**Observed:**

```text
$ node t6.js
openSession(offline) infos: ["cbx/public/v1","cbx/secret/v1"]
   ... navigator.onLine flipped to true ...
save() AFTER going online -> bytes 131257 infos []
  secret ciphertext re-encrypted while online? true
```

`docs/01-spec/vault-format.md:115` and `docs/01-spec/SPEC.md:121,350` state the rule without qualification: *"In Warm Mode the secret compartment is copied byte-for-byte — ciphertext, nonce, and tag together"*, and `SPEC.md:111-118` gives Warm Mode "Vault save: Public compartment only". Here it is decrypted, held, and re-encrypted online.

The packet also overclaims on this point. §5 says *"the secret subkey is created only inside the cold module and only for an explicitly offline open/save path"* and *"Online saves copy the already-encrypted secret compartment"*; §10 says the session *"is closed/zeroed with the session"* — but nothing forces `close()`, and idle auto-lock is P0.13.

No acceptance criterion is broken by this, because no *derivation* happens online. It is still a divergence from the spec and from the packet's own claims.

**Required action:** re-evaluate `networkState()` inside `save()` and refuse (or fall back to opaque copy) when the device is no longer offline; or remove the session primitive from this PR per **F4** and design it with P0.13's auto-lock.

### F7 — Unrecognized KDF profile names silently become `standard`

**Severity:** advisory (must be fixed)
**Location:** `src/cold/vault.js:171-195`

```js
function normalizedProfile(value) {
```

`create({ profile: 'paranoyd' })` silently produces a Standard vault; the user believes they chose Paranoid. `AGENTS.md` §3: "Fail closed — If a guarantee can't be established, refuse to proceed. Never degrade silently."

### F8 — The KDF profile table is duplicated in two modules, and the two copies already differ

**Severity:** advisory (must be fixed)
**Location:** `src/cold/vault.js:22-27` and `src/cold/crypto.js:16-42`

The same four profiles are declared twice. `crypto.js`'s `fallback` entry has **no `memoryKiB` key**; `vault.js`'s has `memoryKiB: 0`. Today the divergence is masked because `profileFromDetails` reads only `details.id` and then re-looks-up `vault.js`'s own table — but that masking is exactly what makes **F1** possible, and nothing enforces that the two tables agree. They *must* agree byte-for-byte: `vault.js`'s numbers go into the header, `crypto.js`'s numbers go into the KEK. P0.12 is "KDF profiles and benchmark" and will edit these next.

`docs/05-development/doc-hygiene.md`'s single-canonical-home rule applies with force to a security parameter that two modules must agree on.

**Required action:** have `vault.js` read the profile parameters from `cryptoLayer.profiles` (already exported at `crypto.js:326`) rather than maintaining a second table, and add `memoryKiB: 0` to the crypto-layer fallback profile so the two representations are identical.

**Severity:** advisory (must be fixed)
**Location:** `src/cold/vault.js:72-90` (`networkState`, `resolveMode`); existing signal at `src/airgap.js:193-194`

`docs/01-spec/SPEC.md:237` and `docs/01-spec/architecture.md:153` both state that mode detection uses **`navigator.onLine`, `navigator.connection`, and the CSP canary**. `vault.js` rolls its own `networkState()` from `navigator.onLine` alone, independently of `src/airgap.js`, which already computes an `online` signal.

Consequences: a cold realm whose CSP canary *failed* — i.e. whose airgap is unproven — is still treated as "offline" and will derive `cbx/secret/v1` whenever `navigator.onLine === false`. That is the same fail-open shape as **F2**, reached through the mode gate rather than the health gate. And a fact that the spec gives one canonical definition for now has two implementations that can drift.

**Required action:** consume the existing airgap/mode signal rather than duplicating it, and include the CSP-canary result in the offline determination — or amend the spec, with an ADR, to state that the vault gate deliberately uses `navigator.onLine` only, and why.

### F10 — Undocumented 64 MiB size limit reported as an authentication failure

**Severity:** advisory (must be fixed)
**Location:** `src/cold/vault.js:15`, `:143-145`, `:262-263`, `:351-353`, `:408-410`

`MAX_VAULT_BYTES = 64 * 1024 * 1024` caps both whole vaults and individual compartments. `docs/01-spec/vault-format.md` defines no such limit, and the packet's §8 Assumptions does not list it. A vault legitimately at or over the cap is reported to the user as `Vault authentication failed.` — which the spec (`vault-format.md`, "Corruption") defines to mean *"wrong passphrase **or** damaged file"*. Both are false, and a user told their file is damaged may destroy or replace a perfectly good vault.

**Required action:** document the limit in `vault-format.md` and record it in the packet's Assumptions, and distinguish an over-size refusal from an authentication failure (the size of a file is not secret, so a distinct message leaks nothing).

## 5. Verdict rationale

The format work itself is largely sound, and several properties are stronger than the packet claims: header tampering was checked here across all 65 bytes and all 255 alternative values with zero silent acceptances; the wrapped-DEK record parser has exact bounds and survived 3,000 fuzz trials and 19 targeted malformations with a single error string; padding lands on a 64 KiB boundary in every case tested; the build is byte-identical across path, locale, timezone and Node major version and refuses non-zero on a corrupted vendor artifact; and no entry point derives `cbx/secret/v1` while the device reports a network. Acceptance criterion 2 is met as written.

It fails on criterion 1 and on two fail-open defects. **F1** is decisive on its own: `createVault` records the header's KDF parameters from the crypto layer's mutable global state instead of the profile it actually used, so two overlapping creations produce a vault that is permanently unopenable and a header that misstates the KDF strength — and P0.12, the next item, adds exactly the multi-profile benchmark that triggers it. **F2** is decisive on its own too: the vault API is installed and fully functional after the AES-GCM known-answer test fails, while the UI in the same document tells the user that vault operations are refused. On top of those, ~90 lines of P0.13 session code rode along in this PR (**F4**), carrying a spec violation of the Warm-Mode byte-for-byte copy rule (**F3**), and the packet misstates the artifact size (**F5**) and contradicts its own self-review about what was run (**F6**).

**To make this a PASS:** fix F1 by building the header from the requested profile and asserting agreement with the crypto layer; fix F2 by gating every vault entry point on the cold realm's self-test and airgap state; remove the session primitive to P0.13 (F4), which also removes F3; then close F5–F10. Each fix needs a regression test, and the re-review will be a fresh verdict on the new commit, not an amendment to this one.

**FAIL**
