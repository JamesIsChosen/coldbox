# P0.14 — Save integrity

> **Historical implementation record.** This packet describes P0.14's then-required generational filenames and manual/QR save semantics. P0.19 and [ADR-0026](../adr/0026-canonical-vault-save-and-live-transfer.md) supersede the current UX with one canonical `<name>--<id8>.cbx`, no look-alike re-save for an unchanged vault, and live-only vault QR transfer. The historical details below remain evidence of what P0.14 actually implemented and reviewed.


Branch: `p0.14-save-integrity`

**Status:** two independent review rounds so far, both FAIL, both addressed on this branch — see §13 (round 1: `b6359d6` → fix) and §14 (round 2: `2aa9707` → fix). §§1–12 are the original packet, preserved as written; treat any command output or count in them as historical, not current. The **current** verification evidence is in §14.

## 1. Summary

[P0.14](../ROADMAP.md) adds verify-after-save, generational filenames, and rollback detection to the warm shell's existing save/load flows. A File System Access save now re-reads the file it just wrote and only clears the unsaved-changes flag if the bytes match exactly; blob download and the manual base64/QR handoff, which cannot be read back through any web API, never clear it automatically. Opening a file whose name parses to an older save generation than one this browser has already recorded shows a warning with both dates and counters. None of this touches the vault format, the message schema, or the realm boundary — see [ADR-0013](../adr/0013-save-integrity-in-warm-shell.md).

## 2. Scope

**In:** `src/save-integrity.js` (new, pure warm-shell module), its wiring into `src/main.js` and `scripts/build.js`, new UI elements in `src/index.html`/`src/styles.css` for the dirty notice and rollback banner, `test/save-integrity.test.js`, `test/save-flow-wiring.test.js`, and the doc updates listed in §12.

**Out, deliberately:**
- No vault-format byte change. `src/cold/vault.js` is untouched.
- No new `postMessage` type. `src/protocol.js` is untouched.
- No editing/CRUD UI (that's P1.6+); the dirty flag's only source of "unsaved changes" right now is "a vault was created fresh and has not yet completed a verified save," since there is nothing else in the app yet that can make an opened vault dirty. See §8.
- No attempt to verify blob-download or manual/QR bytes against disk — no web API allows it. See §8 and §9.

## 5. Security impact

- Realm boundary: **no.** Nothing in this PR runs in, or messages, the cold realm. `test/vault.test.js`'s existing boundary test (`assert.doesNotMatch(warmSource, /__coldboxVault|.../)`) still passes unmodified against the new `src/main.js`.
- Message schema: **no.** `src/protocol.js` is untouched; no new `postMessage` type was added. Verify-after-save is a warm-shell byte comparison against bytes the cold realm already produced and sent across the boundary through the existing `vault.bytes` message — the same trust tier as before this PR.
- CSP: **no.** `src/index.html`'s policy meta tag is untouched.
- Vault format: **no.** `src/cold/vault.js` is untouched; `HEADER_LENGTH` and the byte layout are unchanged. A vault written before this PR opens unmodified after it (implied by every existing `test/vault.test.js` case still passing, since none of that code changed).
- Derivation / randomness: **no.**
- New `connect-src` host: **no.**
- **If this implementation is wrong, what does an attacker — or just bad luck — gain?** The failure mode I most want scrutinized: if `bytesEqual()` had a bug that reported `verified: true` for non-identical bytes, a truncated save would be reported as safe and the user would walk away believing their vault was written when it wasn't — silent data loss, which is exactly what this item exists to prevent. I wrote `bytesEqual()` to fail closed on every shape mismatch (`bytesEqual` initially had a real bug here during development — it accepted a JavaScript `string` as byte-like because strings expose `.length`; the negative test `'bytesEqual catches truncation, single-byte corruption, and type mismatches'` caught it, and I added an explicit `typeof a === 'string'` guard). I have low-to-medium residual confidence that no other exotic array-like shape (e.g. a `DataView`, an `Array` of non-numbers) produces a false positive; `bytesEqual` was not fuzzed, only tested against the concrete shapes the save paths actually pass it (`Uint8Array` throughout).
- Rollback detection is explicitly advisory (see ADR-0013): it is defeated by renaming the file, and it is per-browser-profile. This is disclosed in-app, in `vault-format.md`, and in the ADR — not a silent gap.

## 8. Assumptions made

- **What "dirty" means before any editing UI exists.** P1.6 (registry CRUD) hasn't been built yet, so there is currently nothing in the app that can mutate an *opened* vault's data. I defined the dirty flag as: a vault created fresh inside the cold realm starts dirty (it has never been written to disk); a vault opened from an existing file starts clean. This is inferred from `pendingVaultLoad` — a warm-shell-only flag that is `true` only when the current unlock session began from bytes the warm shell staged via `sendVaultOpen()` — because the cold realm's own create/unlock controls give the warm shell no other signal to distinguish the two. **Basis:** this is the only interpretation that is both correct today (nothing else can create unsaved changes yet) and forward-compatible (P1.6 can flip the flag to `true` on any mutation without touching this PR's plumbing). **What breaks if wrong:** if a future edit path doesn't call into the same `setVaultDirty(true)` entry point, edits could go unmarked as dirty — a real regression risk I can't close from this PR, only flag for whoever builds P1.6.
- **Verify-after-save is a byte comparison, not a second decrypt.** `vault-format.md` says "confirms it decrypts and matches"; I implemented an exact byte-for-byte comparison between the freshly written bytes and a fresh read-back, entirely in the warm shell, with no new cold-realm round trip. **Basis:** the bytes being compared are ciphertext the cold realm already produced via authenticated encryption; if they are byte-identical to the read-back, the read-back necessarily decrypts identically too — there is no code path where identical bytes decrypt differently. The roadmap's own (authoritative, per AGENTS.md) acceptance text only requires that "a deliberately truncated save is caught," which byte comparison does unambiguously and catches strictly more than a re-decrypt would (a decrypt-only check could theoretically pass on a valid-but-different ciphertext with the same plaintext under a different nonce, which byte identity cannot). **What breaks if wrong:** if a reviewer reads "confirms it decrypts" as requiring an actual second AEAD decryption round-trip through the cold realm, this implementation choice would need a new message type (`vault.verify`/similar) — I considered and rejected that design specifically to avoid adding cross-realm attack surface for a property this approach already establishes; see [ADR-0013](../adr/0013-save-integrity-in-warm-shell.md).
- **Save counter and timestamp live in the warm shell, not the vault format.** Full reasoning in [ADR-0013](../adr/0013-save-integrity-in-warm-shell.md). **What breaks if wrong:** rollback detection stays advisory-only (already documented) rather than becoming a cross-device, tamper-evident guarantee; a future item would need to move it into the public compartment.
- **Blob download and manual/QR export never auto-clear the dirty flag.** No web API lets a page read back what a browser's download manager wrote to disk, or what a person did with copied/scanned text. **Basis:** this is a hard platform limitation, not a design shortcut — I looked for a way to satisfy "verify-after-save" for these paths and there isn't one. **What breaks if wrong:** none that I can see; the alternative (claiming a verification that didn't happen) is strictly worse.

## 9. What to scrutinise

- **The `bytesEqual` string-acceptance bug, and whether anything like it remains.** It's fixed (see §5), but it's exactly the kind of "technically satisfies the type check, semantically wrong" bug that's easy to have a sibling of. I'd look hardest at `evaluateRollback`'s handling of `file.lastModified` (a `number`, but could a caller pass something number-like and wrong?) and at `parseFilename`'s regex — I bounded the digit group to `\d{4,9}` somewhat arbitrarily (9 digits caps the suggested counter comfortably under `Number.MAX_SAFE_INTEGER` territory for this use, but I did not derive that bound from anything the spec states).
- **The `pendingVaultLoad`/`pendingLoadFileMeta` state machine in `src/main.js`.** It's the one piece of this PR I could not exercise with a real execution test (no DOM harness for `main.js` in this codebase — see the note in `test/save-flow-wiring.test.js`), only prove by source pattern. Trace it by hand: `loadVaultFile` → `sendVaultOpen(bytes, fileMeta)` → sets `pendingVaultLoad`/`pendingLoadFileMeta` only inside the `try` after `postMessage` succeeds → `handleVaultOpened` snapshots and resets them before computing `setVaultDirty`/the rollback check. I'm fairly confident in it but it's exactly the kind of ordering bug that a regex test can miss if the *meaning* of the pattern is wrong even though the pattern matches.
- **Whether "dirty" should have been called something that survives a browser refresh.** It's pure in-memory JS state — reloading the page (or the tab being killed) loses it silently, same as every other piece of live session state in this app (e.g. `vaultState` itself). I did not add any `beforeunload` warning. Worth a second opinion on whether that's an oversight or correctly out of scope.
- **The UI has never been rendered.** `#vault-dirty-notice` and `#vault-rollback-banner` exist only as markup + JS wiring, verified only by the CSS/HTML being syntactically consistent and the build succeeding. I have no screenshot, no harness run, nothing. If the reviewer has Playwright available, this is the highest-value thing to actually look at.

## 10. Self-assessment

- **What might be wrong:** the exact digit-count bound in `FILENAME_PATTERN` (`\d{4,9}`) is a judgment call, not derived from a spec number. The "dirty means never-yet-saved-since-creation" definition (§8) is my best reading of an item that predates any editing feature; a differently-scoped reviewer could reasonably want it named/scoped differently.
- **What I did not do that arguably should have been done:** no browser verification of any kind (environment-blocked, not skipped by choice); no `beforeunload` warning for a dirty, unsaved vault; did not add a UI affordance to see the current save generation number outside of the rollback banner (a "Generation 12, last verified save 2026-08-06T…" line would be a reasonable follow-up).
- **Known limitations shipping with this change:** rollback detection is defeated by a rename (disclosed); the save counter/timestamp is per-browser-profile (disclosed); blob-download and manual/QR paths never auto-clear the dirty flag even on a successful, correctly-received save (disclosed, and arguably correct rather than a limitation).
- **Follow-up work this creates:** P1.6 (registry CRUD) needs to route every mutation through `setVaultDirty(true)`, or the dirty flag silently stops meaning anything the moment editable data exists. Worth a note in P1.6's own packet when that item starts. No new roadmap item filed for it — it's naturally inside P1.6's own scope, not a separate gap.

## 13. Addendum — independent review round 1 (FAIL, then fixed)

Round 1 review (`p0.14-save-integrity.review.md`, reviewing commit `b6359d6`) returned **FAIL** with two findings, F1 blocking and F2 blocking. This section addresses both, per [review-protocol.md](../review-protocol.md): "the author addresses every finding: fix it, or argue it should be dismissed and say why."

### F1 — Opening a newer vault didn't persist it as the rollback high-water mark. **Fixed.**

The reviewer independently traced the source (not the packet's claims) and found it accurately: `completeVerifiedSave()` was the only place that ever called `writeGeneration()`, so opening an existing file — even one with a higher generation than anything previously recorded — never advanced or persisted `saveGeneration`. Their concrete failing sequence (`47 → open 100 → reload → open 80` fails to warn) is correct; I reproduced it as a test before fixing anything, confirmed it failed, then fixed the code and confirmed the same test passes.

**Root cause:** the remembered generation was being kept as "the highest this browser has *saved*," when both `vault-format.md` and the roadmap's own accept text require "the highest counter this browser profile has *seen*" (opened counts as seen).

**Fix:** added `saveIntegrity.advanceGenerationOnOpen(generation, file)` — a pure function, same module, same testing approach as everything else in `src/save-integrity.js`. `handleVaultOpened()` in `src/main.js` now calls it on every file-backed open, in this order: (1) `evaluateRollback()` against the **old** generation (so an opened file is judged against what the browser already knew, not against itself), (2) `advanceGenerationOnOpen()` to compute the new high-water mark, (3) `writeGeneration()` to persist it. The function never lowers the recorded generation and never fires on an unparseable filename, matching `evaluateRollback`'s existing degrade-silently contract. When the opened file's own `lastModified` is unavailable, it falls back to the current time so the advance can still be persisted (`writeGeneration` requires a valid ISO date).

**New tests** (`test/save-integrity.test.js`): four direct tests of `advanceGenerationOnOpen` (raises the mark for a newer file; never lowers it for an older or equal one; never fires on an unparseable filename; falls back to "now" when `lastModified` is unavailable), plus one end-to-end regression reproducing the reviewer's exact sequence — `'regression: 47 -> open 100 -> reload -> open 80 warns with both counters and dates (F1)'` — using a real `fakeStorage`, calling the functions in the same order and with the same "reload" semantics (a fresh `readGeneration()` from storage between sessions) that `src/main.js` uses, and additionally asserting the next suggested save counter stays above the highest seen generation (the reviewer's second concrete requirement). New wiring test (`test/save-flow-wiring.test.js`): confirms `handleVaultOpened()` calls `evaluateRollback()` before `advanceGenerationOnOpen()`, and `advanceGenerationOnOpen()` before `writeGeneration()`.

The reviewer's container had no DNS route to `github.com` and so could not check out the exact commit to run `npm ci`/`verify-vendor`/`lint`/`test`/build-reproducibility/a deliberate truncation fixture independently — they were explicit that source inspection is not a substitute for that, and FAILed rather than guess. ### Acceptance criteria — re-check against the fix

The "opening an older vault warns with both dates and counters" half of the criterion in §4 was the one F1 found under-delivered (it warned correctly only within a single session; a reload could lose the high-water mark).
