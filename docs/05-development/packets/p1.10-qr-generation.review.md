## 4. Findings

### F1 — The Chromium/Firefox harness does not exercise any P1.10 QR Studio workflow

**Severity:** blocking

**Location:** `scripts/run-browser-harness.js`; `docs/05-development/packets/p1.10-qr-generation.md`

**Observed:** `npm run test:browser` passes in Chromium and Firefox, but PR #43 does not change `scripts/run-browser-harness.js`, and the fresh harness output contains no P1.10 QR Studio case. It exercises pre-existing `file://`, responsive, vault, registry, Seed Forge, P1.9, CSP, provider-neutering, and other flows. The packet itself describes the harness result only as "`file://`, cold-boundary, registry, lock, and responsive checks passed" and separately calls browser-only print/download the least-confidence area.

**Expected:** `docs/05-development/testing.md` states that the Playwright harness is where every browser-observable acceptance criterion is verified. P1.10's core deliverables are browser controls: warm address QR generation, SVG/PNG downloads, cold acknowledgement gating, standard/Compact generation, layout selection, print, and teardown clearing.

**Required action:** Add real Chromium and Firefox P1.10 harness coverage that drives the warm and cold QR flows through the built `file://` artifact, including negative inputs, acknowledgement gating, generated module/payload expectations, export behavior, and lock/session cleanup. Exercise print behavior in a way that proves the shipped sandbox/layout actually permits the claimed flow. A passing generic harness is not sufficient.

### F2 — Ethereum payment QRs encode an ETH amount as wei and add a non-ERC-681 `label` parameter

**Severity:** blocking correctness

**Location:** `src/main.js` — `publicQrUri()`, plus the QR Studio amount/label UI

**Observed:** The UI presents the amount field as a BTC-or-ETH amount. For Ethereum, `publicQrUri()` inserts the user's decimal text directly as `value=<amount>`. Entering `1` ETH therefore emits `...?value=1`. It also appends `label=<text>` when the optional label field is populated.

**Expected:** ERC-681 defines native-payment `value` in the chain's **atomic unit (wei)**. Its own example represents 2.014 ETH as `value=2.014e18`. The ERC-681 parameter grammar permits `value`, gas fields, or ABI type names; `label` is not an ERC-681 parameter key.

Primary reference: https://eips.ethereum.org/EIPS/eip-681

**Required action:** Make the generated Ethereum URI conform to ERC-681. Convert the human ETH amount to the correct atomic-unit/scientific-notation value without precision loss, and do not claim/emit unsupported parameters as EIP-681. Add independent vectors that inspect the exact URI text, including a human `1 ETH` case and a label-present case.

### F3 — CompactSeedQR forces error correction M, so it does not match the required compact template sizes

**Severity:** blocking interoperability/spec

**Location:** `src/cold/qr.js` — `createCode()` / `createCompactSeedQr()`; `src/cold/main.js` — `generateSeedQr()`

**Observed:** `createCode()` defaults to error correction `M`, and `generateSeedQr()` explicitly calls both SeedQR constructors with `{ errorCorrection: 'M' }`.

SeedSigner's pinned format documentation derives CompactSeedQR sizing using error correction **L**:

- 12-word CompactSeedQR: 16 bytes → **21×21**
- 24-word CompactSeedQR: 32 bytes → **25×25**

The same document shows these are deliberately one QR version smaller than standard SeedQR. Coldbox's SPEC requires CompactSeedQR to match the 21×21/25×25/29×29 templates already used by the project. DENSO WAVE documents that QR version increases as required capacity increases and that Version 1-M holds only 14 binary bytes, so a 16-byte CompactSeedQR cannot remain 21×21 at M.

Primary references:
- https://github.com/SeedSigner/seedsigner/blob/56637104b90325e1bc47b58f5f5e8154ea56cf37/docs/seed_qr/README.md
- https://www.qrcode.com/en/about/version.html

**Expected:** CompactSeedQR output must preserve the format's intended compact module dimensions required by SPEC §11.1.

**Required action:** Generate CompactSeedQR with parameters that reproduce the specified SeedSigner template dimensions and add independent module-count tests for at least the official 12- and 24-word cases. Do not only test the intermediate entropy string.

### F4 — Standard SeedQR permits non-English wordlist indices even though SeedSigner SeedQR has no language identifier

**Severity:** blocking interoperability/security

**Location:** `src/cold/main.js` — `wireQrStudio()`, `currentQrSeed()`, and `generateSeedQr()`

**Observed:** QR Studio populates its language selector from every `seedForge.languages` entry. Standard SeedQR then calls `mnemonicToWordIndices(seed.mnemonic, seed.language)`, so a Spanish, Japanese, French, or other non-English mnemonic is encoded using that language's numeric indices.

**Expected:** SeedSigner's pinned SeedQR documentation explicitly states that SeedQR assumes/recommends the **English** BIP-39 wordlist, has no mechanism to specify or detect a language, and that using a non-English wordlist results in an incorrect or invalid seed.

Primary reference: https://github.com/SeedSigner/seedsigner/blob/56637104b90325e1bc47b58f5f5e8154ea56cf37/docs/seed_qr/README.md

**Required action:** Do not emit a non-English index stream while calling it SeedSigner-format Standard SeedQR. Ensure a non-English source either converts through entropy to a compatible English SeedQR representation or is refused/clearly separated from the interoperable format. Add regression/browser coverage for a non-English mnemonic. CompactSeedQR's raw entropy is a separate case and need not inherit this restriction.

### F5 — The advertised cold-realm “Print card” action is blocked by the iframe sandbox

**Severity:** blocking functional

**Location:** `src/main.js` — `startColdRealm()`; `src/cold/main.js` — `qrPrint` click handler

**Observed:** The cold realm is created with:

```text
sandbox="allow-scripts allow-downloads"
```

P1.10's Print card button executes `window.print()` from inside that sandbox.

**Expected:** The WHATWG HTML Standard defines the sandboxed-modals flag as blocking `window.print()`. The flag remains set unless the iframe sandbox includes the appropriate modal permission; the printing algorithm returns immediately when the document has that flag.

Primary reference: https://html.spec.whatwg.org/multipage/browsers.html#sandboxed-modals-flag

**Required action:** Provide a print workflow that actually works in the shipped sealed-realm architecture without casually weakening the security boundary. If the sandbox policy must change, treat that as a deliberate security-surface change and verify it independently. Add Chromium and Firefox coverage proving the user action reaches a real printable state rather than silently returning.

### F6 — Print CSS discards both wallet-sized layout constraints

**Severity:** blocking functional

**Location:** `src/cold/styles.css` — `.cold-qr-card[data-layout=...]` and `@media print`

**Observed:** Screen CSS gives `wallet-12` a `max-width: 15rem` and `wallet-24` a `max-width: 20rem`. But the print rule applies to every `#cold-qr-card`:

```css
width: 100%;
max-width: none !important;
```

That overrides both wallet size constraints exactly when the card is printed.

**Expected:** SPEC §11.1 requires printable A4/Letter cards **and wallet-sized 12/24-word templates**. Selecting a wallet template must remain wallet-sized in print output.

**Required action:** Preserve distinct wallet dimensions under print media and add browser coverage that emulates print media and asserts the selected 12-word and 24-word card dimensions differ from the full-page layout.

**Severity:** advisory — must still be fixed before PASS

**Location:** GitHub PR #43 description

**Observed:** The live PR body still says `npm run test:browser` failed because Playwright binaries were missing, reports the full suite as 295/296, calls the machine-path collision unresolved, and says “Do not proceed to P1.11.” The branch packet and self-review at the actual head instead claim the round-2 browser/full-suite PASS, and the independent collector reproduced those green software gates.
