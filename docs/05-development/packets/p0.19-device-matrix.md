## 3. Maintainer decisions

1. **Creation-only confirmation:** new-vault creation requires new unlock phrase + confirmation inside cold; existing-vault unlock uses one phrase.
2. **Save is primary:** successful creation visibly becomes `UNLOCKED · NOT SAVED` and exposes a prominent Save vault action. Saving still crosses only encrypted bytes.
3. **Names:** every vault has a user-chosen public name for library/filename use, with an explicit do-not-put-secrets warning.
4. **Portable Vault ID:** every new vault gets a cold-generated random UUID. A **device fingerprint was considered and rejected** because multiple vaults share a device, device/browser fingerprints can change/spoof/link activity, and a vault's identity must survive copying to another machine.
5. **Vault Library:** the warm shell detects `.cbx` files only inside an explicitly granted folder or multi-file selection. The user selects the named vault first, then enters one phrase in cold. No silent filesystem crawling is claimed.
6. **Per-vault generations:** filenames include public name + short Vault-ID suffix + that vault's generation; rollback high-water bookkeeping is keyed per vault. Legacy v1 vaults/filenames remain openable.
7. **Zeroization preserved:** normal warm Lock may offer Save first / Lock without saving / Cancel when dirty, but panic/timeout/network/security-health paths lock immediately. Cold emergency lock remains immediate and must say it does not save.
8. **Warm-shell reachability monitor:** active probes run only in warm. Cold keeps `connect-src 'none'` and its runtime/provider guards. `navigator.onLine` becomes a hint/trigger, not the verdict. Unknown fails online-safe.
9. **Truthful status:** successful probes mean online; consecutive all-endpoint failures mean **No external reachability detected**, not "physical airgap verified." Warm network and cold isolation are displayed independently.
10. **Single cold mode authority:** after private-channel validation, `mode.set` is recorded by cold main and is the only network classification consumed by the vault layer. Native `navigator.onLine` disagreement is explicitly regression-tested; unknown mode remains fail-closed.

Structural rationale is canonical in [ADR-0024](../adr/0024-warm-reachability-monitor.md) and [ADR-0025](../adr/0025-vault-identity-library-and-save-ux.md).

## 5. Runtime remediation candidate

The P0.19 branch now carries the accepted runtime design:

- warm-only active reachability probes use the two documented/allowlisted endpoints, treat browser interface state only as a trigger, require consecutive all-endpoint failure for `online:false`, fail unknown/error online-safe, and display warm reachability separately from cold isolation;
- the cold vault layer consumes only the validated `mode.set` state recorded by cold main, never an independent `navigator.onLine`/airgap snapshot; tests force `navigator.onLine === true` while warm reports `online:false` and require secret-capable creation/unlock to follow the validated warm classification;
- the cold realm still owns no probe host and retains `connect-src 'none'` plus runtime/provider guards;
- new-vault creation is gated by strict payload-free `vault.create.prepare {}`, asks for phrase + creation-only confirmation in cold, and creates a CSPRNG UUID in the authenticated public compartment;
- the warm shell keeps the public vault name, exposes a prominent Save action/unsaved state, namespaces generation bookkeeping per full Vault ID (legacy salt namespace for pre-ID v1 vaults), and warns before a normal dirty lock without weakening emergency zeroization;
- the user-granted Vault Library accepts a directory where supported or multiple `.cbx` files as the portable fallback and selects the named file before cold asks for one unlock phrase;
- Node/source wiring tests cover the protocol gate, UUID/name/generation compatibility and warm/cold boundaries; the Chromium/Firefox harness now simulates probe success/failure without external network dependency and exercises creation confirmation, named saves, dirty lock, online-transition zeroization, and two-vault library selection.

The step bundle/self-review provides execution evidence for the exact candidate; this tracked packet does not label a pre-commit run as current-tip evidence.

## 6. Windows manual remediation round 2

The first post-runtime-remediation Windows hands-on pass found four remaining UX/state defects while reporting the rest of the redesigned flow as working as intended:

1. Vault identity must be visibly immutable across save generations; save/re-save may advance only the generation and must never create a new Vault ID.
2. Creation phrase mismatch was rejected internally but the mismatch copy was too easy to miss; the confirmation field now owns an inline assertive error.
3. A verified save cleared the dirty flag but left the status label at `Not saved`; save presentation now distinguishes `Saved · verified` from `Saved · unverified`.
4. The cold realm's visible local Lock button bypassed the warm unsaved-warning gate; it now sends strict `vault.lockRequest {}` so every normal lock uses Save first / Lock without saving / Cancel, while emergency locks remain immediate.

These are P0.19 blockers and keep the item `[~]` until the maintainer re-tests them on the physical matrix.
