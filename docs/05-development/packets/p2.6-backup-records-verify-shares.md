# P2.6 PR packet: BackupRecords and verify-your-shares

## 1. Summary

This branch implements [P2.6](../ROADMAP.md), `BackupRecords and verify-your-shares`, after P2.5. It adds warm public BackupRecord metadata and a cold-only verification flow for SLIP-39, codex32, Seed XOR, Shamir39, and raw SSS. Public BackupRecord text is guarded against all supported share encodings before either projection direction or registry mutation; the SLIP-39 detector is mechanically matched to the canonical 1,024-word list. Before any timestamp is written, the cold session resolves `subjectId` to one cold-stored seed and compares the reconstructed candidate to that subject; unresolved and wrong-subject candidates fail closed. Only a bounded result enum and, on success, a canonical verification timestamp cross the realm boundary; the share material and reconstructed candidate never do.

## 2. Scope

In scope:

- Public BackupRecord CRUD, search, and unverified-by-default rendering in the warm shell.
- `backup.verifyRequest` and `backup.verifyResult` protocol messages with closed schemas.
- Cold-only reconstruction/checking, threshold/group binding, timestamp authority, and teardown clearing.
- Cold-owned subject resolution and candidate binding before completion, with unresolved subjects failing closed.
- Conservative public-text rejection for supported SLIP-39, codex32, Seed XOR, Shamir39, and raw SSS share encodings.
- Durable-save prompting after a successful cold verification.
- Tests, browser harness coverage, security documentation, four backup guides, ADR-0041, changelog, roadmap status, and this packet.

Deliberately out of scope:

- P2.7 scheduling, health dashboard, survivability scoring, or inheritance workflow.
- Physical backup-media inspection or proof that a user stored shares safely.
- Support for `seedqr`, `metal`, `paper`, or `encrypted-file` records; those return `unsupported`.
- A new vault binary-format field. `lastVerifiedAt` remains public registry data and is persisted only by the existing authenticated public-compartment save path.

## 5. Security impact

| Surface | Impact | Evidence |
|---|---|---|
| Realm boundary | Yes. The flow deliberately crosses the existing warm/cold message channel, but only with `backupId`, a closed outcome enum, and an ISO timestamp on success. Every public BackupRecord text carrier also rejects supported share encodings before projection or registry mutation. | Protocol allowlist/schema tests, registry tests, and static runtime-wiring tests reject 20-/33-word SLIP-39 shares, codex32, Seed XOR, Shamir39, raw SSS, private keys, mnemonics, xprvs, passphrases, reconstructed bytes, and `shareMaterial` fields. Cold-session tests prove the timestamp setter rejects a different subject and an unresolved subject. |
| Message schema | Yes. Two new typed messages are added. `backup.verifyRequest` accepts only `backupId`; `backup.verifyResult` accepts only `backupId`, `outcome`, and the success-only `verifiedAt`. | `test/protocol.test.js`; `src/protocol.js`. |
| Cold CSP | No. No CSP directive or `connect-src` host changed. The cold realm remains `connect-src 'none'`. | `npm.cmd run lint`; build/static CSP tests in the full suite. |
| Vault format/crypto | No new cryptographic primitive or vault record. Verification uses the already-vendored cold combiners, the authenticated secret seed record, and the existing public replacement/save path. | `test/vault.test.js`; `npm.cmd run verify-vendor`. |

If this boundary were wrong, an attacker controlling the warm shell could learn the user's share material or reconstructed seed, forge completion state without a valid cold reconstruction, or attach a valid backup set to the wrong subject. The implementation prevents all three: warm code cannot set or clear `lastVerifiedAt`, the cold session owns the completion timestamp, and the timestamp setter compares the candidate against the uniquely resolved cold subject or refuses to proceed. No new network endpoint or host is introduced, so no new service learns anything about the backup.

## 6. Test evidence

New or changed tests include:

- Protocol tests for the BackupRecord schema, exact message whitelist, secret-shaped field rejection, success-only timestamp rules, and failure outcomes.
- Protocol regression tests using independent official/reference fixtures prove every public BackupRecord text carrier (`shareLabel`, `location`, `custodian`, and `notes`) rejects 20-/33-word SLIP-39, codex32, Seed XOR, Shamir39, and raw SSS in both warm-to-cold and cold-to-warm projections.
- Protocol regression tests prove realizable `1-of-1` and `N-of-N` group configurations pass while explicit `N+1-of-N` thresholds fail closed.
- Registry tests proving public records start unverified, warm callers cannot forge completion, and only the cold completion method can set the timestamp.
- Vault tests proving cold-only authority, direct and wallet-mediated cold subject resolution, preservation only across same-identity public replacement, reset on identity change, invalid timestamp rejection, rejection of a valid other-subject set, and fail-closed unresolved subjects.
- Runtime-wiring tests proving no secret-bearing boundary path, one subject-binding gate after every supported reconstruction method, durable-save dirty-state behavior, and browser harness coverage.
- Browser harness coverage in Chromium and Firefox proving an unresolved public subject fails closed, the record stays unverified, input clearing, warm DOM isolation, and teardown.

Independent vector sources already exercised by the underlying cold combiners are preserved and reused by this orchestration layer:

## 8. Assumptions made

- `subjectId` is a UUID supplied by the public record form because warm Seed CRUD does not yet exist. The cold session now resolves it only to an exact secret seed ID or to a public wallet's `seedId`; any missing, ambiguous, or secretless reference fails closed until the public Seed integration exists.
- `groupConfig` is public metadata and is used to bind a submitted share set to the recorded group/member thresholds. The record identity comparison is `subjectId`, `method`, `threshold`, and `groupConfig`; a change clears the cold-owned completion timestamp.
- A `verified` result means the supplied shares passed the format's parser/checksum/math, reconstructed under the recorded threshold/group configuration, and matched the cold-stored subject representation for that method. It does not prove that physical storage is safe or that a separate BIP-39 passphrase was backed up; the cold subject's stored passphrase is used only for the codex32 master-seed comparison.
- SLIP-39's share passphrase is entered only in the cold panel and is not stored in the BackupRecord. The BIP-39 passphrase remains a separate recovery input.
- The timestamp is generated in the cold realm with `toISOString()` and is only accepted in canonical UTC ISO form.
- The supported verification methods are the cold combiners already present in the repository. Physical-only formats are explicitly `unsupported` until their own safe cold workflow is designed.
- JavaScript strings and DOM values cannot be promised to be physically zeroized by this implementation. The code clears references and visible inputs on teardown, and the tests assert that behavior; this is not a claim about garbage-collector memory erasure.

## 9. What to scrutinise

- The threshold and nested group binding in `src/cold/main.js`: a parser-valid set must also match the public record's threshold/group configuration.
- The subject gate in `src/cold/vault.js`: a parser-valid set must also match exactly one cold-stored subject before `lastVerifiedAt` can be written; a public UUID alone is insufficient.
- The warm/cold timestamp lifecycle: the cold result updates the warm registry, marks the vault unsaved, and requires a subsequent authenticated save for durable persistence.
- `preserveColdVerificationAuthority` in `src/cold/vault.js`: same-identity public replacement preserves completion; any identity change resets it.
- The closed protocol schemas and the static no-secret assertions. In particular, check that future edits cannot add share text or reconstructed bytes to either message.
- `isSecretContent` and its conservative public share filters: check exact equality with the canonical 1,024-word SLIP-39 list, both supported share lengths, codex32/Shamir39/raw-SSS framing, Seed XOR-shaped multilingual mnemonics, and false-positive tradeoffs.
- `cleanBackupGroupConfig`: check that an explicit group threshold cannot exceed the number of declared groups before cold binding consumes the configuration.
- Unsupported method behavior and the distinction between `invalid`, `unsupported`, `no-record`, and `vault-locked`.
- The UUID `subjectId` assumption and whether the future Seed registry should replace the temporary form input without weakening the public-only model.

## 10. Self-assessment

- This change does not validate physical share locations, custodians, or survivability; those remain P2.7 work.
- It now compares every supported candidate to a cold-stored subject before completion. Records whose `subjectId` cannot be resolved to that cold authority remain incomplete; this is intentional until the public Seed/wallet relationship is available in normal CRUD.
- No physical devices were available, so the device gaps are real, especially iOS local execution and Android Files execution.
- The browser harness asserts cleared verification input and warm isolation. A timing-sensitive assertion about the cold panel being hidden after Escape was removed because the existing unsaved-lock warning legitimately keeps the warm shell visible; teardown code and input clearing remain directly tested.
- This item adds no independent test vector of its own; it composes already independently pinned combiner implementations. A reviewer should confirm that the orchestration checks do not accidentally bypass those combiners.
- The R1 remediation adds conservative public-format recognition rather than warm decoding. False positives are an intentional fail-closed tradeoff; actual checksum, threshold, and reconstruction validation remains cold-only.
- The R2 remediation mechanically verifies the public SLIP-39 set against the canonical cold list; a separate development-time comparison matched it in count, membership, and order against Trezor revision `17fcce14736afe498871d3018e4fa9330443471a`.
- Follow-up is P2.7 for health scheduling/dashboard and P2.8 for printable cards/worksheets.
