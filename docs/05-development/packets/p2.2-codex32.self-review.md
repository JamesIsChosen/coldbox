## Security review

- The codex32 implementation is assembled only in the cold realm. The warm
  parent has no `__coldboxCodex32` API, and the browser harness asserts that
  generated/recovered values do not reach the parent or a message payload.
- The cold policy remains `connect-src 'none'`; no `allow-same-origin`, network,
  storage, clipboard, or warm-message path was added for codex32.
- Random polynomial coefficients and generated identifiers use
  `crypto.getRandomValues`; generation raises an error when it is unavailable.
- Generated and recovered values are masked by default, revealed only by a
  timed action, and cleared by the existing cold teardown path. A correction
  candidate is never loaded automatically; the user must explicitly compare
  and confirm it.
- Interpolation now refuses empty, incomplete, mismatched, repeated, reserved,
  and non-missing target share sets rather than emitting a plausible
  checksum-valid value from insufficient evidence.
- The checksum constants and field arithmetic were checked against the
  published BIP-93 vectors; the vectors were not generated by this code.

## Residual risk and handoff

The highest residual risk is the hand-transcribed GF(32)/BIP-93 adaptation;
the published vectors do not cover every possible share-set shape. Physical
paper checksum calculation, mobile/iOS local-file execution, and hardware
wallet interoperability remain untested and are explicitly disclosed in the
PR packet. A fresh independent reviewer should scrutinise the checksum
constants, `gfLagrange`, the `s`-anchored polynomial generation, build-manifest
ordering, and cold teardown before any merge.
