# PR packet: P0.13 - Lock, unlock, save, load

## 1. Summary

P0.13 adds the first usable vault session workflow on top of the P0.12 format and KDF layers. The warm shell now offers device loading, File System Access saving when the browser exposes it, blob download, and a complete manual base64 export/import path. The passphrase field, vault API calls, session bytes, lock timer, and panic handling live in the opaque cold frame.

The branch is `p0.13-lock-save-load`, based on the unmerged dependency branch `p0.12-kdf-profiles` at `b24661f`; its PR base must therefore be `p0.12-kdf-profiles`.

The roadmap remains `[~]` because P0.13 explicitly reserves the iOS Safari manual-path claim for the human P0.19 device pass. Chromium and Firefox verify the browser-observable portion, but no physical iOS result is inferred.

## 2. Scope

### In scope

- Warm-shell device load using File System Access when available and a file-input fallback elsewhere
- Cold-only passphrase entry, empty-vault creation, encrypted-byte load, public-only online unlock, full offline unlock, and lock
- Three save paths: File System Access, blob download, and manual base64 text with clipboard/select fallback
- Symmetric manual base64 load, including whitespace-tolerant paste handling and protocol-size validation
- Five-minute cold-realm idle auto-lock with passphrase-field and encrypted working-byte clearing
- `Esc Esc` panic concealment from the warm shell and from the cold frame, with a recovery screen that requires reload
- Private mode signaling; online unlock calls `openPublic`, which never derives `cbx/secret/v1`; an offline signal permits the full opener
- Typed `panic.hide` protocol messages with empty payloads
- Node and Chromium/Firefox coverage for public-only subkey exclusion, blob/manual round-trips, and panic hide
- Roadmap, architecture, crypto-choice, testing, changelog, and packet documentation

### Deliberately out of scope

- Physical iOS Safari, Android, macOS Safari, Tor, or other device-matrix claims; P0.19 owns those checks
- QR rendering or scanning; the manual path is complete as base64 text, while QR tooling is a later route
- Save verification, generational filenames, rollback counters, and dirty-state tracking (P0.14)
- Keyfile unlock (P0.15), public-data editing, wallet creation, and secret-tool workflows

## 3. Security boundary

- The warm shell carries encrypted vault bytes only. It has no `__coldboxVault`, no passphrase input, and no secret-compartment plaintext.
- The cold realm receives `vault.open` ciphertext, reads the passphrase locally, and sends only an empty/public-safe `vault.opened`, encrypted `vault.bytes`, typed status, or generic error.
- The cold realm defaults to online-safe behavior until `mode.set` arrives. Online unlock unwraps the DEK and decrypts only the public compartment; the tracked unit test observes only `cbx/public/v1` HKDF use.
- A transition to online clears an active cold session. Lock and idle expiry clear the input and in-memory encrypted working copy; the warm shell may still hold ciphertext needed for a later reload.
- Panic hide locks before concealing the warm app. A cold-frame `Esc Esc` sends a payload-free typed request to the warm shell.

## 8. Assumptions made

> **Assumed:** The manual base64 path is the universal fallback for a browser that exposes neither File System Access nor a reliable blob download.
> **Basis:** It uses a visible textarea, standard base64, copy when permitted, and ordinary select/paste when clipboard APIs are unavailable.
> **Not verified on:** Physical iOS Safari; that is the explicit P0.19 gate.
> **If wrong:** P0.19 should keep the item `[~]` and adjust the text transport before marking it complete.

> **Assumed:** Creating an empty vault online should produce a public-only vault rather than derive a secret subkey.
> **Basis:** The format permits a zero-length secret compartment, and the online-mode invariant is stronger than making creation fail for a user who has not disconnected.
> **If wrong:** The creation surface should require offline mode before offering a secret compartment.

## 9. What to scrutinise

- Confirm every unlock path is mode-aware and that `openPublic` cannot reach `cbx/secret/v1`.
- Confirm the warm shell never gains a passphrase field or `__coldboxVault` reference through the save/load controls.
- Confirm lock, idle expiry, mode transition, and panic hide clear the cold passphrase field and active session bytes.
- Confirm manual base64 rejects incomplete/oversized text and never sends plaintext through the protocol.
- Confirm every P0.13 branch is based on `p0.12-kdf-profiles`, and that the PR targets that branch rather than `main`.
- Do not mark the roadmap item `[x]` until the P0.19 iOS Safari result exists.
