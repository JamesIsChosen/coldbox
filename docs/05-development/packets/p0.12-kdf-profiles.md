# PR packet: P0.12 - KDF profiles and benchmark

## 1. Summary

P0.12 completes the Argon2id profile selection surface that P0.10 and P0.11 already encode in the vault header. The sealed cold realm now exposes a user-triggered, sequential benchmark for Fast, Standard, and Paranoid, reports elapsed milliseconds from fixed non-secret inputs, and warns that Paranoid's 256 MiB allocation may fail on iOS. A likely iOS device skips that allocation rather than risking a tab crash.

The branch is `p0.12-kdf-profiles`, based on the unmerged dependency branch `p0.11-vault-format` at `304b6d9`; its PR base must therefore be `p0.11-vault-format`.

## 2. Scope

### In scope

- Cold-only `benchmarkProfiles()` API with real Argon2id parameters for all three selectable profiles
- Sequential execution so Fast, Standard, and Paranoid never allocate their working memory concurrently
- Fixed non-secret benchmark passphrase, salt, secret, and associated-data buffers, all wiped after each run
- `performance.now()` timing with a `Date.now()` fallback and one decimal millisecond reporting
- Generic unavailable results when Argon2id is not healthy or a profile allocation/hash fails
- Likely-iOS detection for the Paranoid 256 MiB allocation, with an explicit skip/warning result
- Cold-frame button and result status offered before vault creation; no benchmark control or crypto API in the warm shell
- Real all-profile vault round-trips and header-parameter assertions
- Browser assertions for cold-only API exposure, enabled benchmark control, and the initial not-run state
- Roadmap, changelog, security-choice, testing, and packet documentation

### Deliberately out of scope

- Vault creation, lock/unlock, save/load, or profile selection controls in the warm-shell workflow (P0.13)
- Changing the P0.10 Argon2 KAT or PBKDF2 fallback behavior
- Parallel benchmark samples, historical result storage, or telemetry
- Physical iOS, Android, macOS, Tor, or other device timing claims (P0.19)

## 5. Security impact

- Realm boundary: Yes. The benchmark API, fixed input buffers, Argon2 invocation, result formatting, and button all live in the cold document. The warm source/template contain no benchmark API or control.
- Secret material: No user passphrase, vault bytes, DEK, or seed enters the benchmark. The fixed input buffers are wiped after each profile; benchmark output contains only profile ids, parameters, status, duration, and a static warning.
- Resource safety: Yes. Profiles execute sequentially. A likely iOS device never attempts the 256 MiB Paranoid allocation, and any other allocation/hash failure returns an unavailable result rather than selecting a profile.
- KDF correctness: Yes. The benchmark calls Argon2id with the exact Fast, Standard, and Paranoid parameters already stored by the vault layer. Vault round-trips assert that the requested profile remains in the header rather than silently becoming PBKDF2 fallback.
- Error handling: Yes. Benchmark failures return a generic unavailable status. No raw Argon2 error is rendered or sent across the message channel.
- Network/message surface: No new protocol type or message field. The benchmark is initiated by a cold-local button and does not cross the realm boundary.
- Randomness: No benchmark randomness was introduced. Fixed test inputs make timing comparisons repeatable and keep the CSPRNG path reserved for actual vault material.

## 6. Test evidence

### New and changed tests

- `test/crypto.test.js` verifies three sequential successful timings, the permanent Paranoid/iOS warning, and the likely-iOS skip before allocation.
- `test/vault.test.js` derives and reopens public-only vaults with Fast, Standard, and Paranoid, then checks the exact header parameters.
- `scripts/run-browser-harness.js` verifies that `__coldboxCrypto` and `benchmarkProfiles` remain cold-only, that the button is enabled after a healthy boot, and that benchmarking does not start automatically.
- Existing P0.10 KAT, fallback, CSP, protocol, vendor, tamper, lockdown, and browser tests remain green.

### Negative tests

- Likely-iOS Paranoid allocation is skipped and reported as `skipped` with the iOS warning.
- Missing/failed Argon2 returns unavailable profile results instead of silently timing PBKDF2 as Argon2id.
- A corrupted vendored artifact makes verification exit non-zero.
- Warm source/template contain no benchmark API or control.

### Not tested

No physical iOS Safari, Android Chrome from Files, macOS Safari, macOS Chrome, Linux Firefox, or Tor Browser was available. The iOS path is simulated with a controlled navigator fixture; real memory allocation behavior remains P0.19 work. No vault creation UI exists yet, so the benchmark is offered in the cold details panel as the pre-creation surface for P0.13.

## 8. Assumptions made

> **Assumed:** A single sequential run per profile is a useful pre-creation timing estimate.
> **Basis:** The user needs the cost of the exact profile on the current device; each run uses the real memory, pass count, and lane count and includes the actual Argon2 invocation.
> **Not verified on:** Physical devices, because P0.19 owns that matrix.
> **If wrong:** P0.12 should add repeated samples or a device-specific calibration policy before profile selection is exposed in the creation workflow.

> **Assumed:** The iOS user-agent/platform heuristic is sufficient to avoid the known 256 MiB allocation on common iPhone/iPad browsers.
> **Basis:** It covers iPhone/iPad/iPod user agents and touch-capable iPadOS desktop-mode `MacIntel` reporting, while Paranoid always carries the static warning even when the heuristic does not match.
> **Not verified on:** A physical iPadOS browser.
> **If wrong:** The static warning remains visible, and the actual allocation failure is converted to an unavailable result; the heuristic should be expanded before relying on it as a hard safety gate.

## 9. What to scrutinise

- Confirm the benchmark calls the exact header profile parameters and never times a fallback path as a successful Argon2 result.
- Check that Fast, Standard, and Paranoid run sequentially and that all fixed input/output buffers are cleared after each run.
- Check that the likely-iOS guard is applied before the 256 MiB allocation and that the user-visible warning remains present for a successful desktop run.
- Confirm no warm-to-cold message, protocol field, or warm global can invoke the benchmark or receive its inputs.
- Recheck that this item adds no vault creation or save workflow that belongs to P0.13.

## 10. Self-assessment

- The benchmark measures one sequential full-profile run rather than a median; this is explicit and should be revisited if device noise makes profile choice unclear.
- The iOS guard is conservative and heuristic; the static warning is unconditional for Paranoid and physical validation remains deferred.
- P0.12 does not select or persist a profile itself; P0.11's authenticated header and P0.13's creation workflow own those operations.
- No benchmark telemetry, network request, or user passphrase is introduced.
