## 4. Findings

### F1 — Required physical device matrix remains incomplete

**Severity:** blocking

**Location:** `docs/05-development/ROADMAP.md:188-192`; `docs/05-development/testing.md:150-176`; `docs/05-development/packets/p0.19-device-matrix.md:91-112`

**Observed:** The packet records Windows Edge/Chrome/Firefox non-camera hands-on results, but macOS Safari/Chrome, Linux Firefox, Android Chrome from Files, and Tails/Tor Browser remain deferred. No formal iOS PASS/BLOCKED/UNSUPPORTED result with exact device/iOS version is recorded. The item itself explicitly requires physical execution and forbids inferring one platform from another.

**Expected:** Every supported execution-matrix platform must receive the required physical `file://` pass from `testing.md`. The iOS portability target must separately record PASS, BLOCKED, or UNSUPPORTED with exact device and iOS version; third-party HTML-reader execution is not Safari-from-Files evidence.

**Required action:** Complete and record the remaining physical matrix without inference. Record the formal iOS result with exact device/iOS version. Keep P0.19 at `[~]` until a fresh independent review can verify the resulting evidence.

### F2 — Windows live-QR camera receiver has not passed its required physical path

**Severity:** blocking

**Location:** `docs/05-development/packets/p0.19-device-matrix.md:98-100`; `docs/05-development/testing.md:174`; receiver wiring at `src/main.js:1655-1657` and `src/main.js:2443-2498`

**Observed:** The recorded physical Windows result says the capability panel reports `Camera access: API available`, while the receiver remains at `Camera is off`, `Start camera scanner` is disabled/not clickable, and no receiving-device transfer was demonstrated. My synthetic Playwright camera/`BarcodeDetector` shim could start the scanner in Chromium and Firefox, but that does not reproduce or dismiss the physical `file://` behavior that P0.19 exists to test.

**Expected:** Where the platform exposes the required camera QR-decode path, a real receiving device must scan the live transfer, verify it, require the ordinary passphrase, and begin Not saved. If the required QR decode capability is unavailable in that browser/context, the product must report it honestly as unavailable and direct the user to the `.cbx` fallback rather than presenting an apparently available-but-inoperable receiver.

**Required action:** Diagnose the real Windows `file://` capability/control mismatch. Either make live receive work and demonstrate a device-to-device receive on the applicable Windows browsers, or accurately classify the decoder path as unavailable with the explicit `.cbx` fallback. Record the physical result per `testing.md`.

### F3 — A stale offline classification remains secret-capable while a new reachability probe is in flight

**Severity:** blocking security

**Location:** `src/main.js:1340-1351`, `src/main.js:1394-1461`; contradicted by `docs/05-development/adr/0024-warm-reachability-monitor.md` Decision 4, `docs/01-spec/SPEC.md` §network reachability, `docs/01-spec/architecture.md`, and `docs/02-security/threat-model.md`

**Observed:** After establishing `data-reachability-state="unreachable"` and opening an offline secret-capable vault, I forced the next warm reachability probe to remain in flight. In both Chromium and Firefox the focused diagnostic observed:

```text
during recheck:
  data-reachability-state = unreachable
  data-reachability-checking = true
  cold data-warm-network-online = false
  cold session state = unlocked
  warm vault state = unlocked
  cold vault state = unlocked
```

When that held probe was released as reachable, both engines changed to `reachable` / `data-warm-network-online=true` and locked the session.

The source explains the gap. `runReachabilityCheck()` sets only `data-reachability-checking="true"` when a new round begins; it does not move a prior `unreachable` classification to unknown/online-safe. `updateAirgapBanner()` later sends `mode.set { online: reachabilityState !== 'unreachable' }`, so the stale `unreachable` value continues to authorize offline mode throughout the check. The author source-pattern test named “online-safe on uncertainty” only asserts the final `sendColdMode(reachabilityState !== 'unreachable')` expression and does not exercise this in-flight stale-state transition.

**Expected:** ADR-0024 explicitly requires checking and stale states to be online-safe and to keep the secret compartment sealed. A recheck of a previously offline-classified device must not leave an unlocked offline session authorized while the current reachability result is unknown/stale.

**Required action:** On starting a new reachability round from `unreachable`, immediately move the authority to an online-safe classification and send the corresponding validated `mode.set` before waiting for probe completion, so an unlocked offline session locks/zeroizes at once. Add a real Chromium/Firefox regression that holds the probe unresolved and asserts the cold mode is online-safe and any offline secret-capable session is already locked during the in-flight interval.

**Required action:** Reconcile the dependency row with ADR-0026/current runtime terminology and re-run documentation checks plus a targeted stale-QR wording scan.
