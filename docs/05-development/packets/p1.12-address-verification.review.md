## 4. Findings

### F1 — Warm verification trims pasted text before the character-exact check

**Severity:** blocking security / acceptance defect

**Location:** `src/main.js` — round-trip/inbound/cold verification handlers and `runAddressBatch`; `src/address-verification.js::classify`

**Observed:** The verifier itself treats leading or trailing whitespace as unrecognised input. The reviewer probe confirmed both `" 1Boat…"` and `"1Boat… "` return `unrecognised-format` when passed directly. The warm UI, however, calls `.trim()` on pasted candidate values before verification, and batch rows are trimmed as well. That changes the user-supplied string before the feature that claims to compare it character-exact over the whole string.

**Expected:** The pasted-back destination value must reach the comparison boundary unchanged except for the chain-specific normalisations explicitly documented by P1.12: Bech32 case, EVM case/checksum handling, and no Base58 normalisation.

**Required action:** Remove generic whitespace trimming from P1.12 address-verification inputs. Pass the raw user value to classification/comparison and add committed browser/unit coverage proving leading/trailing whitespace is not silently normalized into a match.

### F2 — Bech32 checksum-invalid addresses are accepted as recognized self-matches

**Severity:** blocking security / validation defect

**Location:** `src/address-verification.js::classify`

**Observed:** Bech32 classification is a character-shape regex plus mixed-case rejection; it does not verify the Bech32 checksum or SegWit address validity. The independent probe used the BIP-173 valid mainnet P2WPKH vector ending `…f3t4` and the specified invalid-checksum mutation ending `…f3t5`. The independent checksum validator accepted the former and rejected the latter. P1.12 classified both as `bech32`, and the invalid-checksum string compared with itself as `match`.

**Expected:** Per the P1.12 spec, a pasted value that is not a valid address on a known chain is `unrecognised`, distinctly from mismatch. BIP-173 checksum-invalid input must never become a registry/self match.

**Required action:** Implement actual Bech32/Bech32m decoding and checksum/address validation rather than regex shape recognition. Add independent official valid and invalid vectors, including the `…f3t5` checksum failure, and prove invalid values cannot match registry records.

### F3 — Base58Check checksum-invalid addresses are accepted as recognized self-matches

**Severity:** blocking security / validation defect

**Location:** `src/address-verification.js::classify`

**Observed:** Base58 classification is only a character/length/prefix regex. The reviewer independently validated `1BoatSLRHtKNngkdXEeobR76b53LETtpyT` as Base58Check-valid and the one-character mutation `1BoatSLRHtKNngkdXEeobR76b53LETtpyU` as checksum-invalid. P1.12 nevertheless classified the mutation as `base58` and self-compared it as `match`.

**Expected:** “Base58Check” means the checksum is validated. A checksum-invalid value is not a valid known-chain address and must not be accepted as a match.

**Required action:** Perform Base58Check decoding and checksum validation before classifying the value as a recognized address. Add independent valid/invalid checksum vectors and registry-match negative tests.

### F4 — Batch verification converts invalid mixed-case EVM addresses into `no-record`

**Severity:** blocking security / acceptance defect

**Location:** `src/main.js::runAddressBatch`

**Observed:** The single-value classifier correctly marks an invalid mixed-case EVM address with `checksumInvalid: true`. Batch verification ignores that flag. When no registry match is found, it checks only whether `classify(candidate).kind === 'unknown'`; an invalid mixed-case EVM value still has kind `evm`, so the row is rendered as `no-record` instead of `checksum-invalid`.

**Expected:** The roadmap requires EIP-55 failure to remain distinctly `checksum-invalid`, and the P1.12 batch model says each row gets its own verdict. Batch processing cannot weaken that outcome.

**Required action:** Preserve `checksumInvalid` in the batch path and render the same closed outcome used by single-value comparison. Add committed batch tests for invalid mixed-case EVM input.

### F5 — Cold re-derivation is wired through a Bitcoin-only identity helper, leaving EVM without the second claim

**Severity:** blocking functional / two-claim-model defect

**Location:** `src/cold/main.js::handleAddressVerifyRequest`; `src/cold/verification.js::deriveWalletIdentity`; existing `src/cold/derivation.js` EVM seed derivation

**Observed:** P1.12’s cold verification request uses the P1.9 `deriveWalletIdentity` helper. That helper derives the Bitcoin script families and does not call the repository’s existing EVM seed-derivation path. The repository does have EVM seed derivation from P1.5. P1.12 simultaneously recognizes EVM addresses and validates EIP-55 in the warm comparison layer, so an EVM address can receive the first claim but cannot be re-derived through the implemented P1.12 cold authority path.

**Expected:** The P1.12 spec’s two claims are separate but apply to a recorded address that can be derived from the seed. Supporting EVM comparison while silently routing cold authority through Bitcoin-only derivation leaves the second claim incomplete for a supported address family.

**Required action:** Select the cold derivation path from the account/wallet chain metadata and support EVM seed-backed address re-derivation using the existing cold EVM engine. Add an end-to-end EVM P1.12 cold-verification test proving the registry state transition and returned verdict.

### F6 — `different-account` results do not name the matching account

**Severity:** blocking specification / user-safety defect

**Location:** `src/main.js::addressVerificationCopy`, `compareAddressAgainstRegistry`, inbound/batch presentation paths

**Observed:** `addressVerificationCopy` accepts only `(result, state)`, performs no account lookup, and renders the literal text “This address is recorded under a different account.” The targeted probe confirmed there is no account lookup or label/name resolution in that renderer. Inbound and batch match copy likewise do not identify the account.

**Expected:** `address-verification.md` explicitly requires an address that matches a record in a different account to be reported as a match **with the account named**.

**Required action:** Carry or resolve the matching account reference and render a bounded public account label/name in the verdict. Add a regression test with two accounts proving the correct account is named.

### F7 — Mismatch presentation does not show both complete strings aligned with the divergence marked

**Severity:** blocking specification / verification-UX defect

**Location:** `src/main.js::addressVerificationCopy`

**Observed:** For `mismatch`, the UI returns only `Mismatch at character N; the complete strings differ.` It does not render the candidate and recorded values, does not align them, and does not visually mark the divergent character.

**Expected:** `address-verification.md` requires the first divergence index **and** both complete strings aligned with the divergence marked. That presentation is part of the poisoning-defense model, not optional decoration.

**Required action:** Render both complete public address strings in an alignment-safe comparison surface with the first divergence marked, while preserving the numeric divergence index. Add browser coverage for a middle-only mismatch.

### F8 — The P1.12 packet reports the historical PR #45 diff size instead of PR #47

**Severity:** advisory documentation defect — must still be fixed

**Location:** `docs/05-development/packets/p1.12-address-verification.md` §3

**Observed:** The packet says the reconciled diff is “13 files, 781 additions, and 2 deletions.” Independent `git diff --shortstat b6c3a3b7…fc154cdc` reports `13 files changed, 939 insertions(+), 2 deletions(-)`. GitHub reports the same 939/2 live PR #47 statistics. The 781 number is the historical closed PR #45 figure.

**Expected:** Review packets must describe the exact PR they hand off. The repository review protocol explicitly treats stale numbers in prose as defects.

**Required action:** Refresh the packet to the exact PR #47 diff and review all other reconciliation/evidence figures for the same historical-PR carryover.
