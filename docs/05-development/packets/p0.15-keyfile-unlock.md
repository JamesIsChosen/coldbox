# P0.15 — Keyfile unlock

Branch: `p0.15-keyfile-unlock` (PR #27, open against `main`). This packet was updated during author remediation of an independent FAIL review (`docs/05-development/packets/p0.15-keyfile-unlock.review.md`); §13 below records what changed and why.

## 1. Summary

[P0.15](../ROADMAP.md) implements wrapped-DEK method 2 (passphrase + keyfile) exactly as already specified in [vault-format.md](../../01-spec/vault-format.md): `KEK = Argon2id(passphrase || SHA-512(keyfile), salt, params)`. A vault created with a keyfile carries a method-2 record in place of the method-1 record — the keyfile becomes required, not optional — and the cold-realm UI adds an off-by-default toggle with an unmissable warning that a lost or byte-altered keyfile means permanent, unrecoverable loss. Structural implementation choices the spec left open (size limits, hint truncation, empty-keyfile handling, method exclusivity) are recorded in new [ADR-0014](../adr/0014-keyfile-unlock-implementation-limits.md).

## 2. Scope

**In:** `src/cold/vault.js` (method-2 record creation/parsing/unwrapping), `src/cold/main.js` (keyfile toggle, warning, `FileReader`-based file input, wiring into create/unlock), `src/cold/index.html` and `src/cold/styles.css` (new keyfile UI section), `test/vault.test.js` (8 new P0.15 tests), `scripts/run-browser-harness.js` (dedicated P0.15 keyfile UI/regression coverage, added during remediation), `docs/01-spec/vault-format.md` (implementation-limit paragraph added to the existing Method 2 description), new `docs/05-development/adr/0014-keyfile-unlock-implementation-limits.md`, `docs/05-development/adr/README.md` (index entry), `docs/05-development/testing.md` (P0.15 coverage paragraph), `CHANGELOG.md`, `ROADMAP.md` (`[~]`).

**Out, deliberately:**
- No change to `src/main.js` or `src/index.html` (the warm shell). Keyfile bytes, like the passphrase, never leave the cold realm — there is no code path for them to.
- No new `postMessage` type. `src/protocol.js` is untouched. The keyfile is passed as a direct in-memory argument to `vaultLayer.create()`/`vaultLayer.openSession()`, both of which already run inside the same cold document; it never crosses the `MessageChannel`.
- No format-version bump. `HEADER_LENGTH` and the fixed header layout are byte-identical; only the (already-generic, already-multi-record) wrapped-DEK block gains a second record *type* it can hold, which `parseWrappedRecords()` required zero changes to support.
- No recovery-share method (method 3) — out of scope, Phase 2 per vault-format.md.
- No P0.17 three-depth help content — the help framework does not exist yet (same precedent as P0.14's packet; see §12).

## 5. Security impact

- **Realm boundary:** no code added or changed in the warm shell (`src/main.js`, `src/index.html`). Keyfile bytes are read via `FileReader` entirely inside `src/cold/main.js`, which already runs inside the sandboxed `srcdoc` iframe. `test/vault.test.js`'s existing boundary test (`assert.doesNotMatch(warmSource, /__coldboxVault|.../)`) still passes unmodified.
- **Message schema:** no. `src/protocol.js` is untouched; no new `postMessage` type was added, and none was needed — the keyfile is a direct function argument between two modules that already share the same JS realm (`src/cold/main.js` calling into `src/cold/vault.js`), not a message.
- **CSP:** no. Neither `src/index.html`'s nor `src/cold/index.html`'s policy `<meta>` tag changed. `FileReader` is a same-realm, no-network API; it needs no CSP allowance beyond what the cold realm already has.
- **Vault format:** the wire format itself is unchanged — vault-format.md already fully specified method 2 before this PR (I did not invent the byte layout, the KDF composition, or the "keyfile hint, never contents" rule; all three came directly from the existing spec). What this PR adds is the *implementation* of a shape the multi-record design was explicitly built to accommodate: `parseWrappedRecords()` needed **zero changes**, because it was already generic over method-data length. A vault written before this PR (method 1 only) opens completely unmodified after it — proven by every pre-existing `test/vault.test.js` case still passing unchanged, plus the new byte-identity assertion in `'P0.15 a vault created without a keyfile is byte-identical in shape to a method-1-only vault'`.
- **Derivation / randomness:** yes, in one specific sense — a new KDF *input composition* (`passphrase || SHA-512(keyfile)` instead of `passphrase` alone), reusing the exact same Argon2id/PBKDF2 derivation code path (`cryptoLayer.deriveKey()`) and the exact same AES-256-GCM wrap/unwrap (`aesGcm()`) that method 1 already uses and that P0.10 already established known-answer tests for. `SHA-512` itself is the same `@noble/hashes` implementation `hkdfSubkey()` already depends on elsewhere in this file (P0.11's HKDF subkey derivation), so no new cryptographic primitive enters the codebase — see §6 on test vectors.
- **New `connect-src` host:** none.
- **If this implementation is wrong, what does an attacker — or bad luck — gain?** The failure mode I most want scrutinized: if `unwrapDek()`'s method-2 branch were reachable *without* the caller actually supplying a keyfile (e.g. a bug where `keyfile` is falsy-but-truthy, like an empty array satisfying a loose truthiness check), a keyfile-protected vault could silently degrade to passphrase-only security while still displaying "keyfile required" in the UI — a confidentiality regression the user would have no way to detect from the outside. I guarded this explicitly with `if (hasKeyfileRecord && keyfile)` (a plain existence check, not a truthiness-only check on something empty-array-shaped) and `normalizeKeyfileBytes()` rejecting a zero-length keyfile *at creation* so an empty keyfile can never end up wrapped into a real vault in the first place — but I have not fuzzed this function against exotic `keyfile` argument shapes the way `test/save-integrity.test.js`'s `bytesEqual` bug (documented in the P0.14 packet) was eventually caught. Second-highest concern: `combinePassphraseKeyfile()`'s zeroing (`zeroBytes(passphraseBytes); zeroBytes(digest);`) happens on the *intermediate* buffers, but the returned `combined` array is zeroed by the caller (`createVault()`'s `finally` block, `unwrapDek()`'s `finally` block) — if any caller forgot that `finally` zero, keyfile-derived key material would linger in memory longer than a passphrase-only vault's KEK does today. I traced every call site and both zero it, but this is exactly the kind of discipline that's easy to regress in a later PR without a dedicated "was this zeroed" test, which I did not write (no existing test in this codebase asserts zeroing behavior via memory inspection — it's a property this codebase currently only enforces by code review, not by test, for any secret, not just this one).

## 8. Assumptions made

- **Method 2 replaces method 1 rather than coexisting with it (one vault, one active unlock method).** Full reasoning in [ADR-0014](../adr/0014-keyfile-unlock-implementation-limits.md). **Basis:** the roadmap's own acceptance text ("fails with a one-byte-altered keyfile") only makes sense as an unconditional requirement if there is no passphrase-only fallback record sitting alongside it that would let someone skip the keyfile entirely. **What breaks if wrong:** if a reviewer believes a vault should be unlockable by *either* credential, this is a different, weaker feature (arguably not "keyfile unlock" as a security property at all, since losing the keyfile would no longer risk anything) needing its own acceptance criteria and its own UI copy — the current warning text is only honest under the "keyfile is mandatory once enabled" model this PR implements.
- **64 MiB keyfile size ceiling, 255-byte hint truncation, empty-keyfile rejection** — all recorded with rationale in ADR-0014. **What breaks if wrong:** the 64 MiB number in particular is a judgment call (reusing the existing vault-size constant rather than deriving a keyfile-specific one); if a reviewer wants a smaller, UX-motivated ceiling instead, that's a one-line constant change with no format implications.
- **The keyfile hint (`options.keyfileHint`) is caller-supplied and unvalidated beyond type/length.** I pass `file.name` from the browser's `File` object in `src/cold/main.js` without sanitizing its content further (beyond UTF-8 encoding and the 255-byte cap). **Basis:** vault-format.md is explicit that the hint is "never contents" and purely advisory display metadata, so unlike the vault's public/secret compartments there is no injection-into-decrypted-data risk — it is authenticated ciphertext structure, not interpreted as markup or executed anywhere I can find in this codebase. **What breaks if wrong:** if a future UI ever renders the hint as HTML instead of `textContent`, a maliciously named keyfile (`<img onerror=...>`) could matter; I did not add an explicit encode-on-render step because no code in this PR renders the hint back out anywhere (it's write-only in the current implementation) — flagged as a forward-looking note for whoever builds a "vault details" panel that displays it.
- **`FileReader` is assumed available whenever the cold realm is otherwise functional.** `keyfileInput`'s `change` listener is gated on `typeof window.FileReader === 'function'`; if absent, the keyfile input simply never wires up (the checkbox still toggles the warning, but selecting a file does nothing observable). I did not add an explicit capability-panel entry for this (unlike `randomValues`/`cryptoSubtle`/`wasm`/etc. in `src/capabilities.js`) because `FileReader` has been part of every browser Coldbox's other capability checks already assume workable File-object handling (blob download, manual export) since long before this PR — I judged it out of scope to retrofit a new capability flag for one specific API this deep into Phase 0, but a reviewer could reasonably disagree.

## 9. What to scrutinise

- **The two acceptance criteria this packet still could not execute-test in its own sandbox: "off by default" and "unmissable warning," plus the new F1/F2 regressions.** `verifyKeyfileUiAndRegressions()` in `scripts/run-browser-harness.js` now exists specifically to test all four by actually clicking the toggle, checking `hidden`/`disabled` attributes, forcing out-of-order `FileReader` completion, and locking/re-selecting a keyfile — but this remediation session never got to run it against Chromium or Firefox (§3a). **This is the top thing for whoever reviews this to independently execute**, not take on faith.
- **`unwrapDek()`'s branch structure** (`src/cold/vault.js`, the rewritten function around `hasPassphraseRecord`/`hasKeyfileRecord`). This is the function carrying the entire security property of "passphrase-only vaults are unaffected" and "a keyfile vault requires the keyfile." I'm fairly confident in it — it's covered by 5 of the 8 new tests directly or indirectly — but it's also the most-rewritten function in this diff (full replacement, not an incremental edit) and exactly the kind of control-flow change where a subtle boolean-logic bug (e.g. `||` where I meant `&&`) would be catastrophic and easy to miss in review. I'd read it line by line rather than trust the tests alone.
- **`combinePassphraseKeyfile()`'s zeroing discipline**, discussed in §5. No test in this PR inspects memory to confirm zeroing actually happened — it's verified by code reading only, same limitation the rest of this codebase's secret-zeroing already has.
- **Whether the 64 MiB keyfile size ceiling is the right number.** It's a defensible but somewhat arbitrary reuse of an unrelated existing constant (ADR-0014's own "what would change our mind" section says as much) — a reviewer with stronger opinions about acceptable keyfile sizes (e.g. capping much lower, since realistic keyfiles are probably kilobytes, not tens of megabytes) should feel free to push back on this specific number without it implicating anything else in the PR.
