# P0.17 — Help framework

Branch: `p0.17-help-framework`
Roadmap item: [P0.17](../ROADMAP.md) (deps: P0.5, satisfied)

**One known, disclosed gap before you read further:** `npm run test:browser` could not be executed in the authoring sandbox — Playwright's Chromium/Firefox binary downloads are blocked by that sandbox's network allowlist (`cdn.playwright.dev` returns `403`). This is the identical class of gap P0.16's packet recorded, for the identical reason, and it resolved the same way there: a later session or the reviewer with real network access ran it for real. Per review-protocol.md, an acceptance criterion that can't be verified is a legitimate FAIL, and I'm not going to argue otherwise — see §4 for exactly which criteria that affects and §10 for what would close it.

## 1. Summary

Implements the P0.17 build-time compiler (`scripts/help-content.js`), the three-depth (`::: plain`/`::: working`/`::: technical`) markdown block model, and the in-app Learn page (depth switcher, offline search, contextual `?` help on five panels, inline tap-to-define glossary). The roadmap's P0.1–P0.16 backfill obligation is fully met: all 46 glossary entries and all 9 guides now carry three-depth content, and `npm run build` produces zero help-content warnings.

## 2. Scope

**In:** `scripts/help-content.js` (new compiler), `scripts/build.js` (wiring + warning emission), `scripts/lint.js` (tooling-syntax registration), `src/index.html` (Learn page markup, five contextual `?` buttons), `src/main.js` (depth preference, search, inline glossary, contextual navigation), `src/styles.css` (Learn page + inline glossary styling), `docs/00-overview/glossary.md` (full rewrite, all 46 entries three-depth), all nine files in `docs/03-guides/` (three-depth content on key explanatory passages), `scripts/run-browser-harness.js` (`verifyHelpFramework` — written, unexecuted, see §7/§10), `test/help-content.test.js` (new, 21 tests), `test/build.test.js` and `test/provenance.test.js` (fixture fix: `createBuildRoot()` helpers now copy `docs/`, since the build reads it; one pre-existing test regex loosened to not false-positive on JSON-escaped compiled content — see §9), ADR-0016, ROADMAP.md, CHANGELOG.md, SPEC.md's bundle-budget table.

## 5. Security impact

- **Realm boundary, message schema, CSP, vault format, derivation, randomness:** not touched by this branch. The Learn page lives entirely in the warm shell; no new message type was added; no cold-realm file changed.
- **New CSP-relevant surface:** none — no new inline script/style block beyond what the existing build already hashes (`scripts/build.js`'s `hashInlineBlocks` covers the whole assembled `<script>`/`<style>` regardless of what's inside them).
- **New `localStorage` key:** `coldbox-help-depth`. A UI preference (which reading-depth to show), not secret material — CONTRIBUTING.md explicitly permits `localStorage` for UI preferences (the existing `coldbox-theme` key is the precedent), and `scripts/lint.js` only forbids `localStorage` inside `src/cold/`, which `src/main.js` is outside.
- **New `innerHTML` usage:** `renderHelpGlossary`/`renderHelpGuides` assign `body.innerHTML = term.byDepth[depth]`, and `linkifyGlossaryTerms` assigns `span.innerHTML = replaced`. Both sources are build-time-compiled from repository markdown (not user input, not vault content, not anything from the cold realm), and `scripts/help-content.js`'s `escapeHtml`/`renderInline` escape all raw text before wrapping it in a small fixed whitelist of tags (`p`,`h3`–`h6`,`ul`,`ol`,`li`,`table`,`thead`,`tbody`,`tr`,`th`,`td`,`code`,`pre`,`strong`,`em`,`blockquote`,`hr`,`button` for glossary-term spans) — no script-capable tag is ever emitted, and CSP would refuse to execute one even if it were. **What to scrutinise if this claim is wrong:** `renderInline`'s link-handling regex and `linkifyGlossaryTerms`'s text-replacement path, since those are the two places raw text is spliced back into an HTML string outside the main block-level escaping loop — see §9.
- **No new `connect-src` host.** No new message type.

## 6. Test evidence

- **`test/help-content.test.js` (21 tests):** parser unit tests (shared/group node splitting, missing-depth warnings naming the exact missing depth, unterminated-block and duplicate-depth-in-group failures), `resolveGroupDepth` fallback ordering, `renderMarkdownToHtml`/`renderInline` (escaping verified with a literal `<script>` payload), `compileGlossary` (categories, terms, alias parsing including the semicolon-separated `"(extended public key; also ypub, zpub, vpub)"` case — see §9 for the bug this caught), duplicate-term-name de-duplication, empty-glossary failure, `compileGuide` title extraction and missing-block warning (against a synthetic fixture), end-to-end real-`docs/`-tree compilation, build embedding round-trip (embedded `HELP_CONTENT` JSON deep-equals a fresh `compileHelpContent()` call), a **regression guard that the real tree builds with zero help-content warnings**, and a negative test that an unterminated `:::` block in a guide fails the build closed with a non-zero exit and no partial artifact is written.
- **Vector sources:** not applicable — no cryptographic content.
- **Negative tests:** unterminated `:::` block → throws (`/unterminated/i`); duplicate depth within one group → throws (`/duplicate/i`); zero-term glossary → throws; malformed input never silently produces empty or wrong content.
- **What could not be tested:** everything requiring an actual rendered browser DOM. `test/help-content.test.js` and the Node-side `test/build.test.js`/`test/provenance.test.js` cover the compiler and the build's embedding of its output; they cannot exercise `src/main.js`'s DOM code (`renderHelpGlossary`, `handleHelpSearch`, `linkifyGlossaryTerms`, contextual-help click handlers), which only runs in a real page. That's exactly what `verifyHelpFramework` was written to close, and exactly what couldn't be executed — see §7.

## 8. Assumptions made

- **Depth-block granularity is per-passage, not per-file** (ADR-0016). `docs/03-guides/README.md` documented the `:::` syntax but not its scope; per-passage was chosen because guides are predominantly procedural and whole-file triplication would mean rewriting identical steps three times. Reversible — a file with one group spanning its entire body already behaves as "whole-file" under this model.
- **Default depth is `plain`**, matching SPEC.md's ordering (plain → working → technical) and the safest fallback direction. Not stated explicitly anywhere as the *default*; a judgment call, recorded per AGENTS.md §4.
- **The "Things people get wrong" glossary entries are wrapped in depth blocks too**, even though the correction itself barely changes across depths — only the technical justification does (a checksum mechanism, a derivation detail). Initially left single-depth as a judgment call in an earlier draft of this branch; revisited and completed once it became clear that leaving four permanent warnings on every build, for content that was easy to wrap, wasn't worth the residual noise.
- **New glossary category "App features (in Coldbox)"** backs the five previously-undocumented P0.1–P0.16 features (capability self-check, KDF profiles, save integrity, keyfile unlock, provenance panel) as glossary entries rather than invented step-by-step guides, since none of these are user-performed workflows — they're status panels and one-time decisions. A guide implies a walkthrough; forcing one into existence for a panel that has no steps would produce padding, not information. Reviewable and reversible if a reviewer would rather see dedicated guide files instead.
- **`test/build.test.js`'s "no machine paths in the output" regex was loosened** (`/[A-Za-z]:\\(?!u[0-9a-fA-F]{4})|\/Users\/|\/home\//`) after real docs content started producing coincidental `letter:\` matches from `<`-escaped tag boundaries in ordinary prose. The fix excludes the unicode-escape shape specifically rather than weakening the check generally — reasoning is inline in the test file. **This is exactly the kind of change I'd want a second pair of eyes on**, since it touches a security-adjacent leak-detection test.

## 9. What to scrutinise

- **The alias-parsing bug this session found and fixed in `compileGlossary`.** The original regex treated *any* parenthetical after a term as an alias list — including `"Vault (in Coldbox)"` and `"Cold realm / warm shell (in Coldbox)"`, which would have produced a bogus `"in Coldbox"` alias, and `"xpub (extended public key; also ypub, zpub, vpub)"`, whose semicolon-separated definition fragment would have been mangled into the alias list too. Fixed to only extract aliases when the parenthetical explicitly contains the word "also". Covered by `test/help-content.test.js`'s alias-parsing tests, but **I would specifically re-derive the fix myself rather than trust my own regex reasoning** — this is exactly the kind of off-by-a-word-boundary bug that's easy to get subtly wrong twice. It also directly caused a second bug I found and fixed while wiring the UI: two contextual `?` buttons pointed at manually-computed slugs (`glossary:cold-realm-warm-shell-in-coldbox`, `glossary:vault-in-coldbox`) that turned out not to match the compiler's actual output (`glossary:cold-realm-warm-shell`, `glossary:vault`) once the alias fix was in place — caught by cross-checking the compiled output directly rather than trusting my own arithmetic.
- **The `jsonScriptLiteral()` bundle-size interaction.** A large amount of compiled prose pushed through the existing `<`/`>`/`&` → `\uXXXX` escaping helper costs roughly 5 extra bytes per angle bracket. That helper is shared with `PROVENANCE_LIBRARIES` and the cold-realm document and predates this item; not changed here, since narrowing its escaping (e.g. to only sequences that could form `</script`) is a security-relevant change to shared code deserving its own review, not a drive-by fix bundled into a content-compiler PR. Flagged in the ADR, CHANGELOG, and SPEC.md as an open, unresolved finding for a follow-up item.
- **The zero manual-browser-testing gap, stated plainly again:** every claim in §4 about DOM behavior rests on code review against the actual selectors/ids in `src/index.html`/`src/main.js`, not on having watched it run. Review caught two real bugs already (the slug mismatches above, and a Learn-page test assertion that checked for text not present in the actual authored glossary prose) — there may be others only actually running the harness would catch.
- **`normalizeLocation`'s changed collapsing behavior.** It now preserves a `#route/topic` hash instead of always collapsing to `#route`, to support shareable deep links into Learn content. A small, deliberate behavior change to existing routing code (not new-route-only code) — worth checking it doesn't interact oddly with any other route that might someday use a `/`-suffixed hash for its own purposes.
- **The new "App features" glossary category's placement decision** (§8) — a reviewer might reasonably want dedicated guide files instead of glossary entries for some of these five features.

## 10. Self-assessment

- **What might be wrong:** anything in the browser-only code paths, per §9. The compiler (Node-side, fully tested) is the part I'm most confident in; the DOM-wiring half is the part I'm least confident in, precisely because it's the untested half.
- **What I did not do that arguably should have been done:** run `npm run test:browser` (blocked by sandbox network policy, not a choice — retried twice, identical failure both times); narrow `jsonScriptLiteral()`'s escaping to recover bundle size (deferred as a separate, shared-code change needing its own review); get a second opinion on whether five new glossary entries or dedicated guide files better serve the P0.1–P0.16 backfill for panel-type (non-workflow) features.
- **Known limitations shipping with this state:** help-content bundle weight (≈344 KB) exceeds SPEC.md's original 180 KB estimate, now corrected there directly with the real figure; zero real-browser verification this session, for the reason repeated throughout this packet.
- **Follow-up work, with roadmap status:** once this PR is reviewed, whoever has real network access should run `npm run test:browser` and either confirm `verifyHelpFramework` passes as-is or fix whatever it finds — per P0.16's own precedent, this doesn't have to block merge if the reviewer is comfortable treating it the same way P0.16's F3 was eventually closed (a later real-network run). Separately, revisiting `jsonScriptLiteral()`'s escaping strategy for bundle size is worth its own roadmap consideration, since it's shared code outside this item's scope.
