## 1. Summary

Implements the P0.17 build-time compiler (`scripts/help-content.js`), the three-depth (`::: plain`/`::: working`/`::: technical`) markdown block model, and the in-app Learn page (depth switcher, offline search, contextual `?` help on five panels, inline tap-to-define glossary). The roadmap's P0.1–P0.16 backfill obligation is fully met: all 51 glossary entries and all 9 guides carry three-depth content, `npm run build` produces zero help-content warnings, and — as of this revision — all five contextual help buttons survive real application initialization rather than three of them being silently deleted by runtime DOM writes.

## 4b. R2 review findings — remediation

**R2-F1 (blocking) — the F1 fix from R1 covered only one of four affected build-root fixtures.** R1's fix added `docs` to `verifyDevOnlyDependency()`'s copied directories. The R2 reviewer found three more functions in `scripts/run-browser-harness.js` that independently build a temporary source-tree copy and invoke `scripts/build.js` against it — `createColdReadySuppressedFixture()`, `createHandshakeResponseSuppressedFixture()`, and `createMissingRandomnessFixture()` — all three still only copying `scripts`/`src`/`vendor`, so the harness failed on the first of these it reached (`createColdReadySuppressedFixture()`, inside `verifyColdRealmTimeout()`) with the identical `ENOENT` on `docs/00-overview/glossary.md`, before ever reaching Chromium's or Firefox's `verifyHelpFramework()` pass.

**Fix:** introduced one shared helper, `copyBuildInputsInto(temporaryRoot, { includeGit })`, that copies `scripts`, `src`, `vendor`, and `docs` (and `.git` when asked). All four fixture functions — `verifyDevOnlyDependency()` plus the three the reviewer found — now call this single helper instead of each hand-rolling its own directory list. This is the reviewer's own explicitly requested fix ("preferably through one shared helper so the build-input list cannot drift again"): there is now exactly one place in the file that knows the complete build-input list, so a future new build dependency can't silently miss three of four call sites the way this one did.

**Re-verification status: confirmed live.** The maintainer ran `npm run test:browser` on their own machine with real network access and the harness ran through every fixture, including all three the reviewer found missing `docs/`, to a full pass in both Chromium and Firefox — see §3 for the complete output.

**R2-F2 (blocking) — three of five contextual help buttons were destroyed by runtime title updates.** `src/index.html` nested each contextual `?` button directly inside its panel's `<h2>` title alongside the title's text. Seven call sites across `src/main.js` (`coldRealmStatusTitle.textContent = ...`, `airgapBannerTitle.textContent = ...`, `vaultStatusTitle.textContent = ...`) rewrite that `<h2>`'s entire `.textContent` whenever the panel's state changes (e.g. cold realm reaching "ready", airgap reaching "green", vault's lock state changing) — and a `.textContent` write deletes every child node, including the nested button. The R2 reviewer's real Chromium probe found only 2 of the claimed 5 buttons survived past app initialization.

**Fix:** each of the three affected titles (`cold-realm-status-title`, `airgap-banner-title`, `vault-status-title`) now wraps its dynamic text in a dedicated child `<span id="...-title-text">`, with the help button as a sibling of that span rather than a sibling of a bare text node. The three `main.js` lookups (`coldRealmStatusTitle`, `airgapBannerTitle`, `vaultStatusTitle`) were retargeted to the new `-title-text` span ids, so every existing `.textContent = ...` call site now rewrites only the span's text, leaving the button untouched. No call site needed to change — only the three `getElementById` targets. The other two panels (capability self-check, provenance panel) were already unaffected, since their titles are never rewritten wholesale.

**New regression coverage:** `verifyHelpFramework()` now waits for the app to fully settle (cold realm ready, handshake ready, airgap amber/green, capability ready) before asserting `document.querySelectorAll('button.help-context-button[data-help-topic]').length === 5`, then loops over all five topic→route→anchor mappings (not just the two the prior version of this test happened to exercise) and confirms each button is clickable and lands on its real glossary anchor. This directly targets the exact defect class the reviewer found: a check that only inspected the static pre-render markup, or only exercised two of five buttons, would not have caught this.

**Re-verification status: confirmed live.** Rebuilt and reran the full Node-side test suite (132/132 pass, unchanged) and lint (clean) — no regression from the added `<span>` wrappers. The new Chromium/Firefox five-button assertion itself then ran for real on the maintainer's machine and passed in both engines — see §3.

**R2-F3 (advisory) — the previous packet again reported stale evidence.** The version of this packet reviewed at R2 stated a build hash and Node-test count that were accurate for commit `3c778ef` but not for the actual reviewed tip `5af0991`, because R2-F1's fixture change and R2-F2's markup/script change were not made yet when that packet text was written. **Fix:** this entire packet, starting with §3, was regenerated from a fresh `npm run build` and fresh `npm test` run against the tip that actually includes both R2 fixes.

## 4c. First real execution of `npm run test:browser` — one more bug found and fixed

At commit `b2cef30` (both R2 fixes applied), the maintainer ran the harness for the first time ever against this branch, with real network access and the pinned Node `24.16.0`. It ran through 38 checks — including every fixture R2-F1 touched — before failing inside `verifyHelpFramework()` with a Playwright strict-mode violation: a locator meant to find the "Seed phrase" glossary entry's body matched 9 elements instead of 1. This was a real bug, caught only because a real browser was finally exercising real compiled content — `hasText: 'Seed phrase'` matches any element whose text contains that substring anywhere, and the phrase "seed phrase" is legitimately mentioned in the compiled prose of 8 other glossary entries (entropy, passphrase, private key, BIP-39, BIP-85, SLIP-39, SeedQR, and the "my seed phrase is my password" myth entry) as a natural consequence of cross-referencing related concepts. **Not a product defect** — the glossary content is correct; the test locator was insufficiently specific. Fixed at commit `53dbd14` by selecting the compiler's own deterministic id (`#help-glossary-seed-phrase`, derived from `glossary:seed-phrase` via `helpDomId()`) instead of a substring match. Rerun immediately after: clean pass in both Chromium and Firefox — full output in §3.

## 8. Assumptions made

- **Depth-block granularity is per-passage, not per-file** (ADR-0016). Reversible.
- **Default depth is `plain`.** A judgment call, recorded per AGENTS.md §4.
- **The R2-F2 fix wraps only the three affected titles' dynamic text in a child span, rather than restructuring all five panels identically for consistency.** The other two panels (capability self-check, provenance panel) never rewrite their title's `textContent`, so they were never affected and don't need the same wrapper — adding it anyway would be a cosmetic-only, unnecessary structural change. Reviewable if a maintainer would prefer visual/structural symmetry across all five regardless.
- **`copyBuildInputsInto()`'s directory list (`scripts`, `src`, `vendor`, `docs`, optionally `.git`) is hand-maintained,** same as the single-fixture version it replaces — it's an improvement in that there's now one list instead of four, not a guarantee that the list itself can never go stale again if `scripts/build.js` grows a fifth input directory. Worth a comment-level reminder, which the helper's own doc comment includes.
