## 2. Scope and acceptance

The canary remains explicitly opt-in and off by default. It establishes a
baseline only after the user enables it, re-reads the clipboard once after a
delay without user action, and reports an observed change as affirmative
clipboard volatility. Denied permission, absent APIs, and unexpected read
failures are visibly unavailable; ordinary address comparison remains usable.

The remediation closes both findings from the preserved FAIL:

- The controller generation guard remains authoritative for state, baseline,
  and timers. The warm UI now has a separate operation generation. Disable,
  enable, and retry each invalidate earlier UI operations; a late result or
  rejection is ignored unless it belongs to the current UI operation.
- A synchronous `permissions.query()` exception is contained and represented as
  unknown permission. The controller still attempts the actual clipboard read;
  a successful read may arm the canary. The focused test, implementation, and
  this packet now state that same contract.

The change message continues to name clipboard managers, sync tools, and
remote-desktop clients before malware. The canary is warm-only and never enters
the opaque cold frame.

The fresh independent review also found stale shipped Help copy in
`docs/03-guides/verify-an-address.md`. Commit `a5a9b48` now states that the
control is in the Verify panel, enable/retry takes one baseline and one delayed
re-read without user action, the canary does not monitor copy actions, and
denied or unavailable access is shown as `unavailable` while address comparison
continues to work.

## 7. Finding closure and self-assessment

F1 is closed by the UI-layer generation token in `src/main.js`. The token is
advanced before disable and at the start of enable/retry. Every success and
failure continuation checks that token before touching the checkbox or
unavailable UI. The browser harness commits and drives the delayed
disable/re-enable and retry overlap regressions, and it asserts the final
`data-state="armed"` plus checked toggle.

F2 is closed by aligning the packet with the existing deliberate contract:
`queryPermission()` catches synchronous query failure as `unknown`, then the
actual `readText()` result determines whether the canary arms. The focused test
still proves that a throwing query followed by a successful read arms the
controller.

The fresh Help-content finding is closed by `a5a9b48`. The guide no longer says
the canary is enabled in settings, no longer implies copy-triggered ongoing
monitoring, and no longer describes permission refusal as merely switched off.
It now names the Verify-panel toggle, the one-shot baseline/re-read sequence,
and the explicit `unavailable` state with address comparison preserved.

A fresh reviewer should still scrutinise the UI generation invalidation,
controller generation checks, delayed timer cancellation, retry semantics, the
warm-only placement, and the fact that clipboard content never enters the cold
protocol. No new ADR was needed: the remediation makes no new vault-format,
realm-boundary, or cryptographic-choice decision.
