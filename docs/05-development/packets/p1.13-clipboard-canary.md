## Scope and acceptance

The P1.12 address-verification surface now has an explicit clipboard volatility canary. It is off by default and cannot be enabled by paste, comparison, or any other feature. The user must enable it, which establishes a baseline through `navigator.clipboard.readText()` and schedules one delayed read with no user action.

The canary handles API absence, denied permission, and stable/changed reads visibly. A changed clipboard is affirmative detection and the message names clipboard managers, sync tools, and remote-desktop clients before malware. A retry control allows the user to request permission again without a reload. The ordinary address comparison remains available in every unavailable state.

## Security boundary

The canary is warm-only and never receives secret material. It does not run in the opaque cold frame, does not enable itself from another action, and does not claim that a stable read proves safety. It reports only observed clipboard volatility.

## Assumptions and scrutiny points

- The delayed check is one scheduled read per explicit enable; the user can disable it and re-enable it with a new baseline.
- A permission query that is unavailable is not treated as permission granted; the actual read is attempted and failures are shown as unavailable.
- A changed clipboard is evidence of volatility, not proof of malware. Benign causes are named first in both the module detail and UI.

Scrutinize the enable/disable generation guard, the permission-denied retry path, and the distinction between `changed`, `stable`, and `unavailable`.

## Known limits

The browser harness passed the existing Chromium file://, cold-boundary, Registry, and lock flows but does not yet drive the new P1.13 control through a real browser permission prompt. The fake-permission matrix is covered by unit tests. Mobile-browser and physical clipboard-manager behavior remain untested.
