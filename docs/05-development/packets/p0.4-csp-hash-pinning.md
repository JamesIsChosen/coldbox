# PR packet — P0.4 CSP hash-pinning in the build

## 1. Summary

P0.4 adds deterministic SHA-256 hash-pinning for every inline `<script>` and `<style>` block in the built CSP. It keeps the documented network policy, adds regression coverage for multiple inline blocks and byte tampering, and fixes the forbidden-construct lint so it permits only the required `wasm-unsafe-eval` CSP token. The P0.3a harness now copies the built file, tampers with that copy over `file://` in Chromium and Firefox, and observes the browser refusal of the tampered script.

Branch: `p0.4-csp-hash-pinning`

Base: `main`

Roadmap item: [P0.4 — CSP hash-pinning in the build](../ROADMAP.md)

## 2. Scope

In scope:

- CSP hash placeholders in `src/index.html`
- Build-time SHA-256 hashing of every inline script and style block
- Injection into the matching `script-src` and `style-src` directives
- Fail-closed checks for missing placeholders and missing inline blocks
- Static regression tests for multiple blocks, exact hash routing, and one-byte tampering
- Browser verification through the existing P0.3a harness, including an untampered positive control and a tampered copy of `build/coldbox.html`
- A narrow lint exception for `wasm-unsafe-eval`; `unsafe-eval` remains rejected
- Roadmap, changelog, build documentation, and this packet

Out of scope:

- Realm bootstrap, message schema, vault format, cryptography, or randomness
- Any new `connect-src` host
- Runtime dependencies or external resources
- Real-device Safari, mobile, or Tor Browser verification; those remain part of the device-matrix work at P0.19

## 4. Acceptance criteria

| Criterion | How satisfied | Test/evidence |
|---|---|---|
| Compute SHA-256 of each inline script and style block; inject into the respective `script-src`/`style-src` directives. | `scripts/build.js` extracts all inline blocks, hashes their exact UTF-8 contents with SHA-256, and injects the resulting tokens into the matching placeholders. | `CSP hashes match every inline script and style block`; the multiple-block test checks both directives independently. |
| Built file runs with no CSP violations. | The built file contains the generated hashes and runs from `file://` with no console errors or CSP violations in both supported harness engines. | `expectNoConsoleErrors()` and `expectNoCspViolations()` pass in Chromium and Firefox. |
| Altering one byte of the inline script post-build causes the browser to refuse to execute it. | The harness copies `build/coldbox.html`, flips one byte in its inline script while leaving the CSP meta unchanged, and verifies both `script-src` rejection and the absence of `#app[data-build-state="skeleton"]`. The untampered build must expose that selector as a positive control. | The built-artifact tamper step passes in Chromium and Firefox; the static test also proves the altered block’s hash is absent from `script-src`. |

## 5. Security impact

- CSP: yes. Inline execution is now restricted to hashes for the exact bytes emitted by the build.
- Realm boundary: no change.
- Message schema: no change.
- Vault format, derivation, cryptography, and randomness: no change.
- `connect-src`: no new host; the existing documented allowlist is copied into the source CSP unchanged.
- Secrets: no new message type or runtime path can carry secrets.

If the implementation were wrong, a modified inline script could execute in a build that users believed was hash-pinned, giving a compromised artifact a larger opportunity to alter the application or exfiltrate secrets. Conversely, a wrong hash causes the browser to refuse legitimate code; that is the intended fail-closed behavior. The build does not add `unsafe-inline` or the dangerous `unsafe-eval` token.

## 6. Test evidence

New P0.4 coverage:

- Independent SHA-256 recomputation of each built inline block
- Correct separation of script hashes and style hashes
- Multiple inline script/style blocks
- Final-document unresolved-placeholder rejection before `build/` is created
- One-byte tampering of a temporary copy of `build/coldbox.html`, leaving its CSP meta unchanged
- Browser observation of untampered built-artifact execution and tampered built-artifact rejection
- Existing P0.3a fixture checks remain separate regression coverage for the reusable harness assertions
- Lint acceptance of `wasm-unsafe-eval` and rejection of `unsafe-eval`
- Dependency-free build matching the normal build byte-for-byte

No cryptographic test vectors are applicable: this change uses the CSP-specified SHA-256 digest of build bytes, not a wallet primitive. The test recomputes the digest independently from the build implementation, and Chromium and Firefox independently enforce the emitted policy.

Negative checks passed:

- Deliberate CSP violation was detected by both browsers.
- One-byte tampering of the built artifact was rejected by both browsers, and its skeleton state was absent.
- A stray final-document `__COLDBOX_` placeholder produced a non-zero build exit and no `build/` directory.
- Existing forbidden-construct fixtures remained rejected.
- `unsafe-eval` remained rejected while `wasm-unsafe-eval` was accepted.
- The browser-runner negative paths still exit non-zero when a check fails or binaries are missing.

## 8. Assumptions made

> **Assumed:** The P0.3a Chromium and Firefox harness is the agent-verifiable acceptance mechanism for P0.4, including its built-artifact tamper step.
> **Basis:** P0.3a explicitly lists P0.4’s no-violation and post-build tamper criteria and the roadmap now states that those criteria are checked against `build/coldbox.html`.
> **Not verified on:** Safari, mobile browsers, or Tor Browser.
> **If wrong:** P0.4 would need to remain `[~]` until a human performs the missing browser checks; P0.19 still owns the full real-device matrix.

> **Assumed:** The CSP hash covers the exact UTF-8 text between the tags, including whitespace and line endings.
> **Basis:** CSP hash matching is byte-sensitive, and the build normalizes source line endings before assembly.
> **If wrong:** a browser could reject the legitimate inline block or accept a different byte sequence; the harness would expose the mismatch.

## 9. What to scrutinise

- The exact bytes passed to SHA-256, especially the leading/trailing newline inside each tag.
- The separation of `script-src` and `style-src` hashes and the fail-closed placeholder checks.
- The narrow `wasm-unsafe-eval` lint exception; `unsafe-eval` must remain rejected.
- The one-byte change in the temporary built artifact, the unchanged CSP meta, and the independent browser observation of rejection plus absent skeleton state.
- The fact that real Safari/mobile/Tor verification is not claimed here.

## 10. Self-assessment

- The P0.4 acceptance criteria are verified against the built artifact in the supported headless engines, but no real mobile browser was available.
- The current app is still the P0.1 skeleton; this PR does not claim any later roadmap item.
- The existing branch predated P0.3a, so its history was updated with a non-rewriting merge of current `main` before final verification.
- No new ADR was needed; CSP policy and browser-harness decisions are already recorded in ADR-0001, ADR-0007, and `docs/02-security/csp-policy.md`.
