### F2 — The schema bans secret field *names*, not secret *content*; acceptance criterion 2 is reinterpreted

**Severity:** blocking
**Location:** `src/protocol.js:153-183` (`PUBLIC_FIELD_RULES`), `src/protocol.js:325-336` (`cleanDeriveResult`), `src/protocol.js:185-208` (`cleanPublicRecord`), `test/protocol.test.js:18-36` (`containsSensitiveKey`), `test/protocol.test.js:110-148`
**Observed:** Every cold→warm free-text field is validated only for `typeof === 'string'` and a length bound. Running the **artifact's own** validator:

- `derive.result` with `payload.xpub` set to a real extended **private** key (`xprv9s21ZrQH143K3QTDL4LXw2F7HEK3wJUD2nW2nRk4stbPy6cq3jPPqjiChkVvvNKmPGJxWUtg6LnF5kejMRNNU3TGtRBeJgk33yuGBxrMPHi`, 111 chars, well inside the 512-char limit) is **accepted and returned intact**.
- `derive.result` with a 12-word BIP-39 mnemonic and a WIF private key as `addresses[0]` and `addresses[1]` is **accepted and returned intact**.
- `vault.opened` with a mnemonic in `publicCompartment.notes[].notes`, an xprv in `.label` and a WIF in `.name` is **accepted and returned intact**.
- `vault.opened` with an xprv in `publicCompartment.settings.notes` is **accepted and returned intact**.

The test that is supposed to assert the criterion inspects key names only:

```js
// test/protocol.test.js:32
if (Object.keys(value).some((key) => sensitiveKeys.has(key))) { return true; }
```

It therefore passes trivially against all four cases above. No test in the repository asserts the property the roadmap states.

The packet reinterprets the criterion to match what was built. Roadmap: *"no message type can carry a mnemonic, private key, xprv, passphrase, or secret-compartment plaintext"*. Packet §1: *"No cold-to-warm message shape can carry mnemonic, private key, xprv, passphrase, or secret-compartment plaintext **fields**"*; packet §4: *"Secret field names are never in the public field allowlist"*; CHANGELOG: *"…cannot carry mnemonic, private-key, xprv, passphrase, or secret-compartment plaintext **fields**"*. ### F7 — Validated payloads have no aggregate size bound

**Severity:** advisory (must fix)
**Location:** `src/protocol.js:110-134` (`cleanStringArray`, `cleanBytes`), `:210-223` (`cleanPublicRecordArray`), `:256-262` (`cleanVaultBytes`), `:325-336` (`cleanDeriveResult`)
**Observed:** Per-item bounds exist, but nothing bounds the total. Against the built artifact's validator:

- `vault.opened` with 10 collections × 10,000 records × 24 max-length (512-char) fields was **accepted**; the validated result is large enough that `JSON.stringify` on it throws `RangeError: Invalid string length` (V8's ~512 MiB string cap). The validator copies every one of those strings into a fresh result object before the receiving realm sees it.
- `vault.bytes` accepted a 64 MiB `Uint8Array` and copied it (`new Uint8Array(value)`), with **no cap of any kind** on byte length in either direction (`vault.open` warm→cold has the same property).
- `derive.result` accepted 10,000 × 256-char addresses (2.56 MB of text).

A malfunctioning or hostile cold realm can therefore wedge or OOM the warm shell through a message that the schema declares valid. The project's governing principle is to refuse rather than degrade; here the boundary accepts unbounded work.

**Expected:** An explicit total-size or total-element budget per message, enforced in the validator, with a documented limit and a negative test that a payload over the budget is rejected with a non-zero/`null` result.
**Required action:** Add aggregate bounds (records per compartment, total string bytes, max `bytes` length) and document the chosen numbers alongside the schema per F6.

## 5. Verdict rationale

The engineering here is careful and much of it holds up under attack. The direction tables match `architecture.md` name for name; the validator resisted every prototype-pollution, homoglyph, case-variant, non-plain-type and forged-envelope input I threw at the code extracted from the built artifact; the frozen API cannot be reassigned; the build is byte-identical across three builds, two paths, two locales, two timezones and two Node majors; every deliberate failure fixture exits non-zero with a clear message; and the handshake state machine correctly refuses a ported bootstrap signal, a foreign-source bootstrap signal, a replayed `cold.ready` and a duplicate port transfer.

It fails on three things. **F2** is the serious one: the criterion says no message type can carry a mnemonic, private key, xprv, passphrase or secret-compartment plaintext, and I put a real xprv through `derive.result.xpub` and a real 12-word mnemonic through `derive.result.addresses[]` and `publicCompartment.notes[].notes` — all three came back intact. The test that claims to assert this checks key names only, and the packet, CHANGELOG and packet §4 all quietly insert the word "fields" that the roadmap and `architecture.md:51,102` do not contain. That is reinterpretation, which the protocol lists as an automatic FAIL. **F3** is structural: the one criterion about post-handshake discard behaviour is defended by nothing but a browser harness that cannot run here, and mutation testing proves it — I deleted the discard branch from both realms and `npm test` still reported 22/22. **F1** is process: an author-signed PASS was committed to the path this protocol reserves for the independent reviewer, while the packet says it has not been written yet.

**To make this a PASS:** resolve F2 by either implementing content-level rejection for the five named secret classes with independently-sourced negative vectors, or amending the roadmap and `architecture.md` by ADR so the documented guarantee matches the field-name allowlist that was built — and then making all four documents say the same thing; make `npm run test:browser` runnable without an outbound download and add Node-level coverage that dies when the discard branch or the bootstrap port check is removed (F3); move the self-review to `*.self-review.md` and correct packet §12 (F1); fix the wrong lockdown diagnostic (F4); reconcile "surface a warning" between code and `architecture.md` (F5); give the new allowlists a canonical doc home and reconcile them with `data-model.md` (F6); bound aggregate payload size (F7); and re-run the upstream vendor check and the suite on Node 24.16.0 (F8, F9).

**Nobody merges on a FAIL.** Note additionally that P0.7 is one of the three items `review-protocol.md:160` places off-limits to reviewer merge even on a PASS — the message schema is security core, and a human must look at this diff before it lands.
