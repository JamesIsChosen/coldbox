## 4. Findings

### F1 — `sendBeacon` and `EventSource` are declared supported but will not behave as asserted

**Severity:** blocking
**Location:** `test/browser/harness.js:5-11` (`NETWORK_PRIMITIVES`), `:110-140`

`NETWORK_PRIMITIVES` declares five primitives. The harness's own fixture exercises only three — `fetch`, `XMLHttpRequest`, `WebSocket`. The two untested ones do not throw when blocked by CSP:

- **`navigator.sendBeacon()` returns `false`** when the request is blocked. It does not throw. The `try/catch` never fires, so `result.threw === false` and the assertion **reports a failure against a correctly sealed cold realm.**
- **`new EventSource(url)` does not throw synchronously** when blocked; it dispatches an `error` event asynchronously. Same false-failure outcome.

This matters beyond a cosmetic gap. P0.6 and P0.8 will use this assertion to verify the project's central security claim. A false failure there costs debugging time — and the tempting "fix" is to loosen the assertion, which would turn a false failure into a false pass on the one check that matters most.

**Expected:** each primitive's blocked-behaviour is asserted according to how that primitive actually signals blocking — `sendBeacon` returns `false`, `EventSource` fires `error`, the other three throw.
**Required action:** either implement per-primitive semantics, or remove `sendBeacon` and `EventSource` from `NETWORK_PRIMITIVES` and state the limitation. Whichever, cover all supported primitives in the fixture.

### F2 — The harness's validation of `expectNetworkPrimitiveThrows` proves monkey-patching, not CSP

**Severity:** blocking
**Location:** `test/browser/fixtures/harness-target.html:16-27`

The "cold frame" in the validation fixture carries **no CSP at all**. It is `sandbox="allow-scripts"` with a `srcdoc` that manually overwrites `window.fetch`, `window.XMLHttpRequest`, and `window.WebSocket` with throwing stubs.

So the assertion is validated against **JavaScript shadowing**, not browser-enforced `connect-src 'none'`. A realm with a completely broken CSP but intact monkey-patching passes this test identically.

The two mechanisms produce different failure signatures — a CSP-blocked `fetch` rejects with a `TypeError` from the network layer, while the stub throws a synchronous `Error`. The harness has never been demonstrated to detect the former, which is the one P0.6 depends on.

Per the roadmap, this is *"the project's central security claim, so the harness assertions for it are the most important tests in the repo."* Validating it against a stub undercuts exactly that.

**Expected:** the validation fixture's cold frame carries a real CSP with `connect-src 'none'`, proving the assertion detects browser-enforced blocking.
**Required action:** add `<meta http-equiv="Content-Security-Policy" content="default-src 'none'; connect-src 'none'; script-src 'unsafe-inline'">` to the `srcdoc` and remove the monkey-patching, so the fixture demonstrates the real mechanism. Keeping a second stub-based fixture alongside is fine, but the CSP one must exist.

### F3 — The tamper test has no positive control

**Severity:** advisory
**Location:** `scripts/run-browser-harness.js:64-76`, `:110-124`

`expectScriptRejected` is only ever run against the *tampered* fixture. Nothing asserts that the **untampered** fixture's script actually runs — marker `true`, no violation.

Without that control, the test passes if the pinned hash is wrong for *any* reason, since a permanently-rejected script is rejected in both the tampered and untampered case. It would look like a working tamper detector while detecting nothing.

I verified the pinned hash is correct **today** (§1), so the test is meaningful as it stands. The finding is that nothing preserves that property — a future change to how hashes are computed would silently degrade this into a test that always passes.

**Expected:** a control asserting the untampered fixture executes normally.
**Required action:** load `tamper.html` unmodified, assert `window.__coldboxTamperScriptRan === true` and zero CSP violations, then run the tampered case.

### F4 — "0 bytes" is verified by string match rather than by bytes

**Severity:** advisory
**Location:** `scripts/run-browser-harness.js:147`

```js
assert.doesNotMatch(built, /playwright/i);
```

This proves the literal string `playwright` is absent. The criterion says Playwright *"contributes **0 bytes**"*. Those aren't the same claim — a bundler that inlined Playwright code without the literal name would pass.

The claim is true — I confirmed 0 occurrences and an unchanged build hash — but the test doesn't establish it.

**Expected:** a check that actually measures bytes.
**Required action:** assert the build hash equals a pinned known-good value, or build from a tree with `node_modules` absent and compare digests.

### F5 — `npm run test:browser` does not run from a clean `npm ci`

**Severity:** advisory
**Location:** `scripts/run-browser-harness.js:36-59` (`ensureBrowserBinaries`), acceptance criterion 1

`npm ci` installs the `playwright` package but **not** browser binaries. `ensureBrowserBinaries()` downloads them on first run, requiring network access to Playwright's CDN.

Consequences: the criterion as written is not met; first run is slow and silently network-dependent; and it fails outright on a machine without CDN access — including an airgapped one, which is this project's own recommended posture for real work.

Exit code 1 is correct behaviour, and the error message is clear. The issue is the criterion's claim, not the failure handling.

**Expected:** either the command genuinely works after `npm ci`, or the prerequisite is documented and the criterion amended.
**Required action:** document `npx playwright install chromium firefox` as a prerequisite in `docs/05-development/testing.md` and `build.md`, and amend criterion 1 to say so. A `postinstall` hook is the alternative, but it makes `npm ci` network-dependent, which is worse — prefer documenting.

## 5. Verdict rationale

**FAIL**, for two independent reasons.

**The findings.** F1 and F2 are blocking because they concern the assertions that P0.6 and P0.8 will use to verify the realm boundary — the project's central claim. As written, `expectNetworkPrimitiveThrows` would report false failures for two of its five declared primitives, and its only validation demonstrates JavaScript shadowing rather than CSP enforcement. A harness whose most important assertion has never been shown to detect the real mechanism cannot be relied on to verify that mechanism later. F3–F5 are advisory and, per protocol, must still be fixed.

**The verification gap.** Independently of the findings, I could not execute a single browser assertion. Under this protocol a criterion that cannot be verified cannot be passed.

**To reach PASS:**

1. Fix F1 — per-primitive blocked-behaviour semantics, or drop the two that don't throw and say so.
2. Fix F2 — validate `expectNetworkPrimitiveThrows` against a frame with a real `connect-src 'none'` CSP.
3. Fix F3 — add the untampered positive control.
4. Fix F4 — verify 0 bytes by hash rather than string absence.
5. Fix F5 — document the browser-install prerequisite and amend criterion 1.
6. Re-review **in an environment with working browsers**, so every criterion is actually executed.

---

## 6. What is genuinely good here

Worth recording, since the verdict is FAIL and that shouldn't obscure it.

The reproducible build holds across path, timezone, and locale — I tried to break it and couldn't. The packet's hash claim is accurate. Playwright really is dev-only and really does contribute nothing to the artifact. The tamper fixture's pinned hash is correctly computed, which is the kind of detail that's easy to get wrong and would have made the test meaningless. Failures exit non-zero. The eight promised assertions all exist and are shaped as reusable primitives rather than one-off scripts, which is what makes them useful to later items.

The problems are in **what the tests prove**, not in whether they run.
