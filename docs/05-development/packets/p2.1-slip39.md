# PR packet - P2.1 SLIP-39

**Status:** REMEDIATION APPLIED; SOFTWARE GATES PASS; READY FOR INDEPENDENT RE-REVIEW.

The roadmap marker remains `[~]`. This packet records the author-side evidence
for P2.1; it is not an independent review and does not authorize a merge.

## 1. Summary

P2.1 adds a cold-only SLIP-39 Backup Lab with the standard 1024-word list,
secure randomness, standard 20/33-word share forms, two-level group
thresholds, optional share passphrases, checksum validation, and local
recovery comparison. The UI operates on the entropy represented by the
selected BIP-39 phrase; a BIP-39 passphrase remains separate backup material.
The implementation and its pinned provenance are documented in
[ADR-0036](../adr/0036-slip39-cold-vendoring.md).

## 2. Scope

In scope:

- Cold-realm SLIP-39 arithmetic, word list, generation, decoding,
  validation, recovery, and zeroization of temporary byte arrays.
- Backup Lab controls for phrase-entropy input, group configuration,
  compatibility acknowledgement, share passphrase, masked output, timed
  reveal, and local threshold recovery comparison.
- Official independent interoperability vectors and negative tests.
- Build assembly, browser-harness coverage, user guide, ADR, dependency
  provenance, changelog, roadmap state, and this packet.

Deliberately out of scope:

- codex32, Seed XOR, Shamir39/raw SSS, vault recovery-share wrapping,
  BackupRecords, health dashboards, and printable cards; those are P2.2-P2.8.
- Hardware-wallet transport or automatic restoration into a device.
- Marking the roadmap item `[x]`; only an independent reviewer may do that.
- Physical iOS, Android, Safari, macOS, Linux, and Tor execution testing.

following criteria are copied from those requirements rather than inferred
from the implementation:

| Criterion | How satisfied | Evidence |
|---|---|---|
| SLIP-39 lives in the cold realm, whose `connect-src` remains `'none'` and whose messages carry no secret material. | `slip39.js` is assembled only into the cold iframe; no new warm/cold message is added. | Full tests, source boundary test, and Chromium/Firefox CSP and warm-isolation harness checks. |
| Standard 1024-word SLIP-39 shares support 20-word 128-bit and 33-word 256-bit forms. | The cold API uses the pinned standard word list and the UI accepts phrase entropy of the supported BIP-39 sizes. | Official vectors, focused 8-test suite, and browser 20-word assertion. |
| Two-level group thresholds, optional share passphrase extension, and checksum validation work. | Generation, decode, validation, and recovery implement group/member thresholds, passphrase extension, and checksum/error paths. | Trezor no-sharing, 2-of-3, two-level, and extendable-backup vectors; malformed, mixed, duplicate, and indexed-corruption negatives. |

| Recovery below threshold fails and local recovery comparison does not expose the seed to warm code. | Recovery requires threshold-valid shares; the UI displays only byte length/match status and clears input and recovered buffers. | Two-share/one-share focused vector test, browser recovery/teardown assertions, and source framing test. |
| User-facing documentation distinguishes SLIP-39 words, BIP-39 phrase entropy, and separate BIP-39/share passphrases. | The Backup Lab guide and ADR describe each boundary and the device-compatibility warning. | `npm.cmd run check-docs`; browser help/source checks. |

## 6. Security impact

Yes: this touches cold-only secret handling, randomness, and backup material.
If wrong, an attacker could learn or reconstruct a wallet seed from an
under-threshold share, a generated share could be unrecoverable, or secret
material could leave the cold realm. The implementation therefore refuses
missing randomness, validates all share metadata/checksums, performs recovery
inside the cold realm, and sends no recovery payload to warm code.

There are no new `postMessage` types, no new `connect-src` hosts, no runtime
dependency fetches, and no change to the cold CSP. The warm shell receives no
share, phrase, passphrase, private key, xprv, or recovered entropy. The browser
harness specifically checks that the whole share text is absent from the warm
parent and that lock/teardown clears the cold output and input.

## 7. Test evidence and independent vectors

New tests are in `test/slip39.test.js` and the SLIP-39 section of
`scripts/run-browser-harness.js`.

- The no-sharing, 2-of-3, two-level, and extendable-backup fixtures are copied
  from the independent [Trezor python-shamir-mnemonic vectors](https://github.com/trezor/python-shamir-mnemonic/blob/master/vectors.json).
- Interoperability is governed by the [SatoshiLabs SLIP-0039 specification](https://github.com/satoshilabs/slips/blob/master/slip-0039.md).
- The browser adaptation is based on `ilap/slip39-js` v0.1.9 under its MIT
  licence. That tag resolves to commit
  `414a73b0a28f2fc966514b8f318eb6f68bf9979a`. The upstream
  `src/slip39_helper.js` source is identified by Git blob SHA-1
  `8bcb9568c6c6191e686de2d34864088c644fc7b2` and exact file SHA-256
  `21c15adf2a2f692662b469b609e6a3e42eb828d4fc5c13707f3a4beea027ea48`.
  Coldbox's `src/cold/slip39.js` is an adaptation, not a byte-identical copy;
  the source identities above are the provenance pin. The upstream source
  link and decision are recorded in ADR-0036.

Negative coverage deliberately exercises unavailable randomness, invalid
secret lengths, malformed metadata, mixed identifiers/groups, duplicate
members, insufficient threshold, bad words/checksums, non-printable
passphrases, and stale-output teardown. The browser harness asserts the
indexed error for a corrupted share rather than accepting a generic success.

Not tested: physical hardware restoration, mobile browsers, macOS Safari,
Android Files, Linux Firefox, and Tor Browser. No real seed, private key, or
vault file was used or committed.

## 9. Assumptions made

1. The primary Backup Lab input is BIP-39 phrase entropy, not the 64-byte
   PBKDF2-derived seed. This is based on the standard 20/33-word SLIP-39 forms
   and SPEC §13's phrase-oriented backup workflow. If this assumption is
   wrong, standard-device interoperability and passphrase semantics would be
   wrong; ADR-0036 records the decision and its alternative.
2. A BIP-39 passphrase is not part of the phrase entropy and therefore is not
   included in generated shares. Users must back it up independently.
3. The adapted upstream helper's prototype methods remain scoped to the sealed
   cold realm. Removing that mutation is follow-up hardening, not a new
   capability or warm-realm surface in this item.
4. The existing documented hardware compatibility matrix is the source for
   the Trezor/Ledger/Coldcard warning; P2.1 does not claim hardware transport.

## 10. What to scrutinise

1. Compare the embedded 1024-word list, bit packing, checksum, group
   threshold, passphrase extension, and identifier handling directly with
   SLIP-0039 and the independent vectors.
2. Inspect the assembled cold artifact, not only `src/cold/slip39.js`, for
   any new path from share text or recovered bytes to warm UI/message code.
3. Check that generation validates options before copying secret bytes, fails
   closed without `getRandomValues`, and clears temporary arrays on every
   success and error path.
4. Check the distinction between the BIP-39 passphrase and SLIP-39 share
   passphrase; neither should be silently omitted from the user's backup
   responsibilities.
5. Review the inherited helper prototype mutation and confirm the opaque,
   sealed cold realm bounds its scope without weakening CSP or message rules.

## 11. Self-assessment

The highest-risk code is the adapted SLIP-39 helper and the UI's source-byte
selection. The implementation does not yet provide hardware restoration or a
physical device matrix, and the low-level API permits 16-64-byte secrets while
the primary UI intentionally uses standard phrase-entropy lengths. The
upstream helper's local prototype mutation is a documented limitation and
should be reconsidered during independent review. P2.2-P2.8 must not assume
that P2.1's phrase-entropy choice automatically defines vault DEK recovery
shares; those items need their own explicit format decisions and vectors.
