# PR packet: P0.11 - Vault format v1

## 1. Summary

P0.11 adds the format-v1 serializer and parser inside the sealed cold realm. It writes the authenticated 65-byte header, a length-delimited multi-record wrapped-DEK block, separate AES-GCM public and secret compartments, HKDF-SHA-512 domain-separated subkeys, and random 64 KiB padding. The warm shell receives no vault API or secret-subkey derivation function.

This branch is `p0.11-vault-format`, based on the unmerged dependency branch `p0.10-crypto-layer` at `8811754`; its PR base must therefore be `p0.10-crypto-layer`.

## 2. Scope

### In scope

- Format-v1 header encoding and strict parsing for magic, version, KDF, cipher, salt, and compartment lengths
- AAD equal to header bytes 0-64 for both wrapped-DEK and compartment authentication
- Length-delimited wrapped-DEK record parsing, with passphrase records implemented and future method records rejected safely
- Random 256-bit DEK, passphrase KEK derivation through the P0.10 layer, AES-256-GCM DEK wrapping, and 12-byte nonces
- HKDF-SHA-512 `cbx/public/v1` and `cbx/secret/v1` subkeys
- JSON length prefix plus random padding to 64 KiB boundaries for both compartments
- Public-only vaults with a zero-length secret ciphertext and no secret-subkey derivation
- Explicit online/offline opening modes: online opening never derives `cbx/secret/v1`; offline opening is fail-closed unless `navigator.onLine === false`
- Cold-only session serialization for later save/load work: offline saves re-encrypt both compartments with fresh nonces, while online saves copy the unchanged secret ciphertext/nonce opaquely and re-encrypt only public data
- Generic authentication failure for wrong passphrases, malformed files, header tampering, and corrupted ciphertext
- Cold-only build wiring, protocol-boundary tests, browser assertions, security documentation, roadmap, changelog, and packet evidence

### Deliberately out of scope

- Keyfile and recovery-share record creation (the parser preserves the record-list structure; later items own additional methods)
- KDF benchmark UI and profile selection UX (P0.12)
- User-facing lock/unlock commands, save/load paths, verify-after-save, generational filenames, or rollback detection (P0.13-P0.14); the internal cold session serializer exists only to enforce the v1 nonce rule for that later workflow
- Warm-shell vault operations or any new warm-to-cold message carrying vault bytes or passphrases
- Physical device claims; P0.19 owns the manual matrix

## 5. Security impact

- Realm boundary: Yes. The serializer/parser is embedded only in the cold document. The warm shell does not load `src/cold/vault.js`, expose `__coldboxVault`, or receive a secret-subkey function.
- AAD: Yes. Header bytes 0-64 are passed as AAD to DEK wrapping and both compartment encrypt/decrypt operations. KDF parameters, cipher id, salt, and lengths therefore cannot be changed without authentication failure.
- Derivation: Yes. A random DEK is wrapped by a passphrase-derived KEK. HKDF-SHA-512 uses distinct `cbx/public/v1` and `cbx/secret/v1` info strings; the secret subkey is created only inside the cold module and only for an explicitly offline open/save path. Online saves copy the already-encrypted secret compartment without deriving its subkey.
- Compartment separation: Yes. Public and secret JSON are padded and encrypted independently with fresh nonces. A public-only vault has no secret ciphertext and does not derive the secret subkey.
- Error handling: Yes. All parse, KDF, unwrap, AEAD, padding, and JSON failures from `open` collapse to `Vault authentication failed.`; the caller cannot distinguish wrong passphrase from damaged bytes through the error.
- Randomness: Yes. DEK, salt, nonces, and padding use the P0.10 `crypto.getRandomValues`-only path. No fallback was introduced.
- Network/message surface: No new network host, message type, or secret-bearing field. The vault mode gate treats an unknown network state as online for default opens; only an explicit offline state may use the secret key.
- If this implementation is wrong, an attacker could exploit unauthenticated metadata, confuse compartment boundaries, or obtain a derived secret subkey from the online shell. The header-as-AAD checks, distinct HKDF labels, cold-only build wiring, and generic failure contract are the controls tested here; full unlock/save workflow review remains later work.

## 6. Test evidence

### New and changed tests

- `test/vault.test.js` uses real P0.10 crypto for a fast-profile public+secret round-trip and a public-only round-trip.
- The online-boundary regression sets `navigator.onLine` true, proves `open` returns no secret data, records only `cbx/public/v1`, and rejects an explicit offline open.
- The session regression proves repeated offline saves rotate both compartment nonces and that an online save re-encrypts public bytes while preserving the secret nonce/ciphertext byte-for-byte.
- The same test mutates each of the 65 header bytes and expects the exact generic authentication failure. It also compares wrong-passphrase and corrupted-ciphertext errors.
- The test statically checks that warm source and warm template contain no vault-layer or secret-HKDF path, and that the cold API does not export `deriveSecretSubkey`.
- `scripts/run-browser-harness.js` verifies `window.__coldboxVault` is undefined in the warm document and is format version 1 inside the cold frame in both engines.
- The P0.10 `deriveKey` API now accepts the explicit `fallback` profile so a fallback-encoded header is not reinterpreted as standard Argon2id on a machine where Argon2 is available.

### Independent sources

- Format field layout and padding rules: repository specification [vault-format.md](../../01-spec/vault-format.md).
- AES-GCM KAT inherited from [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final).
- Argon2id KAT and KDF parameters inherited from [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106#section-5.3).
- HKDF-SHA-512 is the pinned `@noble/hashes` implementation already verified in P0.10; domain-separation strings are fixed by the repository specification.

### Negative tests

- All 65 header-byte mutations fail authentication.
- Wrong passphrase and one-byte ciphertext corruption both return exactly `Vault authentication failed.`.
- Unsupported/malformed record or header shapes fail closed through the same parser boundary.
- Existing CSP, runtime network, protocol, tamper, missing-randomness, and browser lockout fixtures remain green.

### Not tested

No physical iOS Safari, Android Chrome from Files, macOS Safari, macOS Chrome, Linux Firefox, or Tor Browser was available. P0.12 owns production-profile timing and P0.13-P0.14 own real save/load and verify-after-save flows. Keyfile/recovery-share records are structurally reserved but not implemented.

## 8. Assumptions made

> **Assumed:** A zero-length secret compartment still carries its 12-byte nonce because the v1 layout lists a nonce separately from the ciphertext length.
> **Basis:** The specification says `L2` may be zero while showing the secret nonce as a separate field; retaining the field keeps offsets unambiguous and avoids a format branch.
> **Not verified on:** An independent v1 reader, because no other implementation exists in this repository yet.
> **If wrong:** the format needs an explicit interoperability clarification before save/load is exposed.

> **Assumed:** P0.11 can reserve future record methods by parsing the full record list and ignoring unsupported method ids until a later item implements their KDFs.
> **Basis:** The v1 wrapped-DEK block is length-delimited and method-specific; unsupported records must not be guessed or treated as passphrase records.
> **Not verified on:** Keyfile/recovery-share records, which are P0.15/Phase 2 work.
> **If wrong:** the parser must reject the entire file rather than attempt an unsafe migration.

## 9. What to scrutinise

- Recheck every header offset and the fact that the exact 65-byte header, not a reconstructed object, is used as AAD.
- Recheck wrapped-record length accounting: each record length covers method data, nonce, and 48-byte wrapped DEK; the block itself is bounded and can contain multiple records.
- Verify that zero-secret vaults do not call `hkdf(..., "cbx/secret/v1")`, and that the warm shell cannot obtain the cold API through a message or global.
- Review the generic error boundary so no underlying AEAD, KDF, JSON, or parser message leaks through `open`.
- Confirm that later save/load work does not move serializer calls into `src/main.js` or add passphrases/secret bytes to the protocol schema.

## 10. Self-assessment

- This is a format library, not a user-facing vault workflow. No UI can yet create, save, load, lock, or verify a vault.
- Only passphrase records are serialized; the parser is structurally multi-record but unsupported methods are not implemented.
- The test uses the fast Argon2 profile to keep the real round-trip lightweight; standard/paranoid allocation and timing remain P0.12/device-matrix concerns.
- The zero-secret nonce interpretation is explicitly disclosed as an interoperability assumption.
- The warm shell can hold the serialized cold document string, but it has no callable vault object or secret-subkey path; the browser assertion checks the actual runtime global boundary. The session serializer is callable only inside the cold layer and is closed/zeroed with the session.
