# PR packet: P1.3 — Seed Forge

## 1. Summary

This branch implements [P1.3](../ROADMAP.md#phase-1--core-wallet): cold-only
BIP-39 generation and validation, optional passphrase confirmation, and the
BIP-32 master fingerprint. It consumes the existing Entropy Lab `mix()` byte
contract, bundles the already-pinned BIP-39/BIP-32 primitives and all ten
official wordlists, and adds no warm-cold message type. The roadmap remains
`[~]`; the reviewer must independently verify this item and flip it to `[x]`
on PASS.

## 2. Scope

In scope:

- `src/cold/seed-forge.js`: BIP-39 language selection, NFKD normalization,
  per-word/checksum validation, PBKDF2-HMAC-SHA512 seed derivation, and the
  BIP-32 master fingerprint.
- `src/cold/main.js`, `src/cold/index.html`, and `src/cold/styles.css`: cold UI
  wiring, entropy-session generation, marginal-health acknowledgement,
  duplicate passphrase confirmation, masked phrase display, timed reveal, and
  teardown clearing.
- `scripts/crypto-bundle.js`: the pinned `@scure/bip39`, `@scure/bip32`,
  `@scure/base`, secp256k1, RIPEMD-160, and ten wordlist module graphs.
- `test/seed-forge.test.js` and `scripts/run-browser-harness.js`: independent
  vector, negative, language, boundary, Chromium, and Firefox coverage.
- Current specifications, guide/reference copy, ADR-0028, the ADR index,
  CHANGELOG, and ROADMAP status.

Deliberately out of scope:

- BIP-85 child phrases, WIF, address derivation, derivation paths, password
  derivation, QR/SeedQR, clipboard, and persistent storage. The UI names these
  as later work rather than implying they exist.
- Language auto-detection. The user selects one explicit wordlist so a valid
  phrase is never silently interpreted under a different language.
- P0.19 physical device-matrix work. The maintainer explicitly authorized P1.3
  while P0.19 remains deferred and `[~] human-required`; this branch does not
  alter or mark P0.19 complete.

## 4. Acceptance criteria

The roadmap entry is a one-line item with no expanded `Accept:` block. The
criterion copied verbatim is:

> P1.3 Seed Forge: BIP-39 generate, validate, passphrase, fingerprint

The following table maps that criterion to the normative behavior in
[SPEC.md §11.1](../../01-spec/SPEC.md), the existing Entropy Lab contract in
[ADR-0023](../adr/0023-entropy-lab-seed-forge-boundary.md), and ADR-0028.

| Criterion | How satisfied | Test/evidence |
|---|---|---|
| BIP-39 generate | Five valid entropy sizes produce 12/15/18/21/24 words in an explicitly selected one of ten vendored official wordlists. Generation draws through cold `cryptoLayer.randomBytes()`, adds bytes to the Entropy Lab session, then calls `mix()`; it never calls a library-owned random helper. | `test/seed-forge.test.js` round-trips all ten lists; browser harness checks ten language options, CSPRNG generation, and the 256-bit 24-word target. Entropy Lab mix/burn tests remain green. |
| BIP-39 validate | NFKD-normalized input is split into words, each word receives a known/unknown/valid state, valid word counts and the checksum are required, and Japanese PBKDF2 input preserves the canonical ideographic separator. | Official English vector, all-ten-list round trips, Japanese separator assertion, checksum/unknown-word/word-count negatives, and browser per-word status assertions. |
| Passphrase | The optional passphrase must match its duplicate before seed or fingerprint calculation. Both mnemonic and passphrase are NFKD-normalized for the 2,048-round PBKDF2-HMAC-SHA512 derivation. | Official Trezor `TREZOR` vector; NFKD-equivalent passphrase negative/positive coverage; browser mismatch gate and matching validation. |
| Fingerprint | The cold realm builds the BIP-32 master key and displays the first four bytes of HASH160 of the compressed master public key as eight lowercase hex characters. | Independent Node/OpenSSL HMAC-SHA512, secp256k1, SHA-256, and RIPEMD-160 reference; expected `b4e3f5ed` matches the product and browser output. |

## 5. Security impact

- **Realm boundary: yes.** All phrase, passphrase, mixed entropy, PBKDF2 seed,
  and HDKey work remains in the existing opaque cold iframe. The warm page gets
  only descriptive copy; `src/protocol.js` and the message whitelist are
  unchanged. No new message type or payload was added.
- **Randomness: yes.** The generation path uses the existing cold
  `crypto.getRandomValues` wrapper and Entropy Lab `mix()`/burn accounting. A
  missing capability, short draw, invalid target, invalid wordlist, or failed
  mix throws; no shorter or silently substituted phrase is produced.
- **Cryptography: yes.** BIP-39 PBKDF2 and BIP-32 fingerprint code run in the
  cold realm using the pinned vendored module graph. The independent vector and
  fingerprint reference are in §6 below.
- **CSP/network: no policy expansion.** No `connect-src` host, runtime fetch,
  storage API, or dependency is introduced. The cold CSP remains
  `connect-src 'none'`, and the browser harness continues to observe network
  primitives blocked in both engines.
- **If wrong:** a defect could generate a predictable or misinterpreted wallet,
  show a wrong fingerprint, or expose the phrase/passphrase to the warm shell.
  The relevant protections are the explicit entropy-session path, independent
  vectors, negative tests, opaque-frame browser assertions, and the absence of
  a secret-bearing message route. No implementation can protect against a
  deliberately tampered build that defeats the pinned source; the existing
  provenance/CSP tamper checks remain part of the full harness.

## 6. Test evidence

### Independent vectors and references

- The English zero-entropy vector (`00000000…0000` → eleven `abandon` words
  plus `about`) and the `TREZOR` 512-bit seed are taken from the official
  [BIP-39 specification](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki)
  and the [Trezor/python-mnemonic official test vectors](https://raw.githubusercontent.com/trezor/python-mnemonic/master/vectors.json).
- The master fingerprint test does not call the production BIP-32 code for its
  expected value. It independently performs Bitcoin-seed HMAC-SHA512, Node's
  OpenSSL-backed secp256k1 compressed public key operation, SHA-256, and
  RIPEMD-160, then asserts the literal expected fingerprint `b4e3f5ed`.
- The ten wordlist loop checks the vendored public lists independently of the
  browser UI by encoding, validating, decoding, and comparing a fixed 128-bit
  byte vector for each list.

### Deliberate failures

- Unknown word → `unknown-word`, inline unknown state, no fingerprint.
- Known words with a changed checksum word → `checksum`, inline checksum state,
  no fingerprint.
- Two-word phrase → `word-count` and no decode.
- 17-byte entropy → rejected; unsupported language → rejected.
- NFKD-equivalent passphrases produce the same expected seed, while a mismatch
  in the two UI passphrase fields blocks generation/fingerprint calculation.
- The browser harness also exercises cold readiness, CSP, tampering,
  `getRandomValues` absence, and opaque parent isolation while the new Seed Forge
  flow runs.

### Limitations of this evidence

The public vector fixtures are intentionally non-secret and must not be treated
as user wallet material. No fuzzing, side-channel analysis, or independent
implementation of the complete BIP-39 wordlist/checksum algorithm was attempted;
the implementation relies on the pinned `@scure` code, official vectors, and the
independent fingerprint path. Physical/mobile execution remains untested as
shown in §7.

## 8. Assumptions made

- **Maintainer sequencing:** the explicit user instruction to defer P0.19 and
  proceed with P1.3 authorizes this branch; the roadmap records that decision,
  leaves P0.19 `[~] human-required`, and leaves P1.3 `[~]` for independent
  review.
- **Ten wordlists:** the pinned `@scure/bip39@2.2.0` package exposes ten
  official wordlists, including Japanese and both Chinese variants. Existing
  canonical documentation that said nine was corrected; historical packets are
  retained as audit records.
- **Entropy replenishment:** if the selected Entropy Lab session does not yet
  contain enough CSPRNG bytes, Seed Forge draws exactly the missing amount via
  the existing cold random wrapper and adds it to that same session. `mix()`
  remains the only conversion boundary and burns what it consumes.
- **Health acknowledgement:** P1.2 remains advisory. Seed Forge requires an
  explicit checkbox only when the selected physical/manual source is marked
  marginal; insufficient manual evidence does not create a shorter output or
  bypass the selected fresh CSPRNG target.
- **Japanese handling:** the `@scure` Japanese generator emits U+3000 while its
  decoder accepts the same indexed words with ordinary spaces. The wrapper uses
  ordinary spaces only for decoding/checksum lookup and retains U+3000 for the
  PBKDF2 mnemonic text.
- **Fingerprint timing:** the fingerprint is calculated in the cold realm after
  duplicate passphrase confirmation and is displayed as a public identifier;
  it is not a proof that a paper backup was written correctly.

## 9. What to scrutinise

- The crypto-bundle resolver and module graph: every `@scure`/`@noble` import
  must remain vendored, pinned, hash-verified, and inline in the cold document.
- `ensureSeedForgeCsprng()` plus `entropyLab.mix()`: check that a generation
  cannot reuse consumed CSPRNG bytes, silently shorten the selected entropy, or
  bypass the marginal acknowledgement.
- Japanese NFKD/separator handling and the distinction between the ordinary
  space used for decoder lookup and U+3000 used for seed derivation.
- Secret lifetime and UI teardown: generated strings, phrase inputs,
  passphrase inputs, fingerprint output, masking, timed remasking, and
  `clearVaultSession()` should not leave a stale value visible or available in
  the warm shell.
- The warm `Seed Forge` route is intentionally content-only and contains no
  secret fields; the opaque-frame browser assertion should remain in place.

## 10. Self-assessment

- **What might be wrong:** the product wrapper deliberately reimplements only
  the BIP-39 PBKDF2 call shape around the pinned noble primitive instead of
  calling a library convenience function. The official vector and NFKD tests
  cover the result, but this remains the most subtle code path to review.
- **What was not done:** no physical iOS/Android/macOS/Linux/Tor run, no native
  desktop browser run outside Playwright, no fuzzing, and no independent audit
  of the vendored cryptographic implementations.
- **Known limitations:** language selection is explicit rather than inferred;
  no first address or child phrase is derived; `@scure`'s fixed BIP-39 2,048
  PBKDF2 rounds are not user-configurable.
- **Follow-up:** P1.4 owns the derivation engine and later items own addresses,
  BIP-85, QR, and registry workflows. P0.19 still needs the human device
  matrix before its own marker can move to `[x]`.
