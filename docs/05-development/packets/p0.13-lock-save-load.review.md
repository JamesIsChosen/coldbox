### R2-F1 — Runtime airgap violation reports the vault locked without clearing or zeroizing the active cold session

**Severity:** blocking security finding
**Location:** `src/cold/main.js:138-160,498-521`; `src/main.js:1163-1181`; `scripts/run-browser-harness.js:438-489`; `docs/05-development/packets/p0.13-lock-save-load.self-review.md:114-123`.

**Observed:** `clearVaultSession()` is the cold-realm routine that calls `currentVaultSession.close()`, nulls the session, zeroes `currentVaultBytes`, clears pending bytes as requested, resets the idle timer/passphrase field, and marks session evidence locked. Idle expiry, explicit lock, mode transition, and panic use this cleanup path.

`recordRuntimeViolation()`, however, does not call `clearVaultSession()` or `lockVaultSession()`. It only sets the airgap failure state and emits a typed status with `locked: true` / `warnings: ['airgap-violation']`. The warm shell interprets that status as "The cold realm cleared its active vault session" and enters terminal lockdown while deliberately keeping the cold frame. The cold `currentVaultSession`, retained public key/plaintext and (offline) secret key/plaintext, and `currentVaultBytes` therefore remain resident until a later cleanup path such as the idle timer runs.

The browser harness makes this reproducible as a coverage gap: it unlocks the manually reloaded vault at lines 438-441 and, without locking it, deliberately invokes all five cold runtime network primitives at lines 480-489. It verifies that operations become refused, but never asserts `data-cold-session-state="locked"`, `data-cold-working-bytes="cleared"`, or equivalent zeroization after the runtime violation. The focused session test verifies only that a *subsequent `session.save()`* notices a synthetic health drift and closes itself; that is not immediate closure when the health failure occurs.

The exact-tip self-review also states that "health or mode drift closes/zeroes the session". That statement is not true for the runtime airgap-health transition exercised by the browser harness.

**Expected:** A terminal runtime airgap violation while a vault is unlocked must immediately close and zeroize the active session before advertising `locked: true` or telling the warm shell that the session was cleared.

**Required action:** Make the runtime-violation path synchronously invoke the existing session cleanup/zeroization path before posting locked status. Add a Chromium/Firefox regression assertion that starts from an unlocked vault, triggers the runtime airgap violation, and verifies the cold session is locked, working bytes/passphrase are cleared, and no active session remains. Keep the warm status text truthful to the actual cleanup ordering.
