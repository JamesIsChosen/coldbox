## 4. Findings

### F1 — The required expected hash is not visible in the Provenance panel

**Severity:** blocking
**Location:** `src/index.html` Provenance / “Verify this file” section; `src/main.js` `renderProvenancePanel()` / `currentExpectedHash()`

**Observed:** The reviewed build contains the expected digest only in the hidden `<meta name="coldbox-expected-hash">` tag. The digest occurs exactly once in the built HTML, at that meta tag. The visible Provenance UI renders libraries, build date, warm CSP, cold CSP, circularity guidance, the drop zone, and the result area, but no expected-hash value.

**Expected:** P0.16 names “expected hash” as a deliverable, and SPEC §6.4 is explicit that Verify This File must be “showing the expected hash for independent comparison.”

**Required action:** Render the compiled expected hash visibly in the Provenance / Verify This File UI, label it so users do not confuse it with the final-file `.sha256`, and add focused + browser-harness assertions that the visible value equals the build's expected-hash meta value.

### F2 — A byte alteration inside the embedded expected-hash field can false-PASS as “Match”

**Severity:** blocking
**Location:** `src/main.js` `blankExpectedHashMeta()`, `computeSelfHash()`, and `handleProvenanceDropFile()`

**Observed:** `computeSelfHash()` first replaces the dropped file's entire 64-character expected-hash field with zeros, then hashes the blanked document. `handleProvenanceDropFile()` compares only that recomputed value to the running copy's expected value. It never checks whether the dropped file's own declared expected-hash value equals the running copy's expected value.

Independent mutation proved the consequence: changing one hex character *inside the hash field itself* altered the file bytes, but the blank-then-hash result stayed equal to the original running expected hash, so the current comparison would report `Match`.

**Expected:** The UI says the tool hashes the bytes supplied and catches accidental corruption such as a bad download or damaged media. An accidental bit flip in the hash field is still corruption and must not be labeled a match.

**Required action:** Make the comparison fail closed when the dropped file's declared expected hash differs from the running copy's expected hash, in addition to validating the recomputed blank-then-hash relationship (or use an equivalent design that detects corruption anywhere in the file). Add a negative unit test and browser-harness case that changes one byte inside the embedded expected-hash field and requires a mismatch.
