# P0.21 — Cold-realm injected-provider neutering

Branch: `p0.21-injected-provider-neutering`

## 1. Summary

Extends [P0.8](../ROADMAP.md)'s cold-realm runtime neutering to cover the two observable surfaces of an injected wallet provider — `window.ethereum` and the `eip6963:announceProvider` event — on the same non-configurable, non-writable basis as the five network primitives. An observed provider now enters full lockdown as an **isolation failure**, distinct in wording from a network-policy violation, closing the hole [ADR-0020](../adr/0020-injected-providers-rejected-and-neutered.md) identified.

## 2. Scope

**In:** `neuterProviders()` in `src/airgap.js`; wiring into cold bootstrap, vault-health gating, the handshake capability, and a new warm-side warning code (`src/cold/main.js`, `src/cold/vault.js`, `src/main.js`, `src/protocol.js`); unit tests (`test/airgap.test.js`, `test/vault.test.js`); a new browser-harness scenario (`scripts/run-browser-harness.js`); doc updates to `threat-model.md` (removing now-stale "until P0.21" phrasing) and `ROADMAP.md`/`CHANGELOG.md`.

**Not in scope:** the wallet-bridge feature itself — rejected by [ADR-0020](../adr/0020-injected-providers-rejected-and-neutered.md), decision 1. No UI for provider selection, watch-only import, or chain detection is added or intended. P0.19 (device matrix) is untouched — it's `👤 human-required` and out of order-of-pickup for this branch.

## 5. Security impact

- **Touches the realm boundary?** No new message *types* carrying secrets. It extends the existing `ready` capability message with a boolean (`providerNeutering`) and adds a warning code string (`provider-isolation-violation`) to the existing warning-code whitelist in `src/protocol.js` — same shape as `runtimeNeutering`/`airgap-violation`, which the P0.8 review already accepted as secret-free.
- **What does an attacker gain if this implementation is wrong?** If `neuterProviders()` silently fails to install (e.g., a future browser makes `window.ethereum` non-redefinable-but-already-present, or `Object.defineProperty` throws for a reason the code doesn't distinguish from success), the code fails *closed*: `providerNeuteringInstalled` only becomes `true` if both the accessor and the listener install without throwing, and a `false` value blocks `data-cold-state` from ever reaching `"ready"`. I could not find a path where a failed install is misreported as a success — but I did not fuzz this, and browser engine differences here are exactly the kind of thing only a real Chromium/Firefox run would surface. If wrong, the practical risk is: an extension's injected provider goes undetected, which by itself does not leak a secret (this guard is defence-in-depth against a hypothetical `provider.request()` egress channel; the CSP realm boundary and vault crypto are unaffected either way) — it degrades one specific defence layer, not the vault's confidentiality.
- **Any new `connect-src` host?** No.
- **Any new message type, and proof it cannot carry secret material?** No new message *type* — reuses `status`/`ready` with a new boolean field and a new entry in the existing `WARNING_CODES`/capability-name allowlists in `src/protocol.js`, both of which are fixed enumerations, not free-form strings, so neither can carry a mnemonic or key by construction.

## 6. Test evidence

- **New unit tests (6, `test/airgap.test.js`):** setter-attempt reporting on both `window.ethereum` assignment and the underlying property owner; a negative test that `Object.defineProperty`/`delete` cannot remove or redefine the accessor; `eip6963:announceProvider` detection via a dispatched `CustomEvent`; an unrelated-event non-trigger (proves the listener isn't over-broad); two install-failure paths (property already non-configurable and belonging to someone else; `addEventListener` unavailable). `test/vault.test.js` updated its default/failure DOM fixtures to include `data-provider-neutering`, since `vaultHealthReady()` now checks it.
- **Vector sources:** N/A — this item has no cryptographic component. The negative tests are structural (JS property-descriptor semantics), not vector-based.
- **Negative tests:** (1) redefine/delete attempt on the installed accessor — survives, confirmed by unit test. (2) installation-failure simulation (pre-existing non-configurable property owned by a different object) — correctly reports `installed: false`. (3) In the browser-harness code (unexecuted, see below): an unrelated `CustomEvent` dispatch is asserted *not* to trip the guard, to catch an over-broad listener.
- **What I could not test, and why:** `npm run test:browser` end-to-end. This sandbox has no outbound network access to `cdn.playwright.dev` (`npx playwright install chromium firefox` fails with `403 Connection blocked by network allowlist`), the same limitation the P0.18 and P0.20 packets disclosed. `verifyProviderNeutering()` was written against the same DOM contract every other `verify*` function in that file uses (element IDs and `data-*` attributes I confirmed exist in `src/cold/main.js`/`src/main.js` by reading them directly, not inferred), and passes `node --check` and the project's own JS lint, but **it has not actually executed against a real Chromium or Firefox**. This is the single largest gap in this packet — see §9.

## 8. Assumptions made

- **Alarm-text phrasing.** The roadmap requires the text to "distinguish an isolation failure from a policy failure" but doesn't specify exact wording. I chose to open with "Cold realm isolation failure" and explicitly state "This is not a network-policy violation," mirroring ADR-0020's own vocabulary ("isolation failure" vs. the CSP-canary failure). Basis: ADR-0020's Rationale section uses this exact pair of terms. If this is wrong, the fix is a copy change only — no structural risk.
- **`window.ethereum` accessor semantics.** I used a getter that always returns `undefined` and a setter that reports the attempt, rather than a setter that throws. This matches `defineOwnProviderAccessor`'s existing sibling pattern is new to this PR (P0.8's network primitives use function-replacement + throw, not accessor properties, since they're methods, not a data property an extension assigns to). I judged a non-throwing setter correct here because an extension assigning to `window.ethereum` should not itself crash the extension or produce a JS error visible outside the frame — it should be silently absorbed while being *reported* internally. If the spec intended the assignment itself to throw, this would need to change; nothing else depends on the choice.
- **Bundle size delta measured against a `main` build in a temporary `git worktree`** (`origin/main` at `25773ad`), not against a cached number, to avoid the exact measurement-method pitfall P0.20's packet found and corrected (`git archive` vs. `git worktree`, a 17-byte artifact). Both builds used this session's build toolchain (Node v22.22.3, not the repository-pinned v24.16.0 — same network restriction blocks fetching v24 in this sandbox, disclosed the same way P0.20's remediation packet disclosed it).

## 9. What to scrutinise

- **The browser harness code was never run.** This is the top item. `verifyProviderNeutering()` in `scripts/run-browser-harness.js` is my best-effort translation of the roadmap's acceptance criteria into Playwright calls, checked only by static reading against the DOM/attribute contract in `src/cold/main.js` and `src/main.js`, and by `node --check`/lint. A reviewer with real browser access should run `npm run test:browser` on this branch before trusting the 🌐 criterion is actually met — I am not confident every selector and wait condition is correct on a first real run (in particular: whether `#cold-realm-details` textContent updates synchronously with the `data-airgap-state="red"` attribute wait I check it against, and whether Firefox's `CustomEvent` dispatch inside a cross-origin-esque `srcdoc` frame behaves identically to Chromium's).
- **The accessor-vs-throw design choice** in §8 — I'm reasonably confident but it's a judgment call the spec doesn't pin down.
- **Whether `findPropertyOwner` (pre-existing helper, reused here) correctly identifies `window` itself as the owner when `window.ethereum` doesn't yet exist**, versus walking up to some other prototype. I traced this by reading the existing function but did not add a dedicated unit test isolating that helper's behavior specifically for the not-yet-defined case — the existing "blocks... on the target and its prototype owner" test covers it indirectly (it asserts both installations succeed), but doesn't assert *which* object ended up being which.
- **Session history irregularity:** this implementation was originally written directly on `main` in an earlier part of this session (a process error — should have branched first) before being moved onto `p0.21-injected-provider-neutering`. `git log` on this branch should be checked to confirm no stray commits landed on `main` — as far as I can tell none did (the work was uncommitted when moved), but worth the reviewer's own check of `git log origin/main` against this branch's merge-base.

## 10. Self-assessment

- **What might be wrong:** the browser-harness scenario, per §9 — untested code is unproven code, full stop.
- **What I didn't do that arguably should have been done:** I did not attempt to find or install a system Chromium/Firefox outside of Playwright's own binary manager to work around the network block (e.g., an OS-packaged browser Playwright could attach to via `executablePath`). I judged that out of scope for this session given time and the risk of introducing an unpinned, unverified browser binary into a security-sensitive verification path — but a reviewer with a real Playwright setup should be able to close this gap in minutes.
- **Known limitations shipping with this change:** the 🌐 acceptance criterion is unmet pending a real browser run, disclosed above rather than claimed.
- **Follow-up work:** none beyond what's already tracked — P0.19's device matrix will exercise this surface as part of its general pass once P0.21 merges.
