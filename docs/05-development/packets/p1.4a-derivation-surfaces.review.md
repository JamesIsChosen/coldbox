## 4. Findings

### F1 — Blocking — a verbatim acceptance criterion is explicitly not met

**Location:** `docs/05-development/ROADMAP.md` P1.4a acceptance; `docs/05-development/packets/p1.4a-derivation-surfaces.md` §4.1; `docs/01-spec/ui-parity.md`.

**Observed:** P1.4a requires desktop and mobile presentation to match the UI.10a approved reference under the parity contract. The packet explicitly and correctly says this is **NOT MET** because convergence/certification infrastructure is gated behind the still-incomplete workstation/parity sequence.

**Expected:** A PASS requires every verbatim roadmap acceptance criterion to be independently demonstrated. A temporary program-level pause in pixel convergence can explain why evidence is unavailable; it does not reinterpret the P1.4a criterion into “uses similar components” or waive it.

**Required action:** Finish the prerequisite workstation/parity path needed to make this surface certifiable, add these destinations to the required parity state matrix, produce the required desktop/mobile evidence under the contract, and then re-review the new exact head. If maintainers intend to defer/remove the criterion, that must be an explicit roadmap/spec decision made before review rather than a reviewer-side reinterpretation.

### F2 — High — the custom-chain vector gate accepts a prose claim instead of independent vectors

**Location:** `src/cold/main.js` (`chainHasIndependentVectors`, `selectableDerivationChains`, `findSelectableDerivationChain`); `test/p1.4a-derivation-surfaces.test.js` custom-chain gate test; `docs/01-spec/chain-registry.md` “Adding a chain” / CI validation.

**Observed:** production considers a chain vector-backed when `testVectors` is merely a non-empty string:

```js
return Boolean(chain && typeof chain.testVectors === 'string' && chain.testVectors.trim());
```

The corresponding negative/positive test injects a custom entry and then makes it selectable by assigning the fabricated string `"Vendor reference vectors, three paths"`. No known seed, path, expected address, source identity, or executed comparison is required. A future custom entry can therefore bypass the acceptance gate by presenting an arbitrary label.

**Expected:** The roadmap says a custom chain cannot be used until **independent test vectors are recorded for it**. The binding chain-registry quality rule specifies what that means: vectors from an independent implementation, with at minimum a known seed, path, and expected address for at least three paths, and shipped vectors executed in CI. The security property is address correctness, not the presence of prose saying vectors exist.

**Required action:** Represent actual independent vector records (including their provenance and expected outputs), validate the required minimum structure, execute them against the chain implementation before the chain becomes selectable, and make CI fail closed if any vector is absent/invalid/mismatched. Replace the current test with a negative case proving labels/metadata alone cannot unlock a chain and a positive case proving real independent vectors were executed successfully.

### F3 — Blocking integration gate — the branch's required UI.10b parent has not passed review

**Location:** `docs/05-development/packets/p1.4a-derivation-surfaces.md` §2.1; PR #68 base relationship.

**Observed:** The packet correctly says: “This branch cannot merge before UI.10b passes review.” The branch is indeed stacked on the pinned UI.10b commit because current `main` lacks the All flows index and related workstation shell. However, UI.10b remains an unreviewed/unmerged branch. The stack is also no longer simply current-main-plus-UI.10b; current `main` and the pinned UI.10b branch have diverged, making parent review/reconciliation material rather than ceremonial.

**Expected:** The dependency that supplies the shell surfaces this item relies on must itself pass independent review and be integrated/reconciled before a dependent PR can receive a merge-ready PASS. Reviewing/merging the child first would implicitly bless unreviewed parent code.

**Required action:** Independently review and land/reconcile UI.10b first. Then rebase or otherwise reconcile P1.4a onto the approved UI.10b/current-main state, rerun the full exact-head suite/browser/reproducibility evidence, and submit that new head for fresh P1.4a review.

The implementation has substantial positive evidence: the production panels really use the existing derivation engine and focused released-secret model, teardown is wired, no private result/boundary escape was found, the changed regression assertions retain exact invariants, exact-head unit CI is 480/480 with zero skips, the expected build hash reproduces across Windows/Ubuntu and multiple build conditions, deliberate mutations fail closed, and the P1.4a browser scenario runs in both Chromium and Firefox.

One roadmap criterion is expressly not met, the security-sensitive custom-chain gate does not establish the independent-vector property it claims, and the stacked parent that this PR declares a merge prerequisite has not passed review. Under `review-protocol.md`, any finding of any severity is a FAIL and an unmet acceptance criterion cannot be waived by the reviewer.
