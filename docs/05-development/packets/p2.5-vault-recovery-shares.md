## 1. Summary

P2.5 adds an offline-only SLIP-39 recovery route for the vault's 32-byte DEK.
It stores exact public recovery metadata in a fixed method-3 record beside the
normal passphrase or keyfile record, binds that metadata to both encrypted
compartments, and keeps share words in the cold session/UI only. The existing
normal unlock route remains valid, and pre-P2.5 readers reject marked files.

## 2. Scope

Included:

- Accepted [ADR-0040](../adr/0040-vault-recovery-share-record.md) and the
  normative [vault-format contract](../../01-spec/vault-format.md).
- Fixed binary method-3 parsing, generation, offline recovery, replacement,
  metadata binding, marker compatibility boundary, and fail-closed negatives.
- Cold-only controls for configuring, masking, transcribing, and unlocking
  with recovery shares; no share words enter the warm realm or the vault file.
- `vault.dirty` as a boolean-only cold-to-warm persistence signal.
- Independent Trezor SLIP-39 coverage and a deterministic method-data fixture.
- Three-depth user guidance, FAQ/quick-start updates, CHANGELOG, roadmap, and
  this packet.

Not included: BackupRecords, share verification records, health scoring,
printable cards, or mobile/physical-device validation. Those remain later
roadmap work or explicitly untested environments.

## 4. Acceptance criteria

Copied from P2.5 in [ROADMAP.md](../ROADMAP.md):

> method 3 has a versioned fixed binary record with exact bounds, one normal
> record, and a recovery marker that makes pre-P2.5 readers reject
> recovery-enabled files; generation and recovery are cold-only and always use
> the empty SLIP-39 share passphrase; supplied shares must match every
> recorded SLIP-39 parameter and member index, with malformed, duplicate,

> normal unlock route continues to work; replacing an existing set requires an

> outside the cold session; and tests include an independent official vector

## 5. Security impact

This changes the vault format, cold vault unlock logic, AAD, and the cold-to-warm
message whitelist. It does not add a network host, weaken the cold CSP, or add
a warm-to-cold credential message.

The only new message is `vault.dirty` with the bounded payload `{ dirty: true }`.
The protocol maps it to the existing boolean-only cleaner; extra fields such as
`shareMaterial` are rejected. The warm handler only marks persistence state
unsaved and contains no recovery-share identifiers or storage.

If the format binding were wrong, an attacker could attempt to substitute a
valid share set from another vault or alter the recorded threshold/metadata.
The implementation limits that risk by exact metadata comparison and by
including the method-data bytes in both compartment AEAD AAD values. If either
the header or metadata changes, normal and recovery opens fail at the
appropriate authentication check. This is the area requiring the most hostile
independent review.

Recovery bypasses the passphrase KDF by reconstructing the DEK directly. It is
available only in offline mode. The normal passphrase/keyfile wrapping key is
retained only inside an offline cold session to reissue a set; recovery-only
sessions cannot silently reconfigure shares.

wrong/replaced shares, changed metadata, invalid method-data version, non-zero
reserved tail, unknown method ID, malformed metadata, duplicate shares,

during rewrapping.

No real seed, private key, vault, or production share was used or committed.
The test vault values are throwaway literals, and generated share words are
held only in test memory and are not printed in this packet.

## 8. Assumptions made

- The roadmap's existing v1 wrapped-block ceiling of 65,535 bytes makes the
  high-bit marker an unambiguous fail-closed boundary for pre-P2.5 readers.
- A recovery-enabled vault must retain exactly one normal record so an owner
  does not lose the established passphrase/keyfile route.
- The pinned SLIP-39 implementation's rule that a 1-member threshold cannot
  advertise multiple members is part of the method-3 metadata bounds.
- No share passphrase is intentional: the printed threshold set is the full
  recovery authority. Seed-backup SLIP-39's optional passphrase remains a
  separate feature and guide.
- Reissuing requires the normal unlock route because safe rewrapping needs the
  retained normal wrapping key; recovery-only sessions can still save normal
  public edits but cannot create a replacement share set.

## 9. What to scrutinise

- Confirm the recovery AAD is constructed from the exact serialized method
  data in both `openSession()` and `save()`, and that the normal wrapped-DEK
  record uses the marked header bytes after configuration.
- Confirm the parser cannot accept a method-3-only block, duplicate members,
  an extra group, a non-zero reserved tail, a marker mismatch, or an unknown
  method without a non-zero failure.
- Confirm asynchronous close/mode/health changes cannot resurrect state or
  leave the newly built wrapped block alive; the regression test deliberately
  closes during the AES operation.
- Confirm recovery remains unreachable online even when valid shares and a
  public-only vault are supplied.
- Confirm no method-3 words or generated share strings appear in the compiled
  warm realm or in any protocol payload.

## 10. Self-assessment

The implementation passes the full Node suite, vendor provenance, reproducible
build, lint, documentation, and Chromium/Firefox `file://` harness. Physical
mobile/browser matrix testing was not performed and is not claimed.

The subtle remaining risk is format interoperability: the method-3 record is
an internal Coldbox v1 contract, not a pre-existing external vault standard.
ADR-0040 and the byte fixture make the contract reviewable, but an independent
reviewer must still check every offset and boundary against the implementation.

The next dependent work is P2.6 BackupRecords and verify-your-shares; this PR
does not implement it.
