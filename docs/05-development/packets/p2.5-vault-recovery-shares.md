The batch stopped here under `AGENTS.md` §4 and
`docs/05-development/batch-run.md` §5: the vault-format specification does
not define the method-3 record encoding or the unlock-route composition, and
guessing would risk permanent loss or an incorrect recovery authority.

## Evidence read before stopping

- `docs/01-spec/vault-format.md` reserves method 3 and says it stores group
  configuration and share metadata but never share material. It does not
  define the method-data bytes, a version field, bounds, coexistence rules,
  or older-reader behavior.
- `docs/03-guides/inheritance-planning.md` describes recovery shares as a
  second route that opens the vault without the passphrase, but does not make
  the record layout normative.
- `docs/01-spec/data-model.md` defines `BackupRecord` metadata, but that is a
  public record model and does not specify the wrapped-DEK method-3 bytes.
- `src/cold/vault.js` currently parses method 1 and method 2 only. Its record
  parser and `unwrapDek()` therefore cannot safely be extended by inference.
- `src/cold/slip39.js` supplies cold-only SLIP-39 arithmetic and vectors, but
  the existing P2.1 API is for seed-entropy shares, not a defined vault-DEK
  record protocol.

## Proposed resolution

`docs/05-development/adr/0039-vault-recovery-share-record.md` lists the six
questions that must be answered and recommends a versioned fixed binary
method-data structure, exact SLIP-39 metadata binding, method-3 coexistence
with the normal unlock route, and no untracked share-passphrase extension.

That ADR is intentionally **Proposed**, not Accepted. It is not permission to
implement the recommended shape.
