## 3. Finding closure

| Finding | Remediation and evidence |
|---|---|
| F1 - candidate whitespace was stripped generically | Verification candidates now reach classification and comparison unchanged. Only exact empty batch lines are omitted. `src/protocol.js`, `src/main.js`, and `src/address-verification.js` preserve leading/trailing whitespace and reject it as an unrecognised address rather than silently changing the value. |
| F2 - Bech32 was regex-only | `src/address-verification.js` now decodes Bech32 and Bech32m, checks the polymod checksum, enforces Bitcoin HRPs, validates witness versions/program lengths, and performs convertbits checks. Invalid checksums are reported as `checksum-invalid`. |
| F3 - Base58 was regex-only | Base58Check decoding now verifies the double-SHA-256 checksum, exact payload length, and supported Bitcoin mainnet/testnet address versions before classifying an address as valid. |
| F4 - batch lost checksum-invalid outcomes | Batch rows use the same candidate-outcome path as single comparisons, retaining and displaying checksum-invalid rows. |
| F5 - cold verification was Bitcoin-only | `src/cold/verification.js` derives the selected registry account for both Bitcoin and EVM metadata, checks the recorded path/xpub, and updates public provenance only after the derived address matches. The cold UI calls these helpers. |
| F6 - different-account output omitted the account | Warm results now include the account label and asset in the account-specific message. The browser harness asserts the `Trading Ethereum` label. |
| F7 - mismatch output omitted aligned strings | The comparison panel renders the complete candidate and recorded values with a caret at the divergence index. It uses DOM `textContent`, not HTML interpolation. |
| F8 - packet evidence was stale | This packet and the self-review now identify the failed review head, remediation commit, current tests, current browser flow, and the remaining explicit device/permission gaps. |

## 4. Security and protocol impact

The address verification result remains a closed protocol vocabulary. Messages
carry public address strings, record/account references, bounded indexes,
closed outcome/state enums, divergence indexes, timestamps, and public xpub
evidence only. They do not carry mnemonics, private keys, xprvs, passphrases,
or secret-compartment plaintext. The protocol tests continue to reject
secret-shaped fields and free-form result prose.

Cold verification reads the registry only after the cold session is unlocked,
derives inside the cold realm, and performs the public state transition only
after a derived address matches the selected record. The cold realm retains
`connect-src 'none'`; no network primitive, runtime dependency, vault-format
change, or randomness-path change was introduced by this remediation.

Independent vector references used by the tests:

- [BIP-173 Bech32](https://github.com/bitcoin/bips/blob/master/bip-0173.mediawiki)
- [BIP-350 Bech32m](https://github.com/bitcoin/bips/blob/master/bip-0350.mediawiki)
- [EIP-55 mixed-case checksum](https://eips.ethereum.org/EIPS/eip-55)

## 5. Acceptance evidence

The roadmap acceptance criteria are met in the implementation and remain
subject to fresh independent review:

- whole-string comparison reports a middle divergence even when the ends
  match;
- Bech32 is case-insensitive after valid checksum decoding, while Base58Check
  remains case-sensitive;
- invalid mixed-case EVM input is `checksum-invalid`, distinct from match and
  mismatch;
- a locked vault returns `vault-locked`, never `no-record`;
- warm-only unverified and unverifiable outcomes state that limitation inline;
- `address.verifyResult` contains enum codes rather than free-form result text;
- cold EVM and Bitcoin re-derivation both require the selected account metadata.
