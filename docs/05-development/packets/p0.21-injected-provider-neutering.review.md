## F1 (blocking) — pre-existing provider is silently erased instead of triggering lockdown

`defineProviderBlocked()` in `src/airgap.js` replaces an existing **configurable** `window.ethereum` property with the blocking accessor. The accessor reports *future* assignment attempts via `onAttempt`, but installation itself never reports that an actual provider object was already present at install time.

This conflicts with [ADR-0020](../adr/0020-injected-providers-rejected-and-neutered.md)'s explicit decision that provider presence inside the cold realm is an isolation failure, and with the P0.21 roadmap item's acceptance criterion that an observed provider object enters full lockdown.

The existing tests miss this timing:

- the unit fixture predefines `ethereum` with `value: undefined`, not an actual provider object;
- the browser harness waits until Coldbox reaches `ready`, then assigns a provider *afterward* — it never establishes provider presence *before* cold bootstrap runs.

The reviewer independently reproduced the underlying behavior with the same property-descriptor logic:

```
before present = true
installed = true
after = undefined, attempts = []
```

A configurable provider existing before guard installation is neutered (good — it can no longer be used), but no isolation violation is reported and installation is reported as a plain success. Since bootstrap only checks `providerNeutering.installed`, not whether a provider was present, cold bootstrap can reach `ready`/green with a provider having been silently wiped rather than routing through the mandated full-lockdown path.

## Required remediation

1. Detect an actual pre-existing `window.ethereum` provider during guard installation and route it through the isolation-violation/full-lockdown path — without invoking extension-controlled methods on it (do not call into the provider object; a presence check must not execute attacker-controlled code).
2. Still neuter it, and fail closed if safe inspection/replacement is impossible.
3. Add a unit regression where an actual provider object exists before `neuterProviders()` runs.
4. Add a real browser fixture that establishes provider presence before cold bootstrap, then verify Chromium and Firefox enter full lockdown rather than reaching healthy readiness.
5. Rerun the complete verification suite and update the packet.
