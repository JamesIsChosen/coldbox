## 5. Security impact

- Does this touch the realm boundary, message schema, CSP, vault format, derivation, or randomness? **No.** This item is exclusively build tooling, CI configuration, and documentation checking.
- What does an attacker gain if this implementation is wrong? A CI misconfiguration that fails to catch a real regression (a broken link, a nondeterministic build, a supply-chain-altered vendor artifact) doesn't itself introduce a vulnerability, but it removes a detection layer — the actual security properties (CSP, sandbox, vault format) are unchanged by this PR and still enforced by the code and tests those other items shipped, not by CI's mere existence. The most concrete risk is `attestation`: if it silently no-ops instead of failing when misconfigured, a release could ship without provenance attestation while looking otherwise complete. `actions/attest-build-provenance@v1` is used as documented; its actual behavior in this repository is unverified (see §9), which is exactly why this is called out rather than asserted fixed.
- New `connect-src` host: none. `npm run verify-vendor`'s network access is unchanged (it already existed pre-P0.18) and is not part of the shipped `coldbox.html` — it's a CI/dev-time check, same as before.
- New message type: none.

## 8. Assumptions made

- **GitHub-hosted runners have real outbound network access, unlike this authoring sandbox.** Basis: this is GitHub's documented default for hosted runners, and it's the premise the whole `browser-tests` job and the online half of `verify-vendor` rest on. If wrong (e.g., the repository is configured with network-restricted self-hosted runners), `browser-tests` and the `verify-vendor` step would fail closed with a non-zero exit — visibly, not silently — rather than passing incorrectly.
- **`windows-latest` is an adequate second OS**, chosen over `macos-latest` because this repository's own tooling (`.gitattributes`, `AGENTS.md`'s PowerShell notes) treats Windows line-ending/shell divergence as the concrete risk to defend against. Recorded as a decision in ADR-0017, not left as a silent packet-only assumption, since it's a structural call about what the reproducibility story actually tests.
- **`actions/attest-build-provenance@v1` is the correct action for this repository's needs.** Basis: it's GitHub's documented first-party action for build provenance attestation. Unverified against a real repository, per the roadmap item's own `⚠️` marker.
- **Bundle-size reporting should not enforce the 3 MB/4.5 MB budget from `dependencies.md`.** The roadmap line asks for a "report," not a gate; enforcing an undocumented CI-level budget check would be a policy decision (what should happen when the budget is exceeded — warn? fail? at which threshold?) this item wasn't asked to make. Recorded as a scope decision in ADR-0017.

## 13. Remediation of review FAIL

An independent reviewer returned **FAIL** on this PR (#30) with three findings: one blocking (F1), two advisory (F2, F3). Per the review protocol, any finding — including advisory ones — is a FAIL, so all three are addressed below before re-review. ### F1 (blocking): CI builds a shallow synthetic PR merge, so its artifact hash doesn't match a full-history local build

**What the reviewer found:** the hosted checkout log showed `fetch-depth: 1` and a synthetic merge commit (`Merge 64fc0f6... into 3c0b502...`), not the real PR head SHA with full history. `scripts/build.js` derives its embedded build date from `git log -1 --format=%cI HEAD -- src scripts vendor`, so this shallow/synthetic checkout produced a build byte-different from a real full-history local checkout of the identical commit. The reviewer's real hosted-CI artifact hash was `e6b94f72d2b89c54bf6f772efdf65f0bda8da6216f10d9d1857bea77325ffb2e`; two independent fresh full-history local clones both reproduced `8891368cf8122dfe553ab4aa7fba7b976007b57d0c73b2dec4ae7a2449eeed59` instead — violating the roadmap's "CI hash matches a local build" acceptance criterion.

**Fix:** every `actions/checkout` step in `.github/workflows/ci.yml` that precedes a `npm run build` (the `build` matrix job, the `browser-tests` job, and the `attestation` job) now sets:

```yaml
with:
  ref: ${{ github.event.pull_request.head.sha || github.sha }}
  fetch-depth: 0
```

- `ref: ${{ github.event.pull_request.head.sha || github.sha }}` checks out the real PR head commit on `pull_request` events (where `github.event.pull_request.head.sha` is populated) and falls through to `github.sha` on every other trigger (`push`, `release`, tag pushes), where `github.event.pull_request` doesn't exist. This matches the exact pattern GitHub's own `actions/checkout` README documents under "Checkout pull request HEAD commit instead of merge commit" (verified against the pinned `v7.0.1` tag's README — see F2 below).
- `fetch-depth: 0` fetches full history, matching what a plain `git clone` (no depth limit) gives a local builder — the same history depth `build.js`'s `git log -1 -- src scripts vendor` query has always assumed.

**Local verification performed:** this sandbox cannot trigger a real GitHub Actions run (no push access), so the fix can't be observed end-to-end here — same limitation disclosed in the original packet's §3. What *was* verified locally:
1. The YAML still parses cleanly and declares the same four jobs and three triggers as before (`python3 -c "import yaml; d=yaml.safe_load(open('.github/workflows/ci.yml')); print(list(d['jobs'].keys()))"` → `['build', 'compare-hashes', 'browser-tests', 'attestation']`).
2. A local build against this branch's current tip (uncommitted `ci.yml`/doc changes don't touch `src`, `scripts`, or `vendor`, so the build date is unaffected) reproduces the reviewer's own independently-obtained full-history local hash exactly:

```

Built build/coldbox.html (8891368cf8122dfe553ab4aa7fba7b976007b57d0c73b2dec4ae7a2449eeed59)
$ LC_ALL=C TZ=UTC node scripts/build.js
Built build/coldbox.html (8891368cf8122dfe553ab4aa7fba7b976007b57d0c73b2dec4ae7a2449eeed59)
```

This is the same hash (`8891368...`) the reviewer's own two independent full-history clones produced — direct evidence that `build.js`'s determinism against real git history is unaffected by this fix, and that the *shape* of the fix (real PR head SHA, full history) is what a genuine local build has always used. **What remains unverified**: whether GitHub Actions' hosted runner, given these exact `ref`/`fetch-depth` inputs on a real `pull_request` event, actually reproduces this hash. ### F2 (advisory): outdated/deprecated GitHub Actions action versions (Node 20, EOL)

**What the reviewer found:** `checkout@v4`, `setup-node@v4`, `upload-artifact@v4`, `download-artifact@v4`, and `attest-build-provenance@v1` all triggered GitHub's Node-20-deprecation warning.

**Fix:** queried each action's GitHub Releases API directly (`api.github.com/repos/actions/<name>/releases/latest`) rather than relying on prior knowledge, since action releases move over time. As of this fix:

| Action | Old pin | New pin | Verified via |
|---|---|---|---|
| `actions/checkout` | `v4` | `v7` (`v7.0.1`) | Releases API: `tag_name: "v7.0.1"`, published 2026-07-20 |
| `actions/setup-node` | `v4` | `v6` (`v6.4.0`) | Releases page: `v6.4.0` tagged "Latest", published 2026-04-20 |
| `actions/upload-artifact` | `v4` | `v7` (`v7.0.1`) | Releases page: `v7.0.1` tagged "Latest", published 2026-04-10 |
| `actions/download-artifact` | `v4` | `v8` (`v8.0.1`) | Releases API: `tag_name: "v8.0.1"`, published 2026-03-11 |
| `actions/attest-build-provenance` | `v1` | `v4` (`v4.1.1`) | Releases page: `v4.1.1` tagged "Latest", published 2026-06-26 |

All five are on majors that run on the Node 24 Actions runtime, per each release's own changelog entry.

**Breaking-change review:** checked each action's README at the pinned tag for input/output name changes this workflow's usage touches:
- `actions/checkout@v7`: `ref` and `fetch-depth` inputs unchanged from `v4`; the README's own "Checkout pull request HEAD commit instead of merge commit" example uses the identical `ref: ${{ github.event.pull_request.head.sha }}` pattern this fix adds. v7's only behavioral change (refusing fork-PR checkout by default on `pull_request_target`/`workflow_run` triggers) doesn't apply — this workflow only uses `pull_request` (same-repo, not fork-targeting-privileged-context), `push`, and `release`.
- `actions/setup-node@v6`: the one breaking change ("Limit automatic caching to npm") only affects callers using the built-in `cache:` input, which `ci.yml` does not set.
- `actions/upload-artifact@v7` / `download-artifact@v8`: no changes to the `name`/`path`/`if-no-files-found`/`retention-days` inputs this workflow uses.
- `actions/attest-build-provenance@v4`: `subject-path` input unchanged; v4 is now a thin wrapper over `actions/attest` but keeps the same action interface for existing callers per its own README.

**Disclosed limitation (per the original F2 finding's own instruction):** these were the latest majors as of this fix, confirmed via live API/README queries rather than assumed from training knowledge — but action releases move, so the reviewer or a future maintainer should re-confirm currency at merge time rather than trusting this table indefinitely.
