## 5. Security impact

- Does this touch the realm boundary, message schema, CSP, vault format, derivation, or randomness? **No.** This item is exclusively build tooling, CI configuration, and documentation checking.
- What does an attacker gain if this implementation is wrong? A CI misconfiguration that fails to catch a real regression (a broken link, a nondeterministic build, a supply-chain-altered vendor artifact) doesn't itself introduce a vulnerability, but it removes a detection layer — the actual security properties (CSP, sandbox, vault format) are unchanged by this PR and still enforced by the code and tests those other items shipped, not by CI's mere existence. The most concrete risk is `attestation`: if it silently no-ops instead of failing when misconfigured, a release could ship without provenance attestation while looking otherwise complete. `actions/attest-build-provenance@v1` is used as documented; its actual behavior in this repository is unverified (see §9), which is exactly why this is called out rather than asserted fixed.
- New `connect-src` host: none. `npm run verify-vendor`'s network access is unchanged (it already existed pre-P0.18) and is not part of the shipped `coldbox.html` — it's a CI/dev-time check, same as before.
- New message type: none.

## 8. Assumptions made

- **GitHub-hosted runners have real outbound network access, unlike this authoring sandbox.** Basis: this is GitHub's documented default for hosted runners, and it's the premise the whole `browser-tests` job and the online half of `verify-vendor` rest on. If wrong (e.g., the repository is configured with network-restricted self-hosted runners), `browser-tests` and the `verify-vendor` step would fail closed with a non-zero exit — visibly, not silently — rather than passing incorrectly.
- **`windows-latest` is an adequate second OS**, chosen over `macos-latest` because this repository's own tooling (`.gitattributes`, `AGENTS.md`'s PowerShell notes) treats Windows line-ending/shell divergence as the concrete risk to defend against. Recorded as a decision in ADR-0017, not left as a silent packet-only assumption, since it's a structural call about what the reproducibility story actually tests.
- **`actions/attest-build-provenance@v1` is the correct action for this repository's needs.** Basis: it's GitHub's documented first-party action for build provenance attestation. Unverified against a real repository, per the roadmap item's own `⚠️` marker.
- **Bundle-size reporting should not enforce the 3 MB/4.5 MB budget from `dependencies.md`.** The roadmap line asks for a "report," not a gate; enforcing an undocumented CI-level budget check would be a policy decision (what should happen when the budget is exceeded — warn? fail? at which threshold?) this item wasn't asked to make. Recorded as a scope decision in ADR-0017.
- **The `check-docs.js`/`check-docs.test.js`/`package.json` changes and the two ADR link fixes already in the working tree before this session are correctly attributed to a prior session on this same item, not authored fresh here.** Basis: this session's own briefing stated this explicitly and instructed treating them as belonging to this item. Not independently re-verifiable by this session since it has no access to prior session history beyond what was stated.

## 13. Remediation of review FAIL

An independent reviewer returned **FAIL** on this PR (#30) with three findings: one blocking (F1), two advisory (F2, F3). Per the review protocol, any finding — including advisory ones — is a FAIL, so all three are addressed below before re-review. ### F1 (blocking): CI builds a shallow synthetic PR merge, so its artifact hash doesn't match a full-history local build

**What the reviewer found:** the hosted checkout log showed `fetch-depth: 1` and a synthetic merge commit (`Merge 64fc0f6... into 3c0b502...`), not the real PR head SHA with full history. `scripts/build.js` derives its embedded build date from `git log -1 --format=%cI HEAD -- src scripts vendor`, so this shallow/synthetic checkout produced a build byte-different from a real full-history local checkout of the identical commit. The reviewer's real hosted-CI artifact hash was `e6b94f72d2b89c54bf6f772efdf65f0bda8da6216f10d9d1857bea77325ffb2e`; two independent fresh full-history local clones both reproduced `8891368cf8122dfe553ab4aa7fba7b976007b57d0c73b2dec4ae7a2449eeed59` instead — violating the roadmap's "CI hash matches a local build" acceptance criterion.

**Fix:** every `actions/checkout` step in `.github/workflows/ci.yml` that precedes a `npm run build` (the `build` matrix job, the `browser-tests` job, and the `attestation` job) now sets:

```yaml
with:
  ref: ${{ github.event.pull_request.head.sha || github.sha }}
  fetch-depth: 0
```

- `ref: ${{ github.event.pull_request.head.sha || github.sha }}` checks out the real PR head commit on `pull_request` events (where `github.event.pull_request.head.sha` is populated) and falls through to `github.sha` on every other trigger (`push`, `release`, tag pushes), where `github.event.pull_request` doesn't exist. This matches the exact pattern GitHub's own `actions/checkout` README documents under "Checkout pull request HEAD commit instead of merge commit" (verified against the pinned `v7.0.1` tag's README — see F2 below).
- `fetch-depth: 0` fetches full history, matching what a plain `git clone` (no depth limit) gives a local builder — the same history depth `build.js`'s `git log -1 -- src scripts vendor` query has always assumed.

**Local verification performed:** this sandbox cannot trigger a real GitHub Actions run (no push access), so the fix can't be observed end-to-end here — same limitation disclosed in the original packet's §3. What *was* verified locally:
1. The YAML still parses cleanly and declares the same four jobs and three triggers as before (`python3 -c "import yaml; d=yaml.safe_load(open('.github/workflows/ci.yml')); print(list(d['jobs'].keys()))"` → `['build', 'compare-hashes', 'browser-tests', 'attestation']`).
2. A local build against this branch's current tip (uncommitted `ci.yml`/doc changes don't touch `src`, `scripts`, or `vendor`, so the build date is unaffected) reproduces the reviewer's own independently-obtained full-history local hash exactly:

```
$ LC_ALL=C TZ=UTC node scripts/build.js
Built build/coldbox.html (8891368cf8122dfe553ab4aa7fba7b976007b57d0c73b2dec4ae7a2449eeed59)
$ LC_ALL=C TZ=UTC node scripts/build.js
Built build/coldbox.html (8891368cf8122dfe553ab4aa7fba7b976007b57d0c73b2dec4ae7a2449eeed59)
```

This is the same hash (`8891368...`) the reviewer's own two independent full-history clones produced — direct evidence that `build.js`'s determinism against real git history is unaffected by this fix, and that the *shape* of the fix (real PR head SHA, full history) is what a genuine local build has always used. **What remains unverified**: whether GitHub Actions' hosted runner, given these exact `ref`/`fetch-depth` inputs on a real `pull_request` event, actually reproduces this hash. ### F2 (advisory): outdated/deprecated GitHub Actions action versions (Node 20, EOL)

**What the reviewer found:** `checkout@v4`, `setup-node@v4`, `upload-artifact@v4`, `download-artifact@v4`, and `attest-build-provenance@v1` all triggered GitHub's Node-20-deprecation warning.

**Fix:** queried each action's GitHub Releases API directly (`api.github.com/repos/actions/<name>/releases/latest`) rather than relying on prior knowledge, since action releases move over time. As of this fix:

| Action | Old pin | New pin | Verified via |
|---|---|---|---|
| `actions/checkout` | `v4` | `v7` (`v7.0.1`) | Releases API: `tag_name: "v7.0.1"`, published 2026-07-20 |
| `actions/setup-node` | `v4` | `v6` (`v6.4.0`) | Releases page: `v6.4.0` tagged "Latest", published 2026-04-20 |
| `actions/upload-artifact` | `v4` | `v7` (`v7.0.1`) | Releases page: `v7.0.1` tagged "Latest", published 2026-04-10 |
| `actions/download-artifact` | `v4` | `v8` (`v8.0.1`) | Releases API: `tag_name: "v8.0.1"`, published 2026-03-11 |
| `actions/attest-build-provenance` | `v1` | `v4` (`v4.1.1`) | Releases page: `v4.1.1` tagged "Latest", published 2026-06-26 |

All five are on majors that run on the Node 24 Actions runtime, per each release's own changelog entry.

**Breaking-change review:** checked each action's README at the pinned tag for input/output name changes this workflow's usage touches:
- `actions/checkout@v7`: `ref` and `fetch-depth` inputs unchanged from `v4`; the README's own "Checkout pull request HEAD commit instead of merge commit" example uses the identical `ref: ${{ github.event.pull_request.head.sha }}` pattern this fix adds. v7's only behavioral change (refusing fork-PR checkout by default on `pull_request_target`/`workflow_run` triggers) doesn't apply — this workflow only uses `pull_request` (same-repo, not fork-targeting-privileged-context), `push`, and `release`.
- `actions/setup-node@v6`: the one breaking change ("Limit automatic caching to npm") only affects callers using the built-in `cache:` input, which `ci.yml` does not set.
- `actions/upload-artifact@v7` / `download-artifact@v8`: no changes to the `name`/`path`/`if-no-files-found`/`retention-days` inputs this workflow uses.
- `actions/attest-build-provenance@v4`: `subject-path` input unchanged; v4 is now a thin wrapper over `actions/attest` but keeps the same action interface for existing callers per its own README.

**Disclosed limitation (per the original F2 finding's own instruction):** these were the latest majors as of this fix, confirmed via live API/README queries rather than assumed from training knowledge — but action releases move, so the reviewer or a future maintainer should re-confirm currency at merge time rather than trusting this table indefinitely.

**What the reviewer found:** on the real GitHub Actions run at this branch's tip, `build (ubuntu-latest)` succeeded and its artifact hash exactly matched an independent full-history local build (`8891368...`, same hash R1's remediation reproduced). `build (windows-latest)` failed inside `npm test`: 148/149 passed, one failed — `"the compiled help content in the build round-trips the real dependencies-free structural shape (glossary categories, guide slugs)"` in `test/help-content.test.js`, with `AssertionError: HELP_CONTENT must be embedded as a single JSON statement`. **The CRLF hypothesis was investigated and ruled out, not assumed away:**
- `.gitattributes` already existed at the failing commit (`57ebcc4`) with `* text=auto eol=lf`, which forces LF on checkout regardless of a runner's `core.autocrlf` setting — so a naive CRLF-checkout theory doesn't fit without first explaining why that file wouldn't already prevent it.

  ```

  Error: Build refused: source failed forbidden-construct lint
  ```
  A real CRLF-corrupted Windows checkout would therefore surface as *that* failure, not as a malformed-JSON assertion inside `help-content.test.js` — direct evidence the reviewer's specific hypothesis, while a reasonable first guess, was not what actually happened on the hosted runner.

**Actual root cause, found by reproducing the failure locally:** `test/build.test.js`, `test/help-content.test.js`, and `test/provenance.test.js` each spawn their own `node scripts/build.js` child process against the real project tree and read the **same fixed shared path**, `build/coldbox.html`, in the real project root (not an isolated temp directory, unlike most other tests in this suite that already use `fs.mkdtempSync`). `package.json`'s `"test": "node --test"` had no concurrency flag, so Node's test runner ran test *files* in parallel by default. `writeBuild()` in `scripts/build.js` wrote the artifact with a plain `fs.writeFileSync(htmlPath, output)` — which opens the destination with truncate-then-write semantics — so when two or more of these processes' builds and reads overlapped in time, a reader could observe a file that had been truncated by one process before another process's write completed, i.e. a genuinely malformed/truncated `build/coldbox.html`.

This was reproduced directly, independent of any git checkout or line-ending state: a script that fires several concurrent `node scripts/build.js` child processes against one shared repository checkout while polling `build/coldbox.html` on a short interval reliably produced malformed reads —

```
$ node /tmp/race2.js   # 6 concurrent builds/round x 20 rounds, polling every 5ms
CORRUPT: no match, length= 0
CORRUPT: no match, length= 16378
CORRUPT: no match, length= 131042

```

— the exact symptom the reviewer's hosted-Windows run hit (`HELP_CONTENT must be embedded as a single JSON statement`, i.e. the regex that expects one complete JSON object found a truncated one instead). This is a genuine race, not a Windows-specific bug in the strict sense — it reproduces on this sandbox's Linux filesystem too — but it is **far more likely to be hit** on a busier or slower-I/O host (a shared hosted Windows runner under load) than on a fast, lightly-loaded local development machine, which fully explains why the reviewer's own local Windows run passed 149/149 while the hosted run did not: both are the same code hitting the same race with different odds, not different code paths.

**Fix — two changes, addressing both the immediate corruption and the underlying shared-mutable-state hazard:**

1. **`scripts/build.js`: atomic writes.** Added `writeFileAtomic()`, which writes the full contents to a process-unique temp file (`<target>.tmp-<pid>-<random>`) in the same directory as the target, then `fs.renameSync`s it into place. `fs.renameSync` is atomic on both POSIX and Windows when source and destination share a volume, which they always do here (the temp file is created inside `buildRoot` itself). A concurrent reader can now only ever observe the previous complete file or the new complete file — never a partially-written one. `writeBuild()` now calls this for both `coldbox.html` and its `.sha256` sidecar. This is the direct, structural fix for the reported symptom: it makes `build.js` itself correct under concurrent invocation, regardless of what triggers the concurrency (this test suite today, a human running `npm run build` while a file watcher also triggers one, or anything else in the future) — the same "fix the code, don't fight the environment" preference this project applied to the CRLF question before ruling it out.
2. **`package.json`: `"test": "node --test --test-concurrency=1"`.** Serializes test *file* execution so no two test files' spawned child processes ever run at the same time, removing the cross-file race at its source rather than only papering over its most visible symptom. Chosen as defense-in-depth alongside the atomic-write fix rather than instead of it: atomic writes alone prevent corruption, but multiple tests independently building against the same shared real-tree path could still nondeterministically observe *each other's* completed builds interleaved with their own (e.g. one test's locale-specific build clobbered by a concurrent unrelated test's build, landing on a differently-timed but individually-valid file) — serializing file execution removes that class of flake entirely, not just the corruption case this review caught.

### R3-F1 (advisory): the R2 atomic-write fix's comments and packet language overclaimed what `writeBuild()` guarantees on Windows under concurrent writers

**What the reviewer found:** §14's R2-F1 remediation text (and the matching comment block in `scripts/build.js` above `writeFileAtomic()`) stated that the atomic temp-file-plus-rename design means "a reader can now only ever observe the previous complete file or the new complete file — never a partially-written one" and that this "makes `build.js` itself correct under concurrent invocation, regardless of what triggers the concurrency." That second clause is broader than what was actually tested: it reads as a claim of safety under multiple concurrent *writers*, not just a reader racing a single writer. The reviewer tested that broader claim directly — six concurrent real `node scripts/build.js` processes per round, all targeting the same real shared `build/coldbox.html` path, on Windows — and one process failed with:
```
Error: EPERM: operation not permitted, rename
...\build\coldbox.html.tmp-27000-51d6a5aebba9
->
...\build\coldbox.html
```
at `scripts/build.js:391`, `fs.renameSync(tempPath, targetPath)`.

This is real and reproducible: on Windows, `rename()` onto a destination that's momentarily held open by another process (including another process's own temp-file lifecycle, an antivirus scan, or a reader with a handle open) can fail with an EPERM/EBUSY-shaped error — unlike POSIX `rename()`, which has no such failure mode. It is **not** a reopening of the R2-F1 bug itself: that bug was about a *reader* observing a truncated file, and the fix for that (atomic rename, verified in §14) still holds — no truncated read was ever reproduced by the R3 reviewer either. The finding is specifically that the code comment and the packet's prose claimed more than that (safety under concurrent *writers*), and nothing in this codebase's test suite ever exercised or proved that broader claim.

**Decision: Option B — narrow the claim to match reality, rather than build untested concurrent-multi-writer robustness.**

Reasoning, recorded as an **Assumption**: this project's actual usage of `writeBuild()` is single-writer-at-a-time in every real path — `npm test` runs with `--test-concurrency=1` (the R2-F1 fix itself), so test-triggered builds never race each other, and a normal `node scripts/build.js` invocation from a human or CI job is a single process. Building retry/backoff logic for a concurrent-multi-writer scenario that provably does not occur in this project's real usage would be scope creep relative to this roadmap item (P0.18 is CI, not a build-tooling redesign), and — more importantly — it would add new, non-trivial logic (retry counts, backoff timing, a new fail-closed error path) to `scripts/build.js`, a file whose output is a reproducibility contract, without a way to genuinely regression-test the Windows-specific `EPERM` retry path from this sandbox (this sandbox's own filesystem is a Linux/FUSE mount, not Windows, and `scripts/build.js` executes its build as top-level side effects on `require` rather than exposing `writeFileAtomic`/`writeBuild` as an importable, mockable unit — see `test/build.test.js`'s own comment on why it re-implements `jsonScriptLiteral` instead of requiring `build.js` directly). Shipping retry logic with no real regression coverage would itself be an unverified claim of robustness, i.e. the same category of problem this finding is about. This project's actual philosophy, per [AGENTS.md](../../../AGENTS.md) §3, is "fail closed": `writeFileAtomic()` already does that — if `fs.renameSync` fails, it throws immediately rather than silently succeeding with a partial write or hanging. What was inaccurate was the *documentation*, not the *behavior*. Narrowing the claim to what's actually true and tested is therefore the fix that doesn't overclaim, consistent with the project's general practice of not asserting a guarantee it can't back up with a passing test.
