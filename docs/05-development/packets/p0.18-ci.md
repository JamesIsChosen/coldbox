## 1. Summary

Adds `.github/workflows/ci.yml` (build/verify-vendor/lint/check-docs/test on two OSes, a double-build hash comparison, a cross-OS hash comparison, a bundle size report, an always-run browser-harness job, and a tag/release-gated attestation job) and closes the one gap in `scripts/check-docs.js` against `doc-hygiene.md`'s automated-checks table (a `TODO`/`TBD` warning check), with negative-fixture tests for it. [ADR-0017](../adr/0017-ci-workflow-structure.md) records the structural decisions.

| A missing review date fails CI | same step; `checkReviewDates` reports a missing `*Last reviewed:*` line as FAIL | `test/check-docs.test.js`: "a missing review date on a dated doc fails the check" (pre-existing, still passing) |

All five criteria are met in the sense that the mechanism exists and its non-CI-hosted equivalent (`node scripts/check-docs.js` against real and synthetic fixtures) is proven in this session. **The literal "in CI" half of each criterion — a real GitHub Actions run actually producing that pass/fail outcome — is unverified**, disclosed above and in §9.

## 5. Security impact

- Does this touch the realm boundary, message schema, CSP, vault format, derivation, or randomness? **No.** This item is exclusively build tooling, CI configuration, and documentation checking.
- What does an attacker gain if this implementation is wrong? A CI misconfiguration that fails to catch a real regression (a broken link, a nondeterministic build, a supply-chain-altered vendor artifact) doesn't itself introduce a vulnerability, but it removes a detection layer — the actual security properties (CSP, sandbox, vault format) are unchanged by this PR and still enforced by the code and tests those other items shipped, not by CI's mere existence. The most concrete risk is `attestation`: if it silently no-ops instead of failing when misconfigured, a release could ship without provenance attestation while looking otherwise complete. `actions/attest-build-provenance@v1` is used as documented; its actual behavior in this repository is unverified (see §9), which is exactly why this is called out rather than asserted fixed.
- New `connect-src` host: none. `npm run verify-vendor`'s network access is unchanged (it already existed pre-P0.18) and is not part of the shipped `coldbox.html` — it's a CI/dev-time check, same as before.
- New message type: none.

## 8. Assumptions made

- **GitHub-hosted runners have real outbound network access, unlike this authoring sandbox.** Basis: this is GitHub's documented default for hosted runners, and it's the premise the whole `browser-tests` job and the online half of `verify-vendor` rest on. If wrong (e.g., the repository is configured with network-restricted self-hosted runners), `browser-tests` and the `verify-vendor` step would fail closed with a non-zero exit — visibly, not silently — rather than passing incorrectly.
- **`windows-latest` is an adequate second OS**, chosen over `macos-latest` because this repository's own tooling (`.gitattributes`, `AGENTS.md`'s PowerShell notes) treats Windows line-ending/shell divergence as the concrete risk to defend against. Recorded as a decision in ADR-0017, not left as a silent packet-only assumption, since it's a structural call about what the reproducibility story actually tests.
- **`actions/attest-build-provenance@v1` is the correct action for this repository's needs.** Basis: it's GitHub's documented first-party action for build provenance attestation. Unverified against a real repository, per the roadmap item's own `⚠️` marker.
- **Bundle-size reporting should not enforce the 3 MB/4.5 MB budget from `dependencies.md`.** The roadmap line asks for a "report," not a gate; enforcing an undocumented CI-level budget check would be a policy decision (what should happen when the budget is exceeded — warn? fail? at which threshold?) this item wasn't asked to make. Recorded as a scope decision in ADR-0017.
- **The `check-docs.js`/`check-docs.test.js`/`package.json` changes and the two ADR link fixes already in the working tree before this session are correctly attributed to a prior session on this same item, not authored fresh here.** Basis: this session's own briefing stated this explicitly and instructed treating them as belonging to this item. Not independently re-verifiable by this session since it has no access to prior session history beyond what was stated.

## 9. What to scrutinise

- **The entire GitHub Actions execution path is unverified.** This is the biggest gap in this packet. The workflow YAML parses and its steps map to locally-verified commands, but nobody has watched `ci.yml` actually run — not the matrix build, not `compare-hashes` downloading and diffing two artifacts, not `browser-tests` installing Playwright on a real hosted runner, not `attestation`. A reviewer with push access to a real GitHub repository should push this branch and watch an actual run before trusting any of the four jobs.
- **The `compare-hashes` job's artifact-download logic** (`cut -d ' ' -f1` against the sidecar file format `<hash>  build/coldbox.html\n`) was written by inspecting `writeBuild()` in `scripts/build.js` rather than by running it through GitHub's artifact system, since that system doesn't exist in this sandbox. Confirm the parsing is correct against a real uploaded/downloaded artifact.
- **The `browser-tests` job's unconditional (non-path-filtered) execution** is a deliberate, disclosed cost tradeoff (ADR-0017), not an oversight — but it's worth a second opinion on whether that tradeoff is right for this repository's actual CI budget, which this session has no visibility into.
- **The eighth doc-hygiene check's scope** (`docs/00-overview/glossary.md` + `docs/03-guides/` only) is this session's own reading of `doc-hygiene.md`'s "user-facing docs" phrase — the source document doesn't define that phrase precisely. If a reviewer reads it more broadly (e.g., including `README.md`), that's a legitimate disagreement to resolve, not a bug to hide.

## 10. Self-assessment

- **What might be wrong:** the workflow could contain a YAML-valid but semantically incorrect construct that only fails when GitHub actually schedules the jobs (e.g., a typo in an action's input name, an artifact name collision, a permissions scope GitHub rejects). Static parsing catches syntax errors, not this class of bug.
- **What was not done that arguably should have been:** actually triggering a real workflow run. This session has no path to do that — it cannot push to a real GitHub repository or otherwise cause Actions to execute — so it is flagged here rather than silently skipped.
- **Known limitations shipping with this change:** the attestation step's real success is unverified and additionally blocked on repository secrets/configuration the human must grant (per the roadmap item's own `⚠️` marker, unchanged by this work). `browser-tests` is not path-filtered, which is a disclosed cost tradeoff rather than a defect.
- **Follow-up work this creates:** if CI wall-clock time becomes a measured problem, path-scope `browser-tests` (ADR-0017's "What would change our mind"). No new roadmap item filed — this is covered by ADR-0017's own revision trigger rather than needing a separate tracked item.
