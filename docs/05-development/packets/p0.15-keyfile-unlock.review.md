## 4. Findings

### F1 — stale `FileReader` callbacks can replace the user's current keyfile selection

**Severity:** blocking security / permanent-loss risk  
**Location:** `src/cold/main.js:769-803`

**Observed:** Every keyfile input `change` creates a new `FileReader`, but there is no active-reader cancellation, selection generation/token, or callback check that the `file` captured by that reader is still the file currently selected when `onload` or `onerror` fires. Each callback mutates the shared globals `keyfileBytes` / `keyfileName`, and `onerror` calls `clearKeyfileSelection()` globally.

A reproducible ordering exists without any exotic input:

1. choose keyfile A;
2. before A's asynchronous read completes, choose keyfile B;
3. B completes first and becomes the apparent/current selection;
4. A completes later and overwrites `keyfileBytes` / `keyfileName`, or A errors later and clears B.

`createEmptyVault()` and `unlockLoadedVault()` consume those globals. Therefore a vault can be created using stale A bytes while the file picker currently points at B. Because P0.15 intentionally makes a one-byte difference permanently fatal, this can create a vault the user later cannot open with the file they reasonably believe protected it.

**Expected:** Only the most recent still-active keyfile selection may commit bytes or an error into keyfile state. Clearing/toggling off/locking must invalidate any in-flight read.

**Required action:** Add explicit stale-read protection. A suitable implementation is a monotonically increasing keyfile-selection generation plus optional `FileReader.abort()`: capture the generation for each read; increment/invalidate it on every new selection, toggle-off, clear, and lock; in `onload`/`onerror`, mutate state only when that generation is still current, the toggle is still enabled, and the selected file still corresponds to that request. Add browser regression coverage that deliberately completes A/B reads out of order and proves stale A cannot overwrite or clear B.

### F2 — lock clears keyfile bytes but leaves the file input and "loaded" status stale

**Severity:** blocking functional / state-integrity defect  
**Location:** `src/cold/main.js:121-139`, `src/cold/main.js` `clearVaultSession()` around the P0.15 addition after passphrase clearing

**Observed:** `clearKeyfileSelection()` is the helper that zeroes `keyfileBytes`, empties `keyfileInput.value`, and resets the visible status. The P0.15 change to `clearVaultSession()` calls only `zeroKeyfile()`. That clears the in-memory bytes/name but deliberately leaves the browser file input value and visible keyfile status unchanged.

After a keyfile has been loaded and the session locks (manual lock, idle lock, panic path, runtime-health closure, or another path through `clearVaultSession()`), the UI can still display a selected file and `"Keyfile loaded (... bytes)"` even though `keyfileBytes` is `null`. On the next unlock attempt, the code reports that no keyfile is selected. Re-selecting the same file may also fail to emit a `change` event while the file input's old value is still present, forcing an undocumented toggle-off/on recovery.

This directly contradicts the new source comment that the keyfile is "Cleared on lock" as a coherent user-visible selection state.

**Expected:** Whenever lock/session clearing destroys the in-memory keyfile, the visible file-input/status state must be cleared at the same time, and any in-flight reader must be invalidated.

**Required action:** Make lock/session cleanup call a single coherent keyfile-selection reset (or equivalent) that zeroes bytes, invalidates in-flight reads, clears `keyfileInput.value`, resets the status text, and leaves toggle/warning behavior intentionally defined. Add browser regression coverage for load-keyfile → unlock/create → lock → load/open again, including re-selecting the same keyfile and verifying the UI never says "loaded" while the backing bytes are absent.

### F3 — the roadmap's two UI requirements have no dedicated executable browser coverage

**Expected:** A user-facing permanent-loss control that appears verbatim in the roadmap must have executable browser coverage capable of detecting regressions in its required state and warning behavior.

**Required action:** Extend the browser harness (or add a focused Playwright test integrated into the normal gate) to prove at minimum: fresh load has the keyfile toggle unchecked; keyfile input is disabled until opt-in; warning is hidden before opt-in and immediately visible after opt-in; rendered warning states that loss or byte alteration causes permanent unrecoverable loss; selecting a keyfile drives the real create/unlock path; and the F1/F2 lifecycle regressions are covered. Run it in the existing Chromium and Firefox `file://` matrix.

### F6 — ADR-0014 incorrectly equates the NTFS filename limit with a 255-byte limit

**Severity:** advisory documentation — must fix  
**Location:** `docs/05-development/adr/0014-keyfile-unlock-implementation-limits.md:39`

**Observed:** The ADR justifies the 255-byte hint cap by saying "255 bytes ... is itself the POSIX/ext4/NTFS practical ceiling." The ext4 limit is byte-based, but Microsoft's current filesystem documentation states the NTFS maximum filename length as **255 Unicode characters**, not 255 bytes. Therefore the cross-filesystem factual claim is inaccurate.

This does not by itself make a 255-byte application hint cap unsafe; it makes the written rationale factually wrong.

**Expected:** Documentation must distinguish byte-count limits from character/code-unit limits and avoid asserting a false cross-filesystem equivalence.

**Required action:** Rewrite or remove the filesystem comparison. If retained, state the units accurately (for example, ext4's filename limit is byte-based while NTFS documents a 255-Unicode-character maximum) and keep the 255-byte Coldbox hint limit framed as an application-format choice rather than a universal filesystem ceiling.
