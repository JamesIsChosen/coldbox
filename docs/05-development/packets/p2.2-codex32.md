## 1. Summary

P2.2 adds a cold-only, inline BIP-93 codex32 implementation for direct 16-to-64-byte BIP-32 master seeds. It supports regular and long checksums, GF(32) threshold generation/recovery, official interoperability vectors, and a bounded confirmation-gated single-character correction helper. The cold UI masks generated/recovered values, provides timed reveals, and clears all codex32 state on the existing cold-session teardown path.

## 2. Scope

In scope:

- `src/cold/codex32.js`, assembled in a fixed order by `scripts/build.js`.
- Cold-only codex32 generation, recovery, masking, correction confirmation, and teardown UI.
- Official BIP-93 vector and negative tests plus Chromium/Firefox `file://` harness coverage.
- ADR, guide, dependency provenance, changelog, roadmap split/marker, and this packet.

Deliberately out of scope:

- SLIP-39, Seed XOR, Shamir39/raw SSS, vault recovery records, health dashboards, and printable worksheets; those are P2.1/P2.3–P2.8 items.
- BIP-93's full multi-error correction search. P2.2 offers one bounded single-character candidate and requires explicit confirmation; broader arithmetic repair is a later roadmap item.
- Physical paper, printer, mobile, iOS, hardware-wallet, and manual worksheet verification.

## 4. Acceptance criteria

The roadmap currently names this item as:

> P2.2 codex32

The implementation satisfies that item through the BIP-93 surface described by the existing codex32 guide and ADR-0036. The focused suite proves the five independent published vectors, regular/long decoding, interpolation/recovery, generated threshold round-trips, invalid inputs, and missing-randomness refusal. The browser harness proves the user-facing cold-only workflow and teardown.

## 5. Security impact

Yes. This touches secret generation, secret recovery, randomness, the cold-realm assembly, and masked rendering. It does not change the message schema or add any cold-to-warm message.

If interpolation or the polynomial anchor is wrong, the application could produce valid-looking checksummed shares that reconstruct the wrong seed. The official BIP-93 interpolation/recovery vectors and generated 16/32/64-byte round-trips are the principal evidence against that failure. If the masking/teardown path is wrong, a secret could remain visible in the cold DOM after a session lock; the Chromium/Firefox browser test checks both the default masks and teardown clearing.

The cold CSP remains `connect-src 'none'`; no host was added. `codex32.js` has no storage, network, warm DOM, or message-channel path. The warm parent sees no codex32 API and the browser test asserts that isolation.

All random polynomial coefficients use `crypto.getRandomValues`. Missing randomness raises an error and the focused negative test proves generation refuses to proceed. No `Math.random`, `eval`, `new Function`, module import, or runtime dependency was added.

## 6. Test evidence

New tests:

- `test/codex32.test.js`: five official BIP-93 vectors, regular and long checksums, direct decode/recovery, generated threshold round-trips, invalid vectors, correction, missing randomness, and invalid configuration.
- `scripts/run-browser-harness.js`: cold API isolation, masked generation, timed reveal, threshold recovery, masked recovered output, explicit correction confirmation, insufficient-share failure, warm isolation, and lock teardown in Chromium and Firefox.

Vector authority:

- [Bitcoin BIP-93](https://github.com/bitcoin/bips/blob/master/bip-0093.mediawiki), including its reference Python algorithms and published test vectors. The vectors were not generated by this implementation.

Negative cases deliberately exercised:

- Invalid checksums and wrong data-size families.
- Mixed/invalid codex32 text, one altered character, one missing share, repeated/invalid share conditions, and thresholds/counts outside the allowed range.
- Missing `crypto.getRandomValues`.
- Parent-frame API absence and post-lock secret-state clearing.

The full existing `npm.cmd test`, vendor verification, lint, docs check, build, and Chromium/Firefox browser gates also ran. Physical/mobile/browser-device execution and manual checksum calculation remain untested.

## 8. Assumptions made

- The roadmap's one-line P2.2 title is the acceptance surface; the existing BIP-93 guide and architecture documents supply the format and realm requirements because the roadmap does not enumerate separate bullet criteria.
- The current BIP-93 draft is the interoperability authority. Regular and long forms are both implemented because the standard's published vectors include both and BIP-32 allows 64-byte seeds.
- The UI accepts a direct hex master seed rather than a mnemonic because BIP-93 explicitly encodes BIP-32 master-seed bytes, not BIP-39 entropy. It has no passphrase field.
- Share generation uses random polynomials expressed around the secret coordinate `s`; this is necessary for an existing secret to be recovered at the codex32 secret index rather than at zero.
- The P2.2 branch is a sibling cut from `main`, as required by `batch-run.md`; it does not include P2.1's unmerged SLIP-39 code. The roadmap is split into individual markers on this branch so only P2.2 is `[~]`.
- The correction helper is intentionally bounded to a single candidate substitution. P4.3e owns broader codex32 correction and requires its own independent vectors.

## 9. What to scrutinise

First scrutinise `gfLagrange`, the `s`-anchored polynomial generation, and the regular/long checksum constants in `src/cold/codex32.js`. A bug there can preserve checksums while changing the recovered secret. Then scrutinise the build manifest ordering and the main.js guard/teardown calls to ensure the API remains cold-only and state cannot survive a double-Escape lock.

## 10. Self-assessment

- The highest residual risk is the small hand-transcribed GF(32)/BIP-93 adaptation; the official vectors cover interoperability but cannot prove every possible share-set shape.
- The single-character correction search is deliberately narrower than BIP-93's recommended maximum correction capability. The UI and docs state that limitation rather than presenting it as full repair.
- No independent human paper checksum, physical printer, mobile local-file, or iOS execution test was possible.
- The final independent review must inspect the exact standard constants and verify that no generated/recovered codex32 string reaches a message or warm DOM path.
