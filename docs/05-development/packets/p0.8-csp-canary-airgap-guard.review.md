I sliced the `airgap` IIFE out of `build/coldbox.html` (5,088 bytes; confirmed byte-identical to `src/airgap.js`)

assert that each of the five names throws, that each descriptor is `configurable: false, writable: false`, that
`onAttempt` fires with the right name, and that `installed` goes false when any `defineProperty` is refused.
**Required action:** Add that test.

### F5 — Prototype restoration defeats the neutering silently, with no airgap-violation raised

**Severity:** blocking
**Location:** `src/airgap.js:98-142` (`createBlocker`, `defineBlocked`, `neuterNetwork`)
**Observed:** `defineBlocked` installs an **own** property on the global object and on the **`navigator`
instance**. Per WebIDL, `fetch` is an operation on `Window.prototype` and `sendBeacon` an operation on
`Navigator.prototype`, so both originals remain on the prototype chain, unshadowed and unfrozen. Driving the
neutering code extracted verbatim from `build/coldbox.html`:

```text
Navigator.prototype.sendBeacon.call(navigator, …) => RETURNED: NATIVE sendBeacon ran
Window.prototype.fetch.call(window, …)            => RETURNED: NATIVE fetch ran
onAttempt callback fired for: ["fetch","sendBeacon","sendBeacon"]   <- neither prototype call appears
```

The `onAttempt` list is the important half: these routes produce **no** `recordRuntimeViolation`, so
`data-runtime-neutering-violations` never increments, no `airgap-violation` status crosses the port, and the
warm shell never locks down. A fresh realm (`iframe.contentWindow`, or a `blob:` Worker — the cold CSP permits
`worker-src blob:`) also returns a native `fetch`, and `neuterNetwork` covers no worker entry point at all.
Separately, `neuterNetwork` runs only inside `completeBootstrap` (src/cold/main.js:78), i.e. **after** the
canary settles — up to 1,250 ms during which all five primitives are native.
This contradicts packet §5 line 85 (*"The cold guard blocks all five documented network primitives … then
freezes the replacement properties"*), §7 line 105 (*"A cold runtime call to each of … is blocked"*) and §9
line 149 (*"Every cold runtime blocker is non-configurable and non-writable"*), and it contradicts
`docs/02-security/csp-policy.md:127` (*"If any of these ever fires, the CSP has failed … the alarm exists to
make that loud rather than silent"*) — on these routes the alarm is silent.
`connect-src 'none'` still blocks the traffic itself, so **this is a defense-in-depth failure, not a
demonstrated leak.** It is still a finding: the guard does not do what the packet and the security doc say it does.
**Expected:** Either neuter the prototype-side members too (`Navigator.prototype.sendBeacon`,
`Window.prototype.fetch`) and document the fresh-realm/Worker limits as explicitly out of reach, or downgrade the
claims in the packet and `csp-policy.md` to exactly what is enforced.
**Required action:** Pick one and make code and prose agree. Note that the WebIDL placement of
`Window.prototype.fetch` / `Navigator.prototype.sendBeacon` is asserted from the spec, not observed in a real
browser here — confirm it in the harness as part of the fix.

### F6 — The per-primitive "blocked" evidence is indistinguishable from a DNS failure

**Severity:** advisory
**Location:** `test/browser/harness.js:148-298`
**Observed:** The probe URL is `https://coldbox.invalid/network-primitive-test` — a host that never resolves.
The accepted "blocked" signals are `blocked('error-event')`, `blocked('abort-event')`,
`blocked('timeout-event')`, `blocked('close-event')`, `blocked('returned-false')` and `blocked('threw')`, and the
only assertion is:

```js
assert.equal(result.blocked, true, `${name} did not signal a blocked request (…)`);
```

Every one of those signals is what a non-resolving host produces **with no CSP and no runtime guard at all**: an
XHR to a dead host fires `error`; a `WebSocket` fires `error`/`close`; an `EventSource` fires `error`; a `fetch`
rejects and lands in the outer `catch` as `blocked('threw')`. The `signal` field is logged but never constrained,
so the harness cannot tell "the guard threw" from "DNS said no". Only the `sendBeacon` branch does better — it
waits for an actual `connect-src` violation before accepting a `true` return. Combined with F4, a build with a
blocker deleted would still be reported as passing. This is the same class of defect a previous review raised
about `.invalid` probes; it has not been closed.
**Expected:** Assert the signal, not just the boolean — after neutering the only acceptable signal is `threw`
with a message containing `Coldbox airgap blocked <name>`; and any CSP-level assertion should require an observed
`connect-src` violation whose `blockedURI` is the probe URL.
**Required action:** Tighten the assertion, and/or use a resolvable-but-disallowed host so that "blocked" can
only mean "policy blocked it".

## 5. Verdict rationale

The engineering here is better than the packet's evidence. Reproducibility reproduces exactly, under a
non-ASCII path, a Turkish locale and two antipodal timezones. The warm allowlist is byte-identical to P0.7,
`connect-src 'none'` is present in the built cold policy, the sandbox has no `allow-same-origin`, no new message
type or field can carry secret material, and every fail-closed path I could drive — warm canary failure, cold
canary failure, neutering-install failure, missing capability booleans — lands in `red` / `lockdown=full` /
`vault-operations=refused`. The canary is genuinely immune to the DNS-failure objection that sank the earlier
design: a rejected fetch with no `securitypolicyviolation` yields `passed=false`. Green, amber and red are all
reachable and distinguishable, and the banner tracks a silent `navigator.onLine` flip in 1.1 s — comfortably
inside the roadmap's 5 s.

It still fails, on three independent grounds. **Evidence integrity:** the packet pastes output for
`npm run verify-vendor` that the command cannot emit and that its own committed self-review contradicts (F2), and
that self-review sits at the path the protocol reserves for me, declaring PASS with zero findings on a commit two
short of the branch tip (F1). **Coverage:** the two properties this PR exists to establish — exact canary
matching and cold-realm runtime neutering — have no test that can fail. I loosened the canary to a substring
match and deleted two of the five blockers, and `npm test` stayed at 24/24 with a clean build both times (F3,
F4); the harness that would nominally cover them matches on directive rather than URL and accepts
DNS-failure-shaped evidence as proof of blocking (F6). **Substance:** the neutering does not hold up to the
adversarial probing the packet invites — `Navigator.prototype.sendBeacon` and `Window.prototype.fetch` recover
the natives and raise no alarm at all, and a fresh realm is unaffected (F5). CSP still blocks the traffic, so this
is defense-in-depth rather than a leak, but `csp-policy.md` promises a loud alarm that these routes do not ring.
Three docs are left contradicting the shipped behaviour (F7, F8, F9).

Separately and independently: **A1 and D4 are unverifiable in this environment.** `npm run test:browser` cannot
run — no browser binaries, and `npx playwright install` is blocked with HTTP 403 — so every browser-observable
claim in this packet is unreproduced, and jsdom/Node shims enforce neither CSP nor iframe sandbox and cannot
stand in. Under `review-protocol.md:33`, a criterion that cannot be verified is a FAIL regardless of the findings
above.

**To turn this into a PASS:** (1) move the author self-review off the reviewer path and re-issue the packet's
command transcripts as literal output, reconciled with each other; (2) add Node tests that fail when the canary
match is loosened and when any of the five blockers is removed; (3) tighten the harness to assert the observed
`blockedURI` and to require the guard's own `threw` signal rather than anything DNS could produce; (4) either
extend the neutering to the prototype-side members or bring the packet and `csp-policy.md` down to what is
actually enforced; (5) update SPEC.md:252 and architecture.md:126 and add the cold-only stripped fixture; and
(6) re-run `npm run test:browser` and `npm run verify-vendor` (with upstream) on a machine with browser binaries
and registry access, pasting the real output — including the actual `blockedURI` and `effectiveDirective` strings
Chromium and Firefox emit, since the exact match in `src/airgap.js:17-23` will lock down a healthy build if either
engine reports an origin-only URI or a full-directive-text form.

Re-review will be a fresh verdict on the new commit, not an amendment to this one.
