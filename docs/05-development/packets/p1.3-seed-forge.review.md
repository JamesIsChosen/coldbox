## 4. Findings

### F1 — Japanese BIP-39 seed derivation does not match the official vector

**Severity:** blocking cryptographic correctness  
**Location:** `src/cold/seed-forge.js` (`seedMnemonic()`, `mnemonicToSeed()`); `docs/05-development/adr/0028-cold-only-bip39-seed-forge.md`; `docs/05-development/packets/p1.3-seed-forge.md`; `test/seed-forge.test.js`

**Observed:** The reviewer executed the current official Trezor/python-mnemonic first vector for every supported language. Japanese mnemonic generation and entropy decoding are correct, but PBKDF2 seed derivation is wrong.

```text
official Japanese expected seed:
5a6c23b5abdd5c3e1f7d77ad25ecd715647bdafb44dab324c730a76a45d7421d
accee1a4ff0739715a2c56a8a9f1e527a5e3496224d91293bfcd9b5393bfff83

PR #36 actual seed:
edaec723855a2824a36ccd6ba2d4358e979f54a455b58961fee21267627cabd9
185d0dc815b7c3cc62bd7104ba7abbeec854658c7afca634cdf9e0a2cd0bce8f
```

The implementation first NFKD-normalizes input, splits it, then `seedMnemonic()` re-joins Japanese words with U+3000 immediately before PBKDF2. That reconstructed mnemonic is not NFKD-normalized again. BIP-39 requires the mnemonic sentence used as the PBKDF2 password to be UTF-8 NFKD.

The current project test checks only that Japanese output contains U+3000 and round-trips entropy. It never checks the official Japanese derived seed, so the existing 265-test suite and browser harness both miss the defect.

**Expected:** Every supported language must match the official BIP-39 seed derivation, including Japanese normalization.

**Required action:** Build the final PBKDF2 mnemonic text according to BIP-39 NFKD rules after separator reconstruction, then add at least one official Japanese mnemonic + `TREZOR` seed vector as a permanent regression test. Correct ADR-0028 and packet language that currently says U+3000 is retained for PBKDF2 if that statement is incompatible with the normalized password bytes actually required by BIP-39. Re-run all ten official language vectors independently.

### F2 — A user-created Entropy Lab Mix cannot be consumed by Seed Forge

**Severity:** blocking workflow/integrity  
**Location:** `src/cold/main.js` Entropy Lab Mix handler, `generateSeedPhrase()`; `src/cold/index.html`; ADR-0023/ADR-0028 and user-facing copy

**Observed:** Pressing Entropy Lab **Mix** calls:

```text
mixed = entropyLab.mix(entropySession, targetBits)
setEntropyMixOutput(mixed)
```

The byte array is only displayed as hex and is not retained for Seed Forge. The local `mixed` variable goes out of scope.

Later, pressing **Generate seed phrase** in Seed Forge calls `entropyLab.mix(entropySession, targetBits)` again after replenishing CSPRNG bytes. That creates a new mixed result. It does not consume the exact mix the user just reviewed.

This directly conflicts with the shipped user-facing status after manual Mix:

> Seed Forge can now turn this into a BIP-39 phrase inside the sealed realm.

It also defeats the intended human flow: collect/manual input → Mix → inspect exact mixed bytes → explicitly use that exact mix in Seed Forge.

**Expected:** The exact mixed entropy produced by the user's explicit Mix action can be handed to Seed Forge without crossing the cold boundary and without silently re-mixing.

**Required action:** Add a cold-local, ephemeral pending-mix handoff. After a successful manual Mix, expose a **Use this mix in Seed Forge** action. Retain the exact bytes only inside the cold realm; consuming them must not invoke `mix()` again. The pending mix should be one-shot or otherwise have explicit reuse semantics, should be zeroized when consumed/replaced/locked/torn down, and target-size mismatches must fail closed. Update the browser harness to prove the mnemonic is derived from the exact manually mixed bytes, not from a second mix.

Do not implement this as a warm-shell message. Entropy Lab and Seed Forge already share the same cold document.

### F3 — Passphrase edits clear fingerprints but cannot keep the current generated wallet identity recalculated

**Severity:** blocking P1.3 passphrase/fingerprint workflow  
**Location:** `src/cold/main.js` passphrase input listeners, `calculateGeneratedFingerprint()`, `updateValidationStatus()`

**Observed:** Both passphrase `input` listeners do this:

```text
setFingerprintOutput(seedForgeGeneratedFingerprint, 'Not calculated')
setFingerprintOutput(seedForgeValidationFingerprint, 'Not calculated')
```

They validate equality, but do not recalculate either fingerprint.

For an existing phrase, the user can click **Validate phrase** again to force a recalculation. For a generated phrase there is no equivalent "recalculate fingerprint for this same phrase" action. Pressing Generate again calls the entropy path and can create a different phrase.

The maintainer explicitly requires the fingerprint to update when the BIP-39 passphrase changes, provided recalculation remains entirely inside the sealed realm.

**Expected:** Once a valid/generated mnemonic is present, the displayed master fingerprint corresponds to the currently confirmed passphrase pair. A passphrase mismatch clears derived output; a matching pair recalculates the same mnemonic's fingerprint without generating a new mnemonic.

**Required action:** Recalculate derived state for the current generated mnemonic and current valid validation mnemonic whenever the two passphrase fields become identical. A short cold-local debounce is acceptable to avoid UI churn. Keep PBKDF2 seed/private BIP-32 material cold-only, do not log it, zero temporary byte arrays, and clear derived output immediately on mismatch/session teardown. Add Chromium and Firefox assertions that passphrase A → passphrase B changes the fingerprint for the same mnemonic and that mismatch clears it.

There is no inherent realm-boundary reason to avoid this recalculation if it stays entirely inside the cold document.

### F4 — Maintainer-required raw BIP-39 seed output is absent

**Severity:** blocking product requirement added during review  
**Location:** `src/cold/index.html`, `src/cold/main.js`, `src/cold/seed-forge.js`, SPEC/ADR-0028/help content

**Observed:** Seed Forge internally derives the 64-byte BIP-39 seed in `mnemonicToSeed()` only as an intermediate used to build the BIP-32 master key/fingerprint. The UI exposes the mnemonic and fingerprint but no raw Seed Forge key material analogous to Entropy Lab's mixed-entropy hex output.

During this review the maintainer explicitly required Seed Forge to expose a raw output as well. At the P1.3 layer, the unambiguous raw derivation output is the **64-byte BIP-39 seed derived from mnemonic + optional passphrase**. That is distinct from:

- the 128–256-bit pre-BIP-39 mixed entropy;
- the BIP-32 master private extended key (`xprv`);
- extended public keys such as `xpub`/`ypub`/`zpub`;
- WIF, addresses, or account/path derivations.

**Expected:** P1.3 provides the requested raw BIP-39 seed output without weakening the cold boundary.

**Required action:** Amend the P1.3 SPEC/ADR/help contract to name the exact raw value, then expose the 64-byte BIP-39 seed only as an advanced cold-only secret surface: masked by default, explicit reveal, short auto-remask, no warm-shell message, no clipboard/storage path in this item, and cleared/zeroized on mismatch, lock, regeneration, and session teardown. Browser tests must verify conceal/reveal/remask/teardown and that changing the passphrase changes both seed and fingerprint consistently.

`xprv`/`xpub`/`ypub`/`zpub` and script/path-specific derivation outputs are not added to this finding. The current roadmap assigns the derivation engine and Bitcoin script types to P1.4; those should stay there unless the maintainer deliberately changes roadmap scope.

## 5. Verdict rationale

PR #36 cannot pass. The most serious defect is cryptographic: the supported Japanese BIP-39 path produces a seed that disagrees with the official vector, while the current project tests falsely report all-ten-language success because they never test Japanese seed derivation. Separately, the end-to-end cold workflow is incomplete: a user-created Entropy Lab mix cannot be consumed as that exact Seed Forge input, generated-wallet fingerprints do not recalculate when the confirmed passphrase changes, and the maintainer-required raw BIP-39 seed output is absent.

The rest of the security foundation reviewed here is strong enough to isolate these findings: vendor provenance passes, deliberate vendor corruption fails closed, builds are reproducible across independent paths/locales/timezones, `src/protocol.js` is unchanged, no `Math.random()` call appears in the cold realm, the reviewer boundary scan is clean, and the full Chromium/Firefox `file://` harness passes. Those successes do not offset the findings under the repository's binary review protocol.

To reach PASS, the author must address F1-F4, preserve this FAIL report unchanged, keep P1.3 `[~]`, update the packet/spec/ADR/help where the behavior contract changes, add regression/browser evidence for every finding, and request a fresh independent review at a new exact commit.

## 4. Findings

### F5 — Validate Existing Phrase lacks an independent passphrase/fingerprint workflow

**Severity:** blocking workflow and wallet-identity integrity

**Location:** `src/cold/index.html` Seed Forge passphrase and validator sections; `src/cold/main.js` `refreshSeedForgeDerivations()` and passphrase listeners; `scripts/run-browser-harness.js`

**Observed:** The page contains one optional BIP-39 passphrase + confirmation pair before the Generated Phrase and Validate Existing Phrase sections. The validator section itself contains the mnemonic input, word fields, Validate button, validated fingerprint, and validated raw-seed output, but no passphrase or confirmation inputs.

The code then reads that one shared passphrase and, inside the same `refreshSeedForgeDerivations()` call, recalculates both:

```text
generated mnemonic -> generated raw seed + generated fingerprint
validated mnemonic -> validation raw seed + validation fingerprint
```

The browser harness confirms the coupling: to test a validated phrase with `TREZOR` or another passphrase, it fills the same `#cold-seed-forge-passphrase-input` and `#cold-seed-forge-passphrase-confirm` fields used by generation.

Therefore, if a generated phrase is still present and the user enters the passphrase for an unrelated existing phrase they are validating, the generated phrase's displayed raw seed/fingerprint are also recalculated under the validator's passphrase. The crypto stays sealed, but the two wallet-identity workflows are not independently scoped.

**Expected:** `Validate an existing phrase` is a complete, self-contained flow: mnemonic + its own optional BIP-39 passphrase + confirmation -> validated raw seed + validated master fingerprint. Its passphrase state must be independent from the generated-phrase passphrase state.

Changing or mismatching the validation passphrase must update/clear only validation-derived outputs. It must not change the generated phrase's raw seed/fingerprint. Likewise, changing the generated-phrase passphrase must not mutate the validated phrase's derived outputs.

**Required action:** Add a validator-scoped passphrase and confirmation pair inside the Validate Existing Phrase section and give generation and validation separate cold-local passphrase state, error state, listeners, and derivation refresh paths. Keep both entirely inside the cold realm. On mismatch, clear only that flow's derived raw seed/fingerprint. On matching edits, rederive only that flow.

Update Chromium and Firefox coverage to keep a generated phrase and a different valid phrase active simultaneously, assign different passphrases to each, and prove:

1. each fingerprint/raw seed matches its own phrase + passphrase;
2. changing the validator passphrase changes only validation outputs;
3. changing the generated passphrase changes only generated outputs;
4. mismatch in one flow clears only that flow;
5. teardown clears both passphrase pairs and both derived-secret surfaces.

Update user-facing Seed Forge/help copy so the generated and validation passphrase controls are unambiguous.
