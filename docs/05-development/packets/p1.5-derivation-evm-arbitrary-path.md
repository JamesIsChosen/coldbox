# P1.5 — Derivation: EVM and generic arbitrary-path mode

## Summary

- Roadmap item: [P1.5 — Derivation: EVM and generic arbitrary-path mode](../ROADMAP.md#phase-1--core-wallet)
- Branch: `p1.5-derivation-evm-arbitrary-path`
- Dependency/base: `p1.4-derivation-engine-bip32-bitcoin`
- Implementation commit: `981778c` (`Add cold-only EVM and arbitrary-path derivation`)
- Scope: cold-realm EVM derivation, ERC-55 formatting/validation, account-xpub watch-only derivation, and generic BIP-32 arbitrary-path projections. No warm UI or new cross-realm message is added.

P1.5 extends the P1.4 cold derivation module with Keccak-256 and EIP-55, standard EVM account paths, public EVM watch-only batches, and a deliberately named generic recovery API. The generic seed API returns raw private/public keys, xprv/xpub, and compressed WIF to its cold-local caller because unknown-coin recovery needs those values; the public EVM/xpub APIs contain no private material.

## Security impact

This change is security-sensitive. An incorrect EVM address can send funds to an unrelated account, and an incorrect arbitrary-path key or WIF can make a recovery attempt fail.

- Keccak-256 is loaded only in the cold crypto bundle; the build fails if the required function is unavailable.
- EVM seed derivation, account xpub derivation, and generic private-key derivation run only in `src/cold/derivation.js`.
- The EVM result and xpub result contain addresses, paths, xpubs, and public fingerprints only.
- The generic private projection is explicitly secret-bearing and remains a cold-local API. It is not included in any warm/cold message, public projection, vault collection, or UI result.
- Intermediate seed/HDKey state continues to be wiped through the P1.4 derivation engine. Public-key copies used for address formatting are cleared after each address.
- ERC-55 hashes lowercase ASCII hexadecimal address text, not the `0x` prefix, compressed public key, or mixed-case text.
- Generic WIF uses the selected Bitcoin network's version byte and the conventional compressed-key marker; invalid key lengths and paths reject.
- Canonical path parsing, 1,000-address batch limits, non-hardened watch-only restrictions, and EVM account-depth checks fail closed.
- No new message type, CSP relaxation, network request, runtime dependency, or warm secret storage was added.

## Assumptions and scope decisions

1. P1.5 is an engine/API item, not a warm UI item. The roadmap line has no separate UI acceptance criteria, and the architecture requires the private generic projection to stay cold-local. Later UI work must consume only public EVM/xpub results.
2. EVM uses the registry's one-address-per-EVM-chain model. Chain IDs are metadata and do not alter the secp256k1 derivation or address.
3. EVM watch-only input is a mainnet account-level xpub at depth 3. The public xpub does not prove a master fingerprint; the result reports the account fingerprint and leaves the master `fingerprint` null.
4. The generic mode uses BIP-32/secp256k1 and compressed WIF. Ed25519/SLIP-0010, multisig, descriptors, and custom address schemes remain later roadmap items.
5. The generic private projection is intentionally not a public-safe result. Any caller that crosses the realm boundary with it violates the architecture contract and must be rejected in future protocol work.

If any assumption changes, the API contract, protocol review, and ADR-0030 must be revisited together.

## What a reviewer should scrutinise hardest

1. The exact Keccak input and output slicing: uncompressed key body without the prefix, last 20 digest bytes, lowercase ASCII for ERC-55, and per-nibble casing.
2. The distinction between all-lower/all-upper accepted EVM text and mixed-case checksum validation; future address verification must preserve that distinction.
3. The secret-bearing generic projection: raw private bytes, xprv, and WIF must never reach a warm result, message, or public vault collection.
4. Account xpub depth/path semantics and watch-only path reporting, including hardened account indices represented by BIP-32's high bit.
5. Cleanup on exceptional paths around private-key copies and intermediate HDKey objects.
6. The pinned `@noble/hashes` bundle graph: `sha3.js` must be included without a new runtime fetch or unverified artifact.
