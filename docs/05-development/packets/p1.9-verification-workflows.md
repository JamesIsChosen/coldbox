# PR packet — P1.9 Verification workflows

**Status:** STOPPED — self-review FAIL on the second browser round. This
branch is intentionally partial and must not be treated as a completed P1.9
implementation.

## 1. Summary

P1.9 adds a cold-local Verify Bench for device fingerprints, receive
addresses, account xpubs, metal backups, and BIP-39 passphrases. Secret inputs
stay in the opaque cold frame, public comparisons are full-value comparisons,
and the existing lock/panic teardown clears the inputs. The batch stopped
after the second consecutive browser-gate failure, before P1.10 or P1.11.

Roadmap item: [P1.9](../ROADMAP.md).

## 2. Scope

In scope:

- Cold-only `src/cold/verification.js` using the existing Seed Forge and
  Bitcoin derivation APIs.
- Five sealed workflows with public match/mismatch results and secret-input
  clearing after every attempt and on cold session teardown.
- The warm Verify Bench route's non-secret explanation and the updated
  three-depth hardware-wallet guide.
- Official-vector unit tests, negative tests, the build manifest entry, and
  Chromium/Firefox harness coverage.
- ADR-0034 documenting the cold-local/manual boundary.

Deliberately not in scope:

- WebHID, WebUSB, vendor transport, signing, or device authenticity claims.
- P1.11 address verification state, P1.12 clipboard round trips, or P1.13
  clipboard volatility.
- Real hardware-wallet validation. The roadmap explicitly leaves that gate to
  physical devices.

## 5. Security impact

- **Realm boundary:** yes. All secret-capable inputs are created and read in
  the cold frame; the warm shell has no verification API or secret form.
- **Message schema:** no new message type. Verification never uses the
  warm/cold channel.
- **CSP:** no new host. The cold `connect-src 'none'` policy remains intact.
- **Vault format:** no change.
- **Derivation:** yes. The module reuses the already-reviewed cold BIP-39 and
  BIP-32 implementations and returns only public fingerprints, xpubs,
  addresses, paths, and verdicts.

If this boundary were wrong, a compromised warm shell could capture a seed or
passphrase entered for verification. The source test asserts that the
verification module has no `postMessage`, `window.parent`, or message-port
dependency; independent review must still inspect the assembled cold script.

## 8. Assumptions made

- P1.9's software surface can remain cold-local because the spec and ADR-0006
  make Coldbox a companion rather than a hardware transport.
- The initial UI supports English BIP-39 input; Seed Forge's existing language
  support is not duplicated in these forms.
- Receive-address verification uses an account-level Bitcoin xpub plus an
  explicit network, script type, chain, and index. P1.12 owns the later
  registry-linked address state and clipboard comparison.
- Bech32 case is normalized for receive comparison; Base58 and extended keys
  remain case-sensitive. This is documented in ADR-0034 and the guide.

## 9. What to scrutinise

1. The cold-frame event wiring and sandbox permissions: the first browser
   failure demonstrated that ordinary form submission is not available in the
   intentionally opaque frame.
2. The collapsed `<details>` workflows and their browser-harness interaction;
   this is the unresolved second-round FAIL.
3. `clearVerificationSession()`'s placement in the shared lock/idle/panic
   teardown, and whether every secret input is cleared on every path.
4. The wrapper's use of ordinary JavaScript equality and the precise
   Bech32-only normalization; do not let this be mistaken for P1.12's
   checksum-aware clipboard authority.
