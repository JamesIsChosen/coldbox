## 4. Findings

### F1 — Recovery-share configuration can race `save()` and produce a vault whose ciphertext authenticates different AAD than the serialized header/records

**Severity:** blocking  
**Location:** `src/cold/vault.js` — `createVaultSession()`, `configureRecoveryShares()`, `save()`; `src/cold/main.js` — `handleVaultMessage('vault.saveRequest')`

**Observed:**

The session has a `saving` flag, and `configureRecoveryShares()` refuses to start if `saving` is already true. The inverse is not protected.

`configureRecoveryShares()`:

1. checks `saving`;
2. generates method-3 metadata;
3. starts an asynchronous AES-GCM rewrap of the DEK;
4. after the `await`, swaps `state.headerBytes`, `state.wrappedBlock`, and `state.recoveryMethodData`.

It never marks a configuration mutation as in progress and does not re-check `saving` before swapping state.

`save()` can therefore start after configuration has begun. It:

1. sets `saving = true`;
2. snapshots `aad = compartmentAad(state.headerBytes, state.recoveryMethodData)`;
3. asynchronously encrypts the public/secret compartments with that AAD;
4. at final assembly, reads the *current live* `state.headerBytes` and `state.wrappedBlock` rather than snapshots that correspond to the AAD it used.

A deterministic interleaving is therefore possible:

1. configuration begins and pauses in the DEK-rewrap AES call;
2. `save()` begins, captures the old header/method-data AAD, and pauses in compartment encryption;
3. configuration resumes and swaps in the new recovery-marked header/wrapped block/method data;
4. `save()` resumes and concatenates those new serialized bytes with ciphertext authenticated under the old AAD.

The returned `.cbx` is internally inconsistent and should fail authentication when reopened.

The cold `vault.saveRequest` handler does not consult cold `vaultBusy`. A warm save can also be reachable while the vault was already dirty before recovery configuration, so correctness cannot rely on the normal UI's timing.

**Expected:**

Recovery configuration and save must be atomic with respect to one another. A successful save may never serialize header/method metadata different from the exact AAD used for the ciphertext in that same file.

**Required action:**

Add a vault-session operation/mutation lock or generation token shared by `configureRecoveryShares()` and `save()`. If one operation begins first, the other must reject or queue without interleaving. `save()` should either snapshot all header/wrapped-block/method-data bytes used by the save or verify an unchanged session generation before final assembly.

Add a deterministic hostile regression that delays AES operations to force exactly this interleaving. The test must prove the operations cannot produce a corrupt artifact and that the legal post-configuration save reopens by both normal and recovery routes.

### F2 — A mixed or tampered surplus recovery share can be supplied and silently ignored while the vault still unlocks

**Severity:** blocking  
**Location:** `src/cold/vault.js` — `recoveryDekForRecord()`; `test/vault.test.js` P2.5 recovery test

**Observed:**

`recoveryDekForRecord()` decodes every supplied share and checks its public metadata and member-index bounds. It then selects only:

- the first `groupThreshold` usable groups; and
- the first `memberThreshold` members in each selected group.

Only that trimmed `usableShares` subset is passed to `slip39.recover()`.

For a single-group 2-of-3 set, this permits the following:

1. generate the vault's real shares with identifier/configuration X;
2. independently generate another 32-byte secret with the same public SLIP-39 metadata X;
3. supply real member 0, real member 1, and foreign member 2;
4. all three shares pass the wrapper's metadata/index/checksum checks;
5. the wrapper sorts members and drops member 2;
6. only real members 0 and 1 reach SLIP-39;
7. the correct DEK is reconstructed and compartment AEAD succeeds.

The caller supplied a mixed set, but recovery succeeds.

The current P2.5 test explicitly calls `openSession(..., configured.shares)` for a 2-of-3 set. It succeeds only because the wrapper trims the third share before the underlying SLIP-39 combine logic, which itself expects exactly the threshold-sized member set.

This defeats the roadmap's explicit requirement that *supplied* mixed/tampered inputs fail closed. It can also create a false physical recovery rehearsal: a user may type all three printed shares, one bad share may be ignored, and Coldbox can report successful recovery without proving that share is usable.

**Expected:**

Every supplied share must be part of the authenticated recovery decision. No supplied share value may be silently discarded in a way that converts a mixed/tampered input set into a successful recovery.

**Required action:**

Prefer the simple fail-closed rule already used by SLIP-39 combining: require exactly the configured threshold groups and exactly the member threshold for every supplied group, rejecting surplus groups/members.

If surplus input is intentionally supported, every surplus share must be cryptographically validated as belonging to the recovered sharing polynomial/set before success; metadata-only validation is insufficient.

Add vault-level negatives for:

- two valid vault shares plus one checksum-valid foreign surplus member with identical public metadata;
- a surplus usable group from a foreign set;
- a checksum-valid modified surplus share;
- selected and non-selected duplicate/index cases.

### F3 — ADR-0040 and the packet require exact member-count matching that SLIP-39 mnemonics do not encode

**Severity:** blocking  
**Location:** `docs/05-development/adr/0040-vault-recovery-share-record.md`; P2.5 roadmap/packet; `src/cold/slip39.js` `decodeMnemonic()`; `src/cold/vault.js` `recoveryDekForRecord()`

**Observed:**

Method 3 records each group's:

- member threshold; and
- member count.

ADR-0040 says every supplied share must exactly match each group's “member threshold/count.”

The standard SLIP-39 mnemonic encodes identifier, extendable flag, iteration exponent, group index, group threshold, group count, member index, member threshold, share value, and checksum. It does **not** encode the group's total member count `N_i`; total member count is an input to share generation, not a mnemonic field.

Coldbox's own `decodeMnemonic()` reflects the standard and returns no member-count property.

Consequently `recoveryDekForRecord()` cannot compare a decoded share's total member count to `metadata.groups[i].count`. It can only use the stored count as an upper bound on `decoded.memberIndex`.

The packet's statement that the decoder checks “every recorded SLIP-39 field” / exact member threshold-count therefore overstates what the wire format permits.

**Expected:**

The normative contract must only demand equality for fields actually encoded in a share, unless Coldbox adds another authenticated source that proves the generation-time member count.

**Required action:**

Resolve this normatively before code remediation is declared complete:

- either amend the roadmap/ADR/vault-format wording so exact equality applies to mnemonic-encoded SLIP-39 fields, while stored member count is explicitly a Coldbox generation policy used to bound member indices; or
- introduce an authenticated mechanism that can actually prove total member-count equality if that equality is a required security property.

Update tests and packet language to match the chosen contract. Do not silently reinterpret the existing “exact member threshold/count” wording.

### F4 — P2.5 expands root-DEK/wrapping-key lifetime beyond the ADR's stated need, including retaining the DEK in recovery-only sessions that cannot reissue shares

**Severity:** blocking  
**Location:** `src/cold/vault.js` — `openVaultSession()`, `createVaultSession()`, `close()`, `save()`; ADR-0040 Binding and recovery

**Observed:**

Before P2.5, `openVaultSession()` derived compartment subkeys, constructed the session without the root DEK, and zeroed the DEK in `finally`.

P2.5 now copies `dek` into every session. For normal offline unlock it also copies the normal wrapping key into the session. Those root materials are zeroed only when the session closes.

This creates two unnecessary/overbroad lifetimes:

1. A recovery-only session receives and retains `state.dek` even though `wrappingKey` is null and `canConfigureRecoveryShares()` is false. That session can never reissue a share set, so retaining the root DEK serves no P2.5 reconfiguration purpose after the compartment subkeys have been derived.
2. A normal offline session retains both the root DEK and normal wrapping key even after a recovery configuration has been saved. ADR-0040 describes retaining the DEK “long enough to issue a new share set and save the updated encrypted vault,” not for the entire unlocked-session lifetime after that operation is complete.

This is a security-sensitive regression in secret lifetime relative to the pre-P2.5 session design.

**Expected:**

Root key material should exist for the minimum operation that requires it and be zeroed when that authority is no longer needed.

**Required action:**

At minimum, do not place the root DEK in a recovery-only session once its compartment subkeys are derived.

For normal sessions, narrow the root-DEK/wrapping-key lifetime to the recovery configuration/save operation. If later reconfiguration during the same session is required, use an explicit re-authentication/on-demand design rather than retaining the highest-value keys indefinitely. If the project deliberately chooses whole-session retention instead, that broader security decision must be explicitly justified and accepted in ADR-0040 rather than contradicting its present wording.

Add tests proving the selected lifetime and that `close()`/post-save paths make re-use impossible as specified.

### F5 — A forced lock during asynchronous recovery configuration can be overwritten by a stale callback that reports the vault as “unlocked”

**Severity:** advisory  
**Location:** `src/cold/main.js` — `configureVaultRecoveryShares()`, `mode.set` handling, `clearVaultSession()`

**Observed:**

During recovery configuration, the UI sets `vaultBusy = true` and waits on `currentVaultSession.configureRecoveryShares()`.

If a `mode.set` transition changes the device to online while that operation is pending:

1. the mode handler calls `lockVaultSession(...)`;
2. the session is closed, `vaultUnlocked` becomes false, and status is set to locked;
3. the vault-layer configuration correctly fails its post-`await` closed/network check;
4. the UI promise's `.catch()` unconditionally calls:
   `setVaultStatus('unlocked', 'Recovery-share generation failed; the existing vault remains unchanged.')`.

The underlying vault remains closed, but the cold UI's state/status is rewritten to “unlocked” after the terminal lock.

**Expected:**

A stale asynchronous completion must never overwrite a newer lock/mode/health transition.

**Required action:**

Bind recovery configuration to the initiating session/generation. Before changing status or generated-share state in any async completion, verify the operation still belongs to the current unlocked offline session. A completion after lock/mode/health teardown must be a no-op except for zeroing temporary material.

Add a deterministic test that pauses recovery configuration, transitions online/locks the session, releases the operation, and asserts the UI remains locked with no generated shares or stale “unlocked” state.

## 5. Verdict rationale

P2.5 is **not ready to merge** at `f277d791...`.

The remaining findings show that the browser, mobile, compatibility, packet, and reviewer-owned evidence is not strong enough to close a vault-format feature under this repository's review rules.

A future PASS requires all findings to be fixed or explicitly dismissed with accepted reasoning, the P2.5 browser/mobile evidence completed, the packet refreshed to the exact remediated head, and a fresh independent reviewer to execute the mandatory clean-checkout workflow.

### R2-F2 — ADR-0040 overclaims zeroization of the re-supplied normal credentials

**Severity:** advisory — must fix under the binary review protocol  
**Location:** `docs/05-development/adr/0040-vault-recovery-share-record.md` — Binding and recovery; `src/cold/vault.js` `configureRecoveryShares()`; `src/cold/main.js` `configureVaultRecoveryShares()`

**Observed:**

ADR-0040 currently says that reissuing recovery shares requires the normal
passphrase/keyfile to be supplied again and:

> those credentials unwrap the DEK only for the configuration operation and
> are zeroed before it returns.

The runtime design successfully fixed original F4's important issue: the
unlocked session no longer retains the root DEK or normal wrapping key.
`configureRecoveryShares()` uses local mutable copies and its `finally` zeroes
the copied keyfile, local DEK, wrapping key, header/wrapped-block snapshots,
nonce/wrapped-key buffers, and other temporary byte arrays.

But the normal passphrase supplied as `value.normalPassphrase` is a JavaScript
string. JavaScript strings are immutable; the function does not and cannot
overwrite the bytes backing that string. The cold UI clears the input and
drops/reassigns its local string reference after the asynchronous operation,
which is useful lifetime reduction, but that is not equivalent to cryptographic
zeroization of the credential.

The ADR therefore states a stronger memory-lifetime guarantee than the
implementation/runtime can make.

**Expected:**

Security documentation must distinguish between:

- mutable secret byte buffers that are explicitly overwritten;
- UI/local references that are cleared or dropped; and
- immutable JavaScript strings whose backing storage cannot be guaranteed
  zeroized by application code.

**Required action:**

Correct ADR-0040 (and any duplicate wording, if present) to state the guarantee
the implementation actually provides: the credential is used only for
on-demand re-authentication, mutable derived/keyfile/key buffers are explicitly
zeroed, and UI/local passphrase references are cleared/dropped after the
operation, without claiming the immutable JavaScript string itself is
zeroized.

Alternatively, if literal credential zeroization is a required guarantee,
redesign the credential API around mutable byte buffers and prove their
lifetime/overwrite behavior. Do not leave the current absolute wording.
