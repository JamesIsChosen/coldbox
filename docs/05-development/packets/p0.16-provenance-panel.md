# P0.16 — Provenance panel and self-hash verifier

Branch: `p0.16-provenance-panel`
Roadmap item: [P0.16](../ROADMAP.md) (deps: P0.15, satisfied)

## 1. Summary

Adds a Reference → Provenance panel that lists every embedded vendor library (generated at build time from `vendor/vendor-manifest.json`), the live CSP allowlist for both realms, a commit-derived build date, and a drag-and-drop self-hash drop zone that states plainly that self-verification is circular.

## 2. Scope

**In:** the provenance panel UI (`src/index.html`, `src/main.js`, `src/styles.css`), the build-time generation of its data (`scripts/build.js`: library list, build date, blank-then-hash expected-hash injection), the browser-harness coverage for the drop zone (`scripts/run-browser-harness.js`), `test/provenance.test.js`, ADR-0015, and the roadmap/dependencies/changelog updates that describe this.

**Not in this PR:** any change to the vault format, the cold/warm message schema, or existing crypto paths — the panel only reads already-existing data (vendor manifest, live CSP meta tag, the document's own bytes) and does not touch key material.

## 5. Security impact

- **Realm boundary / message schema / vault format / derivation / randomness:** no. This panel only reads data that already exists in the assembled document (vendor manifest contents baked in at build time, the live CSP meta tag, the document's own bytes) and computes a hash over bytes already present client-side. It introduces no new message type between realms and touches no secret material — no mnemonic, key, passphrase, or vault plaintext is read, displayed, or hashed by this feature.
- **If this implementation is wrong:** the worst case is a misleading provenance display — e.g., a stale library entry, an incorrect CSP transcription, or a self-hash that silently always "matches" due to a bug in the blank-then-hash logic (which would defeat its limited corruption-detection value, though it was never meant to defeat a malicious build — the UI says so). None of these failure modes expose secret material or weaken the CSP itself; they only weaken the *user's ability to notice* something is wrong via this in-app panel. The independent checks (`verification.md` — command-line hash comparison against a separately published `.sha256`, from-source rebuild) remain the actual security-relevant checks and are unaffected by any bug here.
- **New `connect-src` host:** none. No network calls are made by this feature; it operates entirely on already-loaded data.
- **New message type:** none.

## 6. Test evidence

- **New tests:** 11 new tests in `test/provenance.test.js`, plus 4 tests added/extended in `test/build.test.js` covering the same build-date and self-hash mechanisms from the build script's side. Full list and what each proves is in the test files themselves (descriptive test names above under §4 double as the proof-per-criterion mapping).
- **Vector sources:** this feature has no cryptographic vectors in the BIP/test-vector sense — it's a build-time data-embedding and string-hashing mechanism, not a cryptographic primitive. The "independent" bar here is instead: the build-date test independently re-derives the expected value via a separate `git log` shell-out rather than re-implementing the build script's internal logic, and the self-hash tests independently recompute SHA-256 over a manually blanked copy of the document rather than calling the build script's own hashing function, so a bug in the build script's hash computation would not be masked by the test using the same buggy code path.
- **Negative tests:** "a stray final-document placeholder fails the build before creating output" (build refuses if more or fewer than exactly one placeholder occurrence is found, rather than silently substituting into the wrong location) — this is the fail-closed behavior for a build-time invariant violation. "a single altered byte elsewhere in the file is caught by the blank-then-hash comparison" — deliberately corrupts a byte outside the hash field and confirms the comparison now fails rather than passing.
- **Could not test:** the actual browser drop-zone interaction end-to-end (drag-and-drop file read, DOM update, match/mismatch styling) — Playwright binaries unavailable in this sandbox, see §3.

## 8. Assumptions made

Recorded in full in [ADR-0015](../adr/0015-provenance-build-date-and-self-hash.md):

1. **Build date = source commit date**, not wall-clock build time, to preserve the existing determinism guarantee (`test/build.test.js` already asserts locale/timezone-independent output; a literal timestamp would break it on every subsequent build). Degrades to an explicit "unknown" string, never a build failure, when git metadata is absent.
2. **Expected hash = SHA-256 of the document with its own placeholder meta tag blanked to 64 zero characters**, not the true hash of the final shipped bytes (`coldbox.html.sha256`), because a file cannot contain its own true hash — the two are deliberately different, disclosed quantities, both in the ADR and in the in-app UI copy.

Both were genuinely unsettled by SPEC.md §6.4, which describes the *what* (a build date, an expected hash, a drop zone) and the security *property* (circular, must disclose) but not the *mechanism*. Per AGENTS.md §4 this warranted an ADR rather than a silent implementation choice.

## 9. What to scrutinise

- **The browser-harness drop-zone test is unverified.** I wrote `verifyProvenancePanel` in `scripts/run-browser-harness.js` following the existing patterns in that file (file-upload emulation via `setInputFiles`), and it passed a code read-through, but it has never actually executed against a real browser in this environment. This is the single largest gap in this PR — a reviewer with Playwright binaries available should run `npm run test:browser` and treat a failure there as blocking, not cosmetic.
- **The blank-then-hash construction itself.** This is a nonstandard, self-hash-adjacent mechanism I designed for this PR (documented in ADR-0015) rather than something copied from an existing spec. Worth an adversarial read: is the placeholder length (64 zero characters, matching a hex SHA-256 digest) actually collision-safe against a real digest value that happens to look like the placeholder, and does the "exactly one placeholder occurrence" build-time check actually prevent the substitution from landing in the wrong byte offset if the source ever legitimately contains that string elsewhere (e.g., in a code comment or test fixture)? I added a negative test for the multiple-occurrence case but a reviewer should independently think about whether the check is airtight.
- **Node version mismatch.** Everything above ran on Node 22.22.3, not the pinned 24.16.0. I have no reason to believe this specific feature is Node-version-sensitive (it's mostly string/buffer manipulation and `child_process.execSync('git log ...')`, both stable across these versions), but I did not verify that assumption on the pinned version.
- **This sandbox's environment quirks** (documented for transparency, not because they affect the shipped code): the mount here is FUSE-backed and doesn't support `unlink`, which caused git to intermittently leave stale `index.lock`/`HEAD.lock` files during this session's commits, and left a `build.old.*` directory and a `.git/worktrees/coldbox-before` entry from an ad hoc bundle-size comparison that could not be fully cleaned up (`rm`/`worktree remove` both fail on this filesystem the same way). Neither is part of the committed diff — confirm with `git status --short` before merging that only the intended files are staged.

## 10. Self-assessment

- **What might be wrong:** the untested browser-harness function (see §9) is the most likely place for a real bug — DOM event wiring for drag-and-drop is easy to get subtly wrong in a way that only shows up in an actual browser.
- **What I didn't do that arguably should have been done:** any manual cross-browser testing (§7); running on the pinned Node version; actually running the online `verify-vendor` check.
- **Known limitations shipping with this change:** the expected-hash field, while accurately labeled and explained, is a second hash value in the UI distinct from `coldbox.html.sha256`, which is a plausible source of confusion if the in-app copy is ever weakened later (flagged as a risk in ADR-0015's Consequences).
- **Follow-up work:** none filed as a new roadmap item — the browser-harness verification gap should be closed by the reviewer (or a follow-up session with Playwright access) as part of reviewing this PR, not deferred to a separate item, since it's coverage for work already claimed as done in this PR.
