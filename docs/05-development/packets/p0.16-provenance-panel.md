# P0.16 — Provenance panel and self-hash verifier

Branch: `p0.16-provenance-panel`
Roadmap item: [P0.16](../ROADMAP.md) (deps: P0.15, satisfied)

**This packet is a remediation of an independent review FAIL, not the original submission.** The original review report is preserved unedited at [p0.16-provenance-panel.review.md](p0.16-provenance-panel.review.md) — permanent audit history. This document is the mutable working packet, regenerated in place to describe the tip after all six findings (F1–F6) were addressed.

## 1. Summary

Adds a Reference → Provenance panel that lists every embedded vendor library (generated at build time from `vendor/vendor-manifest.json`), the live CSP allowlist for both realms, a commit-derived build date, a visibly-rendered expected hash, and a drag-and-drop self-hash drop zone that states plainly that self-verification is circular and fails closed on corruption anywhere in the file — including inside its own hash field.

## 2. Scope

**In:** the provenance panel UI (`src/index.html`, `src/main.js`, `src/styles.css`), the build-time generation of its data (`scripts/build.js`: library list, build date, blank-then-hash expected-hash injection), the browser-harness coverage for the drop zone (`scripts/run-browser-harness.js`), `test/provenance.test.js`, ADR-0015 and its 2026-08-06 amendment, and the roadmap/dependencies/changelog updates that describe this. This remediation additionally touches `docs/02-security/verification.md` and `docs/05-development/build.md` (F5) and `docs/05-development/ROADMAP.md`'s P0.17 entry (F5's help-content deferral note).

**Not in this PR:** any change to the vault format, the cold/warm message schema, or existing crypto paths — the panel only reads already-existing data (vendor manifest, live CSP meta tag, the document's own bytes) and does not touch key material. No other roadmap item is touched.

## 5. Security impact

- **Realm boundary / message schema / vault format / derivation / randomness:** no. This panel only reads data that already exists in the assembled document (vendor manifest contents baked in at build time, the live CSP meta tag, the document's own bytes) and computes a hash over bytes already present client-side. It introduces no new message type between realms and touches no secret material.
- **If this implementation is wrong:** the worst case remains a misleading provenance display. The F2 fix specifically closes a real gap where a one-byte corruption *inside the hash field itself* previously reported a false `Match` — that was the review's F2 finding, proven with an adversarial single-hex-character mutation, and is now caught by an additional declared-value comparison. None of these failure modes expose secret material or weaken the CSP itself; the independent checks (`verification.md` — command-line hash comparison, GPG signature, from-source rebuild) remain the actual security-relevant checks and are unaffected by any bug here.
- **New `connect-src` host:** none.
- **New message type:** none.

## 6. Test evidence

- **New tests this remediation:** 3 added to `test/provenance.test.js` (14 total in that file): F1's visible-hash-matches-meta-value check (with a static binding to the actual shipped `renderProvenanceExpectedHash`/`provenanceExpectedHash.textContent = expected` code, not just a parallel description), F2's adversarial hash-field-byte-mutation case (proves the old blank-then-hash-only logic would false-PASS, then proves the fixed `declaredHash === expected` check catches it, and binds to the shipped `outcome.declaredHash === expected` comparison in `src/main.js`), and F4's two build-date tests (independent re-derivation scoped to `src scripts vendor`, and a synthetic two-commit git repository proving a docs-only `HEAD` commit does not move the embedded date away from the earlier product commit).
- **Vector sources:** unchanged from the original submission — no cryptographic vectors apply here (build-time data-embedding and string-hashing, not a primitive). Tests independently re-derive expected values via separate git shell-outs and manual byte manipulation rather than calling the implementation's own functions, so a bug in the implementation isn't masked by the test sharing its code path.
- **Negative tests:** the F2 mutation test is the significant new one — it specifically reproduces the exact adversarial case the independent reviewer used to prove the original implementation false-PASSed (flip one hex character inside the declared expected-hash field, confirm the fixed logic reports it as not-a-match). The F4 synthetic-repo test is also a negative case in spirit: it proves a commit that *doesn't* touch product paths is correctly *not* picked up.
- **Could not test:** the actual browser drop-zone interaction end-to-end remains untestable in this sandbox — see F3 in §3 and §9.

## 8. Assumptions made

Recorded in [ADR-0015](../adr/0015-provenance-build-date-and-self-hash.md) and its 2026-08-06 amendment:

1. **Build date = the commit date of the most recent commit touching `src/`, `scripts/`, or `vendor/`** (amended from literal `HEAD` this session — see F4). Still never a build failure when git metadata is unavailable.
2. **Expected hash = SHA-256 of the document with its own placeholder meta tag blanked to 64 zero characters**, unchanged from the original decision — deliberately different from `coldbox.html.sha256`, now visibly disclosed in-app (F1) as well as in the ADR.
3. **F2's fix scope:** the declared-value comparison was added *in addition to* the blank-then-hash comparison, not as a replacement — both must hold for a `Match`. This preserves the original genuine-copy-matches / corruption-elsewhere-mismatches behavior while closing the hash-field blind spot.
4. **F5's help-content deferral** is now recorded in ROADMAP.md rather than only asserted in this packet — see the P0.16/P0.17 entries.

## 9. What to scrutinise

- **F3 remains the single largest open gap.** `verifyProvenancePanel` (including its new F1/F2 assertions) has never executed against a real browser in any session so far, in this repository's history. A reviewer with Playwright binaries available should run `npm run test:browser` and treat any failure as blocking — including a failure in the newly added assertions, which have only been read-reviewed, not run.
- **The F2 fix's completeness.** The fix requires both `computedHash === expected` and `declaredHash === expected`. Worth an adversarial read: is there a mutation that changes the file in a way that keeps *both* values in sync with a stale `expected` while still being corrupt? The blank-then-hash construction means `computedHash` only depends on bytes outside the hash field span; `declaredHash` is read directly from that span. Between them, every byte in the document is covered by exactly one of the two checks — a byte inside the span affects `declaredHash` only, a byte outside affects `computedHash` only. No byte is covered by neither.
- **F4's path list (`BUILD_DATE_SOURCE_PATHS = ['src', 'scripts', 'vendor']`) is a hand-maintained list**, same category of risk as any allowlist. If a future build input lives outside these three directories, a commit to it would silently fail to advance the build date. Documented as a residual risk in the ADR amendment; `test/provenance.test.js` pins the current behavior so a change would need to be deliberate.
- **The blank-then-hash construction itself** — unchanged from the original submission, see the original packet's §9 for the collision/placeholder-length discussion, still applicable.

## 10. Self-assessment

- **What might be wrong:** the untested browser-harness function (F3) remains the most likely place for a real bug in browser-specific DOM/event handling that unit tests in Node can't exercise.
- **What I didn't do that arguably should have been done:** manual cross-browser testing (§7); running on the pinned Node version; actually executing the browser harness (F3, structurally blocked in every sandboxed session so far, not skipped by choice).
- **Known limitations shipping with this change:** the expected-hash field remains a second, distinct hash value from `coldbox.html.sha256` — now visibly disclosed (F1 closes the "not disclosed" gap, but the underlying two-values-in-the-UI design is unchanged and still carries the confusion risk ADR-0015 always flagged).
- **Follow-up work:** F3 (execute the browser harness) needs a network-capable environment — flagged, not filed as a separate roadmap item, since it's coverage for work already claimed in this item, per the original packet's reasoning (unchanged by this remediation). P0.17's backfill obligation for three-depth help content (F5) is now tracked in ROADMAP.md under P0.17 itself, not a new item.
