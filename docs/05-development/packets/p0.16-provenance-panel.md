This document is the mutable working packet, now corrected per R3-F1 — see §3 for the corrected evidence and §9/§10 for what that correction means for trusting the rest of this document.

## 1. Summary

Adds a Reference → Provenance panel that lists every embedded vendor library (generated at build time from `vendor/vendor-manifest.json`), the live CSP allowlist for both realms, a commit-derived build date, a visibly-rendered expected hash, and a drag-and-drop self-hash drop zone that states plainly that self-verification is circular and fails closed on corruption anywhere in the file — including inside its own hash field.

## 2. Scope

**In:** the provenance panel UI (`src/index.html`, `src/main.js`, `src/styles.css`), the build-time generation of its data (`scripts/build.js`: library list, build date, blank-then-hash expected-hash injection), the browser-harness coverage for the drop zone (`scripts/run-browser-harness.js`), `test/provenance.test.js`, ADR-0015 and its 2026-08-06 amendment, and the roadmap/dependencies/changelog updates that describe this. This remediation additionally touches `docs/02-security/verification.md` and `docs/05-development/build.md` (F5), `docs/05-development/ROADMAP.md`'s P0.17 entry (F5's help-content deferral note), and — after a real-network `npm run test:browser` run surfaced a pre-existing, unrelated fixture bug — `scripts/run-browser-harness.js`'s `verifyDevOnlyDependency()` and a new `test/build.test.js` case (F3 follow-up, see §3).

**Not in this PR:** any change to the vault format, the cold/warm message schema, or existing crypto paths — the panel only reads already-existing data (vendor manifest, live CSP meta tag, the document's own bytes) and does not touch key material. No other roadmap item is touched.

**A second real-network run went further and found a second, independent fixture bug.** Past the `verifyDevOnlyDependency` fix above, the harness reached `verifyCspStrippedLockdown` — the first check that runs inside real Chromium after a long sequence of others already passed (blob round-trip, CSP probe blocking for fetch/XHR/WebSocket, cold-realm network-primitive blocking for fetch/XHR/WebSocket/EventSource/sendBeacon under both build-time and runtime lockdown, the F3 benchmark control, warm shell routing over `file://`, unlocked-runtime airgap zeroization, unlocked save-time health-failure zeroization, warm/cold Escape-Escape concealment, cold-realm creation-failure and readiness-timeout lockdown, typed-handshake-timeout lockdown, and cold-only CSP-stripped lockdown all passed) — and failed there:

```
Browser harness failed: AssertionError [ERR_ASSERTION]: Expected exactly one warm CSP meta tag
2 !== 1
    at stripWarmCsp (scripts/run-browser-harness.js:212:10)
```

`stripWarmCsp()` scans the whole built document for `<meta http-equiv="Content-Security-Policy" ...>` text and asserts exactly one match — a pre-existing fixture assumption. P0.16's `extractCspFromMarkup()` in `src/main.js` (used to read the cold realm's CSP for display, per the "full CSP allowlist" acceptance criterion) has its own regex literal containing that exact tag-shaped substring, which ends up embedded verbatim in the built document's inline `<script>` block once compiled. The document-wide scan legitimately finds two occurrences: the one real `<meta>` element, and the JS source code that describes one as text. Confirmed directly against the real build (without Playwright) that this is exactly what's happening — one match at byte offset 202 (the real tag, in `<head>`) and one at byte offset 576559 (deep inside the `<script>` block, the regex literal's source text). Not a CSP regression — there is still exactly one real CSP meta tag enforced by the browser; the fixture's "this substring appears at most once, document-wide" assumption stopped holding once legitimate application code needed to reference that substring as a string.

**Fix:** scope `stripWarmCsp`'s search to the text before the first `<script>` tag — the document `<head>`, where the one real tag lives and no inline script body can appear. Verified directly against the real build that this finds exactly one match and ignores the JS-source occurrence.

## 5. Security impact

- **Realm boundary / message schema / vault format / derivation / randomness:** no. This panel only reads data that already exists in the assembled document (vendor manifest contents baked in at build time, the live CSP meta tag, the document's own bytes) and computes a hash over bytes already present client-side. It introduces no new message type between realms and touches no secret material.
- **If this implementation is wrong:** the worst case remains a misleading provenance display. The F2 fix specifically closes a real gap where a one-byte corruption *inside the hash field itself* previously reported a false `Match` — that was the review's F2 finding, proven with an adversarial single-hex-character mutation, and is now caught by an additional declared-value comparison. None of these failure modes expose secret material or weaken the CSP itself; the independent checks (`verification.md` — command-line hash comparison, GPG signature, from-source rebuild) remain the actual security-relevant checks and are unaffected by any bug here.
- **New `connect-src` host:** none.
- **New message type:** none.

## 8. Assumptions made

Recorded in [ADR-0015](../adr/0015-provenance-build-date-and-self-hash.md) and its 2026-08-06 amendment:

1. **Build date = the commit date of the most recent commit touching `src/`, `scripts/`, or `vendor/`** (amended from literal `HEAD` this session — see F4). Still never a build failure when git metadata is unavailable.
2. **Expected hash = SHA-256 of the document with its own placeholder meta tag blanked to 64 zero characters**, unchanged from the original decision — deliberately different from `coldbox.html.sha256`, now visibly disclosed in-app (F1) as well as in the ADR.
3. **F2's fix scope:** the declared-value comparison was added *in addition to* the blank-then-hash comparison, not as a replacement — both must hold for a `Match`. This preserves the original genuine-copy-matches / corruption-elsewhere-mismatches behavior while closing the hash-field blind spot.
4. **F5's help-content deferral** is now recorded in ROADMAP.md rather than only asserted in this packet — see the P0.16/P0.17 entries.

Worth checking that this doesn't quietly weaken the "no devDependency needed" property it exists to prove — the fix only adds `.git` (version-control metadata, not a package dependency) to the copy; `node_modules` is still absent and still asserted absent. Also worth checking the new `test/build.test.js` case doesn't overlap so much with the browser-harness version that one becomes redundant maintenance burden — they currently test the same property through different mechanisms (Node-only vs. browser-harness-adjacent), which was a deliberate choice to get coverage of this property into the fast, universally-runnable `npm test` gate.
- **The F2 fix's completeness.** The fix requires both `computedHash === expected` and `declaredHash === expected`. Worth an adversarial read: is there a mutation that changes the file in a way that keeps *both* values in sync with a stale `expected` while still being corrupt? The blank-then-hash construction means `computedHash` only depends on bytes outside the hash field span; `declaredHash` is read directly from that span. Between them, every byte in the document is covered by exactly one of the two checks — a byte inside the span affects `declaredHash` only, a byte outside affects `computedHash` only. No byte is covered by neither.
- **F4's path list (`BUILD_DATE_SOURCE_PATHS = ['src', 'scripts', 'vendor']`) is a hand-maintained list**, same category of risk as any allowlist. If a future build input lives outside these three directories, a commit to it would silently fail to advance the build date. Documented as a residual risk in the ADR amendment; `test/provenance.test.js` pins the current behavior so a change would need to be deliberate.
- **The blank-then-hash construction itself** — unchanged from the original submission, see the original packet's §9 for the collision/placeholder-length discussion, still applicable.
