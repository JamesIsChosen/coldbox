# P2.7 — Backup Health dashboard

## 1. Summary

This branch implements [P2.7](../ROADMAP.md), `Backup Health dashboard`, after
P2.6. It adds a warm-only dashboard for BackupRecord verification schedules,
unsupported methods, missing placement metadata, and repeated public
location/custodian labels. It deliberately reports distributed placement as
threshold-unproven because the current public model has no per-share placement
map.

## 2. Scope

In scope:

- Warm Backup Health summary with locked/unlocked states, metrics, alerts,
  placement assessment, and per-record status.
- Deterministic public-metadata-only health evaluation for current, overdue,
  unverified, unsupported, and invalid records.
- Conservative repeated-location/custodian and missing-placement warnings.
- Existing Backup Lab record labels now distinguish current, overdue, and
  invalid verification status.
- Node tests, Chromium/Firefox `file://` browser assertions, an ADR, a
  three-depth help guide, threat-model/spec wording, changelog, roadmap status,
  and this packet.

Deliberately out of scope:

- No per-share placement schema, survivability percentage, or
  `thresholdReachable` claim. See [ADR-0042](../adr/0042-conservative-backup-health.md).
- No new warm/cold message, secret-compartment field, or vault-format field.
- No media-verification schedule; that belongs to the future file-hasher
  record workflow.
- No device-firmware, descriptor, multisig-quorum, or inheritance-rehearsal
  scoring. The dashboard links and warns about BackupRecords only.
- No support for cold verification of `seedqr`, `metal`, `paper`, or
  `encrypted-file` records; they remain incomplete as defined by P2.6.

## 5. Security impact

| Surface | Impact | Evidence |
|---|---|---|
| Realm boundary | No new boundary crossing. The health module is warm-only and consumes only the already validated public BackupRecord projection. | `test/backup-health.test.js` static warm-only check; build/lint; browser DOM assertions. |
| Message schema | No change. No new message type or payload field was added. | `scripts/build.js` only assembles the warm module; `src/protocol.js` is unchanged. |
| Cold CSP / network | No change. No URL, fetch, storage, or network primitive is used by the module. | `test/backup-health.test.js`; full CSP and airgap suite; `npm.cmd run test:browser`. |
| Vault format / cryptography | No change. `lastVerifiedAt` remains cold-owned P2.6 public metadata; P2.7 only evaluates it. | P2.6 vault and protocol regressions in the full suite; no `src/cold/` or vault-format files changed. |

If this implementation were wrong, the main risk would be a false sense that
a backup is current or physically survivable. The evaluator refuses current
status for invalid required metadata, labels unsupported methods incomplete,
flags overdue timestamps at the exact due instant, and never emits a numeric
survivability or threshold-reachability claim. It also cannot manufacture
`lastVerifiedAt`; only P2.6's cold verification path can provide that field.

No new `connect-src` host, message type, secret carrier, or external service
was introduced.

## 6. Test evidence

New tests in `test/backup-health.test.js` prove:

- Current and overdue states use exact UTC due dates, with the due instant
  treated as overdue.
- Missing verification remains incomplete and has no due date.
- Invalid schedules and timestamps fail closed as `invalid`.
- Physical-only methods such as `metal` remain unverified and explain that no
  in-app reconstruction workflow exists.
- Repeated normalized locations/custodians produce co-location warnings.
- Missing placement produces an unknown assessment.
- Multiple recorded locations are `distributed-unproven`, and the summary
  contains neither `survivabilityScore` nor `thresholdReachable`.
- The source has no DOM, network, crypto, or secret-field handling.

The health feature is metadata logic, not a cryptographic primitive, so it adds
no new independent cryptographic vector. Existing independent P2.6 vectors and
the cold verification tests remain in the full suite; this branch does not
alter those implementations.

Negative coverage includes malformed dates and intervals, unsupported methods,
missing subject/created-at metadata, missing location/custodian, duplicate
placement labels, locked dashboard rendering, and the unresolved-subject
browser flow that leaves a record incomplete and clears cold input.

The browser harness was run after installing the repository-pinned Playwright
Chromium and Firefox binaries. No physical device, mobile browser, or actual
backup share was used for the new dashboard itself.

## 8. Assumptions made

- The P2.6 public model remains authoritative: a BackupRecord has one public
  `location` and `custodian`, not an individual share-placement map. Adding
  such a map would be a new schema decision, so P2.7 uses conservative
  warnings instead. This is recorded in ADR-0042.
- A record's cold-owned `lastVerifiedAt` is evidence of a successful subject-
  bound reconstruction, not proof that the physical media, custodian, or
  location is safe. The UI and guide use that narrower meaning.
- Location and custodian comparisons normalize surrounding whitespace and
  repeated internal whitespace plus case. They are advisory labels, not
  identity proof; differently written labels for the same place can evade a
  duplicate warning.
- Hidden BackupRecords are excluded from the dashboard until the existing
  hidden-record reveal control makes them visible in the unlocked session.
- A valid `lastVerifiedAt` plus `verifyEveryDays` is current strictly before
  the due instant and overdue at or after it. The dashboard evaluates at the
  browser's current time; Node tests supply a fixed UTC time.

## 9. What to scrutinise

- `src/backup-health.js`: the state precedence for invalid metadata,
  unsupported methods, exact due boundaries, and the distinction between
  `single-location`, `unknown`, and `distributed-unproven`.
- The placement grouping: a repeated location or custodian is only a warning,
  while a missing placement makes the subject assessment unknown. Confirm no
  UI sentence accidentally upgrades this to proof of threshold survival.
- `renderBackupHealth` in `src/main.js`: verify it renders only from the
  visible public registry, hides the workspace when the vault locks, and never
  passes notes, share material, or cold-session values into the module.
- The updated backup record label: overdue and invalid states must not retain
  the green cold-verified styling.
- The browser assertion in `scripts/run-browser-harness.js`: it checks the
  dashboard from the actual built `file://` artifact, not an isolated DOM mock.
- The documentation edits that narrow previously aspirational claims about
  media, device lifecycle, multisig, and inheritance workflows.

## 10. Self-assessment

- The dashboard cannot prove individual share placement or physical
  survivability. That is an intentional limitation, not an unmet hidden
  calculation; P2.8 and any future per-share model need a separate design.
- Browser coverage exercises an unverified record and the locked teardown
  state. Deterministic Node tests cover current and overdue dates; no browser
  fixture waits a real year or manipulates the system clock.
- Actual Chrome, Safari, iOS, Android Files, Linux, and Tor Browser execution
  remain untested. Playwright Chromium/Firefox results must not be generalized
  to those platforms.
- The dashboard is intentionally not a percentage or “healthy” score. A
  future request for numeric survivability should not be implemented by
  extending this module without a new per-share placement ADR.
- Follow-up: P2.8 remains the next roadmap item after independent review of
  P2.7. Any per-device, media, multisig, or inheritance health feeds remain
  their own roadmap work.
