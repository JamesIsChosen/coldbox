## 1. Summary

P2.4 adds two cold-only threshold-share formats:

- Shamir39 splits a valid BIP-39 phrase into `shamir39-p1` mnemonic shares,
  accepting the legacy `shamir39` marker when combining.
- Raw SSS splits even-length hexadecimal data using the secrets.js-compatible
  share format over GF(2^n), with configurable field sizes from 3 through 20
  bits and an 8-bit / 128-bit-padding compatibility default.

The source, generated shares, combine inputs, reconstructed candidate, and
timers stay inside the opaque cold frame. The UI masks shares and results by
default, provides only a user-triggered 30-second reveal, and clears every
secret-bearing surface on lock or panic teardown. No message type, clipboard,
download, print, storage, passphrase, or wallet-device transport path was
added.

## 2. Scope

Included:

- `src/cold/shamir.js`: finite-field arithmetic, published-format parsing,
  split/combine APIs, input validation, CSPRNG enforcement, and no warm/persist
  surface.
- Cold markup, wiring, styles, and build assembly in
  `src/cold/index.html`, `src/cold/main.js`, `src/cold/styles.css`, and
  `scripts/build.js`.
- Independent published compatibility vectors and negative tests in
  `test/shamir.test.js`.
- Chromium/Firefox file:// coverage in `scripts/run-browser-harness.js` for
  masking, reconstruction, warm isolation, malformed shares, and teardown.
- The guide, ADR, dependency provenance, roadmap split, changelog, and this
  packet.

Deliberately not included: SLIP-39, codex32, vault recovery records,
BackupRecords, health dashboards, printable cards, passphrase splitting,
share authentication, durable share storage/export, or any warm-realm share
surface. Those belong to other roadmap items or require a separate decision.

## 3. Independent references and assumptions

The primary references were reviewed on 2026-08-12 and checked out temporarily
at these commits before the temporary directories were removed:

| Reference | Commit | Used for |
|---|---|---|
| [Ian Coleman Shamir39](https://github.com/iancoleman/shamir39) | `30d17d8921200afd1c6365140ee1defead11386a` | `shamir39-p1` marker, parameter encoding, GF(2^11) share data, deterministic fixture |
| [secrets.js](https://github.com/grempe/secrets.js) | `14a4b682a28242b1dbe5506674b5d5f476b78dbf` | raw share prefix/ID/data format, GF(2^n), 8-bit default, 128-bit padding, deterministic fixture |

Assumptions made and their consequences:

| Assumption | Basis | If wrong |
|---|---|---|
| Current Shamir39 compatibility is the published `shamir39-p1` encoding | Ian Coleman specification and reference implementation | Shares would be incompatible; the published vector test would fail and the implementation must be replaced before use |
| The legacy `shamir39` marker may be accepted for combining but new output uses `shamir39-p1` | Reference source compatibility behavior and current specification naming | Older shares may be refused or new shares may need a version-specific output choice |
| Shamir39 uses GF(2^11), with field values 1–2047 for share order and threshold | Reference implementation and its field table | The share limit or interpolation domain would be wrong; upstream vectors would not match |
| Raw SSS defaults to 8 field bits and 128 padding bits | secrets.js README/source | Existing secrets.js-compatible shares would not round-trip |
| UI share entry is bounded to eight fields | This item needs a bounded, reviewable UI; the cold API enforces the larger mathematical limits | Larger sets require a later UI item; the API is not silently presented as unlimited |
| Neither format authenticates a share set | Both reference schemes reconstruct mathematical candidates rather than authenticate provenance | Users could mistake a candidate for proof; the guide and UI require independent verification |

## 4. Acceptance mapping

| Requirement | Evidence |
|---|---|
| Shamir39 accepts valid 12/15/18/21/24-word BIP-39 phrases | `parseBip39Mnemonic()` validates the selected official wordlist, checksum, and supported counts before splitting; combine validates the reconstructed checksum. |
| Shamir39 matches the published encoding | `test/shamir.test.js` combines the five published current-format shares and compares deterministic output byte/word-for-word with the Ian Coleman fixture. |
| Raw SSS supports published secrets.js-compatible shares | The test combines the published compatibility set and compares deterministic 3-of-3 formatting with the reference output. |
| Threshold and malformed-share failures are explicit | Focused tests cover insufficient sets, duplicate IDs/orders, mixed parameters, malformed input, mismatched fields/data lengths, invalid fields, and invalid BIP-39 input. |
| Randomness fails closed | Both split APIs require `crypto.getRandomValues`; the focused test removes it and asserts failure. Source lint also rejects `Math.random`. |
| No secret crosses the realm boundary | `shamir.js` has no `postMessage`, storage, network primitive, or warm API. The browser harness asserts `window.__coldboxShamir` is undefined in the warm page. |
| Masking and teardown are real UI behavior | Browser coverage asserts masked generated shares/results, timed/manual reveal, source/input clearing, malformed-share clearing, and Escape-Escape session teardown in Chromium and Firefox. |
| No runtime dependency or network fetch | The implementation is inline, build assembly is explicit, and vendor verification remains unchanged. |
| Docs and structural rationale are present | `docs/03-guides/backup-shamir.md`, ADR-0038, the dependency provenance rows, guide index, changelog, and roadmap marker are included. |
| Roadmap status is correct | P2.4 is `[~]`; the author does not mark it `[x]`. |

## 6. Security review notes

- `src/cold/shamir.js` contains no `postMessage`, `fetch`, XHR, WebSocket,
  storage, `eval`, `new Function`, or `Math.random` surface.
- `src/cold/main.js` calls `clearShamirSession()` through the shared vault
  session teardown before clearing the cold session state.
- The warm realm has no `__coldboxShamir` binding; browser coverage checks this
  directly from the parent page.
- The raw result and Shamir39 result are masked even after successful combine.
  Revealing is separate, timed, and manually hideable.
- The implementation does not claim share authenticity. A wrong or malicious
  share can yield an incorrect candidate; the guide explicitly requires BIP-39
  checksum/fingerprint or independent raw-hex verification.
- Temporary upstream checkout directories were removed after source review:
  `.source-shamir39` and `.source-secretsjs`. No upstream checkout is staged.

## 7. Review focus and honest gaps

Please scrutinize:

1. The finite-field primitive-polynomial table and the bit/hex padding
   conversions, especially the Shamir39 11-bit-to-hex-to-word round trip.
2. The distinction between a mathematically reconstructable candidate and an
   authenticated share set.
3. Every P2.4 secret-bearing UI path, especially combine-attempt clearing and
   Escape-Escape teardown.
4. The explicit build manifest order and the absence of a new warm message
   type or persistence path.

Honest gaps:

- No physical mobile browser, iOS local execution, Android Files launch,
  macOS Safari, or Tor Browser test was performed in this session. Chromium
  and Firefox headless `file://` coverage is evidence for those engines only.
- No hardware wallet restore path was tested; Shamir39 and raw SSS are
  documented as non-standard/non-interchange formats.
- The UI exposes eight combine fields. The API supports the field’s larger
  mathematical limit, but a larger UI is intentionally deferred.
- No share-authentication or durable encrypted share-record feature is claimed.

## 8. Self-assessment before independent review

The highest-risk areas are compatibility beyond the published fixtures,
malicious-share handling, and future accidental movement of share text into a
warm message or persistence surface. The current implementation fails closed
on malformed/mismatched inputs and returns a candidate only behind a masked
result plus explicit independent-verification guidance. It does not pretend
that this is authenticity.

The branch contains exactly one roadmap item: P2.4. P2.5 must branch from
`p2.1-slip39`, not from this branch, because P2.4 is a sibling of P2.1–P2.3.
