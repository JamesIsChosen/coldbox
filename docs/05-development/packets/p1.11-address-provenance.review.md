## 4. Findings

### F1 — Warm public-data replacement can manufacture `cold-verified`

**Severity:** blocking security / authority-boundary violation

**Location:** `src/protocol.js` (`cleanRegistryRecord`, `cleanPublicDataReplace`); `test/protocol.test.js` (`address verification fields accept only the documented state model`)

**Observed:** `publicData.replace` is a warm-to-cold message. The P1.11 schema accepts `verificationState: "cold-verified"` as an ordinary enum value whenever `lastColdVerifiedAt` and `verifiedAgainstXpub` are also supplied. The reviewer-owned invariant probe submitted that state from the warm side and received an accepted sanitized message. The committed protocol test likewise constructs a warm-to-cold `publicData.replace` with `cold-verified` and asserts that the result remains `cold-verified`.

This means the warm side can create the exact state whose meaning is “re-derived from the seed, offline, with the vault unlocked” without any re-derivation event occurring.

**Expected:** Per the verbatim P1.11 acceptance criterion, an address reaches `cold-verified` **only via an actual cold re-derivation**. Timestamp/xpub fields are evidence metadata, not proof that the cold event occurred.

**Required action:** Enforce verification-state authority in the cold-owned mutation path. A warm replacement must not be able to elevate an unverified/unverifiable/stale address to `cold-verified` merely by supplying self-asserted evidence fields. Preserve existing authenticated `cold-verified` state when appropriate, but require a cold-authoritative transition for any elevation. Replace the current positive warm-forgery test with negative/transition tests that prove the authority rule.

### F2 — Schema 1 is only projected as schema 2; the vault is not migrated on open

**Severity:** blocking data-model / migration defect

**Location:** `src/protocol.js` (`cleanPublicCompartment`); cold vault/session open/save path; `docs/01-spec/data-model.md` Migration section

**Observed:** `cleanPublicCompartment()` always emits `schema: 2` and supplies `addressOrigin: manual` / `verificationState: unverified`, so protocol messages make legacy data *look* migrated.

The reviewer independently created a real schema-1 vault, opened it through the actual cold vault API, saved it without an unrelated Registry mutation, and reopened the saved bytes. Results:

```text
raw schema after open:        1
raw schema after save/reopen: 1
protocol projected schema:    2
```

The PR does not modify the cold vault open/session layer. The documented migration contract says migrations run **on open**, in sequence, with a backup copy before applying them and with failures leaving the original untouched. That does not happen here.

**Expected:** Opening a previous-schema vault must execute the documented schema migration in the cold-owned vault/session state, not merely sanitize a cross-realm projection. The migrated state must carry schema 2 plus the explicit legacy defaults, and the documented backup/original-untouched failure contract must be honored.

**Required action:** Implement the schema-1→schema-2 migration in the actual vault-open migration path and add a real previous-schema vault test that proves: open succeeds; the cold session is schema 2 with `manual`/`unverified` defaults; migrated save/reopen remains schema 2; and migration failure preserves the original according to the documented backup contract.

### F3 — No committed test proves a stale address is never displayed as verified

**Severity:** blocking acceptance/test-coverage defect

**Location:** `test/`; `scripts/run-browser-harness.js`

**Observed:** The roadmap explicitly requires “a test proves a stale entry is never displayed as verified.” The effective PR changes `test/protocol.test.js` and `test/registry.test.js` but does not change the browser harness. A reviewer-owned repository search for committed assertions covering `cold-verified-stale` display / `Cold verification stale` returned no match.

The reviewer-owned Chromium/Firefox probe proves the **current behavior** is correct: a stale record is rendered as `Cold verification stale`, not `Cold verified`. That independent evidence does not substitute for the required committed regression test.

**Expected:** The branch itself contains a regression test that fails if stale state is rendered as verified.

**Required action:** Add committed integration/browser coverage for the Registry address verification display. It must construct or reach `cold-verified-stale`, assert the stale state/label, and explicitly prove it is not displayed as `Cold verified`. Run it in the normal Chromium/Firefox harness or an equivalently committed display-level test.
