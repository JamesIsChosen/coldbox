# PR packet: P1.8 Device registry

## 1. Summary

P1.8 adds a public Device collection and a warm Devices workspace for recording
hardware-wallet inventory, lifecycle, tamper/PIN/purchase context, public seed
fingerprints, location, notes, and the boolean fact that a passphrase wallet is
used. The existing typed public registry mutation boundary, secure UUID path,
soft-hide behavior, lock teardown, and Chromium/Firefox harness now cover
devices. The roadmap marker remains `[~]` until an independent reviewer verifies
the item.

Roadmap: [P1.8 Device registry](../ROADMAP.md).

Branch: `p1.8-device-registry`
Dependency/base: `p1.7-notes-tags-concealment` at `a715c51`
Final code tip: `4a59998`

## 2. Scope

In scope:

- Closed `devices` public-projection schema with the canonical data-model
  fields, bounded ISO dates/text/fingerprints, and the lifecycle enum
  `in-use | retired | lost | destroyed | rma`.
- Warm create, edit, search, soft-hide, session reveal, and lock teardown for
  device records. The page explicitly says that it does not connect to,
  unlock, derive from, or sign with hardware.
- Secure UUID generation and device CRUD through the existing complete
  `publicData.replace` / `publicData.updated` boundary.
- Protocol, Registry, browser-harness, and warm-source boundary tests,
  including unknown-field, invalid-status/date/fingerprint, secret-shaped,
  and missing-randomness negatives.
- ADR-0033, three-depth user help, CHANGELOG, the `[~]` roadmap state, and this
  packet/self-review.

Deliberately out of scope:

- Hardware transport or screen reading; P1.9 owns verification workflows.
- Fingerprint, receive-address, xpub, backup, or passphrase verification
  workflows; those are P1.9.
- QR generation (P1.10), address verification-state migration (P1.11), or
  clipboard work (P1.12/P1.13).
- Secret phrases, private keys, xprvs, secret-note plaintext, or any other
  secret-compartment value in a Device record. `passphraseUsed` is a boolean
  public fact only.

## 5. Security impact

Yes. This item extends the public projection schema and warm rendering, but it
does not add a cross-realm message type or a new vault compartment. Device
mutations use the existing typed `publicData.replace` request and
`publicData.updated` acknowledgement; the protocol strips unknown fields,
bounds all accepted fields, rejects secret-shaped content, and accepts
`passphraseUsed` only as a boolean.

Device fields are intentionally public metadata. No mnemonic, passphrase,
private key, xprv, secret-note plaintext, or secret-compartment bytes are read
or sent by the warm Device page. The warm source contract still rejects a
standalone secret passphrase identifier; its explicit exception is the
documented `passphraseUsed` boolean. The cold realm policy is unchanged,
including `connect-src 'none'` and the existing sandbox without
`allow-same-origin`.

Device IDs use the existing `crypto.getRandomValues` UUID path and fail closed
when secure randomness is unavailable. No runtime dependency, network host,
cryptographic primitive, derivation path, or chain was added.

If this boundary were wrong, a public registry edit could become a path for
secret-shaped text to reach the warm shell or for a future developer to mistake
an inventory record for a hardware verification result. Closed schemas,
negative tests, explicit UI copy, and the deliberate lack of hardware transport
address those risks.

## 6. Test evidence

New tests prove:

- Device schema acceptance for every canonical field, unknown-field stripping,
  bounded fingerprints, valid lifecycle values, and ISO dates.
- Rejection of invalid lifecycle values, malformed dates, malformed
  fingerprints, arbitrary secret-shaped fields, and missing secure randomness.
- Device CRUD, UUID shape, update, soft-hide, include-hidden listing, and
  clone isolation through `Registry`.
- Warm source absence of secret-compartment APIs and absence of standalone
  secret passphrase handling, while the documented public boolean remains
  explicit.
- Browser create, search, hide, cold re-authentication reveal, lifecycle
  update, and lock teardown over `file://` in Chromium and Firefox.

No new cryptographic primitive or chain was introduced, so P1.8 has no new
cryptographic vector claim. The full suite still runs the independent NIST,
BIP-32/BIP-39/BIP-49/BIP-84/BIP-86, and ERC-55 vectors already established by
earlier roadmap items. Vendor verification downloaded and matched all ten
pinned upstream releases.

## 8. Assumptions made

- The `Device` field set and lifecycle enum in [data-model.md](../../01-spec/data-model.md)
  are canonical. Wallet records already have `deviceIds`, so P1.8 does not
  invent a second device-to-wallet relation field.
- Device inventory is public metadata by design. `passphraseUsed` records only
  yes/no configuration metadata; it is not a passphrase hint or input.
- A date-only browser input is normalized to midnight UTC as an ISO timestamp,
  matching the existing protocol's exact ISO validation. Device transport and
  hardware-derived values are intentionally not implied by a typed record.
- Existing vaults that omit `devices` remain readable because the Registry
  fills the missing public collection with an empty list; the next accepted
  public write persists the expanded projection through the existing vault
  format.
- As with the existing Registry forms, a partial update merges omitted optional
  fields. Clearing an already-recorded optional device field is not a new vault
  format feature and remains follow-up UI work if the shared Registry update
  semantics are expanded.

## 9. What to scrutinise

- `cleanRegistryField` and the closed `devices` field map in `src/protocol.js`:
  the public boolean must remain a boolean, fingerprint bounds must remain
  strict, and later fields must not become arbitrary text carriers.
- `prepareRecord`/`update` and the new Device CRUD methods in `src/registry.js`:
  secure UUID failure, clone isolation, soft-hide behavior, and the existing
  complete-projection relationship checks must not be bypassed.
- `renderRegistry`, `handleDeviceFormSubmit`, and lock teardown in
  `src/main.js`: the workspace must never remain visible after lock, and the
  warm source must never acquire a secret passphrase or secret-compartment API.
- The browser-harness path in `scripts/run-browser-harness.js`: its reveal test
  re-enters the phrase only in the cold frame and asserts the final lock state.

## 10. Self-assessment

The formal gate first caught two invalid `data-model.md#device` links; both were
changed to the canonical document link in `b5b78fb`, then the complete suite
and docs gate were rerun. During the pre-gate browser audit, the Device page's
locked/workspace toggles and one stale reset variable were corrected before the
implementation commit. During the final diff audit, a warm-source assertion
cleanup replaced an obfuscated split string with the explicit safe boolean and
was reverified in `4a59998`.

No physical hardware wallet was connected or validated. The item deliberately
does not claim that a listed vendor/model/fingerprint is genuine; that work is
P1.9. Mobile, Edge, Safari, Tor, and Android execution remain untested as shown
in the matrix. No real seed phrase, private key, keyfile, or vault file was
created or committed.
