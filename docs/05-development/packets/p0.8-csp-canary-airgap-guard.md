# PR packet: P0.8 - CSP canary and airgap guard

## 1. Summary

P0.8 adds an executable airgap check to both realms. Each document deliberately attempts `https://coldbox.invalid/csp-canary`; the canary passes only when the browser reports an exact `connect-src` violation for that URL. The warm shell refuses to proceed when its policy is absent or modified. The cold realm runs its canary with the native `fetch` before installing a defense-in-depth runtime guard, and it exposes the two successful checks as typed readiness capabilities.

Inside the cold realm, `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, and `navigator.sendBeacon` are replaced with frozen throwing blockers and made non-configurable/non-writable. Any failed installation or later runtime attempt raises a typed airgap violation and locks the warm shell down. The warm shell displays green, amber, or red airgap states from `navigator.onLine`, `navigator.connection`, online/offline/focus/change signals, and a one-second refresh interval.

This branch is based on the unmerged `p0.7-message-handshake` branch. Its PR base must therefore be `p0.7-message-handshake`.

## 2. Scope

### In scope

- Shared CSP-canary and network-state helper embedded into the warm and cold documents
- Exact canary-violation matching and fail-closed handling for missing/stripped CSP

- Typed cold readiness capabilities and runtime airgap-violation status
- Green/amber/red airgap banner and network-state monitoring
- Stripped-CSP, offline-emulation, runtime-primitive, and negative browser fixtures

### Deliberately out of scope

- Capability self-checks, cryptography, vault storage, and secret-bearing operations (P0.9+)
- Any new warm-shell network allowlist host
- Real-device certification, which remains P0.19
- Any merge of this branch or its dependency branches

## 5. Security impact

- Realm boundary: **Preserved.** The cold frame remains `sandbox="allow-scripts allow-downloads"` without `allow-same-origin`; the warm shell still cannot read its DOM or variables.
- CSP: **Strengthened operationally.** The cold policy remains `connect-src 'none'`; the canary detects a missing/stripped policy before private readiness is accepted. No new network host was added.
- Runtime defense in depth: The cold guard blocks all five documented network primitives after first exercising the native `fetch` path, then freezes the replacement properties. A failed install or later attempt enters visible lockdown.
- Failure mode: The warm shell starts with vault operations refused and only changes to guarded after both canaries, runtime neutering, and the private handshake pass. It never treats a missing canary as success.
- Network-state caveat: `navigator.onLine` describes interface state, not guaranteed Internet reachability. The banner communicates the signal, while the cold CSP and runtime guard remain the actual secret-boundary controls.
- Expected noise: The deliberate invalid-host canary can produce browser console errors; the browser harness allows only the canary-specific fragments and rejects unexpected errors/page errors.

## 8. Assumptions made

> **Assumed:** The deliberately invalid `.invalid` host is suitable for a policy canary.
> **Basis:** It is not an allowlisted warm host, while the cold policy rejects all connections; the success condition is the browser's exact `connect-src` violation, not DNS failure alone.
> **Not verified on:** Real-device browsers.
> **If wrong:** The canary URL must be replaced with another deterministic policy-violating URL without adding a production network allowlist host.

> **Assumed:** The native cold `fetch` canary must run before runtime blockers are installed.
> **Basis:** This distinguishes a browser-enforced CSP result from a JavaScript stub result; the cold readiness response is withheld until both checks pass.
> **Not verified on:** Browser engines outside the automated Chromium/Firefox matrix.
> **If wrong:** The cold bootstrap sequencing requires a security review before any vault operation is added.

> **Assumed:** A one-second refresh interval is acceptable for a five-second banner requirement.
> **Basis:** It is stricter than the roadmap bound and is supplemented by browser events and connection-change notifications.
> **Not verified on:** Background-tab timer throttling on physical devices.
> **If wrong:** The manual matrix must confirm the visible transition timing on the affected platform.

## 9. What to scrutinise

- The canary is accepted only for the exact URL and `connect-src` directive; a generic rejected request cannot satisfy it.
- The cold canary uses native `fetch` before the five runtime primitives are replaced.
- Every cold runtime blocker is non-configurable and non-writable, and an installation failure is terminal.
- The cold typed `ready` response cannot be accepted without both new capability flags.
- A later typed airgap violation preserves the cold frame so the runtime guard remains observable while the warm shell is locked down.
- Stripping both CSP policies produces full lockdown and refuses vault operations; there is no single-realm fallback.
- No new warm `connect-src` host or secret-bearing protocol field was introduced.

## 10. Self-assessment

- The canary is a browser-policy signal, not a substitute for the cold `connect-src 'none'` policy; both remain required.
- `navigator.onLine` can be optimistic or pessimistic about Internet reachability. The banner reports it, but the secret guarantee does not depend on it.
- Runtime neutering is defense in depth and does not relax the CSP or authorize any vault operation.
- The automated matrix covers Chromium and Firefox only; real-device claims remain intentionally unmade.
- P0.8 introduces no crypto, vault, or secret-handling behavior and keeps those items out of scope.
