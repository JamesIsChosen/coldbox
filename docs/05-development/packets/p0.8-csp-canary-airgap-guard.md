# PR packet: P0.8 - CSP canary and airgap guard

## 1. Summary

P0.8 adds an executable airgap check to both realms. The warm shell deliberately attempts `https://coldbox.invalid/csp-canary`; the cold realm deliberately attempts `http://localhost:9/cold-csp-canary`, a target permitted by the inherited warm allowlist but denied by the cold policy. Each canary passes only when the browser reports an exact `connect-src` violation for its own URL. The warm shell refuses to proceed when its policy is absent or modified, and the cold readiness gate refuses to proceed when its own policy is absent or modified. The cold realm runs its native `fetch` canary before installing a defense-in-depth runtime guard, and it exposes the two successful checks as typed readiness capabilities.

Inside the cold realm, `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, and `navigator.sendBeacon` are replaced with frozen throwing blockers on both the exposed objects and their prototype owners, then made non-configurable/non-writable. Any failed installation or later runtime attempt raises a typed airgap violation and locks the warm shell down. The warm shell displays checking, green, amber, or red airgap states from `navigator.onLine`, `navigator.connection`, online/offline/focus/change signals, and a five-second refresh interval.

This branch is based on the unmerged `p0.7-message-handshake` branch. Its PR base must therefore be `p0.7-message-handshake`.

## 5. Security impact

- Realm boundary: **Preserved.** The cold frame remains `sandbox="allow-scripts allow-downloads"` without `allow-same-origin`; the warm shell still cannot read its DOM or variables.
- CSP: **Strengthened operationally.** The cold policy remains `connect-src 'none'`; the cold canary target is allowed by the inherited warm policy but denied by the cold policy, and the exact URL/directive must be observed before private readiness is accepted. No production allowlist host was added; the target uses the already documented localhost pattern.
- Runtime defense in depth: The cold guard blocks all five documented network primitives after first exercising the native `fetch` path, including direct calls through their prototype owners, then freezes the replacement properties. A failed install or later attempt enters visible lockdown.
- Failure mode: The warm shell starts with vault operations refused and only changes to guarded after both canaries, runtime neutering, and the private handshake pass. It never treats a missing canary as success.
- Network-state caveat: `navigator.onLine` describes interface state, not guaranteed Internet reachability. The banner communicates the signal, while the cold CSP and runtime guard remain the actual secret-boundary controls.
- Expected noise: The deliberate invalid-host canary can produce browser console errors; the browser harness allows only the canary-specific fragments and rejects unexpected errors/page errors.

- Warm and cold canaries fail closed when their respective CSP is stripped, independently and together.
- A cold runtime call, including direct prototype-owner calls, to each of `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, and `sendBeacon` is blocked by the labelled runtime guard.
- Exact canary matching rejects near-miss URLs and directives, and a rejected fetch without an exact violation is recorded as failure.
- A deliberate CSP violation and a byte-tampered inline script remain rejected.
- A deliberate forbidden `eval` fixture exits with a non-zero build status.
- The browser harness reports a non-zero result for a failed check and for missing browser installation.
- Existing opaque-frame, handshake, routing, responsive, and cold-realm creation-lockdown checks continue to pass.

## 8. Assumptions made

> **Assumed:** The warm `.invalid` target and the cold `localhost:9` target are suitable policy canaries.
> **Basis:** The warm target is outside the warm allowlist; the cold target is inside the warm `localhost:*` allowance but outside the cold `connect-src 'none'` policy. Both success conditions require an exact `connect-src` violation and exact `blockedURI`, not DNS failure alone.
> **Not verified on:** Real-device browsers.
> **If wrong:** The affected canary URL must be replaced with another deterministic policy-violating URL that preserves independent warm/cold attribution without adding a production allowlist host.

> **Assumed:** The native cold `fetch` canary must run before runtime blockers are installed.
> **Basis:** This distinguishes a browser-enforced CSP result from a JavaScript stub result; the cold readiness response is withheld until both checks pass.
> **Not verified on:** Browser engines outside the automated Chromium/Firefox matrix.
> **If wrong:** The cold bootstrap sequencing requires a security review before any vault operation is added.

> **Assumed:** A five-second refresh interval is acceptable for a five-second banner requirement.
> **Basis:** It is the canonical interval, supplemented by browser events and connection-change notifications.
> **Not verified on:** Background-tab timer throttling on physical devices.
> **If wrong:** The manual matrix must confirm the visible transition timing on the affected platform.

## 9. What to scrutinise

- Each canary is accepted only for its exact URL and `connect-src` directive; a generic rejected request, near-miss URL, or inherited warm violation cannot satisfy the cold check.
- The cold canary uses native `fetch` before the five runtime primitives are replaced.
- Every cold runtime blocker is installed on the exposed object and prototype owner, is non-configurable and non-writable, and an installation failure is terminal.
- The cold typed `ready` response cannot be accepted without both new capability flags.
- A later typed airgap violation preserves the cold frame so the runtime guard remains observable while the warm shell is locked down.
- Stripping the warm policy, the cold policy, or both produces full lockdown and refuses vault operations; there is no single-realm fallback.
- No new warm `connect-src` host or secret-bearing protocol field was introduced.

## 10. Self-assessment

- The canary is a browser-policy signal, not a substitute for the cold `connect-src 'none'` policy; both remain required.
- `navigator.onLine` can be optimistic or pessimistic about Internet reachability. The banner reports it, but the secret guarantee does not depend on it.
- Runtime neutering is defense in depth and does not relax the CSP or authorize any vault operation.
- The automated matrix covers Chromium and Firefox only; real-device claims remain intentionally unmade.
- P0.8 introduces no crypto, vault, or secret-handling behavior and keeps those items out of scope.
