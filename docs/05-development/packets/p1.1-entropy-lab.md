# PR packet: P1.1 — Entropy Lab: dice, coins, cards, CSPRNG, mixing

## 1. Summary

Implements [ROADMAP.md P1.1](../ROADMAP.md#phase-1--core-wallet): a cold-realm Entropy Lab that collects entropy from dice (base-6 and a 4-outcome discard mapping), coin flips, playing cards, and typed hex, tracks a conservative running bit-count, supports per-operation undo, and mixes the collected entropy with fresh CSPRNG output (XOR then SHA-256, block-expanded) into 128–256 bits. Seed Forge (P1.3), the eventual consumer, does not exist yet, so the mixed output is displayed inline inside the sealed realm and carried nowhere.

## 5. Security impact

- **Touches randomness generation, yes.** Does not touch the realm boundary, message schema, CSP, or vault format. No new message type (Entropy Lab is entirely local to the cold realm; nothing about it crosses to the warm shell).
- **What does an attacker gain if this implementation is wrong?** The main risk is a seed generated from less real entropy than claimed — e.g., if the "guaranteed bits" gate overcounted, a user could generate a 128-bit-labeled seed with fewer actual bits of security, or if the mixing construction let either the manual entropy or the CSPRNG alone determine the output, a compromise of just one source (a rigged die, or a backdoored/broken `crypto.getRandomValues`) would compromise the resulting seed. I addressed both: the bit-count gate is integer/`BigInt`-only (no floating-point rounding that could round up past the true guaranteed value — see [ADR-0022](../adr/0022-entropy-lab-mixing.md)), and the mix requires *both* a full-length manual entropy buffer and an equal-length fresh CSPRNG slice, XORed before hashing, so either input alone is insufficient to determine the output (standard property of XOR with an independent uniform operand).
- **I am not fully certain the "guaranteed bits" floor is the tightest possible bound in every case** — see §9. I believe it is conservative (never overclaims), which is the safety-relevant direction, but a tighter bound is possible and I haven't proven this one is optimal.
- No new `connect-src` host. No new message type.

I avoided further `git stash`/destructive git commands after the second occurrence and did all reproducibility re-checks (rebuild, different TZ/locale, `git archive`-based baseline) without needing the index. This is an environment quirk of this sandbox's mount, not a repository issue — flagging it in case it recurs for whoever merges this.
- **"Outputs 128–256 bits to Seed Forge"** is interpreted as "produces a well-defined byte buffer of the requested size, ready for a not-yet-built P1.3 to consume" rather than an actual hand-off, since Seed Forge doesn't exist. See §4's last row.
- **Card identity mapping (`cardId` 0-51 → rank/suit)** is arbitrary (`suitIndex * 13 + rankIndex`, spades/hearts/diamonds/clubs × A,2..10,J,Q,K) — the spec doesn't fix one. Recorded here since a different mapping would change the UI's `<select>` order but not the accumulator's security properties (any fixed bijection between the 52 cards and 0-51 is equivalent).
- **CSPRNG draw size (32 bytes per click)** is my choice, not specified. A user needing more manual-entropy bytes to XOR against (e.g., after many card draws) clicks the button multiple times; the UI's status text says exactly how many more bytes are needed.
- **Target bit-size options restricted to the five BIP-39 `ENT` values** (128/160/192/224/256) rather than "any multiple of 8 from 128 to 256" — narrower than a literal reading of "128–256 bits," justified because the only documented consumer (Seed Forge/BIP-39) can't use anything else. If a future consumer needs a different size, [ADR-0022](../adr/0022-entropy-lab-mixing.md) flags this as something to revisit.

## 9. What to scrutinise

- **The `-1` in `guaranteedBitsForRange` (`bitLength(range) - 1`).** This is the crux of the whole feature's honesty about how much entropy was actually collected. I derived it from "a range of size R has bit-length b, so R ∈ (2^(b-1), 2^b], hence only b-1 bits are guaranteed regardless of where in that interval R falls" — I'm confident this is *conservative* (never overclaims), but I have not proven it's the *tightest* conservative bound, and a reviewer with a stronger combinatorics background should check whether a tighter (still-safe) formula exists, especially for the card accumulator where the range isn't a power-of-6 or a clean base.
- **The counter-mode SHA-256 expansion for the mixing step is my own construction**, not HKDF (see ADR-0022's rejected-alternative section for why). It is simple and I've verified it against an independent SHA-256 implementation, but "simple and independently verified" is not the same bar as "reviewed cryptographic construction." If the reviewer has a security-design objection to inventing a KDF-like primitive instead of using the vendored `@noble/hashes/hkdf`, that's the single most likely place for a real finding, not a cosmetic one.
- **The DOM wiring in `main.js` is untested** (§6, §7). I traced it by hand against the element IDs in `index.html` but did not click through it in a real browser.
- **The `addCsprngBytes`/CSPRNG-unavailable UI path** (`src/cold/main.js`, the `entropyCsprngDraw` click handler) calls `cryptoLayer.randomBytes()`, which is already covered by `test/crypto.test.js`'s fail-closed behaviour, but I did not write a new test asserting the Entropy Lab UI itself surfaces that failure correctly — I traced it by reading the code only.
- **The `NO_MACHINE_PATHS` regex gap I found (§2)** is real but narrow (only triggers when a cold-realm source comment ends a line in `word:` right before a spot where that source gets JSON-embedded elsewhere in the build). I worked around it in my own two comments rather than fixing the regex, on the theory that fixing shared test infrastructure is out of scope for a single roadmap item's PR — but a reviewer may reasonably want that regex gap filed as its own follow-up issue so it doesn't silently bite the next contributor who writes a comment ending in a colon.

## 13. Remediation of review FAIL

**F1 — CSPRNG-only entropy not implemented — fixed.** `src/cold/entropy-lab.js`'s `mix()` now branches on whether any manual entropy was recorded. With none, it returns the requested number of fresh CSPRNG bytes directly (no hash — CSPRNG output is already uniform, and entropy-and-strength.md describes it as "256 bits by definition" in its own right, not only as a mixing ingredient). A new `csprngGuaranteedBits()` reports CSPRNG bytes on hand separately from `guaranteedBits()` (which remains manual-only, since the two gate different things — see F5/F6 below and ADR-0022). New tests: `mix() falls back to a direct CSPRNG-only draw...` and `guaranteedBits() (manual) is 0 for a CSPRNG-only session, but csprngGuaranteedBits()...`. UI: the CSPRNG fieldset's help text and the meter (`#cold-entropy-meter`) now state both numbers.

**F2 — "...to Seed Forge" — not fixed, and I don't believe it can be inside this PR.** I want to be direct rather than argue around this: Seed Forge is P1.3, sequenced after P1.1 on the roadmap, and AGENTS.md requires exactly one roadmap item per PR — building Seed Forge here to satisfy this phrase would itself violate that rule, and building a stub/fake Seed Forge to technically satisfy the literal words would be worse: a plausible-looking hand-off to nothing, which AGENTS.md §8 calls out as the worst outcome ("looks like progress" while quietly failing). I have not changed anything about this finding's substance since the original packet — I flagged it there as unmet rather than reinterpreted, and it is still unmet. What I can do, and have done, is make sure nothing about this PR's design would need to change once P1.3 exists: `mix()`'s return value is a plain `Uint8Array` of exactly the requested byte length, which is the only contract a future Seed Forge needs. I'm leaving this finding open for the reviewer or the human maintainer to adjudicate: either P1.1 cannot reach `[x]` until P1.3 exists to receive its output (in which case this branch should perhaps merge as infrastructure while the roadmap item itself stays open), or the roadmap/SPEC wording should be read as describing the eventual multi-item pipeline rather than a single item's deliverable (in which case an ADR or a SPEC/ROADMAP clarification, not a code change, is what's missing). Either way, I do not think I can make this finding disappear by writing more code, and pretending otherwise would be exactly the kind of silent reinterpretation the review protocol forbids.

**F3 — Card undo DOM desync — fixed.** `src/cold/main.js`'s card `<select>` is now rebuilt from `entropySession.cardRemaining` on every state change (`refreshCardOptions()`, called from `updateEntropyLabControls()`) instead of having individual `<option>` elements added/removed by each click handler. There is no longer any incremental option-list state that can drift from the session — the two cannot desync because the UI has no memory of its own between rebuilds.

**F4 — Stale mixed output — fixed.** `updateEntropyLabControls()` (which every add/undo/CSPRNG-draw handler already called) now clears the displayed mix output (`setEntropyMixOutput(null)`) as its first action, and the target-size `<select>`'s `change` handler does the same. A previously displayed result cannot survive any state-changing action.

**F5 — Formula mismatch — fixed.** The 4-byte counter prefix is gone. `mix()`'s mixed-entropy path is now exactly `SHA-256(manualBytes XOR csprngBytes)`, truncated to the requested length — this works unconditionally because every valid target (128–256 bits = 16–32 bytes) fits inside one 32-byte SHA-256 block, so the counter-based block expansion was both wrong and unnecessary. `test/entropy-lab.test.js`'s two mixing tests were rewritten with fresh independent Node-crypto vectors for the corrected formula (the old counter-based vectors are gone, not left alongside as dead code); `docs/05-development/adr/0022-entropy-lab-mixing.md` gained a revision note explaining what was wrong and why, rather than silently editing history.

**F6 — CSPRNG reuse — fixed.** Both `mix()` paths now remove ("burn") the CSPRNG bytes they actually used from `session.csprngBytes` before returning. A second `mix()` call with no intervening draw fails exactly the way running out of CSPRNG bytes always fails (a thrown, fail-closed error), rather than silently reusing them. New test: `mix() consumes ("burns") the CSPRNG bytes it used...`, which also confirms a subsequent mix with freshly drawn bytes produces a different output.

**F7 — Second-shuffle unsupported — fixed.** `startNewCardShuffle(session)` refills `cardRemaining` to a full 52-card pool once the current one is exhausted (refusing, fail-closed, if cards still remain in the current pool), *without* resetting `cardValue`/`cardOrder`. Each draw's pool size is now recorded per-draw (`cardDrawPoolSizes`) rather than re-derived from a `52 - i` formula that assumed one unbroken pass through the deck, so `cardGuaranteedBits()`/`manualEntropyBytes()` correctly compound a second (or third...) shuffle's range into the same running accumulator — matching entropy-and-strength.md's "1 shuffle ≈ 225 bits, 2 shuffles" row for a 256-bit target. UI: a new "Start new shuffle" button (`#cold-entropy-card-shuffle`), enabled only once the pool is empty. New test: `startNewCardShuffle() refuses while cards remain, and compounds a second shuffle onto the same accumulator...`, which independently recomputes the expected combined range (`52! × 52`) and confirms it exceeds a single shuffle's 225 bits, plus confirms undo restores the exhausted-pool state exactly across a reshuffle-then-draw sequence.

**F8 — Missing mixing diagram — fixed.** `docs/04-reference/entropy-and-strength.md`'s "Mixing — the recommended approach" section now includes an ASCII-art diagram of the XOR-then-hash flow. I used ASCII art rather than SVG or an image because this repository's help-content compiler (`scripts/help-content.js`) has no image/SVG support — it HTML-escapes everything outside its small supported-markdown subset (headings, tables, lists, fenced code, links, bold/italic) by design, so that an unsupported construct fails visibly rather than silently mis-rendering. ## 15. Entropy Lab UX overhaul (manual browser testing feedback)

Manual browser testing (the F9 disposition above) of `build/coldbox.html` in a real browser, done by the maintainer rather than in this sandbox, surfaced UX problems the automated test suite could not have caught since they are about how the controls feel to use, not whether the underlying accounting is correct. This section documents that follow-up work, done in the same PR since it's a direct continuation of the same roadmap item's UI rather than a separable change.

**Bug: silent failure on bulk dice entry.** The maintainer typed a long sequence of digits into the single-character dice input and clicked "Add roll"; the meter read "0 guaranteed bits" with no error or explanation. Root cause: the input only ever read `Number(input.value)`, so a multi-character string parsed to `NaN`, failed the 1-6 range check, and the click handler returned silently. Fixed by replacing the single-value input with bulk sequence parsing (`parseSequence()` in `src/cold/main.js`): every valid character in the input becomes its own roll, and invalid characters are reported by name rather than silently dropped or causing the whole input to be rejected.

**Requested: use any combination of sources, including just one.** This was already true at the accounting level (`guaranteedBits()` sums each source independently; `mix()` only requires the *total* to reach the target, not any particular source), but the UI made it easy to want more than what was practical to enter: a single-character dice/hex input, and a card `<select>` requiring one dropdown-select-then-click cycle per card. Addressed by the changes below, which are about making single- and multi-source use equally low-friction, not by changing the underlying accounting (unchanged, and unchanged tests confirm it).

**Cards redesigned as a click-grid with a running log.** The `<select>` + "Add card" button is replaced with a 52-button grid (`#cold-entropy-card-grid`, built in `src/cold/main.js`'s `refreshCardGrid()`) showing every card in the deck at once; clicking a card draws it immediately. Drawn cards stay visible in the grid but disabled, rather than disappearing, so the grid's layout never reflows mid-shuffle. A separate running log (`#cold-entropy-card-log`, `refreshCardLog()`) lists every card drawn this session in draw order. Both are rebuilt from `entropySession.cardRemaining`/`cardOrder` on every state change, same rebuild-from-source-of-truth pattern the original `<select>` used (see §13 F3) — extended to two elements instead of one, still with no incrementally-tracked DOM state to desync.

**Bulk entry for dice and hex.** Both the dice-face and hex-digit inputs now accept a pasted or typed run of many characters at once (`type="text"`, no `maxlength`). `parseSequence()` splits on optional whitespace/comma/dash separators, applies each remaining character through the existing single-value `add*` function in a loop, and reports how many were accepted plus which characters (if any) were rejected — accepting the valid subset of a mixed-validity paste rather than failing the whole batch closed, since this is a UX convenience layer over already-validated `add*` calls, not a new security boundary.

**Per-source Reset buttons.** Each fieldset (dice, coin, cards, hex, CSPRNG) gained an independent "Reset" button, wired to a new `reset*(session)` function in `entropy-lab.js`. See [ADR-0022's UX-overhaul amendment](../adr/0022-entropy-lab-mixing.md#amendment-ux-overhaul-per-source-reset-buttons-exactbits-split-and-history-kind-tagging) for why this required splitting the previously-shared `exactBits` array into `coinBits`/`discardDiceBits`/`hexBits`, and tagging history entries with a `kind` so `purgeHistoryKind()` can invalidate stale undo closures for the reset source specifically. 7 new regression tests in `test/entropy-lab.test.js` cover every reset function: each is checked to clear only its own source's data and history, leave every other source completely untouched, and leave nothing behind for `undoLast()` to resurrect — the same shape of test as §14's CSPRNG-resurrection regression, generalized to all five sources.

**Per-source "Generate random" convenience.** Each fieldset also gained a configurable-count "Generate random" control that fills that source in via fresh CSPRNG bytes, using a new `drawUniformInt(maxExclusive)` helper in `src/cold/main.js` (rejection sampling on CSPRNG bytes — never `Math.random`, never modulo-biased). This lives in `main.js` rather than `entropy-lab.js` because it only produces *inputs to* the existing, already-tested `add*` functions (a random face 1-6, a random bit, a random nibble, a random remaining-card index) rather than a new accumulation code path; `entropy-lab.js`'s accounting is completely unaware of where a value came from. CSPRNG's own "Draw" control gained a batch-count input (still 32 bytes per batch, one `randomBytes()` call sized to `32 * count`) for the same reason — generating a lot of one kind of entropy quickly is exactly the workflow being asked for.

**Sticky "Collected" meter.** `#cold-entropy-meter` moved above the fieldsets in `index.html` and gained `position: sticky; top: 0` with a solid background in `styles.css`, so it stays visible while scrolling through the source fieldsets below it instead of requiring a scroll to the bottom of the section to check progress.

## 16. Round-3 maintainer remediation — provenance, touch floor, exact-bit serialization, and evidence provenance

A targeted maintainer review of the post-round-2 UX overhaul at starting branch tip `1f44c33ba7f703cdf4f1ea4a0cce27cd4c411ad3` found three substantive defects plus one evidence/provenance cleanup. This section is append-only remediation history. It **supersedes**, but does not erase or rewrite, the §15 statements that generated values were accounting-unaware and that independently padding the split exact-bit arrays was security-neutral. Those statements accurately record what the author believed in that earlier round; the round-3 review proved both were wrong. The preserved independent review report is not modified by this author-remediation round.

### R3-A — device-RNG simulations no longer masquerade as independent manual entropy

The Generate conveniences remain, but their provenance is now first-class state in `src/cold/entropy-lab.js`: values are tagged either `manual` or `device-rng`. Physically/manual-entered dice, coins, cards, and genuinely user-supplied hex receive conservative independent-source credit. Values produced by the Generate controls remain auditable source material but receive **zero** independent-source credit. The distinction therefore survives Undo, per-source Reset, target changes, and mixing; it is not merely UI wording.

A follow-up maintainer clarification, supplied **before this round's implementation/verification runner was executed**, tightened the same security model: the sticky meter must show **Normal output strength**, **Independent physical/manual entropy**, **Independent-source fallback strength**, and **Full two-source protection** as distinct claims. `strengthSummary(session, targetBits)` now derives those claims from the same conservative accounting used by `guaranteedBits()`. The raw independent count is never artificially capped; fallback of a fixed-size result is `min(independentBits, targetBits)`, and full two-source protection is true only when `independentBits >= targetBits`.

This clarification also exposed a cryptographic requirement. A 256-bit selected output with only 32 independent physical bits cannot truthfully claim 256-bit normal strength if the mixed path consumes only 32 CSPRNG bits. The corrected mixed path therefore consumes `max(targetBytes, sourceEntropyBytes.length)` fresh CSPRNG bytes. If canonical source serialization is shorter than the target, it is **right-padded with zeros only for the XOR operation**; the canonical serialization itself is unchanged. Under a sound device RNG the selected output retains its normal target strength, while a completely compromised RNG leaves only the displayed independent-source fallback. Partial physical entropy is useful but is explicitly **not** full two-source protection.

Generated-only simulations may still be included in the XOR/hash transformation when enough fresh CSPRNG bytes are available, but the UI/security state remains **CSPRNG-only security, 0-bit independent fallback** because the same device RNG controls both inputs. Logs group collected values under concise `Physical/manual` and `Device RNG` provenance labels instead of making device-derived values look physically collected.

Regression coverage includes: CSPRNG-only strength; each generated source and generated-source combinations; partial genuine manual fallback; real-manual + simulated mixtures; full target-reaching manual protection; Undo/Reset fallback changes; generated-value Undo/Reset remaining neutral; target-size recalculation; post-mix/reset stale-claim prevention; target-length CSPRNG consumption for partial-source outputs; and fail-closed invalid provenance.

### R3-B — Entropy Lab special-case controls restored to the 44×44 touch floor

The generic Entropy Lab controls already used the project’s `2.75rem` (44px at the default root size) floor, but §15 introduced smaller special-case overrides for the random-count inputs and card grid. Those overrides are removed: random-count inputs are at least `2.75rem` high, card-grid tracks are at least `2.75rem`, and each card button has both `min-width` and `min-height` of `2.75rem`. `test/accessibility.test.js` now asserts the actual special-case selectors so a future CSS override cannot silently shrink them while the generic rule still looks correct.

### R3-C — chronological exact-bit serialization restored while retaining per-source Reset

The per-source Reset storage split remains useful for UI/log reconstruction, but it is no longer the cryptographic serialization boundary. Exact-bit additions (coin, discard-dice, hex) also enter a chronological provenance-bearing event ledger. `sourceEntropyBytes()` flattens the **surviving events in insertion order**, concatenates their exact bits, and pads that combined stream once. Reset removes all events of the selected source while preserving the relative order of the remaining events; Undo removes the exact event created by that operation. Base-6 dice and card accumulators retain their established trailing accumulator encoding.

This deliberately restores the pre-Reset exact-bit packing semantics instead of redefining the byte format to suit the UI. Tests cross source boundaries (`coin + hex`, `coin + discard-dice + hex`), prove ordering differences are preserved, exercise Reset with surviving mixed-source order, and exercise Undo across mixed exact-bit operations. Existing full-length independent Node/OpenSSL SHA-256 vectors remain unchanged; an additional independent partial-source vector covers the new target-length zero-padding-for-XOR rule without changing canonical source serialization.
