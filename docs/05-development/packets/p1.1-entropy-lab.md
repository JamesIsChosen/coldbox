# PR packet: P1.1 — Entropy Lab: dice, coins, cards, CSPRNG, mixing

## 1. Summary

Implements [ROADMAP.md P1.1](../ROADMAP.md#phase-1--core-wallet): a cold-realm Entropy Lab that collects entropy from dice (base-6 and a 4-outcome discard mapping), coin flips, playing cards, and typed hex, tracks a conservative running bit-count, supports per-operation undo, and mixes the collected entropy with fresh CSPRNG output (XOR then SHA-256, block-expanded) into 128–256 bits. Seed Forge (P1.3), the eventual consumer, does not exist yet, so the mixed output is displayed inline inside the sealed realm and carried nowhere.

## 2. Scope

**In scope:** `src/cold/entropy-lab.js` (new), wiring in `src/cold/main.js` and `src/cold/index.html`, CSS in `src/cold/styles.css`, the build-manifest change in `scripts/build.js`, `test/entropy-lab.test.js`, [ADR-0022](../adr/0022-entropy-lab-mixing.md), a new "Defended" entry in [threat-model.md](../../02-security/threat-model.md), `CHANGELOG.md`, and `ROADMAP.md` (`[ ]` → `[~]`).

**Deliberately out of scope:**
- **The Entropy Health Meter's bias detection, chi-square/runs tests, and pattern warnings** — that is P1.2, a separate roadmap item, and SPEC.md itself splits these into two items.
- **Seed Forge / BIP-39 mnemonic generation** — P1.3. This PR outputs raw mixed entropy bytes only, displayed with an explicit "not carried anywhere" note.
- **`docs/03-guides/first-wallet.md` and `docs/04-reference/entropy-and-strength.md`** were *not modified*. Both already existed (written ahead of this implementation, per this repo's spec-first convention) and already describe this exact behaviour, including the literal `SHA-256(user_entropy XOR csprng_output)` formula and the base-6/discard/coin/card bit-count table. I checked every number in that table against my implementation (see §4) rather than rewriting either file.
- **One unrelated pre-existing test-infrastructure gap I found and fixed in-scope:** `test/build.test.js`'s `NO_MACHINE_PATHS` regex (`[A-Za-z]:\\(?!u003c|u003e|u0026)|...`) treats a JSON-escaped newline (`\n`) as satisfying its `letter:` `\` trigger, so any cold-realm source comment ending a line in `word:` immediately before a newline produces a false positive once that source is JSON-embedded elsewhere in the build. Two of my own comments happened to do this. I reworded my own two comments (colon → dash) rather than touching the regex or the exclusion list, since fixing the regex itself is unrelated to this roadmap item and would be its own change.

## 5. Security impact

- **Touches randomness generation, yes.** Does not touch the realm boundary, message schema, CSP, or vault format. No new message type (Entropy Lab is entirely local to the cold realm; nothing about it crosses to the warm shell).
- **What does an attacker gain if this implementation is wrong?** The main risk is a seed generated from less real entropy than claimed — e.g., if the "guaranteed bits" gate overcounted, a user could generate a 128-bit-labeled seed with fewer actual bits of security, or if the mixing construction let either the manual entropy or the CSPRNG alone determine the output, a compromise of just one source (a rigged die, or a backdoored/broken `crypto.getRandomValues`) would compromise the resulting seed. I addressed both: the bit-count gate is integer/`BigInt`-only (no floating-point rounding that could round up past the true guaranteed value — see [ADR-0022](../adr/0022-entropy-lab-mixing.md)), and the mix requires *both* a full-length manual entropy buffer and an equal-length fresh CSPRNG slice, XORed before hashing, so either input alone is insufficient to determine the output (standard property of XOR with an independent uniform operand).
- **I am not fully certain the "guaranteed bits" floor is the tightest possible bound in every case** — see §9. I believe it is conservative (never overclaims), which is the safety-relevant direction, but a tighter bound is possible and I haven't proven this one is optimal.
- No new `connect-src` host. No new message type.

## 6. Test evidence

- **12 new tests in `test/entropy-lab.test.js`**, run via `vm.runInNewContext` against the raw `src/cold/entropy-lab.js` source plus the real `@noble/hashes` vendor bundle (`createCryptoVendorSource`), the same pattern `test/crypto.test.js` uses.
- **Vector source for the mixing construction:** there is no BIP/SLIP/RFC for this bespoke XOR-then-hash construction (it isn't a standard), so the strongest available independent check is a from-scratch reimplementation using Node's built-in, OpenSSL-backed `crypto.createHash('sha256')` — a different codebase and a different SHA-256 implementation than the vendored `@noble/hashes` one the production code calls. Both tests (`mix() matches an independent Node-crypto reimplementation...`) hand-compute the expected XOR and first SHA-256 block outside the test's own `referenceMix()` helper as a literal hex-string assertion (`eb15abd96cd0fc35fcadaaa7d34ea6f3`, `e54d47...`) before ever calling into `entropy-lab.js`, so the reference values themselves aren't circular either.
- **Combinatorial facts checked independently:** `card draws use a factorial-number-system accumulator...` asserts `52!`'s bit-length is 225 — a standard, independently checkable fact (e.g. `log2(52!) ≈ 225.58`, floor 225, computable with any calculator or Stirling's approximation, not derived from this code). `base-6 dice accumulator...` similarly checks `6^10`'s exact value and bit-length against hand-computed numbers in the test's own comments.
- **Negative tests:** `mix()` fails closed on (a) insufficient guaranteed bits, (b) a CSPRNG buffer shorter than the manual entropy it must XOR against, (c) a target bit count outside the five valid sizes; `addCard` rejects a repeated draw; `addDiceBase6`/`addDiceDiscard`/`addHexNibble`/`addCard`/`addCsprngBytes` all reject out-of-range or malformed input (`rejects malformed inputs...`).
- **Not tested:** the DOM wiring in `src/cold/main.js` (button click handlers, meter text updates, the CSPRNG-unavailable UI message) has no automated test — see §9 and §10. The pure logic module it calls into is fully covered; the wiring itself is analogous to the existing KDF-benchmark and vault-controls wiring, which also has no dedicated unit test in this codebase (only the browser harness exercises DOM wiring end-to-end, and I did not add a new browser-harness check — see §7).

## 8. Assumptions made

- **`.git/index.lock` on this checkout's mounted filesystem could not be removed by this session** (`rm`/git's own cleanup both got `Operation not permitted`) partway through verification; the person running this session cleared it manually twice. I avoided further `git stash`/destructive git commands after the second occurrence and did all reproducibility re-checks (rebuild, different TZ/locale, `git archive`-based baseline) without needing the index. This is an environment quirk of this sandbox's mount, not a repository issue — flagging it in case it recurs for whoever merges this.
- **"Outputs 128–256 bits to Seed Forge"** is interpreted as "produces a well-defined byte buffer of the requested size, ready for a not-yet-built P1.3 to consume" rather than an actual hand-off, since Seed Forge doesn't exist. See §4's last row.
- **Card identity mapping (`cardId` 0-51 → rank/suit)** is arbitrary (`suitIndex * 13 + rankIndex`, spades/hearts/diamonds/clubs × A,2..10,J,Q,K) — the spec doesn't fix one. Recorded here since a different mapping would change the UI's `<select>` order but not the accumulator's security properties (any fixed bijection between the 52 cards and 0-51 is equivalent).
- **CSPRNG draw size (32 bytes per click)** is my choice, not specified. A user needing more manual-entropy bytes to XOR against (e.g., after many card draws) clicks the button multiple times; the UI's status text says exactly how many more bytes are needed.
- **Target bit-size options restricted to the five BIP-39 `ENT` values** (128/160/192/224/256) rather than "any multiple of 8 from 128 to 256" — narrower than a literal reading of "128–256 bits," justified because the only documented consumer (Seed Forge/BIP-39) can't use anything else. If a future consumer needs a different size, [ADR-0022](../adr/0022-entropy-lab-mixing.md) flags this as something to revisit.

## 9. What to scrutinise

- **The `-1` in `guaranteedBitsForRange` (`bitLength(range) - 1`).** This is the crux of the whole feature's honesty about how much entropy was actually collected. I derived it from "a range of size R has bit-length b, so R ∈ (2^(b-1), 2^b], hence only b-1 bits are guaranteed regardless of where in that interval R falls" — I'm confident this is *conservative* (never overclaims), but I have not proven it's the *tightest* conservative bound, and a reviewer with a stronger combinatorics background should check whether a tighter (still-safe) formula exists, especially for the card accumulator where the range isn't a power-of-6 or a clean base.
- **The counter-mode SHA-256 expansion for the mixing step is my own construction**, not HKDF (see ADR-0022's rejected-alternative section for why). It is simple and I've verified it against an independent SHA-256 implementation, but "simple and independently verified" is not the same bar as "reviewed cryptographic construction." If the reviewer has a security-design objection to inventing a KDF-like primitive instead of using the vendored `@noble/hashes/hkdf`, that's the single most likely place for a real finding, not a cosmetic one.
- **The DOM wiring in `main.js` is untested** (§6, §7). I traced it by hand against the element IDs in `index.html` but did not click through it in a real browser.
- **The `addCsprngBytes`/CSPRNG-unavailable UI path** (`src/cold/main.js`, the `entropyCsprngDraw` click handler) calls `cryptoLayer.randomBytes()`, which is already covered by `test/crypto.test.js`'s fail-closed behaviour, but I did not write a new test asserting the Entropy Lab UI itself surfaces that failure correctly — I traced it by reading the code only.
- **The `NO_MACHINE_PATHS` regex gap I found (§2)** is real but narrow (only triggers when a cold-realm source comment ends a line in `word:` right before a spot where that source gets JSON-embedded elsewhere in the build). I worked around it in my own two comments rather than fixing the regex, on the theory that fixing shared test infrastructure is out of scope for a single roadmap item's PR — but a reviewer may reasonably want that regex gap filed as its own follow-up issue so it doesn't silently bite the next contributor who writes a comment ending in a colon.

## 10. Self-assessment

- **What might be wrong:** the guaranteed-bits formula's tightness (see §9); the choice to invent a mixing KDF rather than reuse HKDF; the untested DOM wiring.
- **What I did not do that arguably should have been done:** a live browser click-through of every control; a dedicated regression test asserting the `NO_MACHINE_PATHS` false positive I found and fixed around (I fixed my own trigger but didn't add a test proving the gap exists, since fixing the shared regex is out of scope here); accessibility-suite coverage analogous to `test/accessibility.test.js`'s existing single hardcoded check, extended to a new Entropy Lab button.
- **Known limitations shipping with this change:** no bias detection on manual entropy sources yet (P1.2); no hand-off to a mnemonic (P1.3); no pattern-warning system (loaded dice, sequences) — all explicitly out of scope per the roadmap's own phasing.
- **Follow-up work this creates:** P1.2 (Entropy Health Meter, bias analysis) and P1.3 (Seed Forge, the actual consumer of this output) are already on the roadmap and unblocked by this PR. I'm not filing a new item for the `NO_MACHINE_PATHS` regex gap myself, since I'm not certain that's this project's convention for a narrow test-infra finding versus just flagging it here for the reviewer to decide — happy to file one if asked.
