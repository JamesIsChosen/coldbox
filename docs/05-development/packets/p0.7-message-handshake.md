# PR packet: P0.7 - MessageChannel handshake and schema validator

## 1. Summary

P0.7 replaces the provisional cold-realm readiness-only path with a private `MessageChannel` handshake and a shared typed protocol validator. The warm shell accepts the payload-free `cold.ready` bootstrap signal only from the created frame and only without transferred ports, creates a channel, and transfers `port2` in one exact `cold.handshake` message. The cold realm attaches `port1`, replies with a validated `ready` message, and both sides discard and log all later traffic received on the global `message` handler.

The protocol exposes only the message types defined by [architecture.md](../../01-spec/architecture.md), requires `{ id, type, payload }` on private-channel messages, strips unknown fields, and projects public records through an explicit allowlist. No cold-to-warm message shape can carry mnemonic, private key, xprv, passphrase, or secret-compartment plaintext fields.

This branch is based on the unmerged `p0.6-cold-realm-bootstrap` branch. Its PR base must therefore be `p0.6-cold-realm-bootstrap`.

## 2. Scope

### In scope

- Shared warm/cold protocol definitions and payload sanitizers in `src/protocol.js`
- Exact warm-to-cold and cold-to-warm message whitelists from the architecture specification
- `MessageChannel` creation, port transfer, typed readiness reply, and terminal handshake state
- Global-message discard and anomaly logging after the private channel is established
- Protocol unit tests for unknown types, unknown-field stripping, public projections, and secret-bearing fields
- Chromium and Firefox coverage for handshake readiness and post-handshake global-message injection
- Roadmap, changelog, and permanent PR-packet documentation

### Deliberately out of scope

- CSP canary, network-state banner, and runtime network neutering (P0.8)
- Capability detection, cryptography, vault storage, and secret-bearing operations
- Real-device certification, which remains P0.19
- Any merge of this branch or its dependency branches

## 5. Security impact

- Realm boundary: **Preserved.** The cold frame remains `sandbox="allow-scripts allow-downloads"` without `allow-same-origin`; the parent does not read its DOM or variables.
- Message schema: **Yes.** Private-channel traffic is direction-scoped, type-whitelisted, structurally validated, and reduced to safe allowlisted fields. The only global controls are the payload-free `cold.ready` bootstrap signal and the exact `cold.handshake` transfer envelope.
- Secret exposure: **Reduced by construction.** No validator output contains the prohibited mnemonic, private key, xprv, passphrase, or secret-compartment plaintext keys. No secret operation exists yet.
- CSP: **Unchanged and preserved.** The shared protocol source is embedded into both inline realms before the existing hash-pinning and cold-realm CSP assembly.
- Network: **Not expanded.** P0.8 still owns the canary, network-state signals, and runtime neutering; the cold realm retains `connect-src 'none'`.
- Origin handling: The channel uses `'*'` for `postMessage` because the sandboxed `srcdoc` frame has an opaque origin; the transferred port, not a reusable origin, is the private application channel.
- Global handlers: They remain installed solely to discard and log anomalous post-handshake messages. A global message cannot reopen the handshake or reach application protocol handling.

## 6. Test evidence

### New and changed tests

- `src/protocol.js` defines the shared protocol version, direction-specific message tables, payload sanitizers, public-field allowlists, and exact handshake controls.
- `scripts/build.js` embeds the protocol source into both warm and cold inline realms and rejects unresolved protocol placeholders.
- `src/main.js` creates/transfers the channel, validates the cold `ready` response, records terminal failure, and discards post-handshake global traffic.
- `src/cold/main.js` accepts the transferred port, validates channel messages, emits typed readiness, and discards post-handshake global traffic.
- `test/protocol.test.js` covers the complete documented whitelist and secret-field invariants.
- `scripts/run-browser-harness.js` and `test/browser/harness.js` verify private-channel readiness, global anomaly counters, warning logs, and existing CSP/opaque-frame checks.

### Negative tests

- Unknown warm-to-cold and cold-to-warm types return `null` from the validator.
- Unknown envelope, payload, collection, and public-record fields are stripped.
- Secret-bearing fields injected into every cold-to-warm message shape do not survive validation.
- A global message injected into the warm shell after handshake is discarded and logged.
- A global message injected into the cold frame after handshake is discarded and logged.
- Deliberate iframe creation failure still produces a visible terminal lockdown state.
- Deliberate forbidden `eval` source makes the build exit non-zero.
- Existing cold `fetch`, XHR, and WebSocket blocking, parent opacity, CSP violation, and byte-tampering checks continue to pass.

### Not tested

No real iOS Safari, Android Chrome from Files, macOS Safari, Linux Firefox, Tor Browser, or physical-device behavior was available. Those results are not inferred from headless Chromium and Firefox and remain part of P0.19.

## 8. Assumptions made

> **Assumed:** The payload-free global `cold.ready` signal remains the liveness bootstrap before the transferred port exists.
> **Basis:** The architecture explicitly separates cold readiness from the subsequent `MessageChannel` transfer; the bootstrap signal carries no identifier, payload, public data, or secret.
> **Not verified on:** Real-device browsers.
> **If wrong:** A later architecture decision must change the bootstrap boundary before secret-bearing operations are added; the private protocol does not depend on accepting global application messages.

> **Assumed:** `'*'` is the correct target origin for both bootstrap and channel-transfer messages.
> **Basis:** The sandboxed `srcdoc` child intentionally has an opaque origin, so no stable origin can be used for an origin-targeted transfer. The parent checks the frame source before accepting readiness, and subsequent application traffic uses the transferred port.
> **Not verified on:** Real-device browsers.
> **If wrong:** The target can be tightened only with a packaging/origin model that preserves the opaque sandbox boundary; no origin check is guessed into the current local-file artifact.

> **Assumed:** The documented public field allowlist is the correct initial projection for public compartment data.
> **Basis:** The architecture forbids secret-compartment plaintext across the boundary and names the public response shapes; dropping unknown fields is safer than forwarding future fields without review.
> **Not verified on:** Future message types or later vault schemas.
> **If wrong:** Adding a message type or public field requires an explicit schema review and a corresponding protocol test.

## 9. What to scrutinise

- The exact sequencing of the `cold.ready` signal, `MessageChannel` creation, one-time port transfer, and typed `ready` response.
- The parent no-port requirement on the bootstrap event and the child one-port requirement on the handshake event.
- The direction-specific type tables and whether every payload sanitizer returns only documented safe fields.
- The recursive secret-key assertion and the fact that unknown fields are dropped rather than forwarded.
- The post-handshake global listeners: they must only increment an anomaly marker, log a fixed warning, and return.
- The opaque sandbox token, inherited child CSP hashes, and the unchanged `connect-src 'none'` policy.
- The fact that P0.8 runtime network neutering and canary behavior remain unimplemented and explicitly out of scope.

## 10. Self-assessment

- P0.7 establishes the private protocol boundary but does not implement vault operations or secret handling; those must not be inferred from the validator alone.
- The global `cold.ready` signal is deliberately a liveness control, not an application message. All application-shaped messages require `{ id, type, payload }` on the transferred port.
- The validator strips unknown fields and rejects unknown types, so new protocol types require a code review and a test rather than silent pass-through.
- The browser harness covers Chromium and Firefox, including injected post-handshake global messages, but makes no physical-device claim.
- The artifact remains local-file compatible and deterministic; no network allowlist was expanded.
