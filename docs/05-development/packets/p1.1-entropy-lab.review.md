**F3 — Card undo is broken in the UI.** Drawing a card removed its `<option>` element directly; undo restored the internal accumulator state but never restored the option to the selector, desyncing the DOM from the session.

**F4 — Mixed output becomes stale.** Adding further entropy or CSPRNG input, or changing the target size, after a mix did not clear the previously displayed mixed result.

**F6 — CSPRNG material is reused.** Calling `mix()` twice without an intervening CSPRNG draw produced the same output from the same retained CSPRNG bytes, despite the UI and packet describing them as fresh.

**F7 — The documented "2 shuffles" path for 256-bit card entropy could not be entered.** There was only one 52-card pool with no second-shuffle/reset operation.

**F8 — SPEC requires mixing "with a diagram."** No diagram was added; the packet's acceptance-criteria table dropped that phrase rather than checking it verbatim.

**F9 — Browser verification remains missing.** `AGENTS.md`'s Definition of Done requires testing on at least one desktop and one mobile browser from `file://`; the packet explicitly marked the entire device matrix untested.

The CI workflow is designed to build the real PR head SHA, and the packet's evidence did not match it.

**F11 — The reviewer could not complete the mandatory independent clean checkout/vendor/build run.** Their shell could not resolve GitHub; hosted CI passed, but the review protocol requires the reviewer to reproduce those checks independently, which their environment did not permit.

## 4. Findings

### R3-F1 — Invalid stored provenance silently degrades security accounting and `mix()` still produces output

**Severity:** blocking security

**Location:** `src/cold/entropy-lab.js` — `independentExactBitCount()`, `diceGuaranteedBits()`, `cardGuaranteedBits()`, `guaranteedBits()`, `strengthSummary()`, `sourceEntropyBytes()`, and `mix()`.

**Observed:** The public `add*()` APIs correctly reject a provenance argument other than `manual` or `device-rng`, but the session's stored provenance is later consumed without validation. `isIndependentManual()` is only an equality test. An unknown stored value such as `mystery` is therefore silently treated as "not manual" instead of invalid security state.

Independent negative tests against the exact reviewed tip produced four failures:

```text
FAIL corrupted exact-bit provenance makes strengthSummary fail closed: did not throw
FAIL corrupted exact-bit provenance makes mix fail closed: did not throw
FAIL corrupted base6 provenance makes strengthSummary fail closed: did not throw
FAIL corrupted card provenance makes strengthSummary fail closed: did not throw
```

A concrete reproduction with 128 manually entered coin bits reports 128-bit independent fallback before corruption. Changing one stored provenance entry to `mystery` silently changes the accounting to 127 bits; after adding fresh CSPRNG bytes, `mix(session, 128)` still returns an output instead of refusing the invalid state.

**Expected:** Provenance is security state. Before emitting strength/fallback claims or producing mixed entropy, every stored provenance value that affects the session must be validated as exactly `manual` or `device-rng`. Invalid provenance state must throw/fail closed; it must never be converted into an implicit third provenance category by falling through equality checks.

**Required action:** Add a single auditable session/provenance validation boundary used by the security-reporting and mixing paths (at minimum `guaranteedBits`/`strengthSummary` and `mix`, directly or through shared helpers). Add regression tests that corrupt stored exact-bit, base-6-dice, and card provenance after otherwise-valid collection and require throws before any strength claim or output. The validator should also reject provenance-array/event inconsistencies that would make the claimed provenance ambiguous rather than silently choosing a conservative interpretation.

## 5. Verdict rationale

Round 3 successfully fixes the original generated-source provenance credit bug, separates normal strength from fallback strength, restores chronological exact-bit serialization, burns fresh CSPRNG correctly, passes the real Chromium/Firefox Entropy Lab harness, and reproduces exactly at the claimed artifact hash. However, the new provenance field is itself security state and the implementation validates it only at input time. Corruption of stored provenance is silently accepted by the reporting path and does not stop `mix()` from producing key material. The re-review request explicitly required invalid provenance state to fail closed, and `AGENTS.md` makes fail-closed behavior a hard constraint. A fresh re-review can PASS only after R3-F1 is fixed and independently reproduced.
