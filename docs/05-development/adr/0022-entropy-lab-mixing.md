# ADR-0022: Entropy Lab accumulation and mixing — integer accounting, XOR-then-hash

**Status:** Accepted
**Date:** 2026-08-07

## Context

[SPEC.md §11](../../01-spec/SPEC.md) and [entropy-and-strength.md](../../04-reference/entropy-and-strength.md) describe Entropy Lab (P1.1): dice (base-6 and a 4-outcome discard mapping), coin flips, playing cards, hex, and CSPRNG, combined by XOR-then-hash. The current security model deliberately separates **normal output strength** (the selected result size when the device CSPRNG is sound) from **independent-source fallback strength** (the conservative physical/manual entropy that remains if the device RNG is completely compromised). This ADR records the accounting, serialization, mixing-length rule, provenance model, and the exact condition for claiming **full two-source protection**.

**Revision note (post-review):** an earlier version of this ADR and its implementation added a 4-byte block counter to the hash step (`SHA-256(counter ‖ xored)`) to generalize to arbitrary output lengths, and left a CSPRNG-only session unable to generate anything at all. An independent review caught both: the counter construction doesn't match the literal formula in entropy-and-strength.md/first-wallet.md (proven by an independent Node-crypto hand computation showing the two formulas diverge), and it was also unnecessary, since every valid target size fits in one 32-byte SHA-256 block. The Decision section below describes the corrected design; see `docs/05-development/packets/p1.1-entropy-lab.md`'s remediation section for the full review history.

Two properties are non-negotiable given AGENTS.md's "fail closed" rule and SPEC §11.1a's insistence that entropy claims never exceed what was actually delivered:

1. **No floating-point arithmetic in independent-source security accounting.** `Math.log2(6) * n` accumulates rounding error. The fallback figure and the full-two-source threshold therefore use conservative integer/`BigInt` accounting only.
2. **Reproducible, byte-for-byte source serialization**, because the mix step needs an auditable source byte string and the accompanying tests pin it down with independent vectors.
3. **Normal output strength and fallback strength are different claims.** A sound CSPRNG may supply the selected 128–256-bit output strength even when physical/manual entropy is partial, but the UI must never call that partial contribution full two-source protection.

## Decision

**Guaranteed bits are computed from the size of the possibility space via `BigInt`, never from a sampled value or a float.**

- `n` base-6 dice rolls span a range of exactly `6^n` possible sequences. `guaranteedBits = bitLength(6^n) - 1` (the `-1` is deliberate: a range of size `R` sits in `(2^(b-1), 2^b]` where `b = bitLength(R)`, so only `b - 1` bits are guaranteed regardless of where in that interval `R` falls — rounding up would overclaim by up to one bit).
- `k` card draws without replacement from a 52-card deck span `52 · 51 · … · (52-k+1)` sequences (a falling factorial), accumulated the same way: `guaranteedBits = bitLength(range) - 1`.
- Coin flips, the 4-outcome discard dice mapping, and hex nibbles are each claimed to be exactly uniform per unit (1, 2, and 4 bits respectively) and are appended directly as bits — no accumulator needed, and nothing to round.

This matches the worked example already in entropy-and-strength.md (50 base-6 rolls ≈ 129.2 bits by the `n·log2(6)` estimate used for explanatory copy) while keeping the security-relevant fallback/full-protection calculation on integer arithmetic. The two numbers can differ by a fraction of a bit; `strengthSummary()` always uses the conservative integer value.

**Serialization for mixing:** the base-6 accumulator and the card accumulator are each independent `BigInt`s. Each is serialized to the minimum number of *whole bytes* that can hold its declared range (`ceil(bitLength(range) / 8)`), big-endian, zero-padded. Exact bits (coins, discard-mode dice, hex) are flattened from the chronological `exactBitEvents` ledger and packed MSB-first with padding applied once. `sourceEntropyBytes = exactBitsBytes ‖ diceBytes ‖ cardBytes` (any source not used contributes zero bytes). Provenance changes security credit, not byte encoding, so this aggregate may contain both physical/manual and device-RNG-simulated values. The ordering is fixed and load-bearing for the test vectors in `test/entropy-lab.test.js`.

Using whole-byte serialization sized off the *declared range* rather than the *sampled value* means the accumulator's actual value does not need to be uniformly distributed over those bytes — a base-6 accumulator's range `[0, 6^n)` is not a power of two, so its raw byte representation is measurably non-uniform. That non-uniformity is exactly what the hash step exists to erase (see below); the byte-length choice only needs to be *reproducible and long enough*, not uniform.

**Generation has two paths, chosen by whether any dice/coin/card/hex source material was recorded:**

- **No source material (direct CSPRNG-only).** `mix()` returns the requested number of fresh CSPRNG bytes directly. There is no independent-source fallback: `strengthSummary()` reports the selected normal output size and `0` fallback bits.
- **Source material present (XOR-then-hash).** Let `targetBytes = targetBits / 8` and `sourceBytes = sourceEntropyBytes(session)`. The XOR length is `max(targetBytes, len(sourceBytes))`. If `sourceBytes` is shorter than the selected output, it is **right-padded with zero bytes only for the XOR operation**; its canonical serialization is not changed. The function consumes exactly that many fresh CSPRNG bytes, XORs equal-length buffers, hashes once with SHA-256, and truncates the digest to the selected output size. If source material is already at least the target length, established serialization/mixing vectors remain byte-for-byte unchanged.

The minimum-CSPRNG-length rule is load-bearing for the new strength semantics. A 256-bit selection with only 32 bits of physical/manual entropy must still consume at least 32 fresh CSPRNG bytes; otherwise calling the result "256-bit normal output strength" would be false. Under a sound CSPRNG the selected target is the normal output strength. Under a completely compromised device RNG, `strengthSummary()` reports `min(independentBits, targetBits)` as the independent-source fallback. The raw independent count itself is never capped; only fallback of a fixed-length output is naturally bounded by that output length.

**Full two-source protection is a label, not a prerequisite for generation.** It is true only when conservative physical/manual credit reaches or exceeds `targetBits`. A partial manual contribution may still be useful and may be mixed, but the UI must label its smaller fallback honestly. Device-RNG-generated dice/coins/cards/hex have `device-rng` provenance, contribute zero independent bits, and therefore can never create full two-source protection even though they may remain in `sourceEntropyBytes()` for simulation convenience.
**Both paths consume ("burn") the CSPRNG bytes they use.** `mix()` removes the bytes it read from `session.csprngBytes` before returning. This was added after review found that calling `mix()` twice without an intervening CSPRNG draw silently produced the same output from the same retained bytes, contradicting the "fresh CSPRNG bytes" framing in both the UI copy and this document. With burn-on-use, a second `mix()` call fails closed exactly like running out of CSPRNG bytes always does, rather than reusing them.

**Alternative considered and rejected: HKDF.** `@noble/hashes/hkdf` is already vendored and used elsewhere in the cold realm (crypto.js). HKDF-Extract-then-Expand with `IKM = manualBytes`, `salt = csprngBytes`, would be a more standard construction and get the "XOR-then-hash" property implicitly through HMAC. It was rejected here because the shipped user- and reference-docs (entropy-and-strength.md, first-wallet.md) already commit to the literal formula `SHA-256(user_entropy XOR csprng_output)` as the explainable, hand-verifiable construction — a user with a calculator and a hex dump can reproduce it, which HMAC's inner/outer padding makes harder to walk through by hand. If a future review finds a cryptographic reason to prefer HKDF (e.g., need for domain separation across multiple simultaneous sessions), that is a breaking change to the format and needs its own ADR, not a quiet substitution.

**Undo is a per-operation history stack of closures**, each capturing the exact prior state (previous `BigInt` value, previous array length, previous CSPRNG buffer reference) rather than a generic snapshot/diff system. Given realistic session sizes (at most a few hundred manual entries before mixing), this is simpler to audit than a diffing scheme and every `add*` function owns writing its own correct inverse next to the forward operation, so a reviewer can check each pair together.

**Cards support multiple shuffles.** entropy-and-strength.md's table lists "2 shuffles" as the path to a 256-bit target from cards, but a single `[0, 52!)` accumulator only has room for one 52-card pass (≈225 bits, short of 256). `startNewCardShuffle()` refills `cardRemaining` to all 52 cards once the current pool is exhausted, *without* resetting `cardValue` or `cardOrder` — each draw's pool size (recorded per-draw in `cardDrawPoolSizes`, not re-derived from a `52 - i` formula) is multiplied into the same running accumulator, so a second shuffle's draws compound onto the first's rather than starting over. Reshuffling with cards still remaining in the pool is refused (fail closed): the currently accepted pool state would otherwise not correspond to any of the recorded `cardDrawPoolSizes` entries.

## Consequences

- The sticky Entropy Lab meter shows **Normal output strength**, **Independent physical/manual entropy**, and **Fallback if device RNG is compromised** separately. A selected 256-bit output may therefore truthfully show 256-bit normal strength and only ~32-bit fallback.
- `guaranteedBits()` remains the conservative independent physical/manual count. `strengthSummary(session, targetBits)` derives `fallbackBits = min(independentBits, targetBits)` and `fullTwoSourceProtection = independentBits >= targetBits` without altering the underlying count.
- Mixed output remains capped at the five BIP-39 `ENT` sizes. If a future consumer needs a different length, `VALID_TARGET_BITS` must be revisited explicitly.
- CSPRNG bytes required for a mixed transformation are `max(targetBytes, sourceEntropyBytes.length)`. Very large recorded source material can therefore require more CSPRNG bytes than the output length; this is shown to the user rather than silently truncating source material.
- A CSPRNG-only or generated-simulation-only result is not mislabeled as two-source protection. Partial real manual entropy produces partial independent fallback; only target-reaching real manual entropy earns the full-protection state.
- Because CSPRNG bytes are burned on use, a user who mixes and wants another output must draw fresh CSPRNG bytes again. Undo cannot resurrect spent bytes.

## Amendment (round-2 review): CSPRNG consumption is a monotonic offset, not a destructive slice

The "burn" mechanism described above (`mix()` removes the bytes it read from `session.csprngBytes`) was the original implementation, and a second independent review found it buggy: `session.csprngBytes` was replaced with a shorter sliced array on every `mix()` call, but `addCsprngBytes`' undo closure had captured a *reference* to the pre-mix array at draw time. If that closure was popped (via undo) after a later `mix()` call had already replaced `session.csprngBytes` with a new, shorter array, the undo silently restored the old, longer array — resurrecting bytes `mix()` had already spent, indistinguishable from fresh ones.

**Fix:** `session.csprngBytes` is now append-only except for undo, which may only *truncate* it (removing bytes, including ones already marked spent — never regrowing removed ones back in). A separate `session.csprngConsumed` field is a byte offset, monotonically increasing, marking how many leading bytes are already spent; `availableCsprngBytes(session) = session.csprngBytes.subarray(session.csprngConsumed)` is the single source of truth for "what's left." `mix()` advances the offset; nothing ever moves it backward except `addCsprngBytes`' undo clamping it down (never up) to stay within the now-shorter array after a truncation. This makes the resurrection bug structurally impossible rather than merely harder to trigger: undo can only remove information, never restore it, and "spent" is tracked as a position, not as which array object happens to be currently assigned.

## Amendment (UX overhaul): per-source Reset buttons, exactBits split, and history-kind tagging

Hands-on manual testing (browser verification, per ADR-0023's F9 disposition) surfaced that the original all-or-nothing "Undo last" control made it impractical to clear just one source's contribution — a user who wanted to abandon a partial run of dice rolls without also losing coin flips and hex digits already recorded had no way to do it short of undoing every intervening operation one at a time, in reverse order, hoping not to overshoot.

**Decision:** each source (dice, coin, cards, hex, CSPRNG) gained an independent `reset*(session)` function (`resetDice`, `resetCoin`, `resetCards`, `resetHex`, `resetCsprng`) that clears only that source's accumulated state. This required two structural changes:

1. **The source-local UI state remains split (`coinBits`, `discardDiceBits`, `hexBits`), but exact-bit serialization uses a chronological `exactBitEvents` ledger.** The first UX-overhaul implementation incorrectly packed those three arrays independently and claimed that was byte-equivalent to the original shared stream. It is not: padding a one-bit coin value before a following four-bit hex nibble inserts padding that never existed in the combined stream. The corrected design records each coin/discard-dice/hex operation as `{ kind, bits, provenance }` in insertion order. `reset*()` filters only matching events; surviving events retain their relative order; `sourceEntropyBytes()` flattens the surviving exact bits once and applies byte padding once, preserving the original exact-bit format. Base-6 dice and card accumulators remain the same fixed trailing fields.
2. **History entries gained a `kind` tag** (`{kind, undo}` instead of a bare closure), and a new `purgeHistoryKind(session, kind)` removes every entry of a given kind from anywhere in the stack, not just the top. Every `reset*(session)` calls this for its own kind. Without it, a `reset*()` call would leave stale undo closures for the just-cleared source sitting in `session.history`; if one of those closures were later popped (via "Undo last" reversing through unrelated intervening operations), it would restore state the reset had deliberately discarded — the exact same resurrection bug class the CSPRNG `csprngConsumed` fix above exists to prevent, now generalized to every source. 7 regression tests in `test/entropy-lab.test.js` cover this: each reset function is checked to clear its own data, leave every other source's data and history untouched, and leave nothing for a subsequent `undoLast()` to resurrect.

Also added: a "Generate with device RNG" control per source, implemented through `src/cold/main.js`'s rejection-sampled `drawUniformInt`. **Those generated values are not independent manual entropy.** Every `add*` API now accepts an audited provenance (`manual` by default, or `device-rng`); generated controls pass `device-rng`. The values remain in the same source accumulators/serialization for simulation convenience, but `guaranteedBits()` counts only `manual` provenance. A generated-only dice/coin/card/hex session therefore has zero independent-manual credit. It may still produce a normal CSPRNG-backed output when enough fresh CSPRNG bytes are present, but it remains explicitly classified as CSPRNG-only security with 0-bit independent fallback. This distinction lives in `entropy-lab.js` state/accounting, not only in DOM copy.

## Amendment (round-3 maintainer review): provenance is security state, and exact-bit padding is single-stream

A targeted maintainer review of the UX-overhaul candidate found two structural errors that were not cosmetic:

1. The per-source Generate controls used the same browser/device CSPRNG (`crypto.getRandomValues`, through Coldbox's crypto layer) and then called the ordinary `add*()` functions. The old accounting therefore credited those simulated values as if they were physical/manual entropy. **Fix:** provenance is now carried in Entropy Lab state. `manual` values receive independent-source credit; `device-rng` values receive zero. The UI no longer treats security as one number: `strengthSummary()` reports selected normal output bits separately from independent fallback and full-two-source status. Generated values may remain in the transformation, but they can never increase fallback or create the full-protection claim.
2. Splitting the shared exact-bit array for Reset introduced an undocumented format change because `coinBits`, `discardDiceBits`, and `hexBits` were independently byte-padded. **Fix:** `exactBitEvents` restores chronological exact-bit serialization. Coin, discard-dice, and hex bits are flattened in insertion order and padded once. Reset removes only the selected source's events while preserving surviving relative order; Undo removes the exact event it created rather than truncating the ledger by a stale pre-reset length.
3. A follow-up maintainer clarification required the UI to distinguish normal output strength from compromised-RNG fallback strength. That exposed a cryptographic requirement, not just copy: partial source material shorter than the selected output must not cause the mixed path to consume only that short amount of CSPRNG. **Fix:** the XOR input is at least `targetBytes`; shorter canonical source bytes are right-padded only for XOR, so a 256-bit normal output always consumes at least 256 fresh CSPRNG bits while preserving the exact serialization itself.

The regression suite includes cross-source byte vectors (`coin + hex`, `coin + discard-dice + hex`, ordering differences), Reset/Undo ordering cases, generated-only provenance cases for every simulated source, partial-real-manual + generated cases, target-change/full-protection state, target-length CSPRNG consumption, and independent Node/OpenSSL SHA-256 vectors. Any future change to this byte format is a cryptographic format change and requires an explicit ADR amendment plus independent vectors; UI convenience is not sufficient justification to redefine it.
