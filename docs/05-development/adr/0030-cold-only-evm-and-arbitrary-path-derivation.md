# ADR-0030: Cold-only EVM and generic arbitrary-path derivation

**Status:** Accepted
**Date:** 2026-08-10
**Review date:** 2026-08-10

## Context

P1.4 established the cold-only BIP-32 engine for Bitcoin's four single-key
script types. The specification also requires EVM derivation and a generic
arbitrary-path mode for recovery-critical key material. EVM uses the same
secp256k1 curve but a different address rule: Keccak-256 over the uncompressed
public-key body followed by the ERC-55 mixed-case checksum. Generic mode must
support paths that Coldbox cannot predict in advance, including the raw keys
and WIF needed to recover an unknown coin whose address formatter is not yet
implemented.

The warm shell remains network-capable and must never receive a seed, private
key, extended private key, or secret generic-path result. The existing vendored
bundle already contains the required curve, BIP-32, Base58Check, and hash
families; adding a new runtime dependency or message would enlarge the trust
boundary.

## Decision

- Add the already-pinned `@noble/hashes/sha3.js` module to the offline crypto
  bundle and expose only its Keccak-256 function to the cold realm.
- Derive EVM accounts at `m/44'/60'/account'/change/index`, with bounded
  account/change/index batches and a standard account-level xpub watch-only
  mode. One checksummed EVM address is valid for every EVM chain in the
  registry; chain IDs are registry metadata, not separate derivations.
- Implement ERC-55 checksum formatting from lowercase hexadecimal address
  text. Accept all-lowercase and all-uppercase addresses as valid unchecksummed
  forms for later verification, while mixed-case text must equal the computed
  checksum.
- Implement a cold-local arbitrary-path projection for any canonical BIP-32
  path. The private projection includes raw 32-byte private/public keys,
  xprv/xpub, and compressed WIF. The public xpub projection permits only
  non-hardened descendants and contains no private material.
- Keep all new operations inside the existing cold derivation module. No
  warm/cold message type, CSP exception, or network capability is added.

## Rationale

Keccak-256 and secp256k1 are already protocol-mandated and vendored, so this
extends the audited primitive surface without introducing a new package or a
second implementation. The explicit arbitrary-path private projection is
necessary for recovery of unknown or not-yet-formatted assets, but naming and
keeping it as a cold-local result makes its secret-bearing nature visible to
future callers. Public EVM and xpub helpers remain safe to project only because
they return addresses and extended public metadata.

The EVM account path follows the path structure already documented in the
reference guide and the go-ethereum path iterator. The checksum and address
fixtures come from the official ERC-55 specification and the ethereumjs HD-key
test fixture, rather than values generated by Coldbox itself.

## Consequences

### Positive

- EVM addresses can be derived offline and checked against the standard
  checksum without exposing a seed to the warm shell.
- A watch-only EVM account can generate addresses from an account xpub without
  private-key access.
- Generic paths provide the recovery-critical private/public key and WIF
  material even when no address formatter exists.
- Strict canonical paths, bounded batches, hardened public rejection, and
  account-depth checks keep ambiguous inputs fail-closed.

### Negative

- The generic private projection is intentionally secret-bearing and must never
  be serialized into a public result or added to a cross-realm message.
- EVM has no separate network encoding; all EVM chains share the address and
  derivation path, so chain identity remains registry metadata.
- The arbitrary mode is BIP-32/secp256k1 only. SLIP-0010/ed25519, multisig,
  descriptors, and chain-specific formatters remain later work.

### Risks

An incorrect Keccak input (hashing the compressed key, the `0x` prefix, or
  mixed-case text) changes every EVM address. An incorrect arbitrary WIF
version or path interpretation can make a recovery key unusable. Official
ERC-55 and ethereumjs fixtures, strict input validation, and the cold-only
boundary are the controls for these risks.

## Alternatives considered

### Use SHA3-256 for EVM addresses

Rejected. Ethereum uses legacy Keccak-256, which differs from standardized
FIPS SHA3-256 in padding. The vendored module exposes both families; only
`keccak_256` is used here.

### Derive EVM or generic secrets in the warm shell

Rejected. It would require crossing the two-realm boundary with secret key
material and would make the network-capable shell part of the recovery trust
base.

### Add an EVM-specific crypto package

Rejected. The required Keccak and secp256k1 primitives are already vendored and
independently verified. A second address/curve package would add code and
version drift without a security benefit.

### Return raw generic private keys through the existing public projection

Rejected. The generic private projection is a distinct cold-local API. The
public Bitcoin/EVM helpers and the xpub projection contain no private fields,
and the protocol schema remains unchanged.

## What would change our mind

An independent audit finding in the pinned `@noble`/`@scure` releases, a
standards change to Ethereum address checksums, a requirement for an ed25519
generic mode, or a future UI design that cannot preserve the cold-only secret
projection would require a superseding ADR.
