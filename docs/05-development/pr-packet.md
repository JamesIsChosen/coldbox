# The PR packet

Every unit of work ships as a **PR packet**: the branch, plus a document that lets someone who wasn't involved verify the work **without trusting the person or agent who did it**.

That framing drives everything below. A packet that says "I tested it and it works" is worthless for independent review. A packet that says "here is the command, here is its output, here is what I could not verify" is useful.

---

## Where it lives

`PR-PACKET.md` at the repo root on the working branch, deleted or superseded before merge. Its contents also go in the PR description.

---

## Required sections

### 1. Summary

Which roadmap item, what changed, in three sentences or fewer. Link the item.

### 2. Scope

What is **in** this PR and what is deliberately **not**. If you touched something outside the roadmap item, say why.

### 3. How to verify

Exact commands a reviewer runs, with the output you got. Not a description — the commands and their output.

```
$ npm ci && npm run verify-vendor
<paste>

$ npm run build && shasum -a 256 build/coldbox.html
<paste>

$ rm -rf build && npm run build && shasum -a 256 build/coldbox.html
<paste — must match the previous hash>

$ npm test
<paste>
```

### 4. Acceptance criteria

Copy them verbatim from the roadmap item. For each: how it's satisfied, and which test proves it.

| Criterion | How satisfied | Test |
|---|---|---|
| | | |

An unmet criterion means the item isn't done. Say so rather than reinterpreting the criterion.

### 5. Security impact

- Does this touch the realm boundary, the message schema, the CSP, the vault format, derivation, or randomness? Yes/no per item.
- **If yes: what does an attacker gain if this implementation is wrong?**
- Any new `connect-src` host, and what it learns about the user.
- Any new message type, and proof it cannot carry secret material.

If the honest answer to the second question is "I'm not certain," write that. It's the most useful sentence in the packet.

### 6. Test evidence

- New tests added, and what each proves
- Vector sources — **which independent implementation**, with a link
- Negative tests: what you made fail deliberately, and how it failed
- Anything you could not test, and why

### 7. Device matrix

Required for anything touching bootstrap, CSP, storage, or rendering.

| Platform | Result | Notes |
|---|---|---|
| Windows Chrome | | |
| Windows Firefox | | |
| macOS Safari | | |
| macOS Chrome | | |
| Linux Firefox | | |
| **iOS Safari (Files)** | | |
| Android Chrome (Files) | | |
| Tor Browser | | |

Untested platforms are marked untested. Never inferred from a similar one.

### 8. Assumptions made

Every decision not settled by the spec. This is where a reviewer finds the real risk.

> **Assumed:** `srcdoc` iframes inherit parent CSP on iOS Safari 18 as they do on desktop.
> **Basis:** spec text and desktop testing.
> **Not verified on:** iOS 17 and earlier.
> **If wrong:** the cold realm may not be sealed on older iOS; the canary should catch it, but that path is untested there.

### 9. What to scrutinise

Direct the reviewer's attention. Where are you least confident? What's subtle? What would you look at if you were reviewing someone else's version of this?

Answering "nothing, it's straightforward" is almost always wrong and reads as such.

### 10. Self-assessment

- What might be wrong with this?
- What did you not do that arguably should have been done?
- Known limitations shipping with this change
- Follow-up work this creates, with roadmap items filed

### 11. Bundle impact

Before / after / delta, in KB. Note if the budget is threatened.

### 12. Docs updated

Which docs changed. Help content at all three depths for user-facing features. ADR added for structural decisions.

## Standards of evidence

**Show, don't assert.** "Reproducible build verified" is an assertion. Two hashes pasted from two builds is evidence.

**Independent test vectors only.** Vectors generated by the implementation being tested prove nothing. Cite the BIP, the reference library, or the hardware wallet.

**Negative results count.** "I tried X to break it and it held" is evidence. "I tried X and it broke, here's the fix" is better evidence.

**Absence of evidence is reportable.** Couldn't test on iOS because you don't have a device? Say so, in the matrix and in assumptions. A gap you flagged is a manageable risk. A gap you hid is a latent failure.

---

## Reviewer checklist

For whoever reviews — human or agent:

- [ ] Every acceptance criterion is met and evidenced, not reinterpreted
- [ ] Verification commands reproduce the stated output on my machine
- [ ] Build hash matches across two of my own builds
- [ ] Test vectors come from a genuinely independent source
- [ ] No new message type can carry secret material
- [ ] CSP unchanged, or the change is justified and has an ADR
- [ ] No secret can reach `localStorage`, the URL, the page title, or session restore
- [ ] `getRandomValues` used for all key material; no `Math.random` in any security path
- [ ] Failure modes fail **closed**, not open
- [ ] Assumptions are stated and plausible
- [ ] Device matrix is filled honestly, with gaps marked rather than inferred
- [ ] Docs and help content updated in this PR
- [ ] Roadmap status updated

**Reject rather than accept when unsure.** The cost of a delayed merge is hours. The cost of a wrong merge in a tool that handles seed phrases is someone's savings.

---

## Automatic rejection

No amount of good work elsewhere offsets these:

- A secret can cross the realm boundary
- `connect-src 'none'` removed or weakened in the cold realm
- Build is not reproducible
- A vendored dependency doesn't match its upstream hash
- Test vectors are self-generated
- A failure mode fails **open**
- `Math.random` in a security-relevant path
- A chain added without independent test vectors
- Acceptance criteria reinterpreted rather than met
