## 4. Findings

### F1 — P1.4 mistranscribes an official BIP-32 xpub and falsely labels the upstream vector invalid

**Severity:** blocking cryptographic correctness / independent-vector integrity
**PR:** #37 / P1.4
**Location:** `test/derivation.test.js`, BIP-32 vector 1 at `m/0'/1/2'`; P1.4 packet/self-review text

**Observed:** The official BIP-32 vector contains:

```text
...VJrZwQY4VUN...
```

The test fixture contains:

```text
...VJrZwY4VUN...
```

with the `Q` missing. The test then says the published `bitcoin/bips` row is checksum-invalid, marks the local typo `invalidXpub: true`, and deliberately skips the direct equality assertion for `node.publicExtendedKey`.

**Expected:** Independent-vector tests must reproduce the actual upstream value exactly. A local transcription error must not be converted into a claim that the primary source is invalid.

**Required action:** Copy the exact official xpub, remove the `invalidXpub` exception, assert the product xpub equals the official vector at this derivation step, and correct every packet/self-review statement claiming the upstream row is invalid.

### F2 — P1.4 Bitcoin watch-only derivation does not enforce an account-level xpub

**Severity:** blocking derivation correctness
**PR:** #37 / P1.4
**Location:** `src/cold/derivation.js`, `deriveBitcoinFromXpub()`

**Observed:** The function rejects only `accountNode.depth === 0`. Depth 1, 2, 4, 5, and other non-account nodes are therefore accepted and then treated as the base for `/change/index` address derivation, despite the API error text and documentation requiring an account-level extended public key.

**Expected:** The watch-only Bitcoin helper must fail closed unless the imported key has the exact structural shape the API claims to accept.

**Required action:** Enforce account depth 3 and the hardened account child-number invariant. Add negatives for depth 0/1/2/4 and a depth-3 non-hardened child, plus valid BIP-49/84/86 account-xpub cases.

### F3 — P1.4 `addressFromPublicKey()` does not validate that non-Taproot input is a secp256k1 point

**Severity:** blocking fail-closed address correctness
**PR:** #37 / P1.4
**Location:** `src/cold/derivation.js`, `addressFromPublicKey()`

**Observed:** The exported helper checks only for 33 bytes and a `0x02`/`0x03` prefix. P2PKH, P2SH-P2WPKH, and P2WPKH then hash those bytes directly without parsing/validating the point. Taproot happens to call `secp.Point.fromBytes()`, but the other script types can produce an address from a syntactically shaped byte string that is not a point on secp256k1.

**Expected:** A function claiming to accept compressed secp256k1 public keys must validate curve membership before deriving any address. Invalid point bytes must fail non-zero/thrown rather than produce a potentially unspendable address.

**Required action:** Parse/validate the compressed key as a secp256k1 point before every script-family address calculation and add invalid-point negatives for all four script types.

### F4 — P1.5 EVM watch-only accepts a non-hardened depth-3 key and reports it as a hardened account path

**Severity:** blocking derivation/path integrity
**PR:** #38 / P1.5
**Location:** `src/cold/derivation.js`, `deriveEvmFromXpub()`

**Observed:** The function requires `depth === 3`, but accepts either a hardened or non-hardened child number. For a non-hardened depth-3 key it strips the hardened bit only if present, then reports paths using `m/44'/60'/account'/...`, falsely representing that key as a standard hardened EVM account.

**Expected:** The standard EVM account helper must accept only an account node whose child number is hardened. The xpub cannot prove its hidden ancestors, so documentation should state that limitation rather than infer more than serialization proves.

**Required action:** Reject depth-3 keys whose child index is below the hardened offset, add a negative test, and retain explicit documentation that purpose/coin ancestors cannot be proven from an xpub alone.

### F5 — P1.6 accepts orphan Account/Address relationships when loading or replacing a Registry snapshot

**Severity:** blocking data-integrity / fail-closed behavior
**PR:** #39 / P1.6
**Location:** `src/registry.js` `createStore()` / `replace()`; `src/protocol.js` `cleanPublicCompartment()`

**Observed:** `createStore()` and `replace()` perform schema validation and then accept the full state. Relationship checks are performed only by individual `insert()` and `update()` operations. A pre-existing Account may therefore reference a missing Wallet, and an Address may reference a missing Account, without the store rejecting the snapshot.

**Expected:** The complete public projection must satisfy the same relationship invariants regardless of whether it arrived through CRUD, vault open, or acknowledgement replacement.

**Required action:** Add whole-compartment relationship validation before initial state acceptance and before replacement. Add tests for orphan Account and Address records in loaded/replaced snapshots and confirm the surrounding session fails closed.

### F6 — P1.6 update semantics cannot clear optional Registry fields, and P1.8 repeats the defect for Device metadata

**Severity:** blocking CRUD correctness

### F11 — P1.9 passphrase verification trims significant BIP-39 passphrase spaces

**Severity:** blocking wallet-identity correctness
**PR:** #42 / P1.9
**Location:** `src/cold/verification.js`, `text()` and `verifyPassphrase()`

**Observed:** `text()` performs `.normalize('NFKD').trim()`. `verifyPassphrase()` calls `text(settings.passphrase, ...)` before deriving the fingerprint. Leading/trailing spaces are therefore discarded. For example, a passphrase such as `" TREZOR"` is derived as `"TREZOR"` even though BIP-39 defines the seed salt as `"mnemonic" + passphrase` after NFKD normalization; it does not trim the passphrase.

**Expected:** Every passphrase character must participate in derivation. Different passphrases must produce different wallet identities.

**Required action:** Use NFKD normalization without trimming for the secret passphrase, preserve exact code points after normalization, and add vectors proving leading/trailing/internal spaces remain significant.

### F12 — P1.9 public identifier comparison is over-normalized and accepts invalid mixed-case Bech32

**Severity:** blocking verification integrity
**PR:** #42 / P1.9
**Location:** `src/cold/verification.js`, `text()`, `expectedPublicValue()`, `expectedFingerprint()`, `normalizeReceiveAddress()`

**Observed:** The generic text helper NFKD-normalizes and trims public fingerprints, extended keys, addresses, and account-xpub input. Unicode compatibility characters can therefore be silently converted into ASCII before an "exact" comparison. Separately, `normalizeReceiveAddress()` lowercases any `bc1...`/`tb1...` value, which converts invalid mixed-case Bech32 text into a potentially matching lowercase value.

**Expected:** BIP-39 mnemonic/passphrase normalization must not be reused as public-identifier correction. Base58/extended keys and fingerprints require strict canonical character validation; Bech32 may accept uniform all-lower or all-upper presentation but MUST reject mixed case.

**Required action:** Separate secret-text normalization from public-value parsing, enforce ASCII/canonical forms for fingerprints/xpubs/Base58, validate Bech32 case/checksum rules before comparison, and add fullwidth/compatibility-character plus mixed-case negatives.

### F15 — P1.9 Verify Bench is disconnected from the active Seed Forge wallet

**Severity:** blocking verification-workflow completeness / secret-handling UX
**PR:** #42 / P1.9
**Location:** Verify Bench UI and cold-local verification workflow integration

**Observed:** Seed Forge and Verify Bench both execute inside the cold realm, but Verify Bench does not consume the currently active generated/validated Seed Forge wallet. Instead, the user must manually re-enter mnemonic/passphrase material or manually supply already-derived values before the bench can perform the corresponding checks. The current workflow therefore fails to expose the most useful public identity of the active wallet — fingerprint, account xpub family, derivation path, receive/change addresses, and address range — as a directly linked cold-local verification surface.

**Expected:** Verify Bench should offer a cold-local `Use current Seed Forge wallet` handoff. The active Seed Forge mnemonic/passphrase state should remain inside the cold realm while Verify Bench derives and displays the public wallet identity needed for verification. External expected values must remain independent inputs so the bench compares Coldbox-derived public values against a hardware wallet, backup record, or other external source rather than auto-filling both sides from the same computation.

**Required action:** Add a cold-local Seed Forge -> Verify Bench handoff that:
- consumes the active generated or validated Seed Forge wallet without crossing the warm realm;
- exposes the current wallet fingerprint, relevant xpub/ypub/zpub/tpub/upub/vpub, derivation path, script/network, and receive/change addresses/range;
- keeps independently supplied external expected values separate;
- invalidates/clears the linked Verify Bench wallet state on Seed Forge replacement, lock, panic, or cold-session teardown;
- adds Chromium/Firefox coverage proving the handoff never crosses the realm boundary and that external comparison values remain independent.

### F16 — P1.9 standalone BIP-39 Passphrase shell duplicates Seed Forge and should be removed

**Severity:** blocking workflow design / unnecessary secret-entry surface
**PR:** #42 / P1.9
**Location:** Verify Bench BIP-39 Passphrase panel and associated duplicated secret-entry controls

**Observed:** Verify Bench contains a standalone BIP-39 Passphrase workflow that asks for mnemonic/passphrase/passphrase confirmation plus an expected fingerprint even though Seed Forge is already the authoritative cold-realm surface for entering, confirming, generating, and validating BIP-39 wallet secrets. This duplicates secret entry, creates another state that can diverge from Seed Forge, and increases the chance of user transcription mistakes.

**Expected:** Passphrase selection/confirmation belongs in Seed Forge. Verify Bench should consume the active Seed Forge wallet through F15 and verify its derived public identity against external values. A separate secret-entry passphrase shell is unnecessary.

**Required action:** Remove the standalone BIP-39 Passphrase panel and duplicated secret-entry controls from Verify Bench. Preserve cryptographic/unit coverage proving distinct BIP-39 passphrases derive distinct wallet identities, update help/docs/browser tests accordingly, and route passphrase-dependent verification through the active cold-local Seed Forge wallet state instead.
