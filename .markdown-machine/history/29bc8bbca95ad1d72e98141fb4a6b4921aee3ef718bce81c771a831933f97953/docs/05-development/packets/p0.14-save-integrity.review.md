## 4. Findings

### F1 — Opening a newer vault does not persist it as the rollback high-water mark

**Severity:** blocking acceptance defect
**Location:** `src/main.js` — startup `readGeneration(...)`, `completeVerifiedSave()`, and `handleVaultOpened()`; `docs/01-spec/vault-format.md` § Rollback detection; `docs/05-development/adr/0013-save-integrity-in-warm-shell.md` § Decision.

**Observed:** The implementation initializes `saveGeneration` from `localStorage`. The only visible persistence call, `saveIntegrity.writeGeneration(...)`, is inside `completeVerifiedSave()`, which runs after this browser performs a verified File System Access save. When an existing vault is opened, `handleVaultOpened()` parses its filename and evaluates rollback against the existing `saveGeneration`, but does not assign a newer opened counter back to `saveGeneration` or persist it.

That contradicts the branch documentation, which says the single `localStorage` record holds "the highest counter this browser profile has seen" and that opening an older generation than the highest seen warns.

A concrete failing sequence is:

1. Browser profile has persisted high-water counter 47 (or zero on a fresh profile).
2. Open `coldbox-vault-0100.cbx`. No open-path `writeGeneration(...)` persists 100.
3. Reload the app. Startup reads 47 again.
4. Open `coldbox-vault-0080.cbx`.
5. Counter 80 is newer than the stale persisted 47, so it is not recognized as a rollback even though this same browser profile previously saw counter 100. The required older-vault warning with both dates and counters is therefore absent.

The same stale state can also make the next suggested save generation regress relative to a newer loaded filename, because `nextSuggestedFilename()` derives from `saveGeneration` rather than the highest successfully opened generation.

**Expected:** Once an opened filename successfully parses to a generation higher than the current browser-profile high-water mark, that generation must become the remembered high-water mark for future rollback checks (including after reload), while lower generations must warn with both dates and counters.

**Required action:** Advance and persist the high-water record when a successfully opened parseable filename has a higher counter than the remembered value, without lowering it for older files. Add regressions that cover at least `47 → open 100 → reload → open 80` (must warn with both counters and dates) and ensure the next generated save counter remains above the highest seen generation.
