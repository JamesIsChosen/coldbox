# P1.4 — Derivation engine: BIP-32 core plus Bitcoin script types

## Summary

- Roadmap item: [P1.4 — Derivation engine: BIP-32 core plus Bitcoin script types](../ROADMAP.md#phase-1--core-wallet)
- Branch: `p1.4-derivation-engine-bip32-bitcoin`
- Dependency/base: `main`
- Implementation commit: `d97e7cf` (`Remediate P1.4 watch-only validation`)
- Exact branch tip used for this evidence gate: `8f99771d1b66825f99fbd4e4b495869b809d1406` (the existing packet-only closeout is the only commit after the implementation).
- Scope: the cold-realm derivation engine and its independent test vectors. This item does not add a warm-realm UI or a new message type.

The implementation adds a vendored, cold-only derivation layer for BIP-32 secp256k1 keys and the Bitcoin script families currently specified by Coldbox: P2PKH, P2SH-P2WPKH, P2WPKH, and P2TR. It supports mainnet/testnet, account/change/index derivation, account-level watch-only xpub derivation, SLIP-132 public version bytes, strict path parsing, bounded batches, and public-only result projections. The remediation asserts the official `m/0'/1/2'` public vector exactly, requires depth-3 hardened account xpubs for watch-only Bitcoin derivation, and validates every compressed public key as a real secp256k1 point before address hashing.

## Security impact

This is a security-sensitive change. A derivation error can cause a user to send funds to an address they cannot spend from, or fail to recognize funds at an address they own.

- Seed bytes and private HDKey state are created and used only inside `src/cold/derivation.js` in the cold iframe.
- The exported API returns public addresses, xpub-family strings, and fingerprints only. It does not return seeds, mnemonics, passphrases, private keys, or xprvs.
- Intermediate HDKey private state is wiped after derivation, and seed input is copied so the caller's input is not mutated.
- No new warm/cold message type was added. The existing message boundary remains public-only.
- The cold realm keeps its existing `connect-src 'none'` policy and no runtime dependency or network fetch was added.
- Invalid paths, invalid seeds, malformed extended keys, unsupported version/network/script combinations, hardened public derivation, and unsafe batch ranges reject rather than degrade.
- Taproot uses tagged TapTweak hashing and normalizes the internal point to even Y before constructing the output key.

## Assumptions and scope decisions

1. P1.4 is the engine item, not the derivation UI item. P1.3's packet explicitly leaves derivation UI, keys, and addresses to later work, and the P1.4 roadmap line has no UI acceptance criteria. This branch therefore adds the cold engine and tests but no warm controls or protocol message.
2. Watch-only derivation accepts only a depth-3 account-level extended public key whose account child number is hardened. A master xpub, another depth, or a depth-3 non-hardened node is rejected because the engine cannot establish the account boundary safely.
3. A public extended key does not contain the master fingerprint. Watch-only results therefore expose `accountFingerprint` from the extended key and leave `fingerprint` null; the API does not invent a master fingerprint.
4. Bare xpub/tpub version bytes are ambiguous across Bitcoin script policies. The API requires an explicit script type for those versions; SLIP-132 ypub/upub and zpub/vpub versions must agree with the requested script type.
5. Batches default to 20 and are capped at 1,000, with index arithmetic checked before derivation.

If any of these assumptions is changed, the public API contract, protocol documentation, and tests must be reviewed together. No vault-format or message-boundary decision was made here.

## What a reviewer should scrutinise hardest

1. The Taproot point handling: even-Y normalization, x-only serialization, tagged TapTweak hashing, and point addition.
2. SLIP-132 version-byte detection and the rejection of script/network mismatches.
3. Zeroization boundaries around seed copies and intermediate HDKey objects, including exception paths.
4. The distinction between a true master fingerprint and the account fingerprint available from an xpub.
5. The fact that no new message handler was added: public derivation results must remain public-only when later UI work consumes this engine.
6. The official BIP-0032 `m/0'/1/2'` xpub is asserted byte-for-byte; verify the fixture remains an exact transcription of the upstream vector.

## Self-assessment and gaps

- The focused tests and full suite pass, but this session did not perform a third-party cryptographic audit of the vendored libraries or the new composition code.
- The browser harness verifies the integrated cold realm, but no new UI flow exists in this item, so it cannot prove later UI wiring.
- macOS Safari/Chrome, Linux Firefox, iOS Files/Quick Look, Android Files, and Tor remain untested.
- BigInt and secp256k1 behavior were tested in the available Chromium/Firefox environments, not on Safari.
- No physical hardware-wallet validation was performed; P1.4 has no hardware-wallet acceptance criterion and P1.9 owns final hardware validation.

These are declared test gaps, not claims of support. They do not alter the P1.4 engine acceptance mapping above, but they must remain visible to the independent reviewer.
