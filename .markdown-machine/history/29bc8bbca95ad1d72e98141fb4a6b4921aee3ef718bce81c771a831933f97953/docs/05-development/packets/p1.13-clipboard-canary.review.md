## 4. Findings

### F1 - Stale asynchronous completion can overwrite newer clipboard-canary UI state

**Severity:** blocking  
**Location:** `src/main.js`, the `clipboardCanaryController.enable().then(...)`
and `retry().then(...)` handlers around the P1.13 UI wiring at the reviewed
commit.

**Observed:** The controller's generation guard protects controller state, but
the warm UI promise handlers have no matching UI-layer generation token. The
following sequence was reproduced:

1. Enable A starts and waits on permission.
2. The user disables the canary.
3. The user enables B.
4. Stale A completes first.
5. A's UI callback sees the newer controller's `checking` state and unchecks
   the toggle.
6. B completes and arms the controller.

The final state is controller `armed` with the visible checkbox `false`.

**Expected:** Every UI completion must be tied to the operation that started
it. A stale completion must not alter the current checkbox, status, retry
control, or controller-visible state.

**Required action:** Add a UI-layer operation/generation token, or return and
ignore an explicit stale result. Add a committed regression with a deliberately
delayed first permission resolution followed by disable/re-enable, preferably
including retry overlap. Assert that the final controller state and checkbox
state agree, and drive the shipped UI wiring in browser coverage.

### F2 - Packet misstates synchronous permission-query exception behavior

**Severity:** advisory (still a FAIL under the binary protocol)  
**Location:** `docs/05-development/packets/p1.13-clipboard-canary.md`, the
remediation scope statement describing `permissions.query()` exceptions.

**Observed:** The implementation contains the permission-query exception,
converts the failure to an unknown permission state, and still attempts the
actual `navigator.clipboard.readText()` call. The committed test deliberately
throws from `permissions.query()`, allows `readText()` to succeed, and expects
the canary to become `armed`. The packet instead says synchronous browser
exceptions become the normal unavailable path.

**Expected:** Documentation, implementation, and tests must state one
consistent contract.

**Required action:** Correct the packet to say that permission-query failure is
contained and the actual clipboard read determines availability, or change the
implementation and test together if a different contract is intended. Do not
claim the exception itself forces `unavailable` while the test expects `armed`.

## 5. Verdict rationale

The reviewed product head cannot PASS because F1 leaves the visible opt-in
control inconsistent with the controller's actual armed state, and F2 makes the
author evidence materially misleading about a failure path. A fresh review can
PASS only after the UI race is fixed with a committed delayed-overlap
regression, the browser harness exercises the final checkbox/controller
agreement, and the packet/test/implementation contract is aligned.
