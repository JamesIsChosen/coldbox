## Scope and acceptance

P1.11 adds the public schema-2 provenance fields `addressOrigin`, `verificationState`, `lastColdVerifiedAt`, and `verifiedAgainstXpub`. Legacy schema-1 or schema-less public compartments migrate in the cold vault layer on open to schema 2 with explicit `manual` and `unverified` defaults. No verification state is inferred.

The R1, R2, and R3 independent FAILs identified six defects. This remediation addresses the fresh R3 defect while retaining the prior R1/R2 fixes:

1. The cold session now reconciles warm `publicData.replace` mutations against its existing address provenance and the account xpub relationship. A warm replacement cannot create `cold-verified` or `cold-verified-stale` from an unverified/unverifiable record, cannot rewrite authenticated timestamp/xpub evidence, and an account xpub change forces `cold-verified-stale` even when the warm request leaves `cold-verified` in place.
2. Cold vault `open`, `openSession`, and session replacement migrate schema 1/missing schema to schema 2. A successful save/reopen persists the migrated schema; a failed migration rejects without mutating the source bytes.
3. The normal Chromium/Firefox browser harness opens a real stale-state `.cbx` fixture and asserts the rendered Registry label is exactly `Cold verification stale` and is not `Cold verified`.
4. The roadmap contains the exact P1.11 marker `- [~] **P1.11 Address verification state in the data model**` with its existing dependency, description, and acceptance text.
5. When authenticated evidence still matches the current and replacement account xpub, the cold session rejects a warm `cold-verified-stale` request and preserves `cold-verified` plus the original timestamp/xpub evidence. A genuine xpub mismatch still forces `cold-verified-stale`.

The xpub-change transition remains automatic: an existing authenticated `cold-verified` address becomes `cold-verified-stale` while retaining its prior timestamp and xpub evidence. Actual cold re-derivation remains outside this item and is the next verification workflow surface.

## Security boundary

`publicData.replace` is still a warm-origin message. The cold-owned session is the authority for whether persisted provenance already exists; no warm-supplied timestamp or xpub is treated as proof. The protocol continues to validate closed public schemas and reject secret-shaped content. No message type carries mnemonic, private-key, xprv, passphrase, or secret-compartment plaintext.
