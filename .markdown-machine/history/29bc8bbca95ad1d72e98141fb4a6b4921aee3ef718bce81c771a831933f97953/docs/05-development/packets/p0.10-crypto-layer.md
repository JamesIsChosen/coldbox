# PR packet: P0.10 - Crypto layer

## 1. Summary

P0.10 adds the cold-realm cryptographic layer behind the existing sealed iframe boundary. Pure-JS `@noble` AES-GCM is the default, WebCrypto AES-GCM is available only after its NIST known-answer test passes, and Argon2id is loaded from a pinned, embedded WASM distribution. The boot UI and typed capability report expose the KDF that actually passed, including an explicit PBKDF2-HMAC-SHA512 fallback.

This branch is `p0.10-crypto-layer`, based on the completed P0.9 tip `main` at `86f838e`; its PR base is therefore `main`.

## 2. Scope

### In scope

- Deterministic build-time extraction of the selected `@noble/ciphers` and `@noble/hashes` modules into one classic inline cold-realm script
- Pinned `argon2-browser` 1.18.0 tarball with its embedded Argon2id WASM bytes, manifest hash, integrity, size, and upstream verification
- NIST AES-GCM known-answer tests for pure-JS and WebCrypto paths, with WebCrypto locked until its affirmative test passes
- RFC 9106 Argon2id known-answer test with the RFC secret and associated data
- Standard, fast, paranoid, and explicit PBKDF2-HMAC-SHA512 fallback profiles
- `crypto.getRandomValues`-only nonce/random-byte generation
- Typed cold-to-warm KDF and crypto capability fields, visible cold-realm vault details, and warm-shell active-KDF summary
- Browser assertions that the rendered artifact reports `argon2id-standard` and the RFC-backed implementation path
- Protocol, vendor, build, reproducibility, browser, and fallback tests; security/dependency/build/roadmap/changelog documentation

### Deliberately out of scope

- Vault serialization, compartment encryption, unlock/save/load workflows, or key hierarchy wiring (P0.11-P0.18)
- New message types or secret-bearing fields; the existing private MessageChannel schema is extended only with typed public capability results
- Runtime network access, relative WASM loading, service workers, or external runtime dependencies
- Physical Safari, mobile, Tor, or other device-matrix claims; those remain P0.19
- Any merge of this branch or its dependency branches

## 5. Security impact

- Realm boundary: Yes. The crypto vendor, Argon2 bundle, KATs, and KDF status run inside the opaque cold realm. The warm shell receives only typed booleans and a fixed KDF-id enum over the existing private channel; no passphrase, salt, key, nonce, ciphertext, or plaintext is added to the message schema.
- Derivation: Yes. The standard profile is Argon2id 64 MiB / 3 passes / 1 lane; fast is 19 MiB / 2 / 1; paranoid is 256 MiB / 4 / 1; fallback is PBKDF2-HMAC-SHA512 at 1,000,000 iterations. Profile selection is preparatory for the vault workflow and does not yet serialize a vault.
- Encryption: Yes. Pure-JS AES-GCM is the default. WebCrypto is not trusted merely because `crypto.subtle` exists; its encrypt/decrypt result must match the NIST vector first. A pure-JS KAT failure is terminal.
- Randomness: Yes. `randomBytes` uses only `crypto.getRandomValues`; missing or unusable randomness remains the inherited P0.9 hard failure. No `Math.random` fallback was introduced.
- CSP/network: No new `connect-src` host. Argon2 bytes are embedded in the vendor bundle; the cold policy remains `connect-src 'none'`, and the browser matrix confirms the cold runtime blockers. The upstream registry is contacted only by the explicit build-time vendor verification command, never by the shipped artifact.
- Supply chain: The new tarball is pinned to `argon2-browser@1.18.0`, size 44,952 bytes, SHA-256 `cdb11795a4971bde095fe6b836aa424de50c4558ed4b9505bc74111eee7f6d35`, and npm integrity `sha512-ImVAGIItnFnvET1exhsQB7apRztcoC5TnlSqernMJDUjbc/DLq3UEYeXFrLPrlaIl8cVfwnXb6wX2KpFf2zxHw==`. Both local and upstream checks passed.
- If the implementation is wrong, an attacker could obtain an incorrectly derived or incorrectly authenticated vault key, or a user could believe Argon2id is active while using a weaker KDF. The boot KATs and visible profile are intended to make that failure terminal or observable; end-to-end vault correctness is still a later item and is not claimed here.

## 6. Test evidence

### New and changed tests

- `test/crypto.test.js` runs the pure-JS AES-GCM KAT, gates WebCrypto before and after its KAT, runs the RFC 9106 Argon2id KAT, and derives a real PBKDF2 fallback key after removing Argon2 from an isolated VM context.
- `test/protocol.test.js` proves the new public crypto booleans and fixed KDF enum survive while unknown fields are stripped.
- `test/build.test.js` continues to verify one-file assembly, placeholders, CSP hashes, byte determinism, cold policy, and the dependency-free artifact; full `npm test` passes all 39 tests.
- `scripts/run-browser-harness.js` asserts the actual rendered cold realm's crypto state, KDF id, Argon2 label/path, warm summary, CSP, opaque boundary, and existing negative fixtures in Chromium and Firefox.

### Independent vector sources

- Argon2id parameters and expected tag: [RFC 9106 §5.3](https://www.rfc-editor.org/rfc/rfc9106#section-5.3).
- AES-GCM expected ciphertext/tag: [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final), using the standard all-zero 128-bit key, 96-bit IV, and 128-bit plaintext KAT.
- The expected values are fixed in the test and are not generated by the implementation under test.

### Negative tests

- WebCrypto AES-GCM rejects before its affirmative KAT passes.
- Removing Argon2 from the isolated VM selects and visibly retains `pbkdf2-sha512-fallback`; the fallback derives a 32-byte key with 1,000,000 iterations.
- Corrupting one byte of an isolated temporary copy of `argon2-browser` caused `verify-vendor.js` to exit 1 with `Vendor SHA-256 mismatch for argon2-browser@1.18.0`; the committed vendor tree was not modified.
- Existing malformed protocol, forbidden-construct, CSP-stripped, missing-randomness, tampered-artifact, runtime-network, timeout, and opaque-frame fixtures remain green.

### Not tested

No physical iOS Safari, Android Chrome from Files, macOS Safari, macOS Chrome, Linux Firefox, or Tor Browser was available. No vault round-trip is claimed because P0.11-P0.18 have not implemented that workflow. The Argon2 64/256 MiB production profiles were not run during boot; only the RFC low-memory KAT is required at this item boundary, while profile derivation is exposed for later vault integration.

## 8. Assumptions made

> **Assumed:** The embedded `argon2-browser` distribution's base64 WASM path is the path used by the shipped browser bundle.
> **Basis:** The built artifact contains the bundled WASM bytes; the Node VM vector and Chromium/Firefox boot KAT both pass without a network or relative resource.
> **Not verified on:** Physical browsers.
> **If wrong:** the Argon2 KAT must fail and the UI must show the explicit PBKDF2 fallback or full lockdown; no vault workflow may treat the status as Argon2id-active.

> **Assumed:** The RFC 9106 low-memory test is sufficient to validate the Argon2 WASM implementation at boot before production profile benchmarking.
> **Basis:** It exercises Argon2id with the RFC secret and associated data and prevents a broken module from being selected; P0.13/P0.14 own real vault/profile performance.
> **Not verified on:** Low-memory physical devices.
> **If wrong:** the device matrix must record the profile unavailable and the vault must not silently choose it.

## 9. What to scrutinise

- The generated noble bundle is a deterministic internal loader assembled from vendored ESM modules; verify the selected module graph contains no hidden network or dynamic-code path.
- The Argon2 UMD bundle contains browser fallback loaders in its distribution, but the embedded base64 WASM path is used by the shipped `argon2.hash` call. The cold CSP and KAT must remain the safety net if that assumption fails.
- Confirm the warm shell accepts only the fixed public KDF enum and never receives secret-bearing derivation inputs.
- Check that every real KDF failure remains visible in both the cold panel and warm capability summary; a label that says only “crypto ready” would be insufficient.
- Review the later vault-format item before allowing any profile or fallback result to be serialized into AAD or an unlock record.

## 10. Self-assessment

- The implementation is not a vault: no serializer, AEAD record format, compartment key hierarchy, unlock flow, or save/load round-trip is present yet.
- The production Argon2 profiles are configured but not performance-tested on physical devices; standard profile loading may be memory-sensitive and remains a later benchmark concern.
- The fallback is deliberately weaker and visible, but its presence is a compatibility path rather than a security equivalent. The UI must not present it as “ready” without the fallback id.
- The generated artifact grew by 176,543 bytes; it remains far below the 3 MB target and 4.5 MB hard cap.
- The author gate found and fixed one test wording mismatch before this final PASS: the warm assertion now checks the exact safe id `argon2id-standard`, matching the shipped summary.
